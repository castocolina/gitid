<discovery_findings>
Verified against the working tree before planning. Treat these as established
facts; do not re-derive them.

**Correction to the task brief (D1):** the brief says to bind `c` "to the same copy
action the identity detail pane already uses for copying the public key". **The
identity detail pane has no such action** — `c` on `paneDetail` opens the CLONE
prompt (`identities.go:2533` → `openClonePrompt`). The only existing copy-public-key
call site in this file is the create wizard's (`identities.go:3856-3869`):
`w.backend.CopyPublicKey(w.keyPath() + ".pub")`, surfaced as the footer action
`{Key: "c", Label: "copy public key"}` (`identities.go:5515`, `:5521`). That wizard
call site — not a detail-pane one — is the pattern to mirror. `CopyPublicKey` is on
the `Backend` interface (`backend.go:462`), so the register-key pane can call it.

**Footer mechanics (D1, D4):** `RenderFrame` (`frame.go:427`) renders the contextual
footer from `actions` *independently* of `capturesKeys` — only the RESERVED footer
row switches on `capturesKeys`. So adding a `FooterAction` for a key-capturing pane
does render. `view()` starts `var actions []FooterAction` (`identities.go:5300`) and
neither `case paneRegisterKey:` (`:5454`) nor `case paneKeyCeremony:` (`:5432`) sets
it — both currently render a BLANK contextual footer row. Both D1's and D4's hints
therefore cost **zero body rows**, which matters: this screen is under documented
row-budget pressure and `renderKeyCeremony` carries an overflow backstop.

**Register-key pane states (D1, D2)** — `renderRegisterKey` (`identities.go:4639`)
discriminates, in order: `registerKeyErr != ""` → error; `!registerKeyPlanLoaded` →
"Checking eligibility…"; `registerKeyPlan.State != UploadEligibilityReady` →
manual-fallback (`UploadManualHeading` + `backend.UploadInstructions`); 
`uploadRunHasContent(registerKeyRun)` → the run's result section (which may itself
carry `run.ManualFallback != ""`); otherwise "Registering…".

**Existing test that constrains D1** — `TestRegisterKeyPaneMatchesSiblingPaneGeometry`
(`identity_manager_upload_test.go:325`) asserts `len(rv.actions) == 0` for a
freshly-opened pane (plan not loaded). Gating the `c` action to the manual-fallback
states keeps it passing; a pane-wide `c` action would break it.

**`Done (Enter)` (D4)** is emitted by the SHARED `ceremonyModel.view`
(`ceremony.go:357`), reached from `renderKeyCeremony`'s `m.keyCeremony.view(...)`
(`identities.go:2972`). The offer tail is appended *below* it (`:2988`), producing the
misattribution. Editing `ceremony.go:357` unconditionally would change every write
ceremony in the app — `ceremony_test.go:138/278/383` pin `Done (Enter)`'s presence.

**Rotate offer live-key set (D4)** — `identities.go:2817-2865`: while
`keyCeremonyMode == KeyCeremonyModeRotate && rotateDeleteOffer.Available &&
!rotateDeleteResolved`, the accepted keys are `up/down/left/right/tab/shift+tab`
(toggle focus), `enter` (confirm), `esc` (resolves as leave-it). Existing in-pane
hint convention for a choice row: `"↑↓/Tab choose · Enter continue · Esc cancel"`
(`identities.go:5409`, paneDeleteScope).

**D3 is confirmed by two independent signals.** (a) `create-flow-upload-checkbox-disabled.txt`
and `create-flow-upload-checkbox-unauth.txt` are **byte-identical** (`diff` is empty;
