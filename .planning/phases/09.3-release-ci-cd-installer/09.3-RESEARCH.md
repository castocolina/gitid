## User Constraints (from CONTEXT.md)

### Locked Decisions

**Release trigger & artifact matrix**
- **D-01:** A tag matching `v*` (e.g. `v1.2.3`) triggers a new release job in
  `.github/workflows/ci.yml`, separate from the existing `build-cross`/`check`
  jobs.
- **D-02:** All **four** `build-cross` targets are published as release
  assets: `gitid-darwin-amd64`, `gitid-darwin-arm64`, `gitid-linux-amd64`,
  `gitid-linux-arm64`. This promotes `linux-arm64` from "build-only, not
  CI-gated" to a published release asset. Settled, not to be revisited.
- **D-03:** Raw binaries are uploaded as release assets (matching what
  `build-cross` already produces byte-for-byte), not archived
  (`.tar.gz`/`.zip`). A `checksums.txt` with SHA-256 for all four binaries is
  published alongside them.

**Publish mechanism & permissions**
- **D-04:** A **dedicated, SHA-pinned release GitHub Action** (e.g.
  `softprops/action-gh-release`) publishes the release — not `gh release
  create`. Deliberate pick, not a default.
- **D-05:** The release job is triggered ONLY on `v*` tag push and carries
  `permissions: contents: write` scoped to that job only. The existing
  `build-cross` and `check` jobs keep their current `contents: read`
  top-level permission unchanged.

**Version stamping**
- **D-06:** `cmd/gitid/main.go`'s `const version = "0.0.0-dev"` becomes a
  `var` (a `const` cannot be set via `-ldflags -X`). `gitid --version` prints
  **semver + short commit + build date** (e.g. `gitid version 1.2.3
  (abc1234, 2026-08-30)`), built via three separate `-ldflags -X` injections
  at build-cross/release-build time.

**Installer script**
- **D-07:** The install script (e.g. `scripts/install.sh` in the repo) is
  fetched via `raw.githubusercontent.com/<org>/gitid/main/scripts/install.sh`
  — no separate hosting infrastructure. It installs to **`~/.local/bin`** (no
  sudo required), and checks whether that directory is on `PATH`, printing a
  one-line export hint if not.
- **D-08:** The script detects the caller's OS/arch (`uname -s`/`uname -m`),
  downloads the matching binary + `checksums.txt` from the latest GitHub
  Release, verifies the SHA-256 checksum, and only then installs — refusing
  and exiting non-zero on a checksum mismatch (never silently installing an
  unverified binary).

## Summary

This phase adds exactly one new CI job and one new shell script on top of
substrate that already exists and is proven: `build-cross` (four
`GOOS`/`GOARCH` binaries, byte-identical output today), the SHA-pinned
`# vX.Y.Z`-commented action convention already used twice in `ci.yml`, and
the job-scoped `permissions:` pattern GitHub itself recommends. Nothing here
requires GoReleaser or any new build tooling — the user's locked decisions
(D-04, Claude's Discretion note on `checksums.txt`) explicitly steer toward
extending the *existing* Makefile-driven pipeline, not replacing it.

The one piece of load-bearing verification this research adds beyond
CONTEXT.md: **Cobra's default version template is
`"{{DisplayName}} version {{.Version}}\n"`** (confirmed by reading
`cobra@v1.10.2/command.go:2064` directly, this session). That means
`gitid --version` printing `gitid version 1.2.3 (abc1234, 2026-08-30)`
requires **no custom `SetVersionTemplate` call** — it falls out for free as
long as `root.Version` is assigned the fully-composed string
`"1.2.3 (abc1234, 2026-08-30)"` (built from three separate ldflags-injected
vars) rather than the raw semver alone. This is the single detail most
likely to trip up a plan that doesn't check the template source first.

The second load-bearing finding: `build-cross` as it exists today (Makefile,
verified read this session) does **not** inject any ldflags — it is four
bare `go build` invocations. The release job cannot reuse
`build-cross`'s *artifacts* (via `upload-artifact`/`download-artifact`)
because those are unstamped and validated on a different event (push to
main) than the tag that triggers the release. The clean fix, consistent
with the project's single-Makefile-target principle, is to make
`build-cross` itself accept optional `VERSION`/`COMMIT`/`DATE` make
variables (`?=` defaulted to today's dev values so routine CI/local
builds are unaffected) and always pass them through `-ldflags`. The
release job then calls the *same* target with real values instead of a
second, duplicated cross-build target.

**Primary recommendation:** Extend `build-cross` in place with
optional-but-always-injected `-ldflags -X` version variables (default
`0.0.0-dev`/`none`/`unknown`); add one new `checksums` Makefile target;
add one new `release:` job in the existing `ci.yml` gated on
`refs/tags/v*` with job-scoped `contents: write`, using
`softprops/action-gh-release@efb35369e0ad2afab669f228072c1b0d510eae64 # v3.0.3`;
write `scripts/install.sh` as a portable POSIX script using the
`/releases/latest/download/<asset>` URL pattern and a `sha256sum`-or-
`shasum -a 256` fallback for checksum verification.

### Pattern 1: Optional-default ldflags on an existing Make target

**What:** Add `VERSION ?= 0.0.0-dev`, `COMMIT ?= none`, `DATE ?= unknown` to
the Makefile, compose a single `LDFLAGS` variable, and pass it to every
`go build` line in `build-cross` (and optionally `build`, for local dev
parity). Routine invocations (`make build-cross` with no vars set) keep
producing the existing dev-stamped binaries; the release job overrides all
three.

**When to use:** Any time a single Makefile target must serve both a
routine/CI-validation path and a release-stamping path without duplicating
the build matrix.

**Example:**
```makefile
# Added to Makefile, near the existing build-cross target.
VERSION ?= 0.0.0-dev
COMMIT  ?= none
DATE    ?= unknown
LDFLAGS := -X main.version=$(VERSION) -X main.commit=$(COMMIT) -X main.date=$(DATE)

build-cross:
	@mkdir -p $(BIN_DIR)
	GOOS=darwin  GOARCH=amd64 go build -ldflags "$(LDFLAGS)" -o $(BIN_DIR)/gitid-darwin-amd64 ./cmd/gitid
	GOOS=darwin  GOARCH=arm64 go build -ldflags "$(LDFLAGS)" -o $(BIN_DIR)/gitid-darwin-arm64 ./cmd/gitid
	GOOS=linux   GOARCH=amd64 go build -ldflags "$(LDFLAGS)" -o $(BIN_DIR)/gitid-linux-amd64  ./cmd/gitid
	GOOS=linux   GOARCH=arm64 go build -ldflags "$(LDFLAGS)" -o $(BIN_DIR)/gitid-linux-arm64  ./cmd/gitid
```
Invocation from the release job: `make build-cross VERSION=1.2.3 COMMIT=abc1234 DATE=2026-08-30`.
`# Source: pattern cross-checked against 3 independent web sources (linuxera.org, mangohost.net, jvt.me — see Sources) plus this repo's own existing build-cross target read this session`

### Pattern 2: Cobra `Version` field as a pre-composed string (no custom template)

**What:** Cobra's `defaultVersionTemplate` (confirmed by reading
`cobra@v1.10.2/command.go:2064` this session) is:
```go
const defaultVersionTemplate = `{{with .DisplayName}}{{printf "%s " .}}{{end}}{{printf "version %s" .Version}}
`
```
`[VERIFIED: /Users/ramon/go/pkg/mod/github.com/spf13/cobra@v1.10.2/command.go:2064]`
— quoted verbatim above. Given `root.Use = "gitid"` (so `DisplayName` defaults
to `"gitid"`, confirmed `[VERIFIED: cmd/gitid/main.go:86]` — `Use: "gitid",`),
setting `root.Version` to the fully-composed string
`"1.2.3 (abc1234, 2026-08-30)"` makes `gitid --version` print exactly
`gitid version 1.2.3 (abc1234, 2026-08-30)` — CONTEXT.md's target output —
with **zero** call to `SetVersionTemplate`.

**When to use:** Whenever the desired `--version` output is
`"<name> version <anything>"` and the "anything" itself needs multi-part
composition (semver + commit + date). Compose the string once in Go, assign
it to `Version`, done.

**Example:**
```go
// cmd/gitid/main.go — D-06's three ldflags-injected vars, composed once.
var (
	version   = "0.0.0-dev" // -X main.version=<semver>
	commit    = "none"      // -X main.commit=<short-sha>
	buildDate = "unknown"   // -X main.date=<YYYY-MM-DD>
)

// versionString composes the three ldflags-injected parts into Cobra's
// Version field. Cobra's defaultVersionTemplate prints
// "{{DisplayName}} version {{.Version}}", so this function's return value
// IS the full "1.2.3 (abc1234, 2026-08-30)" portion — no custom template
// needed (verified: cobra@v1.10.2/command.go:2064).
func versionString() string {
	return fmt.Sprintf("%s (%s, %s)", version, commit, buildDate)
}
```
Then in `newRootCmd()`: `Version: versionString(),` replacing the current
`Version: version,` (`cmd/gitid/main.go:88`, confirmed
`[VERIFIED: cmd/gitid/main.go:88]` — `Version:       version,`).
`# Source: cobra@v1.10.2 source read directly this session`

### Pattern 3: GitHub's `/releases/latest/download/<asset>` redirect (no API call)

**What:** GitHub serves a stable, undocumented-looking but officially
documented URL suffix `/releases/latest/download/<asset-name>` that
redirects (302, to `objects.githubusercontent.com`) to the named asset on
whichever release is currently tagged "latest." No GitHub API call, no
`jq`, no auth token needed for a public repo.

**When to use:** Exactly the install-script download step (D-08) — the
script never needs to know the current version number; it always resolves
"latest" server-side.

**Example:**
```sh
# scripts/install.sh — no API/jq dependency.
REPO="castocolina/gitid"
ASSET="gitid-${OS}-${ARCH}"
curl -fsSL "https://github.com/${REPO}/releases/latest/download/${ASSET}" -o "$tmp/gitid"
curl -fsSL "https://github.com/${REPO}/releases/latest/download/checksums.txt" -o "$tmp/checksums.txt"
```
`# Source: docs.github.com/en/repositories/releasing-projects-on-github/linking-to-releases (quoted verbatim in Sources)`

### Anti-Patterns to Avoid

- **Duplicating the build matrix in a second Makefile target** (e.g.
  `build-cross-release` alongside `build-cross`): violates the project's
  own stated single-source-of-truth principle (`ci.yml`'s header comment:
  "CI invokes the SAME make targets a human runs locally") and creates a
  drift risk the moment someone adds a fifth `GOOS`/`GOARCH` pair to one
  target and forgets the other. Extend `build-cross` in place instead
  (Pattern 1).
- **Calling the GitHub REST API to resolve the asset URL** in the install
  script: adds a `jq`/`curl -H "Authorization"` dependency and an
  unauthenticated-rate-limit failure mode for zero benefit over the
  documented `/releases/latest/download/` redirect (Pattern 3).
- **Trusting `sha256sum` unconditionally**: macOS does not ship
  `sha256sum` by default (only `shasum -a 256`) — a script that assumes
  `sha256sum` exists fails hard on a stock macOS install with no
  Homebrew/coreutils. Detect and fall back (see Common Pitfalls, Pitfall
  2).

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| GitHub Release creation + multi-asset upload with retry/error handling | A `curl -X POST` script against the Releases API | `softprops/action-gh-release` | The action already handles multipart asset upload streaming, retry-safe re-runs (D-04 approved), auto-generated release notes, and token defaulting — a hand-rolled `curl` script would need to reimplement all of this to be equally robust, for a one-time-per-tag operation that doesn't justify the maintenance cost. |
| "Latest release" asset resolution | GitHub API call + `jq` parsing of the releases JSON to find `browser_download_url` | The documented `/releases/latest/download/<asset>` URL suffix | Zero extra dependency (`jq` is not guaranteed present on a stock macOS/Linux box), zero API rate-limit exposure, officially documented and stable. |
| Cross-platform SHA-256 computation abstraction | A custom Go or Python helper compiled/shipped just for hashing | Native `sha256sum`/`shasum -a 256` with a two-line `command -v` fallback | Both tools are OS-default, produce byte-identical output format, and this is exactly what a `checksums.txt` + `-c` check-mode invocation already solves — no library needed on either the generation (CI) or verification (install script) side. |

**Key insight:** Every piece of this phase has an existing, standard,
zero-dependency mechanism (a Marketplace action, a documented URL suffix, a
system-default checksum tool). The temptation in a "release + installer"
phase is to reach for either a heavyweight framework (GoReleaser) or a
hand-rolled API client; both are unnecessary given the constraints already
locked in CONTEXT.md.

## Common Pitfalls

### Pitfall 1: `build-cross`'s current output is unstamped and cannot be reused by the release job
**What goes wrong:** A plan that has the release job download `build-cross`'s
artifacts via `actions/upload-artifact`/`download-artifact` (to "avoid
rebuilding") ships binaries whose `--version` output is stuck at
`0.0.0-dev` — because the existing `build-cross` target has zero ldflags
today (confirmed by reading the Makefile this session: four bare `go build`
lines, no `-ldflags` anywhere).
**Why it happens:** `build-cross` and the release job run on different
trigger events (push-to-main vs. tag-push) with different Go module states
possible between them; reusing an artifact assumes they're the same build,
which they structurally cannot be once version stamping exists.
**How to avoid:** The release job calls `make build-cross VERSION=... COMMIT=... DATE=...` itself (Pattern 1) — it does not consume `build-cross` job artifacts from elsewhere in the workflow.
**Warning signs:** Any plan task that mentions `upload-artifact`/`download-artifact` between jobs for this phase.

### Pitfall 2: macOS does not ship `sha256sum`
**What goes wrong:** An install script hard-coded to call `sha256sum -c
checksums.txt` exits with "command not found" on a stock macOS machine
(macOS ships `shasum`, a Perl script, not GNU coreutils' `sha256sum`,
unless the user separately installed coreutils via Homebrew).
**Why it happens:** The two most common Unix families diverged on this
specific tool name decades ago and never reconciled.
**How to avoid:** Detect at runtime — `if command -v sha256sum >/dev/null
2>&1; then CHECKSUM_CMD="sha256sum"; else CHECKSUM_CMD="shasum -a 256";
fi` — and use `$CHECKSUM_CMD -c` for verification. The output format is
byte-identical between the two `[CITED: dev.to/priyanshurav/sha256sum-shasum-get-filehash]`,
so a single `checksums.txt` works with either tool.
**Warning signs:** Any install-script draft with a literal, unconditional
`sha256sum` call and no fallback branch.

### Pitfall 3: a shared `on: push:` trigger re-runs `build-cross`/`check` on every tag push too
**What goes wrong:** Adding `tags: ['v*']` under the existing `on: push:`
key (which already has `branches: [main]`) makes the WHOLE workflow
event-eligible on a tag push — including `build-cross` and `check`, which
then run redundantly (wasted CI minutes, and — worse — if `check` is
`needs:`-less and independent, a slow `check` run racing the fast
`release` job could make the release publish before validation finishes,
even though the tagged commit should already have passed `check` on its
prior push-to-main).
**Why it happens:** GitHub Actions' `on:` block is workflow-scoped;
`branches:`/`tags:` filters under one `push:` key apply to every job in
the file unless a job adds its own `if:`.
**How to avoid:** Scope the new `release:` job itself with `if:
startsWith(github.ref, 'refs/tags/v')` (softprops' own README recommends
`if: github.ref_type == 'tag'` as one of exactly two documented patterns
for this `[CITED: raw.githubusercontent.com/softprops/action-gh-release/master/README.md, fetched this session]`).
Whether to *also* guard `build-cross`/`check` to skip on tag pushes is a
planner-level tradeoff (redundant-but-harmless validation vs. faster
releases) not settled by CONTEXT.md — flag as an Open Question below.
**Warning signs:** A workflow diff that adds `tags: ['v*']` to `on: push:`
with no corresponding `if:` on the new job.

### Pitfall 4: Cobra's default template needs the FULL string in `Version`, not just the semver
**What goes wrong:** A plan that sets `Version: version` (the raw semver
var alone, unchanged from today's line 88) and separately tries to make
`--version` print the commit/date via a custom `cobra.Command.SetVersionTemplate`
call duplicates logic Cobra already provides for free, and risks a
template string that doesn't match CONTEXT.md's exact target format
character-for-character.
**Why it happens:** It's not obvious from Cobra's public API surface alone
that `Version` is meant to hold the ENTIRE post-"version "-prefix string,
not just a bare semver, until the actual template source is read.
**How to avoid:** Compose `version`/`commit`/`buildDate` into one string in
Go (Pattern 2) and assign the composed string to `Version` — let Cobra's
existing default template do the rest.
**Warning signs:** Any diff touching `SetVersionTemplate` for this phase —
almost certainly unnecessary.

### Pitfall 5 (reassurance, not a real risk here): macOS Gatekeeper quarantine
**What goes wrong (in general):** Downloaded macOS binaries can be blocked
by Gatekeeper's "unidentified developer" dialog if the OS attached the
`com.apple.quarantine` extended attribute at download time.
**Why it does NOT apply here:** `curl` — unlike Safari/Chrome/Finder —
does **not** set the quarantine xattr on files it downloads
`[CITED: cross-checked across multiple sources this session, see
"Handling macOS Gatekeeper as an Unsigned Indie Dev" and Apple developer
forum discussion in Sources]`. Since D-07/D-08 lock the install path to a
`curl`-based script (not a browser download of the binary), no
notarization/code-signing step is required for this phase's binaries to
run.
**Warning signs:** A plan that adds a code-signing/notarization task for
this phase — likely unnecessary scope creep, since the curl-download path
sidesteps the Gatekeeper trigger entirely. If a future user reports a
Gatekeeper block, the mitigation (`xattr -d com.apple.quarantine
<path>`) is a one-line troubleshooting note, not a build-pipeline change.

```yaml
# Source: pattern assembled from softprops/action-gh-release's own README
# (fetched this session) + this repo's existing SHA-pin/permissions-scoping
# conventions (ci.yml, read this session).
  release:
    name: release
    runs-on: ubuntu-latest
    if: startsWith(github.ref, 'refs/tags/v')
    permissions:
      contents: write
    steps:
      - name: Checkout
        uses: actions/checkout@9c091bb21b7c1c1d1991bb908d89e4e9dddfe3e0 # v7.0.0

      - name: Set up Go
        uses: actions/setup-go@924ae3a1cded613372ab5595356fb5720e22ba16 # v6.5.0
        with:
          go-version: ${{ env.GO_VERSION }}

      - name: Compute release version metadata
        id: relver
        run: |
          echo "version=${GITHUB_REF_NAME#v}" >> "$GITHUB_OUTPUT"
          echo "commit=$(git rev-parse --short HEAD)" >> "$GITHUB_OUTPUT"
          echo "date=$(date -u +%Y-%m-%d)" >> "$GITHUB_OUTPUT"

      - name: make build-cross (stamped)
        run: |
          make build-cross \
            VERSION=${{ steps.relver.outputs.version }} \
            COMMIT=${{ steps.relver.outputs.commit }} \
            DATE=${{ steps.relver.outputs.date }}

      - name: make checksums
        run: make checksums

      - name: Publish release
        uses: softprops/action-gh-release@efb35369e0ad2afab669f228072c1b0d510eae64 # v3.0.3
        with:
          generate_release_notes: true
          files: |
            bin/gitid-darwin-amd64
            bin/gitid-darwin-arm64
            bin/gitid-linux-amd64
            bin/gitid-linux-arm64
            bin/checksums.txt
```
`GITHUB_REF_NAME` is the env-var form of the `github.ref_name` context —
confirmed to be the short tag name without the `refs/tags/` prefix
`[CITED: docs.github.com/en/actions/reference/contexts-reference, fetched
this session]`.

### `scripts/install.sh` skeleton
```sh
#!/bin/sh
# gitid installer. Fetched via:
#   curl -fsSL https://raw.githubusercontent.com/castocolina/gitid/main/scripts/install.sh | sh
set -eu
# (POSIX sh has no `pipefail`; if bash is confirmed as the shebang target,
# `set -euo pipefail` per Common Pitfalls research is preferable — decide
# shebang (#!/bin/sh vs #!/usr/bin/env bash) at plan time; D-07/D-08 do not
# lock this choice.)

REPO="castocolina/gitid"
INSTALL_DIR="${HOME}/.local/bin"

os=$(uname -s)
arch=$(uname -m)

case "$os" in
  Darwin) os_tag="darwin" ;;
  Linux)  os_tag="linux" ;;
  *) echo "gitid: unsupported OS: $os" >&2; exit 1 ;;
esac

case "$arch" in
  x86_64|amd64)  arch_tag="amd64" ;;
  arm64|aarch64) arch_tag="arm64" ;;
  *) echo "gitid: unsupported architecture: $arch" >&2; exit 1 ;;
esac

asset="gitid-${os_tag}-${arch_tag}"
tmp=$(mktemp -d)
trap 'rm -rf "$tmp"' EXIT

curl -fsSL "https://github.com/${REPO}/releases/latest/download/${asset}" -o "${tmp}/gitid"
curl -fsSL "https://github.com/${REPO}/releases/latest/download/checksums.txt" -o "${tmp}/checksums.txt"

if command -v sha256sum >/dev/null 2>&1; then
  checksum_cmd="sha256sum"
else
  checksum_cmd="shasum -a 256"
fi

# Isolate just the one relevant line so verification doesn't require every
# other platform's asset to be present in the same directory.
grep "  ${asset}$" "${tmp}/checksums.txt" > "${tmp}/checksums.filtered.txt"
( cd "$tmp" && $checksum_cmd -c "${tmp}/checksums.filtered.txt" --strict ) || {
  echo "gitid: checksum verification FAILED — refusing to install an unverified binary." >&2
  exit 1
}

mkdir -p "$INSTALL_DIR"
mv "${tmp}/gitid" "${INSTALL_DIR}/gitid"
chmod +x "${INSTALL_DIR}/gitid"

echo "gitid installed to ${INSTALL_DIR}/gitid"
case ":$PATH:" in
  *":${INSTALL_DIR}:"*) echo "PATH: OK" ;;
  *) echo "PATH: ${INSTALL_DIR} is NOT on your PATH — add to shell: export PATH=\"\$PATH:${INSTALL_DIR}\"" ;;
esac
```
`# Pattern assembled from: documented /releases/latest/download/ URL suffix
(docs.github.com), the sha256sum/shasum portability finding, and this
repo's own Makefile install: target's PATH-check idiom
(Makefile:514-521, read this session) — mirrored here for UX consistency.`

## Open Questions

1. **Should `build-cross`/`check` be skipped on a tag push, or run redundantly alongside the new `release` job?**
   - What we know: GitHub's `on: push: tags: [...]` filter is
     workflow-scoped, so without an explicit guard, adding `tags: ['v*']`
     makes every job in `ci.yml` tag-push-eligible (Pitfall 3).
     `softprops/action-gh-release`'s README documents `if: github.ref_type
     == 'tag'` (or the equivalent `startsWith(github.ref, 'refs/tags/')`)
     as the standard way to scope just the release step/job.
   - What's unclear: CONTEXT.md's D-01 says the release job is "separate
     from" `build-cross`/`check` but doesn't explicitly say whether those
     two should be SKIPPED on a tag push (saving CI minutes, trusting the
     tagged commit already passed `check` on its prior push-to-main) or
     left to run redundantly (extra safety net, extra cost).
   - Recommendation: Guard the new `release:` job with `if: startsWith(github.ref, 'refs/tags/v')` (required regardless). Whether to ALSO add `if: ${{ !startsWith(github.ref, 'refs/tags/') }}` to `build-cross`/`check` is a low-stakes tradeoff the planner should make explicitly (and can defer to the user in the plan's own decision log if genuinely ambiguous) — leaning toward "leave them unguarded" (redundant validation on a rare, low-frequency tag-push event is cheap and harmless, and provides an extra correctness signal specifically on the tagged commit).

2. **Overwrite/upgrade UX for the installer (explicitly Claude's Discretion in CONTEXT.md).**
   - What we know: rustup-style installers (researched above) generally
     just overwrite idempotently; CONTEXT.md explicitly says this "was not
     explicitly discussed and is not a hard requirement," and to "keep it
     simple."
   - What's unclear: nothing blocking — this is confirmed low-priority.
   - Recommendation: `mv` overwrite with no existing-install detection,
     matching the plain curl|bash convention. If a future UX pass wants an
     upgrade banner, it's a strictly additive change to `scripts/install.sh`.
