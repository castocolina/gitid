## What actually shipped

Six distinct, real CI-only bugs were found and fixed along the way (all still present in the codebase, all independently valuable regardless of the e2e-in-CI outcome):

1. Flat PTY-wait budgets tuned for local dev hardware, too tight for CI.
2. ~30 direct `waitFor` callers bypassing any single-helper fix — closed by centralizing the multiplier in `waitFor` itself.
3. ~160 unscaled per-test subprocess `context.WithTimeout` calls — the actual dominant ceiling, independent of the poll budget.
4. A hostname-wrap assertion bug: GitHub-hosted runner hostnames are long enough to force a line-wrap that a plain `strings.Contains` can never satisfy, regardless of timeout (`mustSeeUnwrapped`).
5. A long-macOS-`$TMPDIR` path-wrap bug affecting receipt text built from `t.TempDir()`-based fixture helpers (`TMPDIR=/tmp` pinned in CI).
6. An unscaled `keystrokeDelay` constant, plausibly causing dropped/coalesced input under `-race` CPU contention on shared runners.
7. A diagnostic-integrity bug in the test harness's own `waitFor`: it reported an unvalidated snapshot on timeout, making some rc.3–rc.5 failure analyses unreliable.

None of it — including 4-way parallel sharding, which conclusively ruled out cumulative long-process resource contention — closed the gap for a small, consistent set of tests. The residual GitHub-Actions-specific failure is a genuine behavior/environment difference (at least one case observed as a stuck input-driven state transition, not a slow render) that remains **unresolved and undiagnosed**. It does not block this phase: `make test-e2e` passes clean locally on every single attempt (macOS, ~950s, full `-race`), and per the user's explicit direction it now stays a real, valuable local developer gate rather than a CI one.
