# Phase 9.3: Release CI/CD + Installer - Context

**Gathered:** 2026-08-30
**Status:** Ready for planning

<domain>
## Phase Boundary

A version-tag push (`v*`) triggers a new CI release job that builds all four
`build-cross` binaries, publishes them to GitHub Releases with SHA-256
checksums, and stamps `gitid --version` with the real release version. A
hosted `curl | sh` install script then detects the caller's OS/arch,
downloads the matching checksummed binary, verifies it, and installs it to
`~/.local/bin`. Closes BUILD-03 and BUILD-05.

</domain>

<decisions>
## Implementation Decisions

### Release trigger & artifact matrix
- **D-01:** A tag matching `v*` (e.g. `v1.2.3`) triggers a new release job in
  `.github/workflows/ci.yml`, separate from the existing `build-cross`/`check`
  jobs.
- **D-02:** All **four** `build-cross` targets are published as release
  assets: `gitid-darwin-amd64`, `gitid-darwin-arm64`, `gitid-linux-amd64`,
  `gitid-linux-arm64`. This promotes `linux-arm64` from "build-only, not
  CI-gated" (per the existing D-14 in `build-cross`'s Makefile comment) to a
  published release asset — reconfirmed explicitly after the user initially
  asked to drop it, then asked to include it again; the final answer is
  **include it**.
  — **Reversibility:** reversible — dropping an already-published arch from a
  future release doesn't invalidate past releases.
- **D-03:** Raw binaries are uploaded as release assets (matching what
  `build-cross` already produces byte-for-byte), not archived
  (`.tar.gz`/`.zip`). A `checksums.txt` with SHA-256 for all four binaries is
  published alongside them.

### Publish mechanism & permissions
- **D-04:** A **dedicated, SHA-pinned release GitHub Action** (e.g.
  `softprops/action-gh-release`) publishes the release — not `gh release
  create`. The user explicitly chose this after being offered the `gh`-CLI
  alternative (reasoning given: `gh` is already a project dependency
  elsewhere, so it would add zero new CI dependencies) — the dedicated-action
  choice is a deliberate pick, not a default.
- **D-05:** The release job is triggered ONLY on `v*` tag push and carries
  `permissions: contents: write` scoped to that job only. The existing
  `build-cross` and `check` jobs keep their current `contents: read`
  top-level permission unchanged — this phase does not widen permissions for
  the routine PR/push gate.

### Version stamping
- **D-06:** `cmd/gitid/main.go`'s `const version = "0.0.0-dev"` becomes a
  `var` (a `const` cannot be set via `-ldflags -X`). `gitid --version` prints
  **semver + short commit + build date** (e.g. `gitid version 1.2.3
  (abc1234, 2026-08-30)`), built via three separate `-ldflags -X` injections
  at build-cross/release-build time.
  — **Reversibility:** reversible — the print format can change later without
  affecting the release mechanism itself.

### Installer script
- **D-07:** The install script (e.g. `scripts/install.sh` in the repo) is
  fetched via `raw.githubusercontent.com/<org>/gitid/main/scripts/install.sh`
  — no separate hosting infrastructure. It installs to **`~/.local/bin`** (no
  sudo required), and checks whether that directory is on `PATH`, printing a
  one-line export hint if not.
- **D-08:** The script detects the caller's OS/arch (`uname -s`/`uname -m`),
  downloads the matching binary + `checksums.txt` from the latest GitHub
  Release, verifies the SHA-256 checksum, and only then installs — refusing
  and exiting non-zero on a checksum mismatch (never silently installing an
  unverified binary).

### Claude's Discretion
- Exact GitHub Release title/body template (e.g. whether it auto-generates
  release notes from commits, or uses a minimal fixed template).
- Whether the installer detects an existing `gitid` install and offers an
  overwrite/upgrade message, or simply overwrites idempotently (standard
  curl\|bash behavior) — research common installer script precedents (e.g.
  rustup, homebrew-adjacent scripts) if useful, but keep it simple: this was
  not explicitly discussed and is not a hard requirement.
- Exact GitHub Release action to use (`softprops/action-gh-release` was named
  as an example during discussion, not locked as the literal choice) — pick
  a well-maintained, SHA-pinnable action; document the pin with a `# vX.Y.Z`
  comment per the existing `ci.yml` convention.
- Whether `checksums.txt` is generated by the release job itself (via
  `sha256sum` over the four binaries) or by a Makefile target reusable
  locally too — lean toward a Makefile target for parity with `build-cross`'s
  existing "CI invokes the SAME make targets a human runs locally" principle
  stated in `ci.yml`'s own header comment.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `build-cross` Makefile target already produces all four target binaries
  reproducibly — this phase adds a checksum + publish step on top, not a new
  build step.
- `gh` CLI is already a required runtime dependency elsewhere in the project
  (doctor checks for it; the credential-upload feature already shells out to
  it) — informs the "why not gh CLI" discussion, though D-04 ultimately chose
  the dedicated-action route anyway.

### Established Patterns
- Every external GitHub Action in `ci.yml` is pinned to a full 40-character
  commit SHA with a trailing `# vX.Y.Z` comment — the new release job's
  action(s) must follow this exactly.
- `ci.yml`'s existing jobs use least-privilege `permissions:` scoping
  per-job, not a single blanket top-level grant — the new release job's
  `contents: write` must be scoped to itself only.

### Integration Points
- New job in `.github/workflows/ci.yml`, gated on `on: push: tags: ['v*']`
  (or equivalent), depending on (or duplicating) `build-cross`'s binary
  outputs.
- `cmd/gitid/main.go`'s Cobra root command `Version` field already exists and
  is wired — D-06 only changes what value flows into it.

</code_context>
