### Codex Review

**Overall verdict: REVISE BEFORE EXECUTION.** Plan 09.3-01 has a strong,
source-aligned implementation design. Plan 09.3-02 contains three
release-blocking contradictions: annotated-tag verification compares the wrong
Git object, prerelease paths cannot satisfy the installer's default URL while
still closing BUILD-05, and failed releases instruct the executor to reuse a
publicly exposed tag.

#### 09.3-01-PLAN.md

##### Summary

The first plan is thorough and mostly matches the repository's real
architecture. It extends the existing build matrix instead of duplicating it,
follows the established CI permission and action-pinning conventions, and
proposes meaningful end-to-end tests for the version/checksum/installer
contracts. Its main gap is that the release workflow cannot publish a release
with the human-selected prerelease status atomically.

##### Strengths

- The version-stamping path targets the correct production seam: `version` is
  currently a constant, and Cobra receives it directly through
  `Command.Version` at `cmd/gitid/main.go:16` and `cmd/gitid/main.go:84`.
  Composing all three injected values before assigning `Version` will exercise
  Cobra's actual `--version` mechanism.
- Extending the existing Makefile targets avoids a second build matrix. The
  current `build`, four-platform `build-cross`, and `install` commands are
  centralized at `Makefile:489`, `Makefile:494`, and `Makefile:514`. Applying
  one optional-default `LDFLAGS` value across these paths is coherent.
- The proposed release job preserves established CI controls: the workflow
  currently has a top-level read-only token at `.github/workflows/ci.yml:37`,
  full-SHA action pins at `.github/workflows/ci.yml:50`, and separate
  `build-cross` and three-runner `check` jobs at `.github/workflows/ci.yml:43`.
  `needs: [check, build-cross]` therefore provides a real release gate.
- The test design reuses proven repository infrastructure. `SandboxHome`
  isolates user files, `BuildBinary` restores the real HOME for Go's cache,
  and `FakeSSHDir` establishes the fake-executable-on-PATH pattern at
  `e2e/harness_test.go:44`, `e2e/harness_test.go:78`, and
  `e2e/harness_test.go:151`.
- The installer's write ordering matches BUILD-05: download and checksum
  verification remain in temporary storage before creating or replacing
  `~/.local/bin/gitid` (`09.3-01-PLAN.md:348`, `09.3-01-PLAN.md:355`,
  `09.3-01-PLAN.md:369`).

##### Concerns

- **HIGH — The workflow cannot honor the selected prerelease state at
  publication time.** The publish step includes release notes,
  unmatched-file failure, and assets, but no `prerelease` input
  (`09.3-01-PLAN.md:573`). Plan 02 instead proposes correcting the state
  afterward with `gh release edit` (`09.3-02-PLAN.md:308`). An intended
  prerelease can therefore appear temporarily as a stable/latest release.
- **LOW — One verification command executes the checksum manifest and masks
  that failure.** The command runs `./bin/checksums.txt`, suppresses its
  failure, then uses a semicolon before `grep`, so only the grep determines
  the final status (`09.3-01-PLAN.md:413`). It also does not assert that the
  printed count equals four.
- **LOW — The script calls itself POSIX-only but specifies a non-portable
  symbolic exit trap.** The plan requires `#!/bin/sh` and POSIX syntax at
  `09.3-01-PLAN.md:315`, then specifies `trap ... EXIT` at
  `09.3-01-PLAN.md:348`. `trap ... 0` is the portable POSIX spelling.

##### Suggestions

- Encode prerelease status in the release action before publication, or
  constrain this workflow to stable releases.
- Replace the malformed checksum verification with an explicit equality test
  on the four-line count.
- Use `trap 'rm -rf "$tmp"' 0 1 2 15`.
- Add a negative workflow test ensuring prerelease policy cannot be deferred
  to a post-publication edit.

##### Risk Assessment

**MEDIUM.** The local implementation and test architecture are strong. The
prerelease-publication mismatch is the only material release-safety gap; the
other issues are small corrections.

#### 09.3-02-PLAN.md

##### Summary

The second plan correctly recognizes that only a real tag can prove GitHub
Release behavior and appropriately gates that irreversible operation on a
human decision. However, its release verification and requirement-closure
logic are internally inconsistent. Two offered choices knowingly leave the
default installer unusable, annotated-tag verification will compare different
object IDs, and failure recovery reuses a burned tag despite the plan's own
warning against doing so.

##### Strengths

- The human checkpoint accurately treats publication as irreversible and
  requires the developer to choose the tag, prerelease status, and source ref
  (`09.3-02-PLAN.md:225`).
- Real-release verification correctly downloads the published assets and
  verifies those bytes rather than trusting the local `bin/` directory
  (`09.3-02-PLAN.md:308`). That directly tests BUILD-03's current pending
  contract at `.planning/REQUIREMENTS.md:393`.
- The throwaway-HOME installer run respects the repository's user-file safety
  policy and exercises the real installation destination without touching the
  developer's home (`09.3-02-PLAN.md:325`).
- Wiring `lint-shell` through `make lint` also reaches the existing
  pre-commit hook: `lint` currently depends on `lint-tagged` at
  `Makefile:238`, while the hook invokes `make lint` at
  `.pre-commit-config.yaml:20`.

##### Concerns

- **HIGH — Annotated-tag commit verification uses the wrong object.** The
  plan creates an annotated tag (`09.3-02-PLAN.md:296`), while CI stamps
  `git rev-parse --short HEAD` (`09.3-01-PLAN.md:565`). Verification compares
  that value with `git rev-parse --short <tag>` (`09.3-02-PLAN.md:319`),
  which resolves the annotated tag object rather than the tagged commit. The
  repository's existing annotated `poc-0.0.1` demonstrates the mismatch: the
  tag object resolves to `050164f`, while `<tag>^{commit}` resolves to
  `8409908`.
- **HIGH — Two offered choices cannot satisfy BUILD-05 but still mark it
  complete.** The installer defaults to `/releases/latest/download`
  (`09.3-01-PLAN.md:327`). The plan acknowledges that a prerelease is
  excluded from that endpoint and substitutes `GITID_INSTALL_BASE_URL`
  (`09.3-02-PLAN.md:333`); the throwaway option deletes the release entirely
  (`09.3-02-PLAN.md:346`). Nevertheless, both requirements are always marked
  complete at `09.3-02-PLAN.md:341`, contradicting BUILD-05's live
  released-binary dependency at `.planning/REQUIREMENTS.md:401`.
- **HIGH — Failure recovery reuses a publicly exposed tag.** The checkpoint
  warns that deletion cannot undo publication and that reusing a burned
  version is worse (`09.3-02-PLAN.md:229`). Task 3 then instructs the
  executor to delete and re-cut that tag at another commit after a failed run
  (`09.3-02-PLAN.md:300`). That creates mutable release provenance and
  conflicts with the task's own one-way rating at `09.3-02-PLAN.md:385`.
- **MEDIUM — The manual checksum instructions will fail when the user
  downloads only one platform asset.** The README plan says to download "the
  asset" and the four-entry manifest, then run full `sha256sum -c` or
  `shasum -c` (`09.3-02-PLAN.md:157`). The manifest intentionally names all
  four binaries (`09.3-01-PLAN.md:298`), so check mode reports the other
  three files missing.
- **MEDIUM — The documented install URL is not proved before requirement
  closure.** The checkpoint admits that the `main` URL will not resolve until
  merge and substitutes the phase branch (`09.3-02-PLAN.md:245`). Task 3
  still closes BUILD-05 before that merge (`09.3-02-PLAN.md:341`). The live
  branch currently has no upstream, so its raw branch URL is not yet a
  guaranteed hosted artifact either.
- **LOW — The public README would still carry a plainly stale status line.**
  The plan adds installation instructions but leaves "Phase 1 scaffolding
  only" untouched at `README.md:34`, even though the roadmap places the
  project at Phase 9.3 (`.planning/ROADMAP.md:491`).

##### Suggestions

- Use `git rev-parse --short "${tag}^{commit}"` for stamp verification.
- Make requirement closure conditional:
  - Stable release: BUILD-03 and BUILD-05 may close after the exact default
    one-liner succeeds.
  - Kept prerelease: BUILD-03 may close; BUILD-05 remains pending unless the
    installer supports an explicit version/prerelease option.
  - Deleted throwaway release: retain evidence, but do not claim a live
    install path.
- Publish prerelease state in the release action itself.
- Treat release tags as immutable. After a failed public attempt, diagnose
  and publish a new version; never move the old tag.
- For manual verification, filter the manifest to the selected asset or
  instruct users to download all four binaries.
- Merge or explicitly publish the branch before verifying the documented
  `main` URL, then run that exact URL before closing BUILD-05.
- Update or remove the stale README status line.
- Replace the fixed `/tmp/gitid-broken-syntax.sh` test file with `mktemp`.

##### Risk Assessment

**HIGH.** The plan performs irreversible public actions, and its current
verification logic will either fail after publication or close BUILD-05
without a working default installer. These issues should be resolved before
pushing any `v*` tag.
