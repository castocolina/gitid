## Warnings

### WR-01: README.md manual-install macOS checksum command verifies the wrong asset

**File:** `README.md:57`
**Issue:** The "Manual install" section's macOS verification snippet copies
the Linux example verbatim instead of substituting the macOS asset name:

```sh
# Linux
grep ' gitid-linux-amd64$' checksums.txt | sha256sum -c -

# macOS
grep ' gitid-linux-amd64$' checksums.txt | shasum -a 256 -c -
```

Because `checksums.txt` "covers all four binaries" (as the surrounding prose
correctly states), the `grep` on the macOS line still finds a match — the
manifest's `gitid-linux-amd64` entry — and pipes it into `shasum -a 256 -c -`.
`shasum -c` looks for a file named `gitid-linux-amd64` in the current
directory, which a macOS user (who downloaded `gitid-darwin-amd64` or
`gitid-darwin-arm64`) does not have. The command fails with a spurious
"open or read" error unrelated to the file the user actually downloaded,
so following these instructions literally never verifies the macOS binary.
This is exactly the kind of documentation bug that undermines the
checksum-verification story the section exists to teach — the curl-pipe
installer (`scripts/install.sh`) verifies correctly, but this manual
fallback path does not.
**Fix:**
```sh
# macOS (Intel)
grep ' gitid-darwin-amd64$' checksums.txt | shasum -a 256 -c -

# macOS (Apple Silicon)
grep ' gitid-darwin-arm64$' checksums.txt | shasum -a 256 -c -
```

### WR-02: Two PTY keystroke delays bypass the centralized CI timing fix

**File:** `e2e/create_flow_pty_e2e_test.go:179`, `e2e/create_flow_pty_e2e_test.go:1447`
**Issue:** This phase's own investigation (documented in
`09.3-02-SUMMARY.md` and in `keystrokeDelay`'s doc comment in
`e2e/ui_pty_e2e_test.go`) identified an unscaled, flat keystroke-pacing
constant as a real, CI-only cause of dropped/coalesced input under `-race`
CPU contention, and fixed it by centralizing `keystrokeDelay` as a single
`ciTimeoutMultiplier()`-scaled `var` so "the ~390 existing call sites need
no change." Two call sites in `TestCreateFlow_...` (the raw-PgDn viewport
navigation loop and the manual-key-path character-by-character typing loop)
pass a hardcoded `10*time.Millisecond` directly to `sendKey` instead of
`keystrokeDelay`:

```go
s.sendKey([]byte("\x1b[6~"), 10*time.Millisecond)     // line 179
...
s.sendKey([]byte{b}, 10*time.Millisecond)              // line 1447, per-char in a loop
```

These predate this phase's diff (not touched by any commit in
`635ca3d..HEAD`) and are outside the "~390 call sites" the fix intended to
close in one motion — they are exactly the residual pattern the fix's own
stated goal was to eliminate. Since `test-e2e` no longer gates CI (rc.9),
this cannot currently break a release, but it is a real, provable gap in a
fix whose changelog claims full closure, and it is a plausible contributor
to the still-unresolved GitHub-Actions-only flakiness this phase's
follow-up note leaves open (per-char typing is the highest keystroke-volume
loop in the whole suite).
**Fix:** Replace both literal `10*time.Millisecond` arguments with
`keystrokeDelay` (or a fraction of it, e.g. `keystrokeDelay/4`, if the
tighter local-dev pacing is intentional) so both loops scale under
`GITHUB_ACTIONS=true` like every other keystroke pacing constant in the
package.

## Info

### IN-01: install.sh's checksum manifest shares a trust root with the binary it verifies

**File:** `scripts/install.sh:65-87`
**Issue:** `checksums.txt` is fetched from the exact same `BASE_URL` as the
binary itself (both are release assets on the same GitHub Release). The
verification therefore proves the downloaded bytes match what was uploaded
to that release, but provides no protection if the release itself were
compromised (e.g. a compromised publishing token re-uploading both a
malicious binary and a matching malicious manifest) — there is no
independent signature (GPG, sigstore/cosign, etc.) anchoring the manifest
to a separate trust root. This is a common and generally-accepted tradeoff
for this class of installer (comparable to many popular curl-pipe
installers), and is not a regression introduced by this phase, so it is not
a blocker — noting it for awareness given `scripts/install.sh`'s own header
comment already frames the design explicitly around "both fetches always
come from the SAME base."
**Fix:** No action required for this phase. If stronger supply-chain
guarantees are wanted later, consider signing `checksums.txt` (e.g. with
`cosign` or a maintainer GPG key) and having the installer verify the
signature before trusting the manifest.
