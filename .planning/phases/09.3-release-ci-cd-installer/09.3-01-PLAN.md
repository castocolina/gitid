- **D-02** — all FOUR targets are published: `gitid-darwin-amd64`, `gitid-darwin-arm64`,

- **D-03** — raw binaries (no archives) plus a `checksums.txt` covering all four.

  installs to `~/.local/bin`, and prints a PATH hint when that directory is not on PATH.

  SHA-256 verification, and a hard non-zero refusal on mismatch.

Claude's discretion, exercised here (each recorded with its reason):

1. **`generate_release_notes: true`** rather than a fixed body template. The repo already
   commits in descriptive logical groups (CLAUDE.md), so GitHub's auto-generated notes are
   strictly better than any template this phase could invent.
2. **`softprops/action-gh-release@efb35369e0ad2afab669f228072c1b0d510eae64 # v3.0.3`** —
   the example named during discussion, confirmed by 09.3-RESEARCH.md against the GitHub
   REST API (real commit SHA, actively maintained, not archived) and approved in that
   document's Package Legitimacy Audit.
3. **`checksums.txt` is produced by a Makefile target**, per CONTEXT.md's own lean toward
   parity with `build-cross`'s "CI invokes the SAME make targets a human runs locally"
   principle. `checksums` depends on `build-cross`, so one CI step both builds and hashes
   and the manifest can never describe a stale binary.
4. **The installer overwrites idempotently** with no existing-install detection — the
   plain curl-pipe-sh convention CONTEXT.md asked to keep simple.
5. **The release job declares `needs: [check, build-cross]`.** CONTEXT.md's D-01 settles
   that the release is a separate JOB; it does not settle ordering, and 09.3-RESEARCH.md
   flags the ordering as an explicit planner-level Open Question. Without the edge, a tag
   push starts `release` in parallel with `check`, so a public binary can be published
   while (or even after) the gate goes red — which contradicts BUILD-02's "red gates
   block merge" posture for a far more permanent artifact. The cost is one gate cycle of
   waiting per release, on an event that happens a handful of times a year.
6. **Checksum verification compares hashes directly** (extract the expected hash with an
   anchored grep, compute the actual one, compare strings) rather than using check mode
   (`-c`). Check mode would require the downloaded file to carry the published asset name
   on disk and depends on flags whose availability differs between coreutils `sha256sum`
   and the Perl `shasum`; direct comparison is portable by construction and makes the
   "no entry for this asset" case an explicit refusal rather than a silent no-op.
7. **`sh -n` (Task 1 of plan 09.3-02) rather than shellcheck/actionlint** as the static
   gate. Both would be new toolchain dependencies installed on three CI runners; the
   authoritative proof here is that the tests EXECUTE the real script and assert on the
   real result (CLAUDE.md's hypothesis -> test -> implementation rule), with `sh -n` as a
   zero-dependency syntax backstop and `cmd/gitid/release_plumbing_test.go` as the
   workflow-invariant backstop.
</decisions_implemented>

    Header comment block: what it does, the canonical one-liner

    seam together with why it is not a verification bypass — the binary and the manifest are
    always fetched from the SAME base, so overriding it substitutes one self-consistent release
    for another rather than disabling the check.

    Constants: `REPO` set to `castocolina/gitid`; a default base URL of
    `https://github.com/${REPO}/releases/latest/download` (the documented redirect suffix — no
    GitHub API call, no `jq`, no rate limit, per 09.3-RESEARCH.md Pattern 3);
    `BASE_URL="${GITID_INSTALL_BASE_URL:-<that default>}"`; `INSTALL_DIR="${HOME}/.local/bin"`
    (D-07 — no sudo); `BIN_NAME="gitid"`.

    A `fail()` helper that writes `gitid: ` followed by its argument to stderr and exits 1. Every
    refusal below goes through it.

    Preflight: if `command -v curl` finds nothing, fail with
    `curl is required to download the release binary`.

    OS/arch detection (D-08, and ASVS V5): capture `uname -s` and `uname -m`, then map them
    through two `case` statements that are strict allowlists — `Darwin` to `darwin` and `Linux`
    to `linux`, with a `*)` branch failing with `unsupported operating system: ` plus the raw
    value; `x86_64` and `amd64` to `amd64`, `arm64` and `aarch64` to `arm64`, with a `*)` branch
    failing with `unsupported architecture: ` plus the raw value. Both refusals must happen
    BEFORE any URL is built, so an unexpected `uname` output can never be interpolated into a
    request. Compose `asset="gitid-${os_tag}-${arch_tag}"` only from the mapped tags, never from
    the raw `uname` output.

    Scratch space: `tmp=$(mktemp -d)` with a `trap` removing it on EXIT, INT and TERM.

    Download: fetch `${BASE_URL}/${asset}` to `${tmp}/${BIN_NAME}` and `${BASE_URL}/checksums.txt`
    to `${tmp}/checksums.txt`, each with `curl -fsSL` inside an explicit `if ! ...; then` guard
    that fails with `download failed: ` plus the URL. Do not rely on `set -e` alone here — a bare
    abort would leave the user with curl's exit code and no explanation.

    Verification (D-08, ASVS V6): select the tool at runtime — if `command -v sha256sum` succeeds
    use `sha256sum`, else if `command -v shasum` succeeds use `shasum -a 256`, else fail with
    `no SHA-256 tool found (need sha256sum or shasum)`. Extract the expected hash by grepping
    `checksums.txt` with an anchored extended regexp of a 64-hex group, two spaces, the asset
    name, and end-of-line, taking the first match and cutting the first space-delimited field; if
    the result is empty, fail with `checksums.txt has no entry for ` plus the asset name plus
    ` — refusing to install an unverified binary`. Compute the actual hash by running the selected
    command over the downloaded file and cutting the first field. The variable holding the
    selected command is deliberately left unquoted at the call site because `shasum -a 256` must
    word-split into three arguments — say so in a comment so a future reader does not "fix" it.
    Compare the two strings; on inequality fail with `checksum verification FAILED for ` plus the
    asset name, the expected and actual hashes, and ` — refusing to install an unverified binary`.
