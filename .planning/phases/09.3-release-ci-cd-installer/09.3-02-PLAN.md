<objective>
Turn the pipeline plan 09.3-01 built into a proven, documented, publicly usable install path:
add the zero-dependency shell gate, write the user-facing install documentation, get an
explicit developer decision on the first public release, then actually cut that release and
verify — over the real network, from the real GitHub Release — that a stranger's
`curl ... | sh` produces a checksum-verified gitid reporting the right version.

Everything before this point is a local simulation. A GitHub Actions job has no local test
harness (09.3-RESEARCH.md says so explicitly), so exactly one thing can prove BUILD-03 and
BUILD-05: a real tag, a real release, a real download. That is what this plan does — behind a
developer decision, because publishing a public release under someone's name is a one-way door.

Purpose: close BUILD-03 and BUILD-05 on evidence, not on inference — and close each of them ONLY
as far as the evidence actually reaches. BUILD-05's text is about a hosted script installing a
released binary from a live URL; a run that had to substitute a different download base, or that
ended with the release deleted, proves the mechanism but not the live path. This plan says so out
loud instead of ticking a box, and Task 2 lets the developer pick the option that closes both.

Output: a published release, a verified real-network install, documented install instructions, and
requirement closure that matches the evidence — with any residual condition named as a single
runnable command rather than left as a general intention.
</objective>

Claude's discretion, exercised here:

1. **`sh -n` as the shell gate**, not shellcheck. Adding shellcheck means a new binary in
   `setup-env` installed on three CI runners for a single ~90-line script whose behavioral
   contract is already covered by the executing e2e cases plan 09.3-01 added. `sh -n` is a POSIX
   syntax check every host already has, and it catches the class of defect that would be
   catastrophic here — an unterminated quote or `case` in a script people pipe straight into
   their shell.
2. **The real-network verification installs into a throwaway HOME**, never the developer's own
   `~/.local/bin`. CLAUDE.md forbids mutating the user's files without explicit confirmation, and
   a throwaway HOME exercises the identical code path without needing that confirmation at all.
3. **Requirement closure is conditional on which install path was actually provable**, rather than
   a fixed "tick both at the end". BUILD-03 describes the pipeline; BUILD-05 describes a live
   hosted install path. Three of the four release options the checkpoint offers cannot produce a
   working default `/releases/latest/download` URL, so closing BUILD-05 under them would record a
   working install for a URL that 404s — and the next phase's Linux validation would inherit that
   as a fact. The closure table in Task 3 makes the mapping mechanical. This resolves a HIGH
   finding from 09.3-REVIEWS.md.
4. **The prerelease decision is carried by the tag string** rather than by a separate flag the
   executor passes. Plan 09.3-01's release job classifies the tag at publication, so there is
   exactly one source of truth and no window during which the release is publicly mis-stated. The
   cost is that the checkpoint must state the spelling convention explicitly, which it now does.
5. **A failed release run is followed by a new version, never by moving the tag.** The alternative
   (delete and re-cut) was in the previous draft of this plan and directly contradicted the
   checkpoint's own warning; it also produces mutable provenance for a channel whose entire value
   proposition is that a version identifies fixed bytes.
</decisions_implemented>

  <context>
    Plan 09.3-01 built the release pipeline; nothing has been published yet. The next task pushes a
    real tag, which fires the `release:` job and creates a real GitHub Release on
    github.com/castocolina/gitid. That step is a one-way door in three ways: the tag name is
    consumed forever in this repository's namespace, the published asset URLs are fetchable by
    anyone from the moment they exist, and the version chosen now anchors the public numbering of
    every release after it. Deleting a release and its tag afterwards does not un-fetch what was
    already downloaded, and re-using a burned version number is worse than picking the right one
    now. Task 3 treats every tag as immutable in both directions: if the run fails, it does NOT
    move or re-cut your tag — it comes back for a new version.

    Facts that bear on the choice. The repository has no `v*` tag today — its only tags are
    `backup/pre-05.6-squash`, `backup/pre-05.7-compact` and `poc-0.0.1` — so nothing collides and
    nothing constrains the starting number. The milestone in flight is v1.0 and the roadmap still
    has Phases 9.4, 9.5 and 10 open, so the product is not at 1.0 yet. The `release:` job waits for
    `check` and `build-cross` to pass on the exact tagged commit before publishing, so a red gate
    cannot ship.

    **Your prerelease choice is expressed by the tag string itself.** Plan 09.3-01's release job
    classifies the release at publication from the tag: a SemVer prerelease suffix
    (`v0.0.1-rc.1`) publishes as a prerelease and is never marked latest; a bare version
    (`v0.1.0`) publishes as a stable release and becomes latest. There is no separate switch and
    nothing is corrected afterwards, so the tag you name below IS the decision — pick the string
    and the status together.

    **The ref you tag from decides whether BUILD-05 can close in this phase.** The README documents
    `raw.githubusercontent.com/castocolina/gitid/main/scripts/install.sh`, and that URL serves 404
    until this branch is on `main`. BUILD-05's requirement text is about a hosted script installing
    a released binary — so it closes only when that EXACT one-liner, with no base-URL override,
    has been run green. Merging this phase branch to `main` before tagging is the only path on
    which Task 3 can run it. Tagging from the branch instead is perfectly fine; it just means Task
    3 verifies against the branch ref, records the substitution, and leaves BUILD-05 `Pending`
    with the one command that would close it written down.

    **What each option closes.** BUILD-03 is about the pipeline — tag, publish, checksums, stamped
    `--version` — so any option that actually publishes and is verified closes it. BUILD-05 is
    about a live install path, so it closes only under `real-release` + a `main` ref. This is
    stated up front so the closure state is your decision, not a downstream surprise.
