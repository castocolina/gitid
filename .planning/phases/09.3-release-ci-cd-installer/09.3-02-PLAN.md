<objective>
Turn the pipeline plan 09.3-01 built into a proven, documented, publicly usable install path:
add the zero-dependency shell gate, write the user-facing install documentation, get an
explicit developer decision on the first public release, then actually cut that release and
verify — over the real network, from the real GitHub Release — that a stranger's
`curl ... | sh` produces a checksum-verified gitid reporting the right version.

Everything before this point is a local simulation. A GitHub Actions job has no local test
harness (09.3-RESEARCH.md says so explicitly), so exactly one thing can prove BUILD-03 and
BUILD-05: a real tag, a real release, a real download. That is what this plan does — behind a
developer decision, because publishing a public release under someone's name is a one-way door.

Purpose: close BUILD-03 and BUILD-05 on evidence, not on inference.
Output: a published release, a verified real-network install, documented install instructions,
and two requirements marked complete with the evidence that earned it.
</objective>

Claude's discretion, exercised here:

1. **`sh -n` as the shell gate**, not shellcheck. Adding shellcheck means a new binary in
   `setup-env` installed on three CI runners for a single ~90-line script whose behavioral
   contract is already covered by the executing e2e cases plan 09.3-01 added. `sh -n` is a POSIX
   syntax check every host already has, and it catches the class of defect that would be
   catastrophic here — an unterminated quote or `case` in a script people pipe straight into
   their shell.
2. **The real-network verification installs into a throwaway HOME**, never the developer's own
   `~/.local/bin`. CLAUDE.md forbids mutating the user's files without explicit confirmation, and
   a throwaway HOME exercises the identical code path without needing that confirmation at all.

  <name>Task 2: Decide the first public release tag and its prerelease status</name>
  <decision>Which tag cuts the first public gitid release, and is it a prerelease?</decision>
  <context>
    Plan 09.3-01 built the release pipeline; nothing has been published yet. The next task pushes a
    real tag, which fires the `release:` job and creates a real GitHub Release on
    github.com/castocolina/gitid. That step is a one-way door in three ways: the tag name is
    consumed forever in this repository's namespace, the published asset URLs are fetchable by
    anyone from the moment they exist, and the version chosen now anchors the public numbering of
    every release after it. Deleting a release and its tag afterwards does not un-fetch what was
    already downloaded, and re-using a burned version number is worse than picking the right one
    now.

    Facts that bear on the choice. The repository has no `v*` tag today — its only tags are
    `backup/pre-05.6-squash`, `backup/pre-05.7-compact` and `poc-0.0.1` — so nothing collides and
    nothing constrains the starting number. The milestone in flight is v1.0 and the roadmap still
    has Phases 9.4, 9.5 and 10 open, so the product is not at 1.0 yet. The tag will point at the
    current phase branch head unless you say otherwise; the `release:` job waits for `check` and
    `build-cross` to pass on that exact commit before publishing, so a red gate cannot ship.

    One thing no option below changes: the README's documented one-liner points at the `main` ref,
    so it only resolves after this branch is merged. Task 3's real-network verification therefore
    fetches the script from the branch ref and records that distinction explicitly.
  </context>
  <options>
    <option id="throwaway-prerelease">
      <name>A throwaway prerelease, deleted after verification (e.g. v0.0.1-rc.1, marked prerelease)</name>
      <pros>Proves the whole pipeline for real while burning a version number nobody will ever want. Marked prerelease, so GitHub does not treat it as the repository's latest release. Deleting the release and tag afterwards leaves the public numbering completely clean for a real first release later.</pros>
      <cons>Once deleted, `/releases/latest/download/` resolves to nothing, so the README's one-liner is documented but not yet live. Extra ceremony: the tag must be deleted locally and on origin after the evidence is captured.</cons>
    </option>
    <option id="real-prerelease">
      <name>A real, kept prerelease (e.g. v0.9.0, marked prerelease)</name>
      <pros>The verification artifact IS the first usable release. Honest about maturity: prerelease signals that Phases 9.4/9.5/10 are still open. Nothing to clean up afterwards.</pros>
      <cons>GitHub's `/releases/latest/` never points at a prerelease, so the installer's default base URL will not resolve until a non-prerelease exists — Task 3 must override the base URL to the tag's own download prefix and record that the documented one-liner is not yet live.</cons>
    </option>
    <option id="real-release">
      <name>A real, non-prerelease first version (e.g. v0.1.0)</name>
      <pros>`/releases/latest/download/` resolves immediately, so the README's documented one-liner is live and testable exactly as a stranger would run it — the strongest possible evidence for BUILD-05. Nothing to clean up. A 0.x number is already the conventional signal that the surface is not settled.</pros>
      <cons>A public, non-prerelease artifact exists before the v1.0 milestone closes; anyone browsing the repository can install it and form an opinion of an unfinished product. The number is spent.</cons>
    </option>
  </options>
