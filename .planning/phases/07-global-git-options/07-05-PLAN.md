**The frozen command tree (07-CONTEXT.md leaves the shape to Claude's discretion;
DECIDED here, binding for the parity matrix, the schema doc, the tests and every
later phase):**

```
gitid git options  list                  [--json]
gitid git options  apply  <key>...       [--dry-run] [--yes] [--fail-on-advisory] [--json]
gitid git fallback show                  [--json]
gitid git fallback set    [--name <n>] [--email <e>] [--clear-name] [--clear-email]
                                         [--dry-run] [--yes] [--json]
```

No extra verbs. No flat root-level aliases. Two nouns under `git` because there
are two distinct write authorities behind them, and collapsing them would imply a
single ceremony that plan 07-02 deliberately kept separate.

**The `<key>...` arguments are ROW TOKENS, and nothing else (R-5, from cross-AI
review cycle 1: "`options apply` key identity").** This surface carries three
spellings of the same thing — the display key the screen shows, the member config
key git reports, and the row token — and the review correctly found that the plans
never said which one a user types. Plan 07-03 freezes one CLI token per row as a
field on the policy record; that column is the argv vocabulary and the only one.
Read the token table in `07-03-SUMMARY.md` and validate against `internal/globalgit`'s
policy rows, never against a locally-written list.

Three consequences, binding:

- A member key is REFUSED, not silently accepted: `alias.lg`, `core.eol` and a
  lower-cased `init.defaultbranch` each exit with the refusal status and a message
  naming the row token to use instead. Accepting `alias.lg` would imply per-key
  sub-selection of a bundle, which D-09 defers to post-v1 and which the unit-apply
  bundle write cannot honour — a CLI that appears to accept it and then writes all
  eight aliases is lying to a script.
- Token matching is exact and case-sensitive. The tokens are the canonical display
  spelling; a case-insensitive match would make `init.defaultbranch` succeed and
  reintroduce exactly the ambiguity this rule removes.
- The three rows whose display key is prose — the line-endings pair and the two
  bundle sections — are reachable ONLY by their token. There is no argv form of
  `core.autocrlf / core.eol`.

**Nothing is pre-selected, on either surface (R-1's CLI half).** Review cycle 1
noted the adaptive-depth fallback's "nothing pre-selected" appeared to fight the
screen's own defaults. It no longer does: plan 07-01 emptied the TUI's default
selection under 6/D-15, which `07-CONTEXT.md` carries forward from Phase 6 and which
the Global SSH screen already ships. `NewAppOnGlobalGit` therefore does not need to
CLEAR anything — it needs to not add anything — and this plan asserts the resulting
`chosen` set is empty rather than assuming the constructor inherited the property.

**Setting versus clearing is EXPLICIT (D-04's CLI expression; DECIDED here).**
`--name`/`--email` set a half; `--clear-name`/`--clear-email` unset it. Omitting a
flag leaves that half exactly as it is. An empty-string value for `--name` or
`--email` is a refusal, not a silent clear, and supplying both the set and the
clear flag for the same half is a refusal. Rationale: on the TUI the two fields
are visible and pre-filled, so "apply what is on screen" is unambiguous; a CLI has
no screen, and a script that forgets a flag must never silently erase the user's
identity. Say that in the command's help text.

**Schema identifiers:** `gitid.git.options/v1`, `gitid.git.apply/v1`,
`gitid.git.fallback/v1`, `gitid.git.fallbackset/v1`.

**Exit-status table**, matching the SSH noun's own so a script sees one
convention across the tool:

| Code | Case |
|---|---|
| 0 | success, including a success carrying advisories |
| 0 | dry run, even with the advisory opt-in |
| 1 | refusal: unknown key, a key that is not selectable, a malformed or contradictory flag combination, or a required confirmation not given |
| 2 | a write that was attempted and rolled back |
| 3 | the advisory opt-in was supplied and the successful write carried advisories |

| Boundary | Description |
|----------|-------------|
