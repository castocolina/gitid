<objective>
Give the global fallback author the shape the user actually asked for — two independent fields, empty meaning unset — and put it somewhere git's own precedence rules cannot betray.

Purpose: `07-CONTEXT.md` D-04 is a USER OVERRIDE on a frozen design decision, in the user's own words: `user.name` and `user.email` are separate git config, so a single checkbox over one email field is the wrong model. It is also a correctness fix, not a preference: research verified that with only an email set, git silently guesses the author NAME from the OS account and commits succeed as `guessed-name <email>` — so the frozen email-only D9 half-works by construction. D-05 then verified empirically that the obvious implementation, a plain `git config --global user.email`, lands AFTER the `includeIf` blocks on a recipe-shaped file and hijacks every identity's author. This plan implements the pair, places its block where `includeIf` still wins, and makes that invariant a permanent post-write proof rather than a promise in a doc comment.
Output: A two-field fallback author whose empty state is honest, whose block sits above every `includeIf`, and whose precedence is re-proven on the real machine after every write.
</objective>

**The positional primitive.** `filewriter.PrependBlockIfNotFound` is the floor primitive; D-05 needs its sibling. Add to `internal/filewriter/block.go`:

`func InsertBlockAfter(existing []byte, anchorName, name, blockBody string) ([]byte, error)`

Semantics, in this precedence order: if a block named `name` already exists, delegate to `ReplaceBlock` — position is preserved and no second copy appears, exactly as `PrependBlockIfNotFound` behaves for its own floor case. Otherwise, locate the anchor block's end marker and splice the canonical block form directly after it. If the anchor is absent, return the input bytes unchanged plus an error naming the anchor — an insert with no anchor has no defensible position, and silently appending is the one behavior D-05 verified is wrong. Match `ReplaceBlock`'s CRLF tolerance when scanning marker lines, and use the same canonical block form (markers wrapping the trimmed body, each line newline-terminated) so repeated writes stay byte-stable.

Document WHY this primitive exists on the function itself, citing the empirical finding: a plain `git config --global user.email` appends and therefore lands after the `includeIf` blocks, which hijacks every identity's author. Position is the whole point of this function; a future refactor must not "simplify" it into an append.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| the fallback block's position → every identity's commit author | A block below an `includeIf` silently rewrites the author of every repository the user commits to. |
| user-typed name and email → a rendered `[user]` section | Free-form user input crossing into a config file gitid writes. |
| an empty field → the written file | "Unset" and "set to empty" are different to git, and confusing them produces commits authored by nobody. |
| the doctor's destructive fix path → the fallback block | An unregistered reserved name lets the fixer delete a block gitid immediately rewrites. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-07-10 | Spoofing | fallback author overriding an identity's author | critical | mitigate | `InsertBlockAfter` anchors the block immediately below the floor include; a placement test on a recipe-shaped file asserts the block sits above the first `includeIf`; the ceremony's verify stage re-proves matched and unmatched resolution on the real machine and raises an advisory on violation (D-05, D-06). |
| T-07-11 | Tampering | value injection through the name or email field | high | mitigate | Both values pass the existing `validateValue` guard before rendering; a newline-bearing value is rejected before any bytes are composed, asserted by test. |
