## Deviations recorded during Phase 9.1

Three scoped deviations were made across the phase (wave 1 and wave 2 together), each
naming the decision it deviates from, why, and where the substance was preserved.
None were made silently — each is recorded at the commit that introduced it and
consolidated here per Task 3's instruction.

**1. D-03 identity-name run-scoping instead of ONESHOT.md's literal GitHub title
format.** ONESHOT.md's Phase 9 (GitHub) policy names every created key
`gitid-e2e:<run-id>:<purpose>` literally. GitLab keys instead go through the product's
frozen D-07 `KeyTitle` format (`gitid: <name> @ <machine>`), with the run's scoping
string embedded in the disposable IDENTITY NAME (`gitid-e2e-<run-id>`) rather than in a
literal policy-format title. **Why:** emitting the policy's literal title format would
require a test-only product seam that D-06 forbids (the product's title format is
frozen, shipped behavior — a test cannot special-case it). **Substance preserved:**
every created key's title still carries a unique, greppable, unambiguous run-scoping
string (the identity name is embedded verbatim in the frozen title), so every
recorded-ID/scope-re-confirmation/final-sweep guarantee the policy exists to provide
still holds exactly. This deviation is now discoverable in ONESHOT.md's own new "Phase
9.1 GitLab External Account Policy" section, not only inside a plan file.

**2. GLab-marked identifier spelling instead of PATTERNS.md's literal "copy verbatim"
instruction for the cleanup bookkeeping block.** PATTERNS.md's Pattern 2 instructs
copying the LIFO cleanup bookkeeping block (`outstandingRemoteKeys`,
`deleteRecordedRemoteKey`, `drainOutstandingRemoteKeys`, etc.) "verbatim, unchanged."
The actual implementation renames every identifier with a `GLab`-marked prefix/infix
(e.g. `outstandingGLabRemoteKeys`, `deleteRecordedGLabRemoteKey`). **Why:**
collision-safety — `go vet -tags=realaccount,realaccountgitlab ./...` (part of `make
lint`'s own `lint-tagged` guard) compiles the GitHub and GitLab real-account files
together in the same package under a combined build; identical top-level identifier
names between the two files would be a duplicate-declaration compile error, not a
"verbatim copy." **Substance preserved:** every function body, the LIFO ordering
discipline, the outstanding-ID-as-single-source-of-truth invariant, and the
delete-by-recorded-ID-after-scope-re-confirmation logic are byte-for-byte structurally
identical to the GitHub original — only the identifiers carry the disambiguating
`GLab` marker.

**3. `encoding/json` scope-parsing transport instead of a `--jq .scopes` CLI flag.**
RESEARCH.md's primary recommendation was `glab api personal_access_tokens/self --jq
.scopes` — pre-filtering the scopes array via `glab`'s own bundled `jq` support before
the test ever sees the output. The shipped preflight instead calls `glab api
personal_access_tokens/self` with no `--jq` flag and decodes the full JSON response in
Go (`parseGLabTokenScopes`, against the pinned `glabTokenSelf` struct contract). **Why:**
unit-testability — parsing the full response in Go lets
`TestRealAccountGitLabScopeCheckRequiresExactMember`'s 14-case table test exercise edge
cases (a top-level JSON array instead of an object, omitted vs. explicit
`revoked`/`active` fields, a leading banner line, trailing bytes) entirely offline
against synthetic strings; a `--jq`-filtered transport would push that decoding logic
into `glab`'s own bundled `jq`, invisible to a Go-level table test and untestable
without a real `glab` binary on PATH. **Substance preserved:** the exact-member (never
substring) scope-check discipline RESEARCH.md specified is unchanged; only the parsing
transport moved from shell-side filtering to a Go-side, pinned, unit-tested contract —
which is what caught the real `parseGLabTokenScopes` top-level-array bug (09.1-01-SUMMARY.md
Deviation #4) before it ever reached a live `glab` session.
