## Protocol shape

GitLab has ONE combined registration type (not GitHub's separate auth+signing), so
Wave 8's whole "4 keys, 2 phases" shape was driven entirely by GitHub's dual-
registration model. The question: does the per-registration-title API ("Phase N" in
Wave 8) still need its own separate proof for GitLab, or does GitLab's single
registration type make that unnecessary?

| Option | Description | Selected |
|--------|-------------|----------|
| Single phase only | One disposable key pair, driven through the compiled register-key binary only. GitLab has no per-type distinction to separately prove, so skip the engine-level naming-policy phase entirely. | ✓ |
| Keep two phases like Wave 8 | Still validate both the compiled product path AND the engine's direct per-title API call as two separate disposable keys, for symmetry with Wave 8 even though GitLab has only one registration type. | |

**User's choice:** Single phase only.
**Notes:** Confirmed by reading `internal/uploader/uploader.go`/`inventory.go` — GitLab's
`buildArgs`/`deleteArgs` have no registration-type routing, unlike GitHub's post-CR-02
namespace-scoped delete. A second phase would add complexity with no additional coverage.

## Test file structure

Should this live in a new dedicated test file/build tag, or extend the existing GitHub
real-account file?

| Option | Description | Selected |
|--------|-------------|----------|
| New file, new build tag | `e2e/upload_real_account_gitlab_e2e_test.go` under its own e.g. `realaccountgitlab` tag — keeps GitHub and GitLab real-account runs independently triggerable and mirrors the existing file's own "one surface, one tag" precedent. | ✓ |
| Extend the existing file/tag | Add a second test function to `e2e/upload_real_account_e2e_test.go` under the same `realaccount` tag — both providers run together under one make target. | |

**User's choice:** New file, new build tag.
**Notes:** None beyond the recommendation rationale.
