## Summary

This phase is structurally simpler than its Phase-9/Wave-8 GitHub precedent: GitLab
has exactly one SSH-key registration type (`auth_and_signing`), so there is no
"Phase N" engine-level per-title proof to run — only a single compiled-binary
product-path run (Wave 8's "Phase P" shape), with one disposable key pair instead of
four. The reusable engine code (`internal/uploader`'s `buildArgs`, `deleteArgs`,
`Inventory`/`glabInventory`, `DeleteRecordedKey`, `KeyTitle`) and the reusable test
harness (`e2e/harness_test.go`'s `SandboxHome`, `BuildBinary`, `FakeGLabDir`,
`internal/keygen`) are already proven; this phase's job is to point the exact same
LIFO-cleanup/run-scoped-inventory-lookup/final-sweep pattern Wave 8 built at a real,
authenticated `glab` session instead of the fake shim.

The one genuinely new piece of research this phase needs — and the one place Wave
8's pattern cannot be copy-pasted — is the scope preflight. `gh auth status` prints
an exact, parseable `Token scopes: '...'` line; **`glab auth status` does not** (
confirmed empirically this session against a real installed `glab 1.114.0`). GitLab's
own documentation does not enumerate a per-endpoint required-scope table the way
GitHub does either. The closest verified equivalent is the GitLab REST API's `GET
/personal_access_tokens/self` endpoint, which returns a `scopes` JSON array — callable
via `glab api personal_access_tokens/self` — but this only works for PAT-based
sessions, and it needs a live, working `glab` session to prove definitively (this
session's own `glab` install is unauthenticated — `auth status` fails with
`invalid_grant`, an expired OAuth token, not a PAT). The plan must resolve this
concretely before/during Task 1's checkpoint, not defer it silently.

**Primary recommendation:** mirror Wave 8's file/task/threat-model shape exactly
(single dedicated build-tagged file, blocking checkpoint, outstanding-ID map,
LIFO `t.Cleanup` ordering, run-scoped inventory lookup for ID capture, prefix-scoped
final sweep) but (1) collapse to one phase/one key pair per D-01/D-02, (2) replace the
`gh`-style scope-line parser with a `glab api personal_access_tokens/self --jq
.scopes` JSON-array exact-member check (falling back to a named, explicit
`t.Skip` if the endpoint or field is unavailable — e.g. an OAuth-based session that
has no PAT-shaped scopes to read), (3) add `realaccountgitlab` to the Makefile's
`KNOWN_BUILD_TAGS` and a matching `go vet -tags realaccountgitlab ./...` line in
`lint-tagged` (a load-bearing, easy-to-miss step — the `lint-tagged` guard hard-fails
on any unlisted `//go:build` tag), and (4) capture the real `glab ssh-key add` output
string live during Task 2's execution rather than assume it matches the fake shim's
`"Added SSH key."` literal, which is an unverified test-fixture assumption, not a
proven real-CLI output.

### Pattern 1: Single-phase, single-key disposable protocol (D-01/D-02 simplification of Wave 8)
**What:** Wave 8 needed two disposable key pairs and two phases (Phase P: compiled
binary under the product's frozen title; Phase N: engine call under the policy's
literal `gitid-e2e:<run-id>:<purpose>` title) because GitHub has two independently
titled registration endpoints (`user/keys`, `user/ssh_signing_keys`) and the policy's
literal naming clause needed its own proof separate from the product path. GitLab has
exactly one registration endpoint and one registration type
(`RegistrationCombined`/`auth_and_signing`), so there is nothing for a "Phase N" to
separately prove — the D-03 naming deviation (scope through the identity name, not the
title) is carried by Phase P alone.
**When to use:** This phase, exclusively — do not add a second phase per CONTEXT.md
D-02's explicit instruction.
**Example (adapted from the real, merged Wave 8 file):**
```go
// Source: e2e/upload_real_account_e2e_test.go:334-348 (runProductPhase), adapted —
// GitLab needs only ONE registration call (RegistrationCombined), not two.
func runProductPhase(t *testing.T, binary, home, glabConfigDir, realHome, realGLabPath, wrapperDir, identityName string, recorder *argvRecorder) (string, string, string) {
	t.Helper()
	runRealBinary(t, home, glabConfigDir, realHome, realGLabPath, wrapperDir, binary, recorder,
		"create", "--name", identityName, "--provider", "gitlab.com",
		"--git-name", "gitid e2e", "--git-email", "gitid-e2e@example.invalid", "--yes", "--no-upload")
	output := runRealBinary(t, home, glabConfigDir, realHome, realGLabPath, wrapperDir, binary, recorder, "register-key", identityName)
	pubPath := filepath.Join(home, ".ssh", "id_ed25519_"+identityName+".pub")
	pub, err := os.ReadFile(pubPath)
	if err != nil {
		t.Fatalf("reading Phase P sandbox public key: %v", err)
	}
	return output, pubPath, string(pub)
}
```

### Pattern 2: LIFO `t.Cleanup` ordering (carried forward unchanged from Wave 8)
**What:** Register the read-only final sweep's `t.Cleanup` FIRST (immediately after
the run-scoping string is defined, before any key material exists), then register the
outstanding-ID drain's `t.Cleanup` SECOND (the moment the first ID is resolved). Go's
`t.Cleanup` runs LIFO, so the drain (registered second) runs first, deleting every
outstanding ID; the sweep (registered first) runs last, confirming a clean state.
**When to use:** Verbatim in the new file — this ordering is the single most
load-bearing safety mechanism in Wave 8's design and CONTEXT.md D-05 explicitly
carries it forward as non-negotiable.
**Example:**
```go
// Source: e2e/upload_real_account_e2e_test.go:408-429 (sweep) and :439-451 (drain
// registration) — read this session; the comment at line 408 states the mechanism
// explicitly: "Register the read-only sweep first so LIFO cleanup runs
// outstanding-ID deletion before the sweep, including when a later Fatal aborts
// the body."
```

### Pattern 3: Run-scoped inventory lookup for ID capture (carried forward unchanged)
**What:** `glab ssh-key add`, like `gh ssh-key add`, does not return a
machine-readable resource ID (confirmed for `gh` in Wave 8's SUMMARY; for `glab`,
neither official docs nor a live session in this research session could confirm the
add command's exact stdout shape — see Open Questions #2). The ID must be resolved by
reading the inventory (`glab ssh-key list -F json --show-id`, or via
`internal/uploader.Inventory`/`glabInventory`, which already calls `ssh-key list -F
json --per-page 30 --page N`) immediately after the add call, matching on the run's
exact scoping string in the title.
**When to use:** Every ID capture in this test, without exception — identical
discipline to Wave 8.

### Anti-Patterns to Avoid
- **Assuming `glab ssh-key add`'s stdout format:** the existing `FakeGLabDir` test
  shim (`e2e/harness_test.go:1060`) hardcodes `"Added SSH key."` as the fake
  output — this is a TEST FIXTURE literal, not a proven real-CLI string. This
  session could not verify it against a live `glab` session (auth is broken on
  this machine) or an authoritative source. Do not assert on this literal in the
  real-account test without first capturing and recording the actual observed
  output, the same discipline Wave 8 applied to `gh auth status`'s scope-line format
  ("capture it once before writing the parser... record the observed (redacted)
  shape in the SUMMARY").
- **Reusing `gh`'s scope-line parsing logic for `glab`:** `glab auth status` has no
  `Token scopes:`-equivalent line (confirmed empirically). A parser built by analogy
  to `parseGitHubScopeLine` (`e2e/upload_real_account_e2e_test.go:119-137`) would
  silently find nothing and either false-skip on every run or (worse) silently treat
  "no scope line found" as "scopes cannot be verified, proceed anyway" if not written
  defensively.
- **Using `--show-token` anywhere in the preflight or logging path:** confirmed this
  session that `glab auth status --show-token` prints the raw token in plaintext, and
  `internal/uploader.RedactCLIOutput`'s `glabTokenPattern` regex ONLY matches
  `glpat-`-prefixed personal access tokens (`internal/uploader/classify.go:33`) — an
  OAuth-style token (the format this session's own broken `glab` session uses) is
  **not** redacted by the existing helper. Never call `--show-token`; never log raw
  `glab auth status` output without going through `RedactCLIOutput` first (same as
  Wave 8's `gh` preflight), and be aware the existing redaction helper has a gap for
  non-PAT token shapes that this phase's own scope-check code must not reopen.

## Common Pitfalls

### Pitfall 1: `glab auth status` provides no scope information to check exactly — Wave 8's pattern does not port
**What goes wrong:** A planner assumes `glab auth status --hostname gitlab.com`
prints a scopes line like `gh auth status` does, writes a parser for it, and the
parser silently matches nothing on every real invocation — either always skipping
(safe but useless) or, if written carelessly (e.g. "absence of a scope line means
scopes are fine"), proceeding to a real mutation with NO scope verification at all —
precisely the R18 failure mode Wave 8's review caught for GitHub.
**Why it happens:** GitHub's fine-grained/classic PAT scope model surfaces directly
in `gh auth status`'s human-readable output; GitLab's PAT scope model is a separate
concept surfaced only via the REST API (`GET /personal_access_tokens/self`, `scopes`
field), not via `glab auth status`. This asymmetry is not obvious without running
both CLIs side by side, which this research session did.
**How to avoid:** Use `glab api personal_access_tokens/self` (or
`glab api personal_access_tokens/self --jq .scopes`) and parse the returned `scopes`
JSON array for an exact required member, mirroring the "exact member set, not
substring" discipline Wave 8's R18 fix established for `gh`. This only resolves
tokens created as PATs; if the session is OAuth-based (as this dev machine's
currently is — see Environment Availability), `personal_access_tokens/self` may not
apply the same way, and the test must skip with a named, honest reason rather than
guess. **This needs to be proven against a real, working `glab` session before the
plan is executed** — Task 1's checkpoint should require the developer to
re-authenticate `glab` first (this session found the local install's session
expired: `oauth2: "invalid_grant" ...`) and the plan should verify the
`personal_access_tokens/self` approach live before committing to it as the sole
mechanism.
**Warning signs:** A preflight that always reports success regardless of actual
token permissions; a preflight that always skips even when the developer believes
they are authenticated.

### Pitfall 2: `glab`'s config/credential storage under `HOME` will hide the real session from a sandboxed child, exactly like Wave 8's `GH_CONFIG_DIR` finding
**What goes wrong:** Sandboxing `HOME` for the compiled binary's child process (the
same sandbox pattern Wave 8 used) hides `glab`'s real, already-authenticated
credentials from the child, causing a false "unauthenticated" result — the opposite
of the test's purpose.
**Why it happens:** `glab` follows the XDG Base Directory spec by default:
global config lives at `~/.config/glab-cli` (confirmed via `glab config --help`'s own
"Configuration file locations follow the XDG Base Directory specification" line, and
via `glab auth status`'s own output on this machine showing `Token found in
configuration file (plaintext)`), and additionally can store credentials in the OS
keyring. Sandboxing `HOME` breaks both paths for a child process.
**How to avoid:** `glab` documents an explicit override: **`GLAB_CONFIG_DIR`** —
"Set to a directory path to override the global configuration location" [CITED:
docs.gitlab.com/cli]. Resolve the real config directory BEFORE swapping `HOME` (read
`GLAB_CONFIG_DIR` if already set, else compute the default `~/.config/glab-cli` from
the ambient, pre-swap `HOME`) and pass it through explicitly to every child process
this test spawns, exactly mirroring Wave 8's `resolveRealGHConfigDir` /
`GH_CONFIG_DIR` plumbing (`e2e/upload_real_account_e2e_test.go:65-101`). **If the
account's credential is stored in the OS keyring rather than the plaintext config
file** (glab's default when a keyring is available), `GLAB_CONFIG_DIR` alone may not
be sufficient — the keyring lookup itself may depend on OS session context that a
sandboxed child inherits differently. This must be verified empirically during Task
2's own execution (with a real, working `glab` session) rather than assumed; Wave 8's
own `GH_CONFIG_DIR` finding was itself a cycle-2 review catch, not something the
first draft anticipated.
**Warning signs:** The real-account test silently skips because it "cannot find a
glab session" even though the developer confirms `glab auth status` works in a plain
shell.

### Pitfall 3: the Makefile's `lint-tagged` guard hard-fails on a new `//go:build` tag it doesn't know about

### Pitfall 4: `RedactCLIOutput`'s glab token pattern only matches `glpat-`-prefixed tokens
**What goes wrong:** Any code path that logs raw `glab` output (auth status, error
output, etc.) and relies on `uploader.RedactCLIOutput` for safety assumes it redacts
all token shapes. It does not.
**Why it happens:** [VERIFIED: internal/uploader/classify.go:33] `glabTokenPattern =
regexp.MustCompile(`\bglpat-[A-Za-z0-9_-]{20,}\b`)` — this matches only GitLab's
classic Personal Access Token prefix. An OAuth-issued access token (this session's
own dev-machine token, confirmed to NOT start with `glpat-`) passes through
unredacted.
**How to avoid:** Never call `glab auth status --show-token` anywhere in the new
test or its logging. Rely only on the default `glab auth status` output, which
already self-redacts the token field (confirmed this session: default output shows
`Token found in configuration file (plaintext): **************************`, already
masked by `glab` itself, unlike `--show-token` which prints it in full). If any new
code needs to guard against a non-PAT token shape reaching a log line, that is a
defensive addition worth flagging to the planner, not an assumption to make silently.
**Warning signs:** A SUMMARY.md or test log containing a long alphanumeric string
near the word "token" that was not redacted.

### Pitfall 5: UP-04's literal wording claims a "per-registration-title API" proof that D-02 explicitly descopes

## Open Questions

1. **What EXACT GitLab scope(s) gate SSH-key write access, and how does the
   real-account test check for them, given `glab auth status` prints no scope
   information?**
   - What we know: GitLab's official scope-description docs [CITED:
     docs.gitlab.com/security/tokens/access_token_scopes/] list `api` ("Grants
     complete read and write access to the API for the token's scope...") as the
     only scope that is NOT limited to reads or to repository-scoped operations;
     `/user/keys`-family endpoints are user-account-scoped, not
     repository-scoped, so `write_repository`/`read_repository` do not obviously
     apply. A non-authoritative web source (a blog post, not GitLab's own docs)
     claims glab overall needs `api` and `write_repository` scopes — but that is
     for glab's full feature surface (repo operations need `write_repository`;
     general API calls need `api`), not specifically for `ssh-key add`. GitLab's
     own docs do not enumerate required scopes per endpoint the way GitHub's
     fine-grained-PAT docs do.
