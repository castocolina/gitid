# Phase 9.1: GitLab Real-Account Validation - Context

**Gathered:** 2026-08-30
**Status:** Ready for planning

<domain>
## Phase Boundary

Prove gitid's GitLab upload/delete path against a real, authenticated GitLab
account — the GitLab equivalent of Wave 8's (09-08-PLAN.md) real-account GitHub
validation. Closes UP-04. GitLab's upload/delete logic is currently proven only
against offline `glab` PATH shims; no automated test has ever reached a real
`glab` session.

</domain>

<decisions>
## Implementation Decisions

### Protocol shape (differs structurally from Wave 8)
- **D-01:** GitLab has ONE combined registration type (`RegistrationCombined`,
  `glab ssh-key add <pub> -t <title> --usage-type auth_and_signing`), not
  GitHub's two separate registrations (auth + signing). Wave 8's "4 keys, 2
  phases" shape existed entirely because GitHub's per-registration-title API
  needed its own proof separate from the product path, and a policy-literal
  title collided with the product's frozen D-07 title. Confirmed via
  `internal/uploader/uploader.go`'s `buildArgs`/registration-type mapping and
  `internal/uploader/inventory.go`'s `deleteArgs` (GitLab delete is
  `glab ssh-key delete <id>`, single namespace, no registration-type
  discrimination needed).
- **D-02:** This phase uses a **single phase, single disposable key pair** —
  drive the compiled `gitid register-key` binary only (mirroring Wave 8's
  "Phase P"). Do NOT add a second "Phase N" engine-level per-title proof: GitLab
  has no per-registration-type distinction to separately validate, so a second
  phase would add complexity with no additional coverage. — **Reversibility:**
  reversible — if a future finding shows GitLab's title API needs separate
  proof, add it as a follow-up task; nothing here blocks that.
- **D-03:** The SAME Wave-8-style naming deviation applies: GitLab keys still
  go through the product's frozen D-07 `KeyTitle` format
  (`gitid: <name> @ <machine>`), which cannot literally match ONESHOT.md's
  `gitid-e2e:<run-id>:<purpose>` policy format without a test-only product seam
  (D-06 forbids this). Scope the run through the disposable identity name
  (`gitid-e2e-<run-id>`) embedded in the product title, exactly as Wave 8's
  Phase P did — this is a recorded, reviewed deviation, not silently glossed
  over.

### Test file structure
- **D-04:** New dedicated file `e2e/upload_real_account_gitlab_e2e_test.go`
  under its own build tag (e.g. `realaccountgitlab`), NOT extending
  `e2e/upload_real_account_e2e_test.go`'s `realaccount` tag. Keeps GitHub and
  GitLab real-account runs independently triggerable
  (`make verify-upload-real-account` stays GitHub-only;  a new
  `make verify-upload-real-account-gitlab` target is added, following the same
  `smoke-network-test`-precedent isolation: its own tag, never a prerequisite
  of any routine gate). — **Reversibility:** reversible.

### Safety protocol (carried forward from Wave 8, not re-discussed — same rigor applies)
- **D-05:** Same safety posture as Wave 8's plan, adapted to GitLab: `autonomous:
  false`, opens with a blocking human-action checkpoint requiring explicit
  authorization naming the GitLab account handle; exact-scope preflight (name
  the exact `glab auth status` command and the exact required scope(s) — the
  planner/researcher must determine GitLab's precise scope name(s) that gate
  SSH-key write access, mirroring how Wave 8 pinned `admin:public_key`/
  `admin:ssh_signing_key` for GitHub); disposable key only, generated fresh,
  never touching the real `~/.ssh`; resource ID captured by a run-scoped
  inventory lookup after registration (never claimed as "returned by" the add
  call, since `glab ssh-key add` likely has the same non-machine-readable
  output shape as `gh ssh-key add` — confirm during research); idempotent
  cleanup via an outstanding-ID map with LIFO `t.Cleanup` ordering (sweep
  registered first, deletion closure second, so deletion runs before the
  final read-only sweep); delete by recorded ID only, re-confirming the run's
  scoping string immediately before each delete, never a broad query; a
  read-only final sweep confirming zero remaining entries carrying the run's
  scoping string. — **Reversibility:** one-way — this IS the safety protocol
  protecting a real external account; any planner deviation from this must be
  treated as a `checkpoint:decision` before implementation, not silently
  simplified.
- **D-06:** UP-04 closes ONLY if the real-account run EXECUTED (not skipped,
  not blocked) — same closure discipline as UP-03 in Wave 8. A skipped/blocked
  run leaves UP-04 open with the blocker named.

### Claude's Discretion
- The exact GitLab OAuth/PAT scope name(s) required for SSH-key write access
  — research this during planning (glab's own docs / `glab auth status`
  output on the development machine) rather than guessing; do not assume it
  mirrors GitHub's `admin:public_key`/`admin:ssh_signing_key` naming.
- Whether GitLab's `glab ssh-key add` output includes any parseable
  confirmation text worth asserting on (mirroring Wave 8's stdout assertions
  for `gh`).

</decisions>
