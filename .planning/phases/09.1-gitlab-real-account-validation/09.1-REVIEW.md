## Summary

This is a post-hoc review of a real, already-executed GitLab account mutation
(register, resolve-by-inventory, delete, sweep). The mutation itself ran once,
succeeded, and the orchestrator independently confirmed the account is back to
its pre-existing 3-key baseline — so this review is not trying to stop a
mutation that already happened safely. It is instead adversarially checking
whether the code's *claimed* safety mechanisms (exact-scope preflight,
redaction, LIFO cleanup, exact-ID deletion, build-tag isolation) are correctly
implemented as promised for any *future* re-run of `make
verify-upload-real-account-gitlab`, since this file is permanently opt-in and
will run again.

Verified independently and confirmed correct: build-tag isolation
(`//go:build realaccountgitlab` keeps the file out of `go build`, `make test`,
`make test-e2e -tags e2e`, and plain `go vet`); `make lint`'s `KNOWN_BUILD_TAGS`
and per-tag `go vet` wiring (0 issues, confirmed by direct run); no
identifier collision between this file and the GitHub sibling under either tag
alone or combined (`go vet -tags=realaccount,realaccountgitlab ./...` exits 0,
confirmed by direct run); the exit-0-only `register-key` contract claim against
`cmd/gitid/identity_upload.go`; the `tuikit.UploadResultOKFmt` /
`UploadRegistrationLabelCombined` success-row composition; and the exact-member
(never substring) scope check. The `.planning/REQUIREMENTS.md`,
`.planning/ROADMAP.md`, and `.planning/ONESHOT.md` closures are factually
consistent with the recorded evidence (account handle, run ID, resource ID,
before/after key counts) and correctly avoid co-occurring a closed checkbox
with a blocked/skipped marker.

One real gap was found in the exact area this review was asked to focus
hardest on — redaction of subprocess output on failure paths — and three
maintainability/coverage gaps around the collision-safety and safety-gate
machinery. None of these affected the one run that already executed (all fire
only on a *failure* path that did not occur), but all are real defects in
code that is designed to be re-run against a live external account.

## Critical Issues

### CR-01: Three failure paths bypass RedactCLIOutput entirely, contradicting the phase's own stated invariant

**File:** `e2e/upload_real_account_gitlab_e2e_test.go:547`, `:666`, `:676`

**Issue:** 09.1-01-PLAN.md's must_haves state as a binding truth: "No token ever
reaches a log line, a test message, or the SUMMARY: every logged glab output
passes through `uploader.RedactCLIOutput` first." The implementation upholds
this on the *success*-logging path (`redactGLabOutputLines` at line 664) and on
the preflight's skip messages (lines 315, 332, 336, 339, 341) — but not on
three `t.Fatalf` failure paths that were newly introduced in this phase's
wave 2:

- `runRealGLabBinary` (line 538-550), the driver used for *every* compiled
  `gitid` invocation in this file (`create` and `register-key`), fatals with
  the **raw, unredacted** `CombinedOutput()`:
  ```go
  out, err := cmd.CombinedOutput()
  if err != nil {
      t.Fatalf("compiled gitid %s failed: %v\noutput:\n%s", strings.Join(args, " "), err, out)
  }
  ```
- `TestRealAccountGitLabUploadRoundTrip` fatals twice more with the raw,
  unredacted `productOutput` if the compiled binary's output doesn't contain
  the expected markers:
  ```go
  if !strings.Contains(productOutput, "Running:") {
      t.Fatalf("compiled register-key output did not announce its command: %s", productOutput)
  }
  ...
  if !strings.Contains(productOutput, wantSuccessRow) {
      t.Fatalf("compiled register-key output did not contain the GitLab combined success row %q: %s", wantSuccessRow, productOutput)
  }
  ```

All three are reached only when a real invocation against the live GitLab
account fails or behaves unexpectedly — exactly the scenario a re-run of this
opt-in target is most likely to hit (e.g. a future `glab` CLI version change,
a scope regression, a network blip mid-registration). On that path, the raw
`CombinedOutput()` of the compiled `gitid` binary — which itself wraps `glab`'s
own stderr/stdout — is written verbatim into `go test -v` output with **no**
home-path redaction and **no** token-pattern redaction, even though the
project already has a `RedactCLIOutput` call one line above it for the
success case. This is confirmed to be new code in this diff (not inherited,
unreviewed legacy): `runRealGLabBinary` and the two `productOutput` fatals
are all first declared in wave 2 (`git diff ae6ab71..HEAD` shows them as pure
additions).

Two concrete leak vectors this creates:
1. The developer's real home directory / username (not itself a "secret" but
   the exact class of information `RedactCLIOutput`'s `homeDir` parameter
   exists to strip, and the phase's other 6+ call sites take care to strip it).
2. Any token-shaped text `glab` embeds in an error response body. Note this
   risk is compounded by the fact that `RedactCLIOutput`'s own token regex
   (`internal/uploader/classify.go`) only matches `glpat-`-prefixed PATs — an
   OAuth-backed session's bearer token (the exact session type this
   developer's account carried for part of this phase, per
   `09.1-01-SUMMARY.md`) would not be caught by the pattern anyway. That
   existing narrowness is a separate, previously-accepted gap, but it makes
   these three sites' *total* bypass of redaction strictly worse than "not
   catching every token shape" — they don't even attempt it.

**Fix:** Route all three sites through the same per-line redaction helper
already built for this purpose:

```go
// runRealGLabBinary
out, err := cmd.CombinedOutput()
if err != nil {
    t.Fatalf("compiled gitid %s failed: %v\noutput:\n%s", strings.Join(args, " "), err, redactGLabOutputLines(string(out), realHome, 2000))
}
```

```go
// TestRealAccountGitLabUploadRoundTrip, both call sites
if !strings.Contains(productOutput, "Running:") {
    t.Fatalf("compiled register-key output did not announce its command: %s", redactGLabOutputLines(productOutput, realHome, 2000))
}
...
if !strings.Contains(productOutput, wantSuccessRow) {
    t.Fatalf("compiled register-key output did not contain the GitLab combined success row %q: %s", wantSuccessRow, redactGLabOutputLines(productOutput, realHome, 2000))
}
```

`redactGLabOutputLines` already exists in this file for exactly this
multi-line-output problem (added in this same wave to fix the logging defect
documented in `09.1-02-SUMMARY.md`) — it is available at every one of these
call sites and is not currently used by any of them.

## Warnings

### WR-01: `make lint` never vets the two real-account files together — the collision-safety guarantee has no automated gate

**File:** `Makefile:230-234`

**Issue:** The entire justification for renaming every top-level identifier in
this file with a `GLab` marker (PATTERNS.md's "copy verbatim" instruction
overridden — see `09.1-02-SUMMARY.md` Deviation #2) is that `go vet
-tags=realaccount,realaccountgitlab ./...` compiles both real-account files
together in the same package and a name collision would be a duplicate-
declaration compile error. That combined-tag invocation was run and
confirmed passing multiple times *ad hoc* during this phase's execution (both
SUMMARYs record it), and I independently reconfirmed it in this review — but
`lint-tagged`'s `KNOWN_BUILD_TAGS`/go-vet loop (Makefile:230-234) only ever
vets each tag **in isolation**:

```makefile
go vet -tags realaccount ./...
go vet -tags realaccountgitlab ./...
```

There is no `go vet -tags=realaccount,realaccountgitlab ./...` line anywhere
in the Makefile. This means the one property the entire `GLab`-marked naming
convention exists to protect — that the two files can compile together — is
never mechanically re-verified by any gate a future change would have to
pass. A future edit to either file (e.g. someone copy-pastes a helper from one
into the other, or independently reintroduces a same-named type) would sail
through `make lint` with 0 issues and only be caught the next time someone
manually remembers to run the combined-tag invocation by hand.

**Fix:** Add the combined invocation as its own `lint-tagged` line (it is
cheap — `go vet` only, no test execution):

```makefile
go vet -tags realaccount ./...
go vet -tags realaccountgitlab ./...
go vet -tags=realaccount,realaccountgitlab ./...
```

### WR-02: `countUnscopedGLab` is computed twice in the same conditional

**File:** `e2e/upload_real_account_gitlab_e2e_test.go:629-630`

**Issue:** Minor but avoidable duplicate work / drift risk:

```go
if baselineRecorded && countUnscopedGLab(inventory, productScope) != baselineUnscoped {
    t.Errorf("pre-existing unscoped inventory count changed: before=%d after=%d", baselineUnscoped, countUnscopedGLab(inventory, productScope))
}
```

`countUnscopedGLab(inventory, productScope)` is called twice against the same
`inventory`/`productScope` pair. This is not a correctness bug (the function is
pure and deterministic), but it is unnecessary re-computation and a small
maintenance hazard: if the two call sites are ever edited independently (e.g.
one gains a filter the other doesn't), the error message would silently
misreport.

**Fix:**
```go
if unscopedNow := countUnscopedGLab(inventory, productScope); baselineRecorded && unscopedNow != baselineUnscoped {
    t.Errorf("pre-existing unscoped inventory count changed: before=%d after=%d", baselineUnscoped, unscopedNow)
}
```

### WR-03: `isGLabAlreadyAbsent`'s wording predicate can false-positive on an unrelated "404" substring

**File:** `e2e/upload_real_account_gitlab_e2e_test.go:786-792`

**Issue:** This is a pre-existing, explicitly documented "known unverified
gap" (both plans flag it and neither closes it, since the one live run never
exercised a delete-path error), so it is not a new defect — but it is worth
re-flagging precisely because it is load-bearing for the cleanup drain's
success/failure classification, and its current form is broader than it needs
to be:

```go
func isGLabAlreadyAbsent(err error) bool {
    if err == nil {
        return false
    }
    text := strings.ToLower(err.Error())
    return strings.Contains(text, "404") || strings.Contains(text, "not found")
}
```

`strings.Contains(text, "404")` matches the literal digits `404` anywhere in
the error text — including, hypothetically, a resource ID that happens to
contain those digits embedded in an unrelated error message (e.g. a rate-limit
or transient-network error whose body echoes the failing request URL
containing the numeric key ID). Because the file's own error-wrapping
(`realAccountGLabUploaderDeps.RunCmd`) already embeds the raw redacted command
output into the error string via `fmt.Errorf("%w: %s", err, ...)`, an ID like
`21497184` would never literally contain `404`, but the pattern is fragile in
general and its fail-open direction (treating an unrecognized-but-substring-
matching error as a successful "already absent" delete) is the more dangerous
of the two possible failure modes for a cleanup drain — a real deletion
failure gets silently classified as success. The known-gap comment above it
correctly documents the fail-*closed* direction for an *unrecognized* wording,
but does not address this fail-*open* direction for an over-broad match on a
recognized substring.

**Fix (when real wording evidence becomes available, per the existing
follow-up plan):** anchor the "404" check to a word boundary or to GitLab's
actual HTTP-status-line shape (e.g. `"(HTTP 404)"`, matching the exact error
envelope shape already observed for the `400` case in
`09.1-01-SUMMARY.md`) rather than a bare substring, so an incidental digit
sequence in unrelated error text cannot match.

## Info

### IN-01: `parseGLabTokenScopes`'s quote-trimming is defensive with no corresponding failing case

**File:** `e2e/upload_real_account_gitlab_e2e_test.go:267-273`

Each scope string is trimmed of surrounding `'`/`"` characters after JSON
decoding:
```go
scope := strings.Trim(strings.TrimSpace(raw), "'\"")
```
`encoding/json` already strips quote delimiters from string values during
decode, so a decoded scope string would only ever contain a literal `'`/`"`
character if GitLab's API embedded one inside the value itself (extremely
unlikely for a scope name). This is harmless defensive coding, but the
14-case table test (`TestRealAccountGitLabScopeCheckRequiresExactMember`) has
no case exercising this branch, so it is currently unverified dead-in-practice
code. Consider either adding a table case for it or removing it if no
plausible GitLab response shape requires it.

### IN-02: Comment on line 24-28 references "two independently titled endpoints" without linking to the underlying source

**File:** `e2e/upload_real_account_gitlab_e2e_test.go:23-32`

The file-level doc comment's D-01/D-02 explanation is accurate per
`09.1-CONTEXT.md`, but for a reader arriving at this file without the

asserting the GitLab-vs-GitHub shape difference as fact. This is a
documentation-durability nit, not a defect.
