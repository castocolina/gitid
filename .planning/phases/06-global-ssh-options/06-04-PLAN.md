## The precedence model (BINDING — read before writing a single test)

`ssh_config(5)`: **"For each parameter, the first obtained value will be used."** OpenSSH does not let a later assignment override an earlier one. Every shadowing claim in this plan is derived from that one rule, and the previous revision of this plan got it backwards.

The RESOLVED ORDER for a `ssh -G <host>` run against `~/.ssh/config` is the file read top-to-bottom, with each `Include` directive splicing its matched files IN PLACE at the point the directive appears, then — last of all — `/etc/ssh/ssh_config`.

Three facts about where gitid's own bytes sit in that order, all verified in source:

1. The gitid-owned `Include` line is FLOORED AT THE TOP of `~/.ssh/config` (`internal/sshconfig/include.go:19-28`, `EnsureIncludeLine` via `filewriter.PrependBlockIfNotFound`), precisely so its content is "first-match-wins ahead of any later hand-written Host block".
2. The gitid managed globals block is written LAST IN ITS FILE, after every identity Host block (`internal/sshconfig/writer.go:10-15`, `internal/sshconfig/renderer.go:112-114`, `internal/sshconfig/migrate.go:473-486` `reorderGlobalLast`), so per-alias values stay authoritative over the wildcard stanza.
3. `/etc/ssh/ssh_config` is read LAST and therefore can NEVER shadow a user-config value — which is also why plan 06-01 refuses to name it as a provenance without an explicit corroborating parse.

Combining them, the four cases this plan must model:

| Layout | Where the competing directive sits | Shadows gitid's block? | Why |
|---|---|---|---|
| Include'd | main config, **BELOW** the floored `Include` line | **NO** | The Include spliced gitid's block in at the top; gitid's value is obtained first. This is the whole point of the floor model. |
| Include'd | main config, **ABOVE** the `Include` line (a hand-edit prepended over the floor) | **YES** | Obtained before the splice point. |
| Include'd | another `config.d/*.config` file that the glob returns **before** gitid's own file | **YES** | `filepath.Glob` returns sorted matches; an earlier-sorting file is spliced first. |
| either | the **same file**, in a matching stanza **above** gitid's managed block | **YES** | gitid's globals block is last in its file, so any earlier matching assignment wins. Under the IN-FILE layout this is the dominant real-world case. |

A "matching" directive means one whose enclosing `Host` pattern matches `globalssh.ProbeHost` under OpenSSH's pattern rules — a directive inside `Host github.com` does not compete with the wildcard stanza for the probe host. That rule is implemented ONCE, in `internal/sshconfig`, and this plan EXPORTS it so `internal/globalssh` can call it (see `<matcher_extraction>`). Do not write a second matcher, and do not attempt to call `aliasCollides` — it is unexported and it is a file walker, not a pattern matcher.

## The host-pattern matcher is EXPORTED here, not reused as-is (BINDING — cycle-3 HIGH)

`06-REVIEWS.md`'s cycle-3 HIGH, orchestrator-verified against source: the previous revision told `internal/globalssh/shadow.go` to "reuse the negation-aware matching `aliasCollides` already implements". That instruction cannot be executed.

Verified in `internal/sshconfig/validation.go`:

- `aliasCollides` (line 164) is **unexported** — invisible outside `internal/sshconfig`.
- Its exported wrapper `AliasCollision(configPath, candidate string) (bool, error)` (line 160) takes a **config file path**: it reads the file, parses it, walks its `Include` graph and returns a boolean about the whole tree. It is not a matcher over directive data the scanner has already extracted.
- `HostMatch(pattern, candidate string) bool` (line 103) IS exported, but it matches ONE pattern token. The negation-aware, stanza-level rule — a stanza matches when at least one non-negated pattern matches and no negated pattern in the SAME stanza matches — lives inline in `aliasCollides`' loop (lines 198-216) and is exported nowhere.

**The fix is extraction, chosen over duplication.** The stanza rule is ~12 lines and has no I/O, so factoring it out is small, safe, and matches this project's "one function per verb, no reimplemented stages" precedent. Duplicating it inside `internal/globalssh` is the outcome this finding exists to prevent: two negation implementations that drift, in a matcher whose failure mode is naming the wrong file in a security warning.

In `internal/sshconfig/validation.go`, add:

```
// HostPatternsMatch reports whether a Host stanza whose pattern tokens are
// patterns matches candidate under OpenSSH stanza semantics.
func HostPatternsMatch(patterns []string, candidate string) bool

// HostLineMatches applies the same rule to the raw whitespace-separated
// pattern text of a Host line — the shape DirectiveHit.HostPattern carries.
func HostLineMatches(patternLine, candidate string) bool
```

`HostLineMatches` is a `strings.Fields` wrapper over `HostPatternsMatch`; it exists so the scanner's string-shaped `HostPattern` field is tokenised in ONE place rather than at each call site. `HostPatternsMatch` contains the rule and calls the existing `HostMatch` per token.

### The call-site projection, spelled out (BINDING — cycle-4 LOW)

`06-REVIEWS.md`'s cycle-4 LOW, raised independently by both reviewers: `aliasCollides` holds `host.Patterns`, which is `[]*ssh_config.Pattern` — the kevinburke parser's own type — while `HostPatternsMatch` takes `[]string`. Go will not convert between them, so "replace the inline loop with a call to `HostPatternsMatch`" is not a substitution of the loop body. Project first, then call. Four mechanical rules, all load-bearing:

1. **Build the token slice explicitly.** Range `host.Patterns` and collect `pat.String()` into a `[]string` sized with `make([]string, 0, len(host.Patterns))`. `Pattern.String()` has a value receiver, so calling it on the pointer element auto-dereferences; no extra handling is needed.
2. **Keep every token EXACTLY as `pat.String()` returns it, negation prefix included.** `Pattern.String()` returns the raw pattern text, which is precisely why the current inline loop tests the returned string for a negation prefix before trimming it. **The trim belongs inside `HostPatternsMatch`, never at the call site.** A caller that pre-trims hands the shared matcher a token that no longer looks negated, silently converting every exclusion into an inclusion — a stanza that should NOT match starts matching. This is also what makes `HostLineMatches` correct: `strings.Fields` over a raw `Host` line yields tokens in the same negation-carrying shape, so both argument shapes hand `HostPatternsMatch` identical tokens. One rule, two argument shapes, one place that decides what a negated token means.
3. **The two structural guards above the matching loop STAY at the call site.** `aliasCollides` currently skips a stanza with zero patterns, and skips the single-`*` stanza the parser synthesises for an empty file. Those are facts about `cfg.Hosts`' shape, not about pattern semantics. Moving either into `HostPatternsMatch` would break BOTH callers: `AliasCollision`'s behavior would change (which this extraction must not do), and `internal/globalssh` would lose its ability to match a real wildcard stanza — `HostPatternsMatch([]string{"*"}, ProbeHost)` MUST return true, because `<resolution_order>` row 4's dominant shadowing case is exactly a `Host *` stanza competing with gitid's managed block. A matcher that skips wildcards cannot name the most common shadow there is.
4. **No `ssh_config` type crosses the new API.** `internal/globalssh` has no parser dependency and must not acquire one to name a shadowing line; the projection is what keeps the boundary at `[]string`.

`aliasCollides`' inline loop is REPLACED by a call to `HostPatternsMatch` — the extraction is only correct if the original caller ends up on the shared implementation. Its behavior must not change: `AliasCollision`'s existing tests (`TestAliasCollisionExact`, `...Wildcard`, `...Negated`, `...IncludeAware`, `...MissingFile`, `...MalformedConfig`, `...CyclicInclude`) are the regression gate and must pass untouched.

Out of scope, stated so it is not silently inherited: `aliasCollides`' own `seen` map is a single global visited set and therefore has the diamond-graph false positive described in `<action>` for `BuildGraph`. That is pre-existing behavior of a different verb, this plan does not change it, and `BuildGraph` must NOT copy that pattern.

**Cycle detection uses TWO sets, and conflating them is `06-REVIEWS.md`'s cycle-3 MEDIUM finding.** Keep:
- `active` — the RECURSION STACK of absolute paths on the current descent. Push before recursing into a file, **pop on return.** A path already in `active` means the file is including itself transitively: that is a real cycle, and the error names it.
- `expanded` — a MEMO of every absolute path already discovered anywhere in the walk. **Never popped.** A path already in `expanded` but NOT in `active` is a DIAMOND: the same file legitimately reached through two branches. Skip the re-descent (its subtree is already in the graph) and continue — this is not an error and must not produce `Inconclusive`.

A single global visited set cannot tell those two apart and would report a perfectly valid diamond layout as a cycle, handing the user an unearned INCONCLUSIVE on a config that `ssh` reads without complaint. That is exactly the shape `aliasCollides`' own `seen` map has (`<matcher_extraction>` records it as pre-existing and out of scope) — do not copy it here.

`SimulationGraph.Files` therefore carries each unique path exactly ONCE, in first-discovery order, so the mirror materialises one copy of a diamond's shared file. That is safe for the naming step because `ssh` splices a doubly-included file at BOTH points and `shadowSourceFor` returns the FIRST hit in resolution order, so the earlier occurrence is the one that decides — a later re-visit could not change the answer. State that reasoning in `BuildGraph`'s doc comment, next to the two-set rule, so nobody "simplifies" the sets back into one.

Recursion is required, not optional: `sshconfig.ManagedBlockNames` and `DetectInclude` are both deliberately single-hop, and `06-REVIEWS.md`'s cycle-2 finding is that mirroring only the entry point's DIRECT includes makes the mirror an unfaithful copy — a nested include would either silently vanish from the simulation (a false clean result) or, worse, resolve to the user's REAL file from inside the mirror. Say both consequences in `BuildGraph`'s doc comment. Discovery is bounded and cycle-checked because a hostile or merely careless config can otherwise loop forever; the honest answer for a graph gitid cannot faithfully reproduce is INCONCLUSIVE, and that is why the inconclusive path exists.

`func Simulate(deps Deps, graph SimulationGraph, keys []string) ShadowResult` is the pre-write half:
1. Create a private mirror root under the OS temp root with mode 0700 — OpenSSH refuses a group- or world-writable config, so the mode is a functional requirement, not hygiene. Clean the whole tree up with a deferred removal that runs on every path including the error paths.
2. Materialise EVERY `graph.Files` entry inside the mirror at mode 0600, with the entry whose path equals `ManagedTargetPath` written as `CandidateContent` instead of its own bytes. Preserve the relative structure so Include directives can be rewritten to mirrored paths and nothing resolves outside the mirror. When `ManagedTargetPath` equals `EntryPointPath`, the candidate IS the entry point and there is exactly one file.
3. Rewrite each Include directive in EVERY mirrored file — not just the entry point — to name the mirrored path, so a nested include cannot reach back out. An Include gitid could not resolve is rewritten to a path inside the mirror that does not exist, so the simulation degrades to "that file contributes nothing" rather than silently reading the user's real file — an unresolved include must never leak the real machine into the simulation.
4. Run the resolution probe against the mirrored ENTRY POINT with the isolated-config flag plus the probe host, reusing `deps.RunSSHG` so the timeout, the group-kill and the argument-slice safety all carry over unchanged.
5. For each requested key, compare the resolved value against the policy's recommended value. Unequal means the fix will be shadowed.
6. Only for keys that came back unequal, call `shadowSourceFor` to NAME the offending directive.
7. Any probe error, cycle or depth-cap hit sets `Inconclusive` with the reason and returns zero findings.

State the correction in the doc comment, with its reason: running the probe against the candidate file alone cannot observe a directive in the main config, and under the Include layout — which is the DEFAULT on a fresh machine — the main config is exactly where a user's own `Host *` block lives. A simulation that cannot see it would return a clean result for the case the feature exists to catch.

`func Verify(deps Deps, keys []string) ShadowResult` is the post-write half: the same comparison, run against the live machine with NO isolated-config flag, so it reflects the real resolution order including files gitid does not manage. **`func shadowSourceFor(graph SimulationGraph, key string) (text, file string, line int)` — the static scan. Its selection rule is FIRST-OBTAINED-VALUE and getting it backwards is exactly the cycle-2 HIGH finding; read `<resolution_order>` before writing it.**

It runs in three steps:

1. **Linearise the graph** into an ordered `[]sshconfig.DirectiveSource` that mirrors how `ssh` actually reads it. For each file, walk its `Include` directives in file order and emit: the slice of that file ABOVE the directive (with the file's running `LineOffset`), then — recursively — the linearisation of each file that directive globs to, in glob order, then continue with the remainder of the file below the directive (with the offset advanced past it). A file with no `Include` contributes one source with its accumulated offset. Under the Include'd layout this puts the included `config.d/*.config` files ahead of everything in the main config below the floored `Include` line, which is precisely the behavior `internal/sshconfig/include.go:19-21` was designed to produce. A file reached twice through a DIAMOND is linearised twice on purpose — `ssh` splices it at both points, so both occurrences are part of the resolved order and the first one wins. Guard this walk with the same popped-on-return recursion stack `BuildGraph` uses, never with a global visited set: deduping here would delete a real occurrence from the order. `BuildGraph` has already rejected true cycles as `Inconclusive`, so the guard is a backstop rather than the primary defence.

3. **Return the FIRST surviving hit**, with its file and 1-based line. First, not last: under first-obtained-value the earliest matching assignment is the one `ssh -G` actually reported, so any later hit is a bystander and naming it would send the user to edit a line that changes nothing. ## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| candidate configuration graph → mirror directory → `ssh` subprocess | gitid writes a whole config tree that a subprocess then reads and acts on. |
| the user's real config files → the mirror | An unresolved Include in the mirrored entry point could reach back into the real machine. |
| async commit goroutine → user's `~/.ssh` | The write runs off the update loop, concurrently with other transactions. |
