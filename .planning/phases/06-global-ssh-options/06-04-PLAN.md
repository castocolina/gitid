  <behavior>
    - A migration over files that nobody else touches behaves exactly as it does today: same steps, same result, same backups.
    - When either file's on-disk content changes between the transaction's own snapshot and the moment it is about to write, the transaction aborts with an error naming the changed file and writes nothing beyond the backups it had already taken.
    - An abort caused by detected concurrent modification restores any file already written in this transaction, so the abort leaves the machine in its pre-transaction state.
    - Detection is based on the file's content, not only on a timestamp, so a modification within the same clock tick is still caught.
    - A file that did not exist at snapshot time and exists at write time is treated as a concurrent modification.
    - The check does not fire for the transaction's own writes: the second step's write does not see the first step's write as external.
  </behavior>
  <action>
`Migrate`'s doc comment records a precondition against the interactive wiring this phase performs: it snapshots each file once at preflight and reuses that snapshot for every write, so a concurrent external edit would be silently overwritten and may not be recoverable from the backups. Close that gap before the screen can reach it.

Add the detection to the transaction rather than to a caller — a caller-side check would race by construction. At preflight, alongside the existing content snapshot, record a content digest for each of the two files (and an explicit absent marker for a file that does not exist). Immediately before each write step, re-read the file that step is about to touch through `deps.ReadFile` and compare its digest against the recorded one; a mismatch aborts through the existing `rollback` path with an error naming the file and stating that it changed while gitid was working on it.

Reconcile with the transaction's own writes: after `Migrate` writes a file, update that file's recorded digest to the bytes it just wrote, so step 4's check compares against step 3's result rather than against preflight. Getting this wrong makes every two-step migration abort, so make it an explicit assertion in the tests rather than something only the happy path exercises.

Use a content digest, not a modification time. A same-tick edit is exactly the case an interactive flow makes likely — the user alt-tabs to an editor and saves while the ceremony is open — and timestamp granularity would miss it.

Do not change the step ORDER or the add-to-destination-before-remove-from-source guarantee; that ordering is what makes every crash point safe, and it is not what this task is fixing.

Update the `Migrate` doc comment: replace the precondition paragraph with a statement of what is now detected and what remains out of scope (a modification landing between the final validation and the caller observing success is still possible and is not a data-loss risk, because nothing further is written).

Test using the existing `afterStep` seam plus a `ReadFile` that returns different bytes on a chosen call: mutate the source between preflight and the source write, mutate the destination between preflight and the destination write, create a file that was absent at preflight, and a happy-path case asserting the transaction's own writes never trigger the check. Assert each abort's error names the affected file and that both files match their pre-transaction content afterwards.
  </action>
