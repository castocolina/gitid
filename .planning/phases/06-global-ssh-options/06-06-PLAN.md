## Command tree (frozen)

```
gitid ssh options list    [--json]
gitid ssh options apply   <key>... [--dry-run] [--yes] [--fail-on-advisory] [--json]
gitid ssh storage show    [--json]
gitid ssh storage migrate --to <include|in-file> [--dry-run] [--yes] [--json]
```

No flat root-level aliases for this noun: `05-CONTEXT.md` D-01 reserves flat aliases for the identity verbs, and adding `gitid list` collisions here would defeat the reservation the `ssh` placeholder exists to protect.

## Adaptive-depth contract (frozen)

`05-CONTEXT.md` D-02's three branches, resolved through the EXISTING `depthResolver` in `cmd/gitid/identity.go:135-171` — not a second implementation, and not a per-verb rule. `06-REVIEWS.md`'s cycle-2 finding is that the previous revision described a TTY fallback in prose without freezing which invocations reach it or what the opened surface shows; both are frozen here.

| Verb | "Complete" means | Incomplete + stdinTTY && stdoutTTY | Incomplete + any other descriptor combination |
|---|---|---|---|
| `options apply` | at least one `<key>` positional | open the TUI on the Global SSH view, **Options sub-tab**, selection EMPTY | exit 1 naming the missing positional argument |
| `storage migrate` | `--to` supplied | open the TUI on the Global SSH view, **Storage sub-tab**, radio on the CURRENT layout, no target pre-selected | exit 1 naming `--to` |
| `options list`, `storage show` | always complete (reads are always headless, D-02) | n/a | n/a |

**Nothing is ever pre-selected in the opened TUI, and that is deliberate.** D-02 says the wizard opens "pre-filled from the given flags" — but the only INCOMPLETE form of each write verb here is the one that supplies nothing to pre-fill from (`options apply` with zero keys; `storage migrate` with no `--to`). Any invocation that DOES name a key or a layout is complete and runs headless. So there is no conflict with D-15's empty-opt-in-selection rule, and the resolution is stated rather than left to the implementer: the TUI opens on the right surface with its normal empty starting state. If a future flag makes a partially-specified invocation possible, that is a new decision and must be raised, not improvised.

Both branches route through `depthResolver` and `confirmationPolicyFrom` (`cmd/gitid/identity.go:135-213`) unchanged, including D-02's dry-run exemption (a `--dry-run` cannot write, so it is accepted without a terminal and without `--yes`, and is routed BEFORE the confirmation gate).

## JSON envelope (frozen, versioned)

`gitid ssh options list --json`:

```
{
  "schema": "gitid.ssh.options/v1",
  "options": [
    {
      "key": "<policy key, in Policy declaration order>",
      "current_value": "<string, empty when unset>",
      "recommended_value": "<string>",
      "risk": "low|medium|high",
      "scope": "global|per-alias",
      "state": "needs-action|already-set|differs|not-applicable",
      "source": "gitid-parsed|outside-gitid|system-file|baseline|inconclusive",
      "source_file": "<display path, empty when unknown>",
      "source_line": <integer, 0 when unknown>,
      "not_applicable_reason": "none|platform|version-too-old|version-unverified|nothing-to-verify",
      "version_note": "<string, empty when none>",
      "probe_error": "<string, empty when none>"
    }
  ]
}
```

`gitid ssh storage show --json`:

```
{
  "schema": "gitid.ssh.storage/v1",
  "layout": "include|in-file",
  "target_path": "<display path>",
  "main_config_path": "<display path>",
  "include_line_present": true
}
```

`gitid ssh options apply --json` (the WRITE-RESULT envelope):

```
{
  "schema": "gitid.ssh.apply/v1",
  "dry_run": false,
  "applied": ["<policy key>"],
  "declined": ["<policy key named on the command line but refused>"],
  "target_path": "<display path>",
  "backups": ["<display path>"],
  "restored": ["<display path, present only when a failed write was rolled back>"],
  "advisories": ["<post-write verification advisory, e.g. the fix landed but is shadowed>"],
  "simulation_inconclusive": false,
  "simulation_note": "<string, empty when none>",
  "error": "<string, empty on success>",
  "exit_code": 0
}
```

`gitid ssh storage migrate --json`:

```
{
  "schema": "gitid.ssh.migrate/v1",
  "dry_run": false,
  "from_layout": "include|in-file",
  "to_layout": "include|in-file",
  "moved_identities": ["<alias>"],
  "moved_globals": true,
  "backups": ["<display path>"],
  "restored": ["<display path>"],
  "error": "<string, empty on success>",
  "exit_code": 0
}
```

**Why the write verbs get `--json` at all** — `06-REVIEWS.md`'s cycle-2 finding is that this plan's threat model (T-06-43) promised the advisory would be carried "in the output AND the JSON" while the frozen tree granted `--json` only to the read verbs, leaving a script with nothing but the exit code and scraped terminal text. Two resolutions were available: drop the promise, or freeze the envelope. The envelope is frozen, because dropping it would leave `--fail-on-advisory` as the ONLY machine-readable signal of an advisory — a boolean where the useful information is WHICH option is shadowed and by what — and because `05-CONTEXT.md` D-03 records terminal-scraping as a documented CI pain point this surface exists to remove. `advisories` and `exit_code` in the apply envelope are what make the zero-on-advisory default safe to consume: a script can act on the detail without gitid having to fail by default for being honest.

`exit_code` is emitted INSIDE the envelope as well as returned as the process status, so a consumer that captured stdout can reason about the outcome without also having had to capture `$?` — the two are produced by the same mapping helper and a test asserts they agree for every row of the exit-status table.

Rules (all four envelopes): the `options` array is ordered by `globalssh.Policy` declaration order, never sorted or filtered; every enum string above is part of the contract and is lower-case kebab; every path is a display path, never a raw absolute sandbox path; a field is emitted even when empty, so a consumer can rely on its presence; and a `schema` value changes only on a breaking change, at which point the old value must be retired in the same commit as the document.

## Exit-status contract (frozen)

| Code | Meaning |
|---|---|
| 0 | The command succeeded. For a write, this includes a successful backed-up write whose post-write verification reported an advisory (for example, the fix landed but is shadowed). |
| 1 | Usage, validation or refusal: an unknown or non-writable option key, a version gate that could not be verified, a missing confirmation off a terminal, an unknown layout. Nothing was written. |
| 2 | The write or the migration failed and was rolled back. |
| 3 | Reserved for `--fail-on-advisory` only: the write succeeded AND an advisory was reported. Never returned without that flag. |

The zero-on-advisory default is the direct consequence of D-04 and D-14: shadowing is ADVISORY and never blocking, so a script that pipes gitid into a provisioning run must not fail because gitid was honest about a pre-existing directive. `--fail-on-advisory` gives a stricter script the opt-in it needs without making honesty a failure by default. Record this reasoning in the parity matrix's notes column so a future reader does not "fix" it toward a nonzero default.
