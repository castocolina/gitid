Three defects, one transaction. Fix them together because they interact.

**A backup-only seam (`internal/filewriter`).** Export `func Backup(path string) (backupPath string, err error)` wrapping the existing unexported backup primitive: it copies the file to its timestamped sibling and does NOT touch the original. A missing file yields an empty path and a nil error. Add its own tests asserting the original's bytes and mode are unchanged and that the backup's content matches.

**Use it in the transaction (`internal/sshconfig/migrate.go`).** Add `BackupFile func(path string) (string, error)` to `MigrateDeps`, bound to `filewriter.Backup` in `RealMigrateDeps`. Change step 2 to call it instead of calling `WriteFile` with the snapshotted bytes. The previous mechanism obtained a backup as a side effect of replacing the target with its own content, which meant the "backup" step was itself a content-changing write — so an external edit landing between preflight and step 2 was destroyed before any check could see it. That is the review's HIGH finding, and this is its root cause. Say so in the step's comment.

**A pure planning function AND a plan-consuming writer — the pair, not just the first half.**

Extract:

```
type MigrationPlan struct {
    Direction       MigrateDirection
    SourcePath      string
    DestPath        string
    SourceBefore    []byte
    DestBefore      []byte
    SourceAfter     []byte
    DestAfter       []byte
    MovedIdentities []string
    MovedGlobals    bool
    Diff            string
    // Digests is the content digest of the EXACT bytes this plan was computed
    // against, keyed by path, with an explicit absent marker for a file that
    // did not exist. It is what makes the plan verifiable at commit time.
    Digests map[string]string
}
func PlanMigration(direction MigrateDirection, deps MigrateDeps) (MigrationPlan, error)
func MigrateWithPlan(plan MigrationPlan, deps MigrateDeps) (MigrateResult, error)
```

`PlanMigration` performs the reads, the classification (`migrationClasses` from plan 06-02), `composeDestination`, `composeSource` and `reorderGlobalLast` — everything up to but not including any write — records `Digests` from the bytes it just read, and returns the exact bytes the transaction would produce. It reads files and nothing else; it never writes, never backs up, and never shells out.

`MigrateWithPlan` is the ONLY function in this package that writes. Its FIRST action, before the backups and before anything content-changing, is to re-read both files and compare them against `plan.Digests`; a mismatch returns a distinct, caller-testable `ErrConfigChangedSincePreview` (an `errors.Is`-matchable sentinel wrapped with the changed file's path), having written nothing and backed up nothing. Only after that check passes does it take the backups and write precisely `plan.DestAfter` and `plan.SourceAfter` — it never recomposes. The per-write digest re-check from the concurrency section below still runs inside it, guarding the narrower backup-to-write window; the plan-digest check guards the much wider preview-to-confirm window that the per-write check cannot see.

`Migrate(direction, deps)` KEEPS its current signature and becomes a two-line convenience: `PlanMigration` then `MigrateWithPlan`. Existing tests and existing callers are unaffected, and there is exactly one composition path and one write path.

**Why the pair rather than just the pure function** — state this in `MigrateWithPlan`'s doc comment, citing `06-REVIEWS.md`'s cycle-2 HIGH finding: a pure `PlanMigration` that both the preview and `Migrate` call independently is TWO reads of disk at TWO different times. The preview renders plan A; the user reads it, thinks, and confirms; `Migrate` computes plan B against whatever disk says now and commits plan B. Both plans are internally consistent, the concurrency detector inside `Migrate` sees nothing wrong because plan B matches the disk it was just computed from, and the user has approved bytes that were never written. Carrying the plan object plus its digests is what closes that window; nothing weaker does, because the defect is not a race inside the transaction, it is the transaction planning from a different premise than the one the human agreed to.

**Concurrency detection, early and per-file — THREE checkpoints, widest window first.** At preflight, alongside the content snapshot, record a content digest for each of the two files, with an explicit absent marker for a file that does not exist. Then check:
0. **the plan's own digests, first of all**, as described under `MigrateWithPlan` above — this is the PREVIEW-to-CONFIRM window and it is the one the previous revision had no check for at all;
1. immediately BEFORE the backups, re-read both files and compare against the preflight digests; a mismatch aborts having written nothing;
2. immediately before EACH content-changing write, re-read that file and compare.

Checks 0 and 1 collapse into the same comparison when `Migrate`'s convenience wrapper is used (the plan was computed microseconds earlier, so its digests and the preflight digests are the same values) — that is expected and costs one re-read. They are genuinely different windows only on the interactive path, which is exactly the path that has a human sitting between them. Keep both rather than deduplicating them: the code that guarantees "what you saw is what gets written" should not depend on which caller reached it.

After `MigrateWithPlan` writes a file, update that file's recorded digest to the bytes it just wrote, so the source step's check compares against the destination step's result rather than against preflight. Getting this wrong makes every two-step migration abort, so assert it explicitly in a happy-path test rather than leaving it to chance.

Use a content digest, not a modification time. A same-tick edit is exactly the case an interactive flow makes likely — the user alt-tabs to an editor and saves while the ceremony is open — and timestamp granularity would miss it.

**Abort handling that preserves the external edit.** Track, per file, whether THIS transaction has written it. On abort, `rollback` restores only files with that flag set. A file gitid has not written is never restored, because restoring gitid's stale preflight snapshot over an edit another process just made would destroy exactly the data the detector was built to protect — the review's third HIGH finding. Make the error text say which file changed externally and that its current content was left alone, and, when gitid HAD already written the other file, that gitid's own write was rolled back. Add the invariant to `rollback`'s doc comment so a future refactor cannot quietly widen it back to "restore both".

Do not change the step ORDER or the add-to-destination-before-remove-from-source guarantee; that ordering is what makes every crash point safe, and it is not what this task is fixing.

Update the `Migrate` doc comment: replace the precondition paragraph with a statement of what is now detected, when it is checked, what abort does and does not restore, and what remains out of scope (a modification landing between the final validation and the caller observing success is still possible and is not a data-loss risk, because nothing further is written).

Test using the existing `afterStep` seam plus a `ReadFile` that returns different bytes on a chosen call: mutate a file between preflight and the pre-backup check, asserting NO backup was taken and neither file changed; mutate the source between the backup and the source write; mutate the destination between the backup and the destination write; create a file that was absent at preflight; and a happy-path case asserting the transaction's own writes never trigger the check. For the abort cases, assert specifically that the externally modified file still holds the EXTERNAL content afterwards — not the preflight snapshot — and that any file gitid did write is back at its pre-transaction bytes. Add a same-length-different-content case. Add a test asserting `Migrate`'s written bytes equal `PlanMigration`'s returned bytes for the same inputs.

For the plan-identity half, write the tests as an explicit SEQUENCE that reproduces the interactive shape: call `PlanMigration`, hold the returned plan, mutate a file on disk, THEN call `MigrateWithPlan` with the held plan — and assert `errors.Is(err, ErrConfigChangedSincePreview)`, that the error names the mutated file, that NO backup file was created, and that both files' bytes are exactly what they were before the call. A test that only calls `Migrate` cannot see this defect, which is why the sequence must be written out rather than folded into the convenience wrapper.
