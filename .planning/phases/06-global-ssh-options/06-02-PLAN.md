<objective>
Retire the scattered globals-name literals into one registry, and fix the migration classification that registration would otherwise break.

Purpose: `06-CONTEXT.md` D-08 requires the rename plus registry consolidation, and `internal/sshconfig/include.go`'s own doc comment carries the hand-off note naming this phase as its owner. `06-REVIEWS.md` then found the trap: the migration engine's movable-block filter excludes the globals block by name AND excludes everything the reserved registry names — so the moment 06-01's new name is registered, a storage migration would relocate every identity block and strand the globals block in the old layout. That is not a cosmetic gap: it produces TWO wildcard stanzas across the two files, which is precisely the D-06 invariant this phase exists to establish. The registry change and the classification fix therefore ship together, in one plan, so no wave ever ships a knowingly-wrong filter.
Output: One name authority, one wildcard block, and a migration that carries it.
</objective>

The predecessor filter answered one question — "which blocks are per-identity content" — and used the answer for a different one: "which blocks move". Those diverged the moment D-07 made the globals block layout-following. Split them.

Replace `movableBlockNames` with an explicit three-way classification. `func migrationClasses(content []byte) (identities []string, globals []string)` walks `filewriter.ListBlocks` and sorts each block: a name `IsGlobalBlockName` reports true for goes into `globals`; any other name `IsReservedBlockName` reports true for (that is, the Include-line block) is stationary and appears in NEITHER return; everything else is an identity block. Keep a thin `movableBlockNames` wrapper only if an existing caller still needs the identity-only list; otherwise delete it and repoint. Write the rule in the doc comment with the reason: the Include line is what makes the destination reachable, so moving it would break the very wiring the migration depends on, while the globals block is layout-following content per D-07 and stranding it produces two wildcard stanzas across two files — the exact D-06 violation this phase exists to close.

Extend `composeDestination` and `composeSource` to take the globals list alongside the identity list and treat it identically for the move itself. Extend `reorderGlobalLast` to recognise BOTH globals names rather than looping on one literal, and to run AFTER the globals block has been added to the destination, so the destination ends with identities first and the wildcard stanza last (D-09).

Detect the pathological both-files case at PREFLIGHT, before any backup or write: if `migrationClasses` reports a non-empty globals list for the source AND for the destination, abort with an error naming both file paths and stating that gitid will not guess which wildcard stanza wins. Merging them silently would be a security-relevant guess about which `Host *` body governs the user's authentication, and the Options screen is where the user resolves it deliberately. Say that in the error text and in the doc comment.

Update `Migrate`'s doc comment: its step list currently describes moving "every managed identity block"; it now moves every managed identity block plus the globals block, and explicitly does not move the Include wiring.
