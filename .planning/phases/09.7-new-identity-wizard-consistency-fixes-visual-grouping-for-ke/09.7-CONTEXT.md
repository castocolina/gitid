# Phase 9.7: New-Identity Wizard Consistency Fixes - Context

**Gathered:** 2026-09-07
**Status:** Ready for planning

<domain>
## Phase Boundary

Fix concrete UX inconsistencies a direct user audit found in the New-Identity
wizard: weak visual grouping of related field clusters (Key section in step 0,
author-identity fields in step 2), weak differentiation between success/
warning/error states in the Test-connection step, warnings that disappear
once the wizard advances past the step that produced them, an untyped
proof/log transcript, and inconsistent text-input width/hint-visibility
behavior across the wizard that causes visible layout jumps. This phase does
NOT touch step 3 (Review/ceremony) or the post-creation Register-key modal —
both were audited and found already consistent on every axis below.

</domain>

<decisions>
## Implementation Decisions

### Visual grouping technique
- **D-01:** Hybrid grouping technique: a bold-text header + blank-line
  separator by default (zero row cost, matches the existing "Match strategy"
  / "Key" header pattern already in `gitForm.view` / `renderKeyBody`), with a
  bordered `PreviewBlock`-style box reserved for cases where the per-step row
  budget genuinely allows it. The planner decides per-cluster which variant
  fits, but bold-header is the default assumption, not the box.
- **D-02:** Grouping scope, confirmed exhaustively across the whole wizard
  (not just the two steps the user personally saw):
  - Step 0 (SSH form): the "Key" cluster (`renderKeyBody`,
    `internal/tuikit/identities.go:4995`) needs a clearer visual boundary
    from the SSH field rows above it.
  - Step 1 (Test connection): the "Demo failure control" toggle cluster
    needs separation from the warning/upload cluster below it — currently
    they run together with no header or blank line
    (`internal/tuikit/identities.go:5266-5280`).
  - Step 2 (Git form): the user.name/user.email/Force SSH cluster needs the
    same bold-header treatment "Match strategy" already has
    (`internal/tuikit/identities.go:1001-1041` — Match strategy has a header,
    the author-fields block above it does not).
  - Step 3 (Review/ceremony) and the post-creation Register-key modal: no
    change — both reuse shared, already-consistent machinery
    (`ceremonyModel`, `renderRegisterKey`) with no independent field
    clusters to group.

### Test-connection: color, persistence, typed log
- **D-03:** Reinforce the existing glyph+color convention
  (`styleHealthy`/`styleWarning`/`styleError`, already 3 distinct styles at
  `internal/tuikit/identities.go:5231,5240,5307`) AND add a blank-line
  separator between blocks of different message type. The color system
  itself is not the gap — the lack of spatial separation between
  differently-typed blocks is what reads as "everything blended together."
- **D-04:** The `ReachableNotUploaded`/`keyUnused` warning
  (`stageWarningLine`, currently rendered only inline in the step-1 render
  path and gone once the wizard advances — `internal/tuikit/identities.go:
  5239-5243`) must persist for the rest of the wizard session by being
  written into the proof/log transcript (`wizardModel.proofText()`,
  `internal/tuikit/identities.go:1735`) as a permanent entry, rather than a
  new banner element or a second copy in the Review step. `proofText()`/
  `refreshProof()` already ARE the wizard's immutable session transcript —
  this reuses that mechanism instead of inventing session-persisted UI
  state.
- **D-05:** `proofText()` changes from concatenating a single plain string
  (`appendResult`, `internal/tuikit/identities.go:1737-1749`) to building a
  list of typed entries (an enum: info/success/warning/error) that the proof
  viewport (`ExactTextViewport`) colors per-entry at render time. This is a
  structural change local to `proofText`/`refreshProof`/`renderProof` — NOT
  a text-heuristic/regex-based coloring approach, which was explicitly
  rejected as fragile against copy changes and the viewport's own
  truncation.

### Text-input width
- **D-06:** Apply a fixed width to every text input across the wizard
  (`sshForm` and `gitForm` — currently `newTextInput`,
  `internal/tuikit/identities.go:93`, never calls `SetWidth`, unlike the
  archived POC's `mkInput` which did:
  `.planning/archive/0.0.1-poc-product-features-in-tui/tui/wizard.go:551`).
  Every field gets a fixed width, not just the ones that visibly wander
  most. **Claude's discretion:** the exact numeric width per field — the
  planner sizes each field to its expected longest realistic value (e.g.
  email needs more room than Port), following the archived POC's
  `formFieldWidth` precedent as a starting reference, not a literal value to
  reuse verbatim.

### Hint visibility policy
- **D-07:** Unify every wizard field's hint line onto the "always reserved"
  pattern Match strategy already uses (`gitForm.view`'s "STABLE HINT ZONE"
  comment, `internal/tuikit/identities.go:1042-1046`) rather than the
  current mixed behavior where Hostname/Port hints appear only on focus and
  occupy zero rows while blurred (`internal/tuikit/identities.go:547,568`).
  This directly eliminates the layout-jump the user reported. Every field
  reserves its hint row even when the row renders blank.

### Cross-cutting: row-budget checkpoint
- **D-08 (explicit planner gate, mirrors 09.4 D-06's precedent):** D-01
  (grouping headers/blank lines), D-03/D-04 (Test-connection blank-line
  separators + persisted warning entry), and D-07 (always-reserved hints)
  all add rows simultaneously against the wizard's fixed 30-row pane budget
  — a budget the codebase already documents as tight enough to have broken
  a real test once (`gitForm.view`'s CR-08 comment,
  `internal/tuikit/identities.go:1019-1029`, describes exactly this
  failure mode: one added row pushed the frozen Continue/Skip hint below
  the visible frame in `TestWizardGitStepButtonsAreFocusable`). The planner
  MUST measure the actual row cost of every step with all of D-01/D-03/D-04/
  D-07 applied together — not step-by-step in isolation — before
  implementation, and decide what to trim (e.g. compacting faint
  explanatory lines) if a step doesn't fit. Rate this checkpoint
  `checkpoint:decision` before implementation, same convention 09.4 used for
  its own row/tab-count-affecting merge decision.
  — **Reversibility:** reversible (the checkpoint itself; the row-fit
  outcome it produces may force per-step trade-offs the planner must
  record).

### Claude's Discretion
- Exact numeric fixed width per text input (D-06).
- Exact wording/placement of the blank-line separators in D-01/D-03 — keep
  consistent with the existing `helperLine`/`formFieldLine` row-construction
  style rather than inventing new primitives.
- Which specific faint/explanatory lines to compact or drop per step if the
  D-08 row-budget measurement comes up short — record the trade-off, don't
  silently drop content.

</decisions>

<specifics>
## Specific Ideas

- User's original bug report (from an earlier conversation turn, Spanish
  original in `09.7-DISCUSSION-LOG.md`): text fields in step 0 lack any
  section/subtitle/delimited area for the Key cluster (a group of 3
  elements with its own dynamics); step 1 shows errors the user didn't
  understand alongside a success message with no visual distinction between
  warning and success, and this warning disappears on Next or after
  success; some fields' hints appear/disappear on focus change while others
  don't, causing visible screen jumps; text-input width was raised as minor
  curiosity, not a priority.
- When asked to confirm the grouping technique, the user explicitly widened
  scope from "steps 1-2 I personally saw" to "review the whole wizard for
  the same pattern" — this drove the D-02 exhaustive per-step audit
  (documented inline) rather than assuming the two originally-reported
  steps were the only affected ones.

</specifics>
