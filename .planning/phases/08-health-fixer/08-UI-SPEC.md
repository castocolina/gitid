## ⚠ Known Divergence #1: the live app has FOUR tabs today; the binding design needs FIVE

**The conflict, stated precisely.** Two sources currently disagree about
whether the Fixer is its own top-level view:

- `internal/tuikit/frame.go:58-68` (LIVE, currently shipping in both
  `cmd/gitid` and `cmd/gitid-dummy`): `TabID` indexes **four** primary
  views — `TabIdentities, TabGlobalSSH, TabGlobalGit, TabDoctor` — with the
  comment *"the four primary views (SHELL-01 as redesigned: the Fixer is
  NOT a tab — FIX-02 re-homed it into Doctor)"*. `tabLabels` is
  `["Identities", "Global SSH", "Global Git", "Doctor"]`. Key `4` opens a
  single combined `doctorModel` (`internal/tuikit/doctor.go`) that lists
  ALL findings (fixable and not), shows a live detail pane, and lets the
  user press `f`/`F` to fix one/all findings **on that same screen** — no
  separate Fixer surface exists at all today.
- `.planning/phases/02-design-all-mockups-checkpoint-1/02-UX-DIRECTION.md`
  §2 (the project's **single source of truth** key-allocation table,
  unchanged since Phase 2): *"Five primary views reachable by number keys
  `1`–`5`… **1 Identities · 2 Global SSH · 3 Global Git · 4 Health ·
  5 Fixer**"* — with `4 | health | ActivationKey | Health` and
  `5 | fixer | ActivationKey | Fixer` as two DISTINCT rows. `08-CONTEXT.md`
  (this phase's own binding context, gathered 2026-07-07, AFTER the
  frame.go comment was written) restates this unambiguously: *"a
  READ-ONLY Health screen (view `4`, 5 states)… and the write-side Fixer
  (view `5`, 6 states)"*, and both `health/FIELDS.md` and `fixer/FIELDS.md`
  were authored as two SEPARATE frozen contracts with their own
  `ActivationKey` (4 and 5 respectively) — never a combined surface.
  ROADMAP.md's own Phase 8 success criteria list Health (criteria 1-3) and
  the Fixer (criterion 4) as textually distinct deliverables, matching
  MGR-06/SHELL-01's ROADMAP wording for Phase 5: *"all **five** primary
  views (Identities, Global SSH, Global Git, Health, Fixer) are reachable"*.

**Resolution (binding, not a planner choice):** `02-UX-DIRECTION.md` §2 +
`08-CONTEXT.md` govern — they are the more recent, more specific, and
explicitly-approved sources for THIS phase. `frame.go`'s "SHELL-01 as
redesigned" comment was a **scoped stand-in** for the period between Phase
5 (when the tab shell was built) and Phase 8 (when Health/Fixer's own
checks and screens actually exist) — not a permanent redesign. This is
exactly the condition `08-CONTEXT.md`'s own Integration Points line
describes: *"Views 4/5 replace the last demo screens — the Phase 3 D-16
banner era ends with this phase."* Phase 8 corrects the stand-in.

**Concrete implementation action for the planner (not optional, this
phase's own scope):**
1. `TabID` (`frame.go:58-68`) grows from 4 to 5 values: `TabIdentities,
   TabGlobalSSH, TabGlobalGit, TabHealth, TabFixer`. `tabLabels` becomes
   `["Identities", "Global SSH", "Global Git", "Health", "Fixer"]`.
   `frame.go:58-59`'s stale comment must be corrected in the same commit
   (it currently asserts a fact this phase makes false).
2. `newScreens` (`app.go:637-646`) returns `[5]screenModel`, adding a new
   Health screen model and a new Fixer screen model in place of the single
   `newDoctorModel()`.
3. Key `4` routes to Health (`app.go:402`'s existing
   `TabID(int(key[0]-'1'))` numeric-tab convention already generalizes to
   5 values with no change to the routing arithmetic itself — only the
   `TabID` constant count changes).
4. `a.backend.DemoBanner(a.tab)` (`app.go:551`, the D-16 banner) must be
   evaluated for the two new `TabID` values; this is the literal "banner
   era ends" moment `08-CONTEXT.md` names.
5. Any PTY e2e / visual-gate test keyed to `TabDoctor` or a 4-tab header
   width must be updated in the SAME commit (buildable-boundary rule,
   CLAUDE.md).

**What ports directly, unchanged (do not reimplement):**

## ⚠ Known Divergence #2: Fixer's `v→x→y→z` 4-screen chain is ALREADY a 2-state ceremony in code

Same class of correction Phase 6 (`06-UI-SPEC.md`) and Phase 7
(`07-UI-SPEC.md`) each already applied to their own FIELDS.md.
`fixer/FIELDS.md` describes 4 separate named screens reached by 4 keys —
`v` (fix-preview) → `x` (confirm-destructive) → `y` (backup-notice) → `z`
(result-applied) — plus `e` (nothing-to-fix). **The live substrate already
implements the flagship walk-through as ONE instance of the project's
shared 2-state `ceremonyModel`** (`internal/tuikit/ceremony.go`, the SAME
component "reused by every mutating flow: create, edit, delete, global
apply, fixes" — its own doc comment), not a 4-screen chain:

- `fixCeremonyFor` (`identities.go:2487-2499`) already builds a
  `ceremonyConfig` combining, on state A alone: `Heading` ("Fix: " +
  title), `Targets`/`Backups` (the "Touches"/"Backup →" lines — FIELDS.md's
  own `backup-notice` screen's content), `Preview`+`PreviewDiff` (the
  true `-`/`+` rewrite diff — FIELDS.md's `fix-preview` screen's content),
  and `Destructive: plan.Destructive` (the typed-confirm warning —
  FIELDS.md's `confirm-destructive` screen's content). State B
  (`ceremony.go:328-342`) renders the success message + "Wrote →"/"Backed
  up →" — FIELDS.md's `result-applied` screen's content.
- `PlanFor` (`fixplans.go:30-67`) is **already the D-09/D-11 flagship
  fixture, byte-for-byte**: the `ssh-identitiesonly-contradiction` case
  returns `Destructive: &FixDestructive{ConfirmWord: "clientb.github.com",
  Warning: ...}` — the exact D-11 typed-hostname-confirm ruling, already
  implemented, already test-asserted (`fixplans_test.go:48-49`). D-11
  requires **zero new code** — only the FIELDS.md sentence amendment
  08-CONTEXT.md already authorizes.
- The destructive typed-confirm mechanism itself (`ceremony.go:135-152`,
  the placeholder `Type "<word>" to enable the destructive action`, the
  Cancel-never-default-focused rule) is the SAME mechanism
  `identities.go`'s own "delete everything" ceremony uses
  (`identities.go:2817`, `ConfirmWord: plan.Name`) — `fixer/FIELDS.md`
  itself already names this precedent ("mirrors identity-manager's
  'delete everything' precedent"). This is not a new interaction pattern
  for the Fixer to invent; it is a second call site of an existing one.
- D-12's "auto-advancing queue of per-finding ceremonies" is **already
  implemented** as `doctorBatch{queue, total}` (`doctor.go:27-31`) + the
  `F` batch-fix key (`doctor.go:238-251`): each successful fix pops the
  queue and immediately opens the NEXT finding's own `fixCeremonyFor`
  instance — never a combined ceremony — with a live `"Fix all — k / n
  fixed"` progress line (`doctor.go:359-361`, `styleInfo`). This is
  `fixerBatchFixNote`'s exact behavior, already coded.

**What genuinely still needs new code (D-12/D-13/D-14, not yet present):**
- `FixFinding`'s reducer (`store.go:386-...`) currently just prunes the
  matched ID from `s.Findings` — correct for the DUMMY fixture (approximates
  "this finding is now resolved"), but the REAL backend must satisfy
  **D-13**: re-run ALL doctor checks after every applied fix and rebuild
  the queue from fresh findings matched by signature (not a local prune).
  This is a real-backend requirement; the dummy's simpler prune stays as
  an acceptable fixture approximation (same class as every other
  dummy/real divergence this project already carries, e.g. `PersistError`).
- **D-14**'s convergence alarm (a finding reappearing after its own fix
  reported success → error-severity "fix did not converge" finding,
  permanently excluded from re-offer) has no visual precedent in
  `doctor.go` today — new copy + a new finding-list treatment (an entry
  that is itself unfixable, i.e. no `SuggestedFix`, so it renders exactly
  like `git-opensource-no-host-block`'s existing info-only row shape,
  just at error severity — no new render code, only new DATA).
- **D-06.1**'s Class-1 orphan downgrade and **D-16**'s single-fix-rollback
  queue-halt message are backend/copy changes with no new render
  mechanism — the existing "finding disappears from the list" (success)
  and the ceremony's existing `commitFailed`/`commitErr` retry state
  (`ceremony.go:282-292`, already rendered at `ceremony.go:350-360`) cover
  the visual shape; D-16 only adds a specific halt-message string (see
  Copywriting Contract).

**Action for the planner/executor:** treat `doctor.go` + `fixplans.go` +
`ceremony.go` as the authoritative interaction model for the Fixer's write
flow. Split `doctorModel` into two screen models (Known Divergence #1), but
carry `fixCeremonyFor`/`PlanFor`/`doctorBatch`/the `f`/`F` keys into the
NEW Fixer screen model unchanged in shape. Do not resurrect a `v`/`x`/`y`/`z`
4-screen chain — no design re-freeze is required, this compaction already
shipped project-wide (Phases 3–7 all reuse the same `ceremonyModel`).

Accent reserved for (unchanged from prior phases, Phase 8 adds no new
element): the focused/selected list row only — **never** used to color the
severity taxonomy itself (that is glyph + word + role, matching the
project's NO_COLOR-legible contract).

**Color dominance (TUI-adapted 60/30/10):** default foreground/background
carries the overwhelming majority of rendered characters on every screen —
plain finding text, labels, and structural chrome. The four severity roles
(Info/Warning/Error/Healthy) together are the secondary layer, applied only
to glyphs, state words, and the specific lines they gate. Accent (the
focused-row highlight) is the smallest layer: at most one row at a time,
never a whole-screen treatment.

**Explicit note on Health's read-only posture:** Health NEVER renders
`styleSelected`/`styleBold` on an action button — there is no button to
render. The negative assertion (`health/FIELDS.md`: "no confirm/backup/
apply write-ceremony marker string appears anywhere") extends to color: no
row on the Health surface may use a "primary action" visual treatment
(the reverse-video/bold button styles `ceremony.go` uses for Cancel/
Confirm) — those styles are reserved for the Fixer surface exclusively.

## Inherited Non-Negotiables (quick reference for the executor)

Restated for convenience only — NOT decided by this document; each is
cited from its binding source and must not be re-litigated during Phase 8
planning or execution.

- **Five primary views, number keys `1`-`5`** (`02-UX-DIRECTION.md` §2,
  the project's single source of truth key-allocation table) — Health is
  `4`, Fixer is `5`. Known Divergence #1 above is this phase's job to
  make the live code match this table, not a license to deviate from it
  further.
- **Master–detail archetype** — list ~44% width left, detail ~56% width
  right — `frame.go`'s existing helpers, do not reimplement.
- **Glyph contract, LOCKED**: `~` info (cyan), `!` warning (yellow), `✗`
  error/critical (red, word-disambiguated) — `design.go`'s
  `HealthSeverityGlyph`, never a 5th glyph, never reuse `✗` for warning.
- **Read-only integrity is Health's own highest-risk affordance**
  (`02-UX-DIRECTION.md` §4(6)): no write ceremony appears on Health AT
  ALL — negatively asserted, not just documented.
- **Fix-in-place rewrites of existing directives is the Fixer's own
  highest-risk affordance** (`02-UX-DIRECTION.md` §4(7), `08-CONTEXT.md`
  D-09): the Fixer — and ONLY the Fixer — may rewrite exactly ONE
  existing directive outside managed blocks, through the full ceremony
  (true diff preview, typed confirm per D-11, timestamped backup named
  before apply, mandatory D-10 verification loop).
- **Compressed 2-state ceremony** (preview+diff+destructive-confirm+
  backup-promise → result) for every write, no exceptions — `ceremony.go`'s
  documented contract (Known Divergence #2). Do NOT reintroduce
  FIELDS.md's separate fix-preview/confirm-destructive/backup-notice/
  result-applied screens as literal, separately-keyed screens.
- **Traceability, not re-derivation**: the Fixer's finding list IS
  `fixableFindings(Health's findings)` — never an independently maintained
  second list. HLTH-04's own "available on the Fixer screen" hand-off text
  and MGR-07's per-identity slice both depend on this single-source
  discipline.
- **"The backup is the undo story"** — the ceremony's backup-path promise
  (state A) and its "Backed up →" line (state B) must stay first-class,
  never buried, on every Fixer write.
- **D-13's re-run-ALL-checks-after-every-fix invariant** — this is a
  BACKEND requirement with a specific visual consequence: after any fix
  applies, the finding list the user sees next MUST be freshly computed,
  not a stale local removal (the dummy fixture's simpler prune is an
  accepted approximation, not the real-backend contract).
- **Advisory-vs-mandatory severity discipline carried from prior phases**:
  `SeverityInfo` findings are ALWAYS report-only (no fix ever attached, no
  escalation) — the D-05 "set, differs" hard-cap and D-06.1's orphan
  downgrade both rely on info severity meaning exactly this, project-wide.
- **Copy-freeze grep gate**, extended per this document's DRAFT strings
  once approved — `02-STYLE-SPEC.md` §6.
- **100×30 capture geometry** is kept identical — do not change frame
  dimensions to fit the growing finding count; resolve overflow (UI
  Considerations) within the existing frame, reusing Phase 7's
  established scrolling-window mechanism if the fixture count triggers it.
- **NO_COLOR legibility**: every row (including D-14's convergence alarm)
  must remain fully legible under `NO_COLOR` — glyph + word carries the
  meaning, color is additive only.
