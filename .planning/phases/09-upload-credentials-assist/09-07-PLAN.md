<objective>
Close ROADMAP Phase 9's fourth success criterion and D-09's capture obligation: raw
keystroke PTY coverage of every new upload screen state against the real compiled
binary, fresh approved frames minted for exactly the amended screens, and an
automated real-vs-dummy comparison in which every difference is explicitly
classified.

Purpose: ONESHOT.md rule 8 is explicit that for a TUI-surface phase, "UI review" and
Definition-of-Done mean the compiled real binary exercised through a real PTY with
raw keystrokes — a unit or wiring test never substitutes. Rule 11 adds that every
real-vs-dummy difference must be classified as a UX improvement or a defect, and
that an unclassified difference fails review. This plan makes both mechanical.

Output: a green `make test-e2e` covering every upload state, a green
`make gate-visual-regression` with Phase 9 registered, four Phase 9 negative
controls proving the gate can fail, and a committed set of approved frames.

ordering placed the dummy demo states and the capture-and-approve step BEFORE the
render rework. That ordering is not expressible in the current architecture —
`cmd/gitid-dummy` renders through the SAME `internal/tuikit` code as `cmd/gitid`
(09-RESEARCH.md Substrate Reality Check #5; STATE.md's Phase-4 CR-15 finding), so a
dummy state cannot exist before the shared renderer does. D-09's substance lands
here: fresh approved captures for exactly the amended screens, used as the
visual-regression baseline, with a parity critique before phase close.
