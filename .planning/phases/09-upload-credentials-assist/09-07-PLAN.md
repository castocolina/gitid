<objective>
Close ROADMAP Phase 9's fourth success criterion and D-09's capture obligation: raw
keystroke PTY coverage of every new upload screen state against the real compiled
binary, fresh approved frames minted for exactly the amended screens, and an
automated real-vs-dummy comparison in which every difference is explicitly

Purpose: ONESHOT.md rule 8 is explicit that for a TUI-surface phase, "UI review" and
Definition-of-Done mean the compiled real binary exercised through a real PTY with
raw keystrokes — a unit or wiring test never substitutes. Rule 11 adds that every
real-vs-dummy difference must be classified as a UX improvement or a defect, and
that an unclassified difference fails review. This plan makes both mechanical.

Output: a green `make test-e2e` covering every upload state, a green
`make gate-visual-regression` with Phase 9 registered, four Phase 9 negative
controls proving the gate can fail, and a committed set of approved frames.

**Carried forward from plan 09-01's APPROVAL.md addendum:** D-09's literal step
ordering placed the dummy demo states and the capture-and-approve step BEFORE the
render rework. That ordering is not expressible in the current architecture —
`cmd/gitid-dummy` renders through the SAME `internal/tuikit` code as `cmd/gitid`
(09-RESEARCH.md Substrate Reality Check #5; STATE.md's Phase-4 CR-15 finding), so a
dummy state cannot exist before the shared renderer does. D-09's substance lands
here: fresh approved captures for exactly the amended screens, used as the
visual-regression baseline, with a parity critique before phase close.

## Cross-AI review corrections folded into this plan (09-REVIEWS.md)

**(R1, inherited and enforced here) Hermetic provider PATH for every new PTY entry
point.** The review rated this wave HIGH because it adds twelve new PTY tests plus
two paired compiled-binary comparisons on top of a suite whose environment
constructors leaked the ambient PATH. Plan 09-02 Task 2 closed that suite-wide with
the `e2eEnv` constructor and `TestEveryE2EChildEnvIsHermetic`. This plan adds new
entry points and therefore inherits the obligation: every test it adds builds its
environment through `e2eEnv`, including the DUMMY session of each paired comparison,
and the guard test fails this plan's commit if any of them hand-rolls one. Note in
particular that `TestCreateFlow_UploadCheckboxDisabledState` — which deliberately
runs with no provider shim — now gets the deny shim behind its prefixes, which is
what makes its "disabled/unauthenticated" state deterministic on every machine
rather than dependent on whether the developer has `gh` installed.

**(R14) Approved frames need provenance, not just a filename.** Frames are produced
into a gitignored directory and then copied into the phase directory by hand. Without
a recorded hash and a single promotion command it is possible — accidentally — to
commit a frame from a different run than the passing test, which would make the
approved baseline a fiction. Task 1 adds a machine-checked provenance record and one
reproducible promotion command; Task 2 adds the registry-to-frame mapping test.

**(R15) The `agent-ui-ux-designer` critique is an orchestrator/human step, and a
missing critique must be recorded as missing.** An autonomous wave cannot summon that
agent, and the one outcome that must never happen is a synthesized critique attributed
to it. Task 3 states the honest-unavailable path explicitly.
