<objective>
Prove the autonomous upload path against a real GitHub account exactly once, under
ONESHOT.md's Phase 9 External Account Policy, and close the phase's requirements
with evidence.

Purpose: every automated test in plans 09-02 through 09-07 runs against offline PATH
shims. That is the right default — but it means nothing in the phase has yet proven
that gitid's argv is accepted by the real `gh` against a real account, that GitHub
really does require the same key registered twice, or that the post-upload inventory
confirmation sees what it expects. ONESHOT.md's policy authorizes exactly this
validation and specifies the protocol; it also states plainly that if authentication
or scope is unavailable, the blocked evidence is recorded and the run stops — a mock
must not be silently substituted for the required real-account validation.

Output: one recorded real-account validation run, a permanently opt-in test that can
be re-run, and a closed requirement set.

**Safety posture, stated once and binding for this plan.** This is the only plan in
Phase 9 that touches a real external account. It is `autonomous: false` and opens
with a blocking human-action checkpoint, because ONESHOT.md rule 9 requires stopping
for a required confirmation before a real external-account mutation, and because the
account being mutated belongs to the developer, not to the tooling.

**Relationship to the hermetic e2e boundary (plan 09-02 Task 2).** Every other test
in the repository is now hermetically prevented from resolving a real `gh`/`glab`.
This file is the single, deliberate exception, and it is exempt BY BUILD TAG rather
than by a filename allowlist: it carries its own tag, is never compiled under the
`e2e` tag, and `TestEveryE2EChildEnvIsHermetic` skips it only because it declares a
non-`e2e` build constraint. It must NOT use `e2eEnv`, because its entire purpose is
to reach the real `gh`. State that inversion explicitly in the file's doc comment so
a future reader does not "fix" it into hermetic conformance and silently destroy the
only real-account validation in the project.

## Cross-AI review corrections folded into this plan (09-REVIEWS.md)

The review rated this plan HIGH. Five corrections land here; four of them change what
the test actually does.

**(R16) The test must drive the COMPILED BINARY, not the uploader engine.** The
earlier draft called `uploader.UploadKeys` directly, which bypasses compiled CLI/TUI
wiring, `buildUploaderDeps`, provider eligibility, the autonomous trigger, the shared
orchestration, the printed outcome, and post-upload control flow. That is an uploader
integration test against a real account — not the "autonomous upload path proven
against a real GitHub account" the plan's own success criteria claim. Task 2 now runs
`gitid register-key` from the compiled binary in a temporary HOME as its primary,
authoritative phase.

**(R17) The title-policy clause and the product path cannot both be satisfied by one
registration pair — so the test does both, honestly.** `.planning/ONESHOT.md` requires
every created key to be named `gitid-e2e:<run-id>:<purpose>`. The product names keys
with D-07's frozen `gitid: <name> @ <machine>` format, and there is no way to make the
compiled binary emit a colon-delimited policy title without adding a product seam D-06
explicitly forbids (no env-var opt-out in v1.0). Rather than silently deviate or
silently drop the product path, the run has TWO phases with TWO disposable key pairs:

- **Phase P (product, authoritative for UP-03):** the compiled binary registers key
  pair A under the product's own D-07 title. Run-scoping is achieved through the
  disposable IDENTITY NAME, which is constructed to embed the literal string
  `gitid-e2e-<run-id>`, so that exact string appears verbatim in every title the
  product creates and is therefore uniquely recordable, deletable, and sweepable.
  **This is a recorded, reviewed deviation from the policy's literal naming clause**,
  taken because the alternative — a test-only product seam — would violate D-06 and
  would mean the validated path is not the shipped path. The policy's INTENT (every
  created key uniquely attributable to this run, deleted by exact recorded ID,
  sweepable by an exact run-scoped string) is fully preserved, and the `<purpose>`
  distinction is preserved by GitHub's own endpoint separation (`user/keys` vs
  `user/ssh_signing_keys`), which is a stronger discriminator than a title suffix.
  The checkpoint in Task 1 puts this deviation in front of the developer for explicit
  acknowledgement rather than burying it.
- **Phase N (naming, authoritative for the policy clause):** the engine registers key
  pair B directly through `uploader.UploadKeys` with per-registration titles
  `gitid-e2e:<run-id>:<purpose>` — the policy's exact format — which also proves plan
  09-03's R4 per-registration-title API against the real provider. A second key pair
  is required because GitHub rejects the same public key added twice as the same key
  type.

Four disposable keys total. The checkpoint says four.

**(R18) Scope verification must be exact and named.** "Attempting a scope-revealing
read" does not prove upload authorization: a read endpoint may be reachable with a
read-only scope. Task 2 pins the command and the parsing rule and requires both exact
scope names.

**(R19) `t.Cleanup` plus explicit deletion double-deletes.** Cleanup was registered
right after the IDs were recorded and the test then deleted the same IDs explicitly,
so unless the closure tracks what is already gone it fires a second time. Task 2
replaces the plain slice with an outstanding-ID set.

**(R20) A blocked or skipped run must not close UP-03.** The earlier draft permitted
marking UP-03 closed while noting the validation was blocked, contradicting its own
"required evidence" framing. Task 3 makes the closure conditional and mechanically
checked.
