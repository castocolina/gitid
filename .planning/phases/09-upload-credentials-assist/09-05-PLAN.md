<objective>
Give upload its headless surface: the shared orchestration extracted so both the TUI
and the CLI run identical logic, the `register-key` verb as the manual re-run
surface, and D-06's `--no-upload` / `--dry-run` controls with derived autonomous
upload on every write verb that produces new key material.

Purpose: D-01 requires the headless CLI to "mirror the checkbox with flags; defaults
derived identically". The only way that is true rather than approximately true is
if there is exactly ONE orchestration function and ONE result printer. This plan
extracts them and wires every surface to them.

**Scoped deviation from 09-CONTEXT.md's `gitid copy --upload-keys` phrasing, recorded
here and binding for the rest of the phase.** D-01 and 09-UI-SPEC.md's integration
table name `gitid copy --upload-keys` as the CLI trigger and manual re-run surface.
That command does not exist: `cmd/gitid/copy.go` was archived wholesale in Phase 3's
commit `d60a4d7`, and `cmd/gitid/main_test.go`'s
`TestNewRootCmdArchivedPOCCommandsAreGone` asserts the `copy` and `upload` command
names stay absent as a locked regression test. 09-CONTEXT.md was gathered
2026-07-08, before that archival landed (09-RESEARCH.md Pitfall 6 documents exactly
this class of stale citation). The SUBSTANCE of D-01 is preserved unchanged — a
CLI-triggered, explicitly-opt-in manual re-run surface exists — delivered as
`gitid identity register-key <name>` with its flat alias `gitid register-key`,
matching 09-UI-SPEC.md's own action-menu label "Register key (u)". Invoking the verb
IS the opt-in that `--upload-keys` expressed. No archived command name is
resurrected and the locked regression test is not edited. D-10 already directs that
the archived surface be REDESIGNED to the new contract rather than patched forward;
this verb is that redesign on the CLI side, exactly as plan 09-02's promptless
`testUpload` beat is on the TUI side.

Output: full CLI parity for upload, machine-checked by the existing bidirectional
parity-matrix checker and proven headlessly against the fake provider shims.

## Cross-AI review corrections folded into this plan (09-REVIEWS.md)

**(R1, inherited and enforced here) Hermetic provider PATH for every CLI e2e case.**
The review rated this wave HIGH partly because enabling default autonomous upload on
four write verbs means any existing CLI test that builds the real backend could probe
or upload through the ambient PATH. Plan 09-02 Task 2 closed that suite-wide with the
`e2eEnv` constructor and its two guard tests. This plan adds NEW e2e entry points, so
it inherits the obligation rather than restating a per-test promise: every case Task 3
adds builds its environment through `e2eEnv`, and `TestEveryE2EChildEnvIsHermetic`
fails this plan's commit if any of them hand-rolls one.

**(R10) `register-key`'s exit code must distinguish success from failure.** The
earlier draft had the verb always return nil "because upload never gates". D-03's
rule is that an upload failure must not change the exit code of the PRIMARY
operation — but `register-key` has no other operation: the registration IS the
primary operation. Always exiting 0 makes the verb unusable from a script, which is
the entire point of a headless surface. Task 2 therefore gives it a defined exit
contract (below) while leaving the four write verbs' unconditional exit 0 untouched.
This is a reading of D-03's substance, not a departure from it; the plan states the
reasoning at the call site so a later reader does not mistake it for drift.

**(R11) `--dry-run`'s help text must not promise more than it delivers.** A dry run
performs no remote MUTATION, but it does perform reads (`auth status`, and the
inventory read that computes the missing-type diff). "Executes nothing" is a stronger
claim than the behavior. Tasks 2 and 3 make the help text and the parity-matrix rows
say exactly which reads may occur and that no remote mutation does.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| shell/script → gitid CLI | A non-interactive caller supplies the identity name and flags; the tool must never silently substitute a default or open an interactive surface. |
| upload outcome → process exit code | A script must be able to trust that a non-zero exit means the PRIMARY operation failed. |
| CLI output → operator | The printed announce lines are what an operator will trust as "what ran". |
| TUI surface ↔ CLI surface | Two surfaces implementing the same outcome differently is itself a defect class this project's parity matrix exists to prevent. |
