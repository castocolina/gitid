**Two decisions Claude's Discretion covers, resolved here with rationale:**

1. **Inventory shape (09-RESEARCH.md Open Question 1):** full JSON parsed with
   stdlib `encoding/json` in Go, NOT `gh api --jq` filtering. Rationale: the
   codebase has no third-party JSON dependency and no `--jq` precedent anywhere,
   and a `--jq` expression couples the argv to a specific response shape that
   changes silently on the provider's side, whereas an unrecognized field in a Go
   struct is simply ignored.
2. **Inventory failure posture (D-15, restated as code):** `Inventory` returns
   `([]ExistingKey, error)`, and every caller treats a non-nil error as "no dedupe
   information available" — never as a reason to stop. The degraded path is
   surfaced through `UploadRunView.InventoryDegraded`, the field plan 09-02 already
   declared.

## Cross-AI review corrections folded into this plan (09-REVIEWS.md)

**(R4) `UploadKeys` must accept a title PER REGISTRATION.** The earlier draft's
signature took one `title string` for the whole batch. `.planning/ONESHOT.md`'s
Phase 9 External Account Policy requires every key plan 09-08 creates to be named
`gitid-e2e:<run-id>:<purpose>` with a distinct `<purpose>` per registration kind — a
single batch-wide title parameter makes that literally unexpressible, which one
reviewer rated an execution blocker against 09-08's own protocol. Task 1 changes the
batch API to per-registration requests. The product's D-07 behavior is unchanged: it
supplies the SAME machine-scoped `KeyTitle` for every registration, but now says so
explicitly through a named helper instead of relying on the API's shape. This also
closes the related concern that D-07's product-mode `KeyTitle` could silently
override a caller-supplied policy title — with per-request titles there is nothing
left to override, and a test asserts it.

**(R5) `.pub`-suffix checking does not establish the public-key-only invariant.** A
private key copied or symlinked under a `.pub` name passes a
`strings.HasSuffix(path, ".pub")` test, so the earlier draft's ASVS V5 claim was
stronger than its mechanism. Task 1 replaces the suffix-only guard with content
validation: read the file through an injected `Deps.ReadFile` seam, reject anything
carrying a private-key PEM marker, and require the remainder to parse as an OpenSSH
authorized-key line. The suffix check is KEPT as a cheap first filter, but it is no
longer the invariant.

**(R6) `DeleteKey` accepts an arbitrary ID with no shape validation.** The ID comes
from provider-controlled JSON and goes into a destructive command's argv. Task 2
validates the ID's shape before the call so a title, a path, or a flag-looking
string can never be passed where an ID is expected, and adds a safer
`DeleteRecordedKey` entry point that binds the ID to the title it was recorded
under.</objective>
