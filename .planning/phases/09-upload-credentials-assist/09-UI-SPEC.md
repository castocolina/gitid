# Phase 9 — UI Design Contract

> Visual and interaction contract for Phase 9 (Upload / Credentials Assist).
> Generated by gsd-ui-researcher, verified by gsd-ui-checker.

This project's stack is a Go Bubble Tea v2 terminal app (not a web app);
template sections written for CSS/web design systems are translated to
their TUI equivalent (theme roles instead of hex/CSS tokens, 100×30 fixed
capture geometry instead of responsive breakpoints) — the same translation
Phases 3–8's own `0N-UI-SPEC.md` established.

**This document is different from Phases 3–8 in one respect**: those phases
derived an already-approved Phase-2 mockup screen. Upload has **no frozen
Phase-2 design** — `09-CONTEXT.md` D-08 explicitly calls it "no frozen
contract exists for upload." This document IS that missing contract: a
NEW shared component spec, amending `create-flow/FIELDS.md` and
`identity-manager/FIELDS.md` (D-08's own approved sequence, step 1 of 6).
Read "Design Decision: Where the section lives" FIRST — it resolves the
one placement question `09-CONTEXT.md` left open ("pinned during the UI
wave").

## Design Decision: Where the section lives

**The constraint, stated precisely.** D-08 (09-CONTEXT.md): "Upload is a
**section, not a navigable surface**." D-05: upload runs "after the key
exists and before the `ssh -T` test loop." The live wizard today
(`internal/tuikit/identities.go`) has exactly 4 steps
(`wizardSteps = []string{"SSH details", "Test connection", "Git identity",
"Review & write"}`), and key material is generated **lazily inside
`TestStage1`** (`cmd/gitid/wiring.go:1073-1085`: "the key is generated (if
it does not exist yet) and tested DIRECTLY against the provider endpoint"
— `b.stagedKeyFor(...)` runs before the actual `ssh -T` probe). D-05's
window ("key exists, before the test loop") therefore falls **inside**
step 1 ("Test connection"), between the existing staging call and the
existing `PreWrite`/`ResolvedVia` probe calls — not between two wizard
steps.

**Resolution (binding for this phase, not a planner-open question):**

1. `wizardSteps` stays **4 entries, unchanged** — the checker gate on
   `Step n/4` byte-exact copy is not touched. Upload does **not** get its
   own numbered step (this is D-08's "section, not a surface" made
   concrete).
2. Step 1's pane-state sequence gains ONE new sub-beat, inserted **before**
   `testRunning1`: `testIdle` → **`testUpload`** (the shared upload-section,
   all its own sub-states below) → `testRunning1` → `testStage1` → … The
   existing keystroke that currently starts stage 1 (`enter` on
   `testIdle`, `identities.go:3234-3238`) now first stages the key and
   enters `testUpload`; the section resolves (autonomously or via the
   checkbox), then auto-advances into `testRunning1` — no extra keystroke
   the user must remember, consistent with D-02's "no prompt, no cancel
   timer."
3. The auto-upload **checkbox itself** is decided one step earlier, on
   step 0 ("SSH details"), the moment `Provider`/`Hostname` are known
   (D-01's derivation needs both) — rendered as the LAST row of the SSH
   form, after `Port`. Its checked/unchecked/disabled state carries
   forward into step 1's `testUpload` sub-beat; nothing about D-01's
   derivation logic re-runs there.
4. New intra-step key: **`u`** toggles the checkbox on step 0 (mnemonic,
   unclaimed in `02-UX-DIRECTION.md` §2's key-allocation table — the
   planner must add this row in the same commit that wires it, per that
   table's own "single source of truth" discipline). No new key is needed
   inside `testUpload` itself — D-02 (announce-and-do, no prompt) means
   the section only ever needs `enter`/auto-advance, both already claimed
   patterns.

**Integration points (D-03's "reused across create/rotate/clone/copy"),
resolved concretely:**

| Flow | Where the section renders | Binding detail |
|------|---------------------------|-----------------|
| Create (this phase's primary target) | Wizard step 1, new `testUpload` sub-beat (above) | D-05 timing |
| Clone, same-key reuse | **Omitted** — the key is already registered with the provider from the source identity; nothing new to upload | no new key material exists |
| Clone, new key | Same as create — the clone wizard already runs "the full two-stage gate on same-key clones" (STATE.md 05-05); the new-key path shares the identical `testUpload` sub-beat | reuses create's wizard, not a new render |
| Rotate | The key-ceremony pane's own pre-test beat (`keyCeremonyMode == KeyCeremonyModeRotate`, `identities.go:2281`+), inserted at the SAME relative point (after the new key is staged, before its own connectivity probe) | same component, second call site |
| New-key (repair) | Same key-ceremony pane, `KeyCeremonyModeRepair` | same component, third call site |
| Rotate, AFTER the new key passes (D-04) | A NEW sub-beat appended to the rotate ceremony's result screen: the interactive old-key delete offer (see Copywriting Contract) | replaces `keyCeremonyGraceHintFmt`'s current passive hint |
| `gitid copy` (CLI, `--upload-keys`) | No TUI render — CLI-only, prints the same announced-and-do lines + per-key results as plain stdout | unchanged trigger, upgraded internals (D-11/D-15/D-16) |
| Identity Manager, existing `key-unused`/`key-used-ssh-only` identity | NEW modal reached from the action-menu (`a` → new row, see FIELDS.md amendment below) — the manual re-run surface for an identity that landed on `ReachableNotUploaded` and was never auto-uploaded | D-08's "identity-manager/FIELDS.md — copy modal" amendment target |

## The shared upload-section component (D-08) — states

ONE component contract, rendered at every integration point in the table
above. States, in the order a user encounters them:

| State | Trigger | Renders |
|-------|---------|---------|
| `omitted` | `Provider` doesn't match `github`/`gitlab` (D-13, main-domain scope) — self-hosted/unknown host | nothing — the section does not appear at all; the create wizard proceeds straight to `testRunning1` |
| `checkbox-disabled` | Provider matches but neither `gh` nor `glab` is on PATH (D-01 scenario 3) | ONE line, unchecked and dimmed, with the reason (Copywriting Contract) |
| `checkbox-unchecked-unauth` | Provider matches, tool present, NOT authenticated (D-01 scenario 2) | ONE line, unchecked but toggleable (`u`), with the `gh auth login`-class hint |
| `checkbox-checked-auth` | Provider matches, tool present, authenticated (D-01 scenario 1) | ONE line, PRE-checked, toggleable (`u` unchecks it) |
| `announcing` | Step 1 reaches `testUpload` with the checkbox checked | one `Running: <command>` line per registration actually attempted (D-16: only MISSING types, per the inventory diff — see D-15) — gh shows up to 2 lines, glab shows 1 |
| `per-key-results` | Each announced command completes | one result row per announced command: `✓ registered` / `✓ already registered (skipped)` / `✗ failed: <classified reason>` |
| `manual-fallback` | `omitted` is false but autonomy did not run (checkbox left unchecked, degraded to unauth, or every attempted registration failed) | the EXISTING `internal/upload.Instructions(provider)` block, byte-identical, under a short heading |
| `dry-run` | `--dry-run` (CLI only, D-06) | the SAME `announcing` lines, with a trailing "nothing was executed" note; no `per-key-results` state ever renders |

No state adds a row when the section is `omitted` — the 100×30 row budget
that step 1 already fits inside (verify at PTY e2e time, same discipline
`08-UI-SPEC.md` documented for its own new banners) must absorb at most
`checkbox` (1 row) + `announcing`/`per-key-results` (up to 2 rows for
GitHub, 1 for GitLab) + `manual-fallback` (the existing multi-line
`Instructions` block, only when reached) — never all of these
simultaneously.

---

**Focal points (per-screen primary focus, for executor clarity):**
- Step 0's checkbox row — primary focus: the row must read correctly as ONE
  line in all three states (`checkbox-disabled`, `checkbox-unchecked-unauth`,
  `checkbox-checked-auth`) without ever wrapping to a second line — the
  disabled/hint reason is inline on the same row, never a stacked line
  underneath. This is the first thing a user sees about upload, and the
  D-01 autonomy model lives or dies on this row being scannable at a glance.
- Step 1's `testUpload` sub-beat — primary focus: the `announcing` →
  `per-key-results` transition must visually match `renderStageOutcome`'s
  existing command/PASS-row treatment exactly (same faint/command styling,
  same glyph+word shape) so upload reads as "one more stage in the same
  test-loop the user already saw," not a bolted-on new UI language. The
  highest-implementation-risk item here is `announcing` staying up long
  enough to be legible before `per-key-results` replaces it — never a
  same-frame flash.
- The manual-fallback block — primary focus: it must be byte-identical to
  the existing `internal/upload.Instructions(provider)` output. Any
  divergence (even reformatting) breaks the "shown command equals the run
  command" contract (UP-02/UP-03) this whole phase exists to satisfy.
- Rotate's delete-offer (D-04) — primary focus: this is the one new
  confirmation ceremony in the phase and the only place autonomy is
  deliberately absent — the Yes/No choice row must default-focus "No"
  (leave the old key) per D-04's non-destructive-by-default posture, never
  default to the delete option.
- Identity Manager's copy-modal — primary focus: this is a new `identPane`
  value (`paneRegisterKey`), matching the exact shape of the existing
  `paneClone`/`paneDeleteScope` panes (same `handleKey`/`view` switch-case
  pattern) — not a call into any overlay-composition helper. Any deviation
  from the existing pane rendering/geometry convention is a defect, not a
  design choice.

## Typography (TUI-adapted: semantic roles, not px sizes/weights)

Unchanged from Phases 3–8. Phase 9 introduces **zero new roles**.

| Role | TUI treatment | Usage in Phase 9 |
|------|----------------|-------------------|
| Label | `Bold(true)` | checkbox label text, modal heading |
| Field (value) | plain, no styling | manual-fallback instructions body |
| Command | `Faint(true)`, matches `renderStageOutcome`'s existing command-line rendering | the `Running: <command>` lines — MUST be the literal string `CommandPreview`/`buildArgs` produces (D-02 shown==run, structural) |
| Info | `styleInfo` (cyan) | "already registered (skipped)" rows (idempotent success, D-15) |
| Warning | `styleWarning` (yellow) | disabled-checkbox reason line, unchecked-unauth hint, D-04's non-destructive old-key question |
| Healthy | `styleHealthy` (green) | `✓ registered` result rows |
| Error | `styleError` (red) | `✗ failed` result rows, glab cross-account-conflict finding |
| Hint / Faint | `Faint(true)` | checkbox helper text, "nothing was executed" dry-run note |

**Non-negotiable, carried forward unchanged:** every colored state pairs
with a glyph AND a word — never color alone (project-wide NO_COLOR
contract). The checkbox itself is a glyph pair (`☐`/`☑`), not a color
toggle — legible under `NO_COLOR` by construction.

## Color

ANSI-16 only, unchanged. Phase 9 reuses the existing role table exactly;
no new hue, no new role.

| Role | Value | Usage in Phase 9 |
|------|-------|-------------------|
| Dominant surface | terminal default fg/bg | checkbox label, command text, manual-instructions body |
| Secondary | `Faint`/`Hint` (dim) | checkbox helper/disabled-reason text, dry-run note |
| Accent (ANSI 4, blue) | `styleSelected` | the checkbox row when keyboard-focused (unchanged focus mechanism) |
| Info (ANSI 6, cyan, `Theme.Info`) | `styleInfo` | idempotent "already registered" results |
| Warning (ANSI 3, yellow, `Theme.Warning`) | `styleWarning` | disabled/unauth checkbox states; D-04's old-key removal question (non-destructive framing, reversible by re-adding) |
| Error (ANSI 1, red, `Theme.Error`) | `styleError` | failed registrations; glab cross-account-conflict finding |
| Healthy (ANSI 2, green, `Theme.Healthy`) | `styleHealthy` | successful registrations |

**Color dominance (TUI-adapted 60/30/10):** default foreground/background
carries the overwhelming majority of characters — command text, labels,
manual instructions. The four severity roles are the secondary layer,
applied only to glyphs, state words, and their gated lines. Accent is
reserved for the checkbox row's focus highlight only — never used to
color the announce/result lines themselves (those are glyph+word+role,
matching the project's NO_COLOR-legible contract).

**Explicit note on D-04's delete-offer:** this is the ONE new
confirmation surface Phase 9 adds. It is deliberately styled `Warning`
(yellow), **not** `Error`/destructive-red — remote key removal here is
reversible (the same `.pub` can be re-added with one command) and is
never the project's D-09/D-11-class "rewrite an existing directive"
danger tier. It uses a plain default-focused-No confirm (the project's
standard destructive-default-no pattern), **not** a typed-word gate — the
typed-`ConfirmWord` ceremony (`ceremony.go`) is reserved for the Fixer's
local-file rewrite class (Phase 8, `08-UI-SPEC.md`); reusing it here would
overstate the risk of an action a `gh`/`glab` re-add trivially undoes.

## Inherited Non-Negotiables (quick reference for the executor)

Restated for convenience only — NOT decided by this document; each is
cited from its binding source and must not be re-litigated during Phase 9
planning or execution.

- **Upload never gates** (`09-CONTEXT.md` domain statement, D-11):
  create/copy/rotate/clone succeed regardless of upload outcome — every
  failure/degraded state above ends in exit 0 + the manual-fallback block,
  never a blocked flow.
- **Shown command equals run command** (D-02, structural via the shared
  `buildArgs`/`CommandPreview` functions, `internal/uploader/uploader.go`)
  — the `UploadRunningLineFmt` line is never a hand-typed approximation.
- **No prompt, no cancel timer** (D-02) — the section auto-runs and
  auto-advances; the ONLY user-facing toggle is the D-01 checkbox, decided
  BEFORE the section runs, never mid-run.
- **NEVER cross-route tools** (D-11): a GitLab identity never falls back
  to an authenticated `gh`, and vice versa — `omitted`/`manual-fallback`
  is the correct degrade, not silently using the wrong tool.
- **Machine-scoped title matching** (D-07): `gitid: <name> @ <hostname>`
  — matching for dedupe/delete-offer purposes never crosses machines.
- **No persisted upload state** (D-18): every state on this page is
  transient UI, computed fresh each time the section runs or the modal
  opens — never a cached/stale success claim.
- **NO_COLOR legibility**: every row (checkbox, announce, result, D-04's
  offer) must remain fully legible under `NO_COLOR` — glyph + word carries
  the meaning, color is additive only.
- **Copy-freeze grep gate**, extended per this document's DRAFT strings
  once approved — `02-STYLE-SPEC.md` §6.
- **100×30 capture geometry** is kept identical — do not change frame
  dimensions to fit the new rows; resolve overflow (UI Considerations)
  within the existing frame, reusing Phase 7's established scrolling-window
  mechanism if row-count growth triggers it.
- **D-09 backend recipe alignment**: the two-GitHub-registrations /
  one-GitLab-registration shape this whole component exists to automate is
  not a UI invention — it is `recipes/README.md`'s own "one ed25519 key,
  authentication + commit signing" model, read before this document was
  written, per CLAUDE.md's binding instruction.
