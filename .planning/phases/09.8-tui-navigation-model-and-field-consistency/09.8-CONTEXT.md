# Phase 09.8: TUI Navigation Model and Field Consistency - Context

**Gathered:** 2026-09-22
**Status:** Ready for planning

<domain>
## Phase Boundary

One coherent, app-wide keyboard interaction model for the gitid TUI, applied to EVERY screen
(main frame, Identities and all its panes/modals, New-identity wizard, Global SSH, Global Git,
Git Ignore, Doctor, shared confirm/write ceremony, help/palette/quit overlays), plus:

- identical presentation and behavior of each field kind (text, multi-option, checkbox, list) on
  every screen;
- one predictable change → save → confirm pattern with no redundant confirmations;
- the Global Git fallback author `user.name` / `user.email` editable;
- root-cause fixes (not view masks) for default/chosen values that show warnings again after the
  app is reopened;
- the resulting key mappings documented.

Out of scope: new capabilities (new screens, new config keys, new CLI commands). CLI output changes
only where a row state changes meaning (see D-20).

### Why this phase exists (verified evidence, 2026-09-22)

A read-only audit (4 parallel investigations, file:line evidence) established:
- There is NO central keymap: every screen does ad-hoc `msg.String()` matching; the `?` help table
  (`internal/tuikit/app.go:82-94`) and footers are hand-kept copies.
- `←/→` has five meanings (top-level view `app.go:519`, sub-tab `globalssh.go:1247` /
  `globalgit.go:1265`, value cycle, wizard step `identities.go:3808` + step-2 buttons `:4100-4118`,
  text cursor). Global SSH/Git trap the arrows (you can never arrow out).
- Global SSH's option editor is never rendered (no view code for `optionEditor`).
- Global Git fallback author: footer says "Enter edit" (`globalgit.go:2306`) but Enter opens the
  write ceremony or does nothing (`:1394-1403`, `fallbackApplyOffered` `:776-786`); typing goes
  nowhere; the real key `e` is never advertised; `fieldEditing` is dead (never set true; read at
  `:1013`, `:2298`); Enter in pair mode discards `Commit()`; the editor is never reset to nil.
- Changing one value = `e` → `←/→` → Enter (stage) → `a` → Enter (confirm) → Enter (receipt);
  staging calls `withToggled` and un-chooses an already-chosen row; `gitApplyChosen` can list a key
  twice (`globalgit.go:678-685`). Doctor's non-async fix ceremony needs two Enters
  (`ceremony.go:280-282`, `doctor_screen.go:204`).
- Warnings that reappear after reopen (proven with the real binary in a scratch HOME):
  - Git: `internal/globalgit/classify.go:255-264` classifies any value in gitid's OWN managed block
    that differs from `Recommended` as `StateNeedsAction`; `88c37cc` only fixed unset==git-default.
  - SSH: provenance scan reads only `~/.ssh/config` (`internal/globalssh/probe.go:132-141`,
    `hitsFromContent` :234 ignores `Include`), so gitid's own writes in
    `~/.ssh/config.d/gitid.config` are "set outside gitid"; `ssh -G` reports `AddKeysToAgent yes`
    as `true` and `stateFor` compares with `EqualFold` → `StateDiffers`
    (`internal/globalssh/classify.go:136-148`).
  - Both screens hide this in-session with overlays (`globalgit.go:636-641` GitBaselineApplied,
    `globalssh.go:625-640` overlaidOptions forcing `CurrentValue = Recommended`).
  - Fresh HOME without `~/.gitconfig.d`: `gitid git options list` fails
    `chdir .../.gitconfig.d: no such file or directory` (probes chdir into the baseline dir).
- Prior phases claimed done but weren't: 09.6-04's own fail condition (`rg 'm\.fieldEditing'`)
  still matches; 09.6-05 "SUBSTANTIALLY COMPLETE … Task 3 deferred" with no continuation; 09.6
  VERIFICATION flipped to passed without the requested PTY assertion; PTY tests assert only that
  the words "name"/"email" appear. The help/quit overlays tell real-app users "Everything is
  dummy, in-memory data" (`app.go:721-723`, `:744`).

<decisions>
## Implementation Decisions

### Supersessions (explicit — downstream agents must update these contracts, not work around them)
- **D-00:** This phase's keymap SUPERSEDES: Phase 2 checkpoint-2 **D4** (top-level plain-arrow view
  switch — now only on the main menu, not inside screens) and **D7** (Shift+←/→ wizard step chord —
  retired); 09.4 **D-05** (←/→ switches Global SSH sub-tabs — now `[`/`]`); 09.6 CONTEXT
  "`e` opens the editor, Enter commits, Esc dismisses" for option rows (now direct edit on focus).
  `02-STYLE-SPEC.md`, the per-surface `FIELDS.md` files, `09.6-UI-SPEC.md` and the `gate-copy-freeze`
  strings that encode the retired keys must be updated in lockstep, with the supersession cited. —
  **Reversibility:** costly — frozen copy, visual-regression frames and PTY tests encode the old keys.

### App-wide key model (Model A, user-selected)
- **D-01:** ONE central keymap (bubbles `key.Binding` / `help.KeyMap` style) in `internal/tuikit`;
  every screen routes key handling through it; footer and `?` help are GENERATED from it (never
  hand-written copies). — **Reversibility:** costly — every screen's `handleKey` is rewired.
- **D-02:** `1`–`5` jump to top-level views from anywhere, except while a text input has focus
  (digits are text there). On the main menu, arrows move between views as today. `Esc` backs out
  exactly one level: picker → field focus/edit → subview → screen → main menu. Arrow keys inside a
  screen NEVER switch top-level views.
- **D-03:** `[` / `]` = previous / next subview everywhere (Global SSH/Git sub-tabs, wizard steps).
  The sub-tab strip shows the `[ ]` hint.
- **D-04:** `Tab` / `Shift+Tab` = next / previous focusable (fields and buttons); `↑/↓` = move within
  lists and between form fields.
- **D-05:** `←/→` do exactly one thing: change the value of the focused multi-option field (and move
  the caret inside a focused text input). Nothing else.
- **D-06:** `Enter` = activate: open the picker on a multi-option field, press the focused button,
  pick-and-close inside a picker (the pick commits the field value — NO second confirm); on a text
  field, advance to the next field.
- **D-07:** Text fields are MODELESS: a focused text field accepts typing immediately; single-letter
  shortcuts (`q`, `n`, `e`, `a`, `/`, …) are inactive while a text input has focus.
- **D-08:** `Ctrl+S` = save (a visible `[ Save ]` button is equivalent) → ONE diff preview → `Enter`
  confirms. Typed confirmation remains ONLY for destructive rewrites (per quick 260919-jnl). Applies
  to Global SSH, Global Git, Git Ignore (textarea: Enter inserts a newline there; Esc leaves the
  editor; Ctrl+S saves), identity edit panes, and Doctor fixes (Doctor's non-async double-Enter is
  removed). The CLAUDE.md write discipline (preview, timestamped backup, idempotent managed blocks,
  explicit confirmation) is unchanged.
- **D-09:** `?` toggles full help (generated); short help/footer always visible; `q` quits (not in a
  text field); `Ctrl+C` force-quits.

### Option rows: edit & save flow (Global SSH / Global Git)
- **D-10:** Direct edit on focus (replaces 09.6's `e` gesture): focus a row → `←/→` cycle a
  multi-option value, typing edits a text value (`init.defaultBranch`, fallback author name/email),
  `Enter` opens a picker with per-value descriptions (e.g. the zdiff3 version-gate note).
- **D-11:** Batch staging: any changed row is marked pending (visible "modified" marker); `Space`
  toggles "apply the recommended value" on untouched rows; `Ctrl+S` opens ONE diff preview for all
  pending rows → `Enter` → written. There is no separate "stage" step. Fixes the Space/stage
  un-ticking bug and the duplicate key in the apply set.
- **D-12:** After a confirmed write: no receipt page — return to the list with a one-line inline
  status (e.g. "Saved 3 options · backup ~/.gitconfig.d/00-baseline.bak-…", advisories inline) and
  RE-READ the rows from disk. In-memory "applied" overlays that mask real state
  (`GitBaselineApplied`, `SSHApplied`/`overlaidOptions`) are removed: the screen must show exactly
  what reopening the app would show.
- **D-13:** Unsaved pending changes survive switching views (footer shows "N unsaved"); quitting the
  app with unsaved changes asks "Discard N unsaved changes?".

### New-identity wizard
- **D-14:** `Enter` on the last field or `[ Continue ]` = next step; `Esc` = previous step; on step 1
  `Esc` leaves the wizard (asks to discard if anything was typed); `[` / `]` also step back/forward.
  Shift+←/→ is retired (D-00).
- **D-15:** Forward navigation only when the current step is valid, with an inline reason (e.g.
  "needs user.name + a valid email"); backward is always free and keeps entered data.
- **D-16:** Multi-option look, identical everywhere: ≤5 values render as an always-visible radio row
  (`● ed25519  ○ ecdsa  ○ rsa`, keeps the approved D2 look) — including Global SSH/Git option rows;
  longer lists render as `‹ value ›` and `Enter` opens a picker. Same keys in both: `←/→` change,
  `Enter` picker.
- The test-connection step's `Space` "toggle failure demo" must not exist in the real app.

### Row status semantics after reopening
- **D-17:** A value the user deliberately set through gitid that differs from the recommendation
  shows a settled, neutral "set by you" state with a dim "recommended: X" hint — no orange `!`, and
  it is NOT counted as an issue anywhere (Options screens, `gitid git/ssh options list`, Health/Doctor).
- **D-18:** A value set outside gitid (hand-edited `~/.gitconfig` / `~/.ssh/config`) that differs gets
  the same neutral "set by you" treatment with its source shown (file + line where known).
  Equal-meaning OpenSSH synonyms compare equal (`yes`/`true`, `no`/`false`).
- **D-19:** Unset + built-in default differs from the recommendation → orange `!` needs action
  (unchanged). Unset + built-in default equals the recommendation → already set (keeps `88c37cc`).
  The `!` disappears once the user applies OR deliberately chooses a value.
- **D-20:** Fix at the root, shared by TUI, CLI and Doctor so all three agree after a restart:
  the Git classifier's single-member branch (`internal/globalgit/classify.go:255-264`); SSH
  provenance following gitid's own `Include` (home-aware, reusing quick 260922-brh's
  `DetectIncludeForHome`; includes the `hasIncludeLine()` glob-vs-directory mismatch that 260922-brh
  proved makes `gitid ssh storage show` print `include_line false`); SSH synonym normalisation; and
  the fresh-HOME `.gitconfig.d` chdir probe failure. Any new/renamed row state in the versioned JSON
  envelopes (`gitid.git.options/v1`, SSH equivalents) must follow the envelope versioning rules from
  Phase 7 (07-05) — additive or a version bump, never a silent meaning change. — **Reversibility:**
  one-way — published CLI JSON envelope contract.

### Letters, footer, fallback author
- **D-21:** One verb per letter app-wide: `n` new item in this view, `e` edit the selected item,
  `d` delete, `c` copy public key, `a` actions menu (lists every action for the selection, incl.
  clone / register key / upload), `/` filter. `a`-as-apply is removed (replaced by `Ctrl+S`). Letters
  are inactive while a text field has focus (D-07). No letter may mean two different things in
  comparable contexts.
- **D-22:** The footer shows the keys valid for the CURRENT focus, generated from the keymap, ending
  with `? more`; it can never advertise a key that does not work. The "Everything is dummy,
  in-memory data … nothing on your machine is touched" copy is removed from the real app's help and
  quit overlays (it may remain only in the dummy/fixture build).
- **D-23:** Global Git fallback author `user.name` / `user.email` are ordinary text rows: focus →
  type; `Tab` moves between them; saved via `Ctrl+S` like any other pending change. The dead
  `fieldEditing` path is deleted; Enter no longer opens the write ceremony from that row.

### Proof (user-selected: real-binary PTY tests + recorded demos)
- **D-24:** Real-binary PTY tests (compiled gitid, scratch HOME, never the real one): for every
  editable field on every screen, type into it, save with `Ctrl+S`, assert the exact bytes written,
  RESTART the binary, assert the row reads "set by you" with no `!`. Assertions must be
  discriminating (the old tests' "frame contains 'name' and 'email'" style waits are forbidden).
  Plus a keymap conformance test: every screen dispatches through the central keymap, every footer
  binding is actually handled, and no key has two meanings in comparable contexts.
- **D-25:** Recorded demos (asciinema cast and/or GIF via the repo's screenshot/VHS tooling) of each
  flow — identity edit incl. name/email, options change → save → restart showing the settled state,
  full wizard walk, Global Git fallback author edit — stored in the phase directory for review.
- **D-26:** Document the final key mappings in the generated `?` help and a README "Keyboard" section
  (and the updated design specs per D-00).

### Claude's Discretion

  `user.name`/`user.email` (today only via the unadvertised-in-context `g`); whether SSH and Git
  edits become one pane or `e` + an actions-menu entry is a planner/UI-SPEC call, provided name/email
  are reachable via the advertised keys.
- Picker visual design, pending-change marker glyph, exact footer wording, and how `[`/`]` is drawn
  on the sub-tab strip — follow 02-STYLE-SPEC tokens; produce a 09.8-UI-SPEC.md (ONESHOT.md
  Per-Phase Checklist item 2 requires it for a TUI-surface phase).
- Whether `Ctrl+S` on a screen with zero pending changes is a no-op with a hint or disabled in the
  footer.
- Wave structure; the central keymap + conformance test should land first as the contract wave
  (mirrors 09.6-01's contract-first lesson).
