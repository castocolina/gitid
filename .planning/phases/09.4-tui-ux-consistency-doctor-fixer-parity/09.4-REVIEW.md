# Phase 09.4: Code Review Report

**Reviewed:** 2026-09-03T17:20:00Z
**Depth:** standard
**Files Reviewed:** 16
**Status:** issues_found

## Summary

Phase 09.4 merges Health + Fixer into one `Doctor` tab, unifies the Global SSH /
Global Git option-row rendering (bracket toggle column, derived first-row focus,
uniform checkbox column), and wraps Global SSH's local sub-tab strip in a
bordered box. The rename/merge itself is mechanically clean: no `healthModel`,
`fixerModel`, `TabHealth` or `TabFixer` references survive, the copy-freeze
Makefile entries were updated in step with `design.go`, and the visual-regression
allowlist was migrated to the new `doctor-*` screen IDs.

The defects are in behaviour, not naming. Two of them were **reproduced against
the real render stack** (a throwaway driver over `tuikit.NewApp` + the fixture
backend), not inferred:

1. A failed (or empty) Global SSH option probe makes that screen swallow
   **every** key — `1`..`5`, `←/→`, `?`, and `q` — leaving the user unable to
   navigate or quit from the keyboard. This is precisely the fail-open behaviour
   the sibling Global Git screen documents and implements, so it is a direct
   miss against this phase's own "consistency parity" objective.
2. An open write ceremony survives a **mouse** tab switch while `activate()`
   silently clears the selection, so confirming that still-displayed ceremony
   dispatches a commit with an **empty** key set — a confirmed write whose
   payload does not match the previewed diff. In a tool whose contract is
   "nothing is written that was not previewed and confirmed", that is a
   first-order violation.

Two further correctness holes sit in the new merged Doctor screen: the fix
ceremony resolves its write target through a silent "fall back to the first
finding" lookup (so a mid-batch ID change applies a fix the user never
previewed), and the parse-error frame hijacks `view()` while `handleKey()` still
drives fix ceremonies to completion off-screen.

Several new tests assert less than their names claim (the strip-geometry test
explicitly skips the two tightest states; the `RowAccountingIsSingleSourced` test
never pins the render to the constant it is named after; three real-PTY Doctor
assertions match strings that are present in the header of every frame).

## Critical Issues

### CR-01: A failed Global SSH option probe traps the user — every key is swallowed, including `q`

**File:** `internal/tuikit/globalssh.go:550-555` (with `internal/tuikit/globalssh.go:138-143`)
**Issue:** `activate()` stores `m.options = nil` on a probe error; `handleKey`
then hits:

```go
options := m.overlaidOptions(s)
if m.subTab == gssOptions && len(options) == 0 {
    return keyResult{model: m, handled: true}
}
```

`handled: true` short-circuits `App.handleKey` **before** the globals switch
(`app.go:481-511`), so tab keys `1`-`5`, plain `←/→`, `?` and `q` are all
consumed and discarded. Reproduced against the real stack with a Backend whose
`GlobalSSHOptionStates` returns an error — after pressing `2`, every one of
`1`, `3`, `4`, `5`, `right`, `?`, `q` left the breadcrumb on
`Global SSH › Options`. Only `Ctrl+P` (handled earlier) or the mouse escapes.
The zero-row/no-error case (`NoopGlobalSSHPlanner`, the exact substitution the
`WR-17` comments in this same file anticipate) traps identically.

Global Git already fixed this class explicitly — `globalgit.go:537-542`:
"this screen must not consume navigation keys and trap the user here
(07-UI-SPEC.md RESOLVED 'error' row)". Global SSH was never given the same
treatment, and this phase's consistency sweep did not catch it.

**Fix:** mirror the Global Git shape — return unhandled so the globals still
run, and keep only the row-specific keys inert:

```go
options := m.overlaidOptions(s)
if m.subTab == gssOptions && len(options) == 0 {
    // Advisory / fail-open: no rows to act on, but navigation must still
    // reach the globals (tabs, ?, q) — never trap the user on this screen.
    switch key {
    case "left", "right":
        m.subTab = gssStorage
        m.storageChoice = s.SSHStorage
        return keyResult{model: m, handled: true}
    }
    return keyResult{model: m}
}
```

Add a regression test next to `TestGlobalSSHOptionsErrorRendersNoteInsteadOfBlankPane`
(`globalssh_test.go:414`) that presses `1` after the failed probe and asserts the
tab actually changed — the existing test only asserts the rendered note.

### CR-02: An open ceremony outlives a mouse tab switch, and `activate()` empties the selection under it — confirming writes an EMPTY key set

**File:** `internal/tuikit/globalgit.go:116-124` + `internal/tuikit/globalgit.go:495-504`; same shape in `internal/tuikit/globalssh.go:135-152` + `internal/tuikit/globalssh.go:511-517`
**Issue:** `App.handleMouse` routes a header-row click straight to `setTab`
(`app.go:528-536`) with **no** `capturesKeys` guard, so a user can leave a screen
whose ceremony is open (the keyboard cannot, because the ceremony consumes keys).
`globalGitModel.activate` resets `m.chosen = map[string]bool{}` (D-15) but leaves
`m.ceremonyOpen` (and Global SSH's `m.mode`) untouched. `ceremonyConfirmed` then
**recomputes** the key set at confirm time:

```go
keys := m.gitApplyChosen(m.overlaidGitOptions(s))   // now empty
m.applyCommitPending = true
return keyResult{..., cmd: m.backend.CommitGlobalGit(keys)}
```

Reproduced end to end against the real render stack (100x30, fixture backend):
select a row, press `a`, click `[1] Identities` in the header, click `[3] Git`
— the frame still shows the full "Write global-git managed block to
~/.gitconfig.d/00-baseline" preview with its complete `[init]/[core]/[pull]/…`
diff, while `GlobalGitUIState()` reports `chosen = 0`. Pressing Enter moves the
ceremony to `Writing… / Will write → ~/.gitconfig.d/00-baseline` and dispatches
`CommitGlobalGit(nil)`.

Consequences: the confirmed write does not match the previewed diff, the receipt
reports "0 global git options applied", and on the SSH side
`runGlobalSSHApply(nil, …)` (`cmd/gitid/lifecycle.go:802`) rebuilds the managed
`Host *` block from an **empty** explicit overlay — a backed-up but unrequested
rewrite of a block the user may have previously populated.

**Fix:** either (a) close the ceremony on re-activation, or (b) freeze the key
set when the ceremony is built instead of recomputing it at confirm time — both,
ideally:

```go
// activate(): a screen re-entered from scratch must not resume a ceremony
// whose selection this same call just cleared.
m.ceremonyOpen = false
m.applyCommitPending = false
m.fallbackCommitPending = false
m.ceremony = ceremonyModel{}
```

```go
// handleKey, "a": capture the exact previewed set …
m.appliedKeys = chosen
// … and at ceremonyConfirmed dispatch THAT set, never a recomputed one:
return keyResult{model: m, handled: true, cmd: m.backend.CommitGlobalGit(m.appliedKeys)}
```

Additionally consider ignoring header/footer clicks while `sv.capturesKeys` is
true in `App.handleMouse`, so the mouse cannot do what the keyboard is forbidden
from doing.

### CR-03: The Doctor fix ceremony resolves its write target through a silent "first finding" fallback — a mid-batch ID change applies a fix that was never previewed

**File:** `internal/tuikit/doctor_screen.go:154-204` (via `internal/tuikit/doctor.go:89-99`)
**Issue:** the fixing branch resolves the target with

```go
sel, _, ok := selectFinding(ordered, m.selectedID)
```

and `selectFinding` **falls back to `ordered[0]` and returns `ok == true`** when
the ID is absent. On `ceremonyFinished` that `sel` is what builds the dispatched
action and the backup path:

```go
plan := m.backend.FixPlanFor(sel)
action := FixFinding{ID: sel.ID, Backup: NewBackupPath(plan.File)}
```

The batch walk makes this reachable. IDs are content-derived with an occurrence
counter (`cmd/gitid/wiring.go:4991-5005`): two findings sharing
`Family|Title|Identity` become `X` and `X|2`. `F` queues `[X, X|2]`; applying `X`
causes the re-scan to renumber the survivor from `X|2` back to `X`, so
`m.selectedID == "X|2"` no longer exists. The next Enter therefore previews
finding `X|2` on screen while dispatching `FixFinding{ordered[0].ID}` — a
different file, a different backup path, and a receipt naming the wrong fix. The
same happens whenever one fix resolves another queued finding.

**Fix:** in the fixing branch, resolve by exact ID only, and abort loudly rather
than substituting a neighbour:

```go
sel, ok := exactFinding(ordered, m.selectedID) // strict: no ordered[0] fallback
if !ok {
    m.fixing, m.batch = false, nil
    m.batchHalt = "The selected finding is no longer present after the last fix — re-run the scan before continuing."
    return keyResult{model: m, handled: true}
}
```

Keep `selectFinding`'s lenient fallback for list/selection rendering only; never
let it choose a write target.

### CR-04: The parse-error frame hides an active fix ceremony while keys still drive it to a real write

**File:** `internal/tuikit/doctor_screen.go:298-301` vs `internal/tuikit/doctor_screen.go:151-208`
**Issue:** `view()` returns the parse-error screen unconditionally, before any
`m.fixing` check:

```go
func (m doctorModel) view(rawState DemoState, width, height int) screenView {
    if finding, ok := parseErrorFinding(orderedFindings(rawState)); ok {
        return parseErrorScreenView(finding)
    }
```

`handleKey`, however, still accepts `f`/`F` and still walks the ceremony to
`ceremonyFinished`, dispatching `FixFinding` (a real, backed-up write through
`Persist`). With a critical `Files` parse error present and any other fixable
finding in the scan, the sequence `F`, Enter, Enter mutates the user's config
with **no preview, no confirm affordance and no receipt ever rendered** — the
screen shows only "Checks paused until this configuration parses again." This
directly contradicts the project's write contract (CLAUDE.md: preview →
confirm + backup → re-test) and the ceremony's own reason for existing.

**Fix:** make the parse-error frame either render the ceremony or refuse the
keys — refusing is simpler and matches "checks paused":

```go
func (m doctorModel) handleKey(msg tea.KeyMsg, rawState DemoState) keyResult {
    if _, halted := parseErrorFinding(orderedFindings(rawState)); halted {
        // Checks are paused: no fix may be opened or confirmed from this frame.
        return keyResult{model: m}
    }
    ...
```

## Warnings

### WR-01: Sub-tab strip click hit-test is off by one column, uses byte length, and hardcodes the label row

**File:** `internal/tuikit/globalssh.go:679-705` (render at `internal/tuikit/globalssh.go:631-649`)
**Issue:** the render builds `labelLine = "┊ " + (" " + options + " " + storage) + " ┊"`,
so the `" Options "` span starts at column **3**, not 2. The hit-test uses
`labelStartX := 2`, shifting both spans one column left: a click on column 12
(the blank gap *between* the labels) activates Storage, and the last cell of each
label is inert. The spans are also computed with `len(...)` (bytes) rather than
`ansi.StringWidth`, and the label row is hardcoded as `if y == 1` instead of
being derived from `gssSubTabStripRows()`. All three contradict this file's own
header comment ("handleClick hit-tests against the same strings, so the spans can
never drift", `globalssh.go:43-49`) and the phase's single-source-of-truth claim.
`TestSubTabStripClickSwitchesSubTabs` and the PTY click tests all target the
*first* character of each label, so the shift is invisible to them.

**Fix:** derive the spans from the rendered line the same way every other click
zone in this codebase does:

```go
if y == stripRows/2 { // the label row, derived — not a literal
    body := m.view(s, width, height).body
    switch {
    case hitNeedle(body, x, y, gssTabOptionsLabel):
        m.subTab = gssOptions
        return keyResult{model: m, handled: true}
    case hitNeedle(body, x, y, gssTabStorageLabel):
        m.subTab = gssStorage
        m.storageChoice = s.SSHStorage
        return keyResult{model: m, handled: true}
    }
}
```

### WR-02: The bordered strip spends 2 of the ceremony's ~4 spare body rows; the geometry test explicitly skips the two tightest states

**File:** `internal/tuikit/globalssh.go:626-628`, `internal/tuikit/globalssh.go:902`; test at `internal/tuikit/globalssh_test.go:1463-1552`
**Issue:** both ceremony modes render `m.subTabStrip() + "\n" + m.ceremony.view(width-2)`,
so the ceremony now starts 3 rows down instead of 1. Measured at the canonical
100x30 geometry with the fixture backend: the apply ceremony ends its
`Cancel (Esc) / Apply selected (Enter)` row on body row 22 of 25 — **2 rows of
headroom**. `ceremony.view` wraps `Touches …` to the pane width and emits one
`Backup → ` row per target (the storage ceremony has two targets, and the Phase 6
captured frame already shows two backup rows), so one extra wrapped `Touches`
line plus a second backup line consumes the entire remaining margin; anything
beyond that is silently cut by `RenderFrame` (`frame.go:439-442`), taking the
confirm/cancel row with it.

`TestSubTabStripFitsFixedGeometryInEveryStripState` measures four browse states
and then states: *"State 5 … The apply and storage ceremonies prefix the strip
too, but they render the ceremony body which is already tested for overflow
separately."* Those separate tests predate the +2 rows and do not account for
them, so the one test named "in every strip state" skips exactly the two states
the change put at risk.

**Fix:** add the two ceremony states to that test (build the ceremony with a
long, wrapping target list and two backups, then assert
`strings.Contains(lastRenderedBodyLine…, "(Enter)")`), and either drop the strip
from the ceremony body or shrink `PreviewMaxLines` by the strip's cost while a
ceremony is open.

### WR-03: `doctorBatch` is a shared pointer mutated in place, so the "pre-dispatch snapshot" is not a snapshot

**File:** `internal/tuikit/doctor_screen.go:181-190`; consumer at `internal/tuikit/app.go:313-331`
**Issue:** `doctorModel` is copied by value, but `batch *doctorBatch` is a
pointer. `queue := m.batch.queue[:0]` filters in place over the shared backing
array and then `m.batch.queue = queue` mutates the struct the *pre-dispatch*
model (`prevScreen` in `checkFixBatchHalt`) also points at. `haltBatch`'s doc
comment claims the snapshot "still correctly names … the batch state exactly as
it stood right before the doomed dispatch" — for `batch.queue` that is false; it
survives only because `haltBatch` happens to read `total` and
`len(batchSucceeded)` and never the queue. Any future halt message that reports
remaining work will silently be wrong.

**Fix:** copy on write, like every other model field in this package:

```go
queue := make([]string, 0, len(m.batch.queue))
for _, id := range m.batch.queue {
    if id != sel.ID {
        queue = append(queue, id)
    }
}
next := *m.batch      // value copy — the snapshot keeps the old one
next.queue = queue
m.batch = &next
```

### WR-04: The batch walk can leave a stale ceremony on screen when the next queued finding is missing

**File:** `internal/tuikit/doctor_screen.go:191-198`
**Issue:**

```go
m.selectedID = queue[0]
for _, f := range ordered {
    if f.ID == queue[0] {
        m.ceremony = fixCeremonyFor(m.backend, f)
    }
}
return keyResult{model: m, handled: true, ...}
```

There is no `else` and no post-loop check: if `queue[0]` is not in `ordered`,
`m.ceremony` remains the just-finished ceremony (already in its `done` receipt
state) while `m.fixing` stays true. Combined with CR-03's lenient
`selectFinding`, the next Enter confirms a receipt belonging to fix *N* and
dispatches fix *ordered[0]*.

**Fix:** treat "next finding not found" as an explicit halt (see CR-03's fix) and
`break` out of the loop once the ceremony is built.

### WR-05: Doctor status tone renders `warning` (yellow) for error and critical findings

**File:** `internal/tuikit/doctor_screen.go:319-324`
**Issue:**

```go
tone := "info"
for _, f := range ordered {
    if f.Severity != SeverityInfo {
        tone = "warning"
    }
}
```

`SeverityError` and `SeverityCritical` are locked to red everywhere else in this
codebase (`frame.go:196-207`, `design.go:563-573`: "error AND critical both use
`✗` (red)"). The merged tab's own status line downgrades them to yellow, so the
one always-visible summary line contradicts the severity contract the tab exists
to communicate.

**Fix:**

```go
tone := "info"
for _, f := range ordered {
    switch f.Severity {
    case SeverityError, SeverityCritical:
        tone = "error"
    case SeverityWarning:
        if tone == "info" {
            tone = "warning"
        }
    }
}
```

### WR-06: The header region anchor leaves the last nav tab inside the allowlisted `header-status` region

**File:** `internal/screenshot/createflow_regions.go:529-561` and `internal/screenshot/createflow_regions.go:792-819`
**Issue:** `headerNavAnchor = "Doctor "` is the **second-to-last** nav label, and
both extractors split the header there. `RegionHeader` (the byte-compared,
non-allowlisted chrome region) therefore stops after `[4] Doctor`, and
`[5] Ignore` falls inside `RegionHeaderStatus`, which every registry
allowlists as a fixture-vs-live divergence (`contains:"ids"`). A regression in
the fifth nav tab's label, spacing or styling cannot fail the gate. The comment
frames this as preserving "one trailing nav segment plus the chip" for existing
allowlists — the previous anchor (`"Fixer "`) had the same hole, so this is a
carried-forward gap, not a new one, but the merge was the natural moment to
close it.

Secondary: `extractHeaderStatus` now `panic`s when no status follows the anchor
(`:812`), which converts a narrow-frame capture into a stack trace instead of a
named test failure.

**Fix:** anchor on the LAST nav label (`tabNavLabels[len-1]`, i.e. `"Ignore "`)
so every nav segment stays inside the byte-compared `RegionHeader`, and export
the label list from `internal/tuikit` (or derive the anchor from
`headerTabText`) so the anchor cannot go stale on the next tab change. Replace
the panics with `return header` plus a clear region-empty failure at the call
site.

### WR-07: Three of the new strip/Doctor tests assert less than their names claim

**File:** `internal/tuikit/globalssh_test.go:1382-1436`, `internal/tuikit/globalssh_test.go:1562-1600`, `e2e/doctor_pty_e2e_test.go:118-137`
**Issue:**
- `TestSubTabStripRowAccountingIsSingleSourced` never compares the rendered strip
  height against `gssSubTabStripRows()`. It asserts `gssOptionsTopLines(a.state)
  >= gssSubTabStripRows()` — but `gssOptionsTopLines` *is* implemented as
  `gssSubTabStripRows() + banner`, so the assertion is a tautology. Changing
  `gssSubTabStripRows()` to 5 while the render still draws 3 rows (the exact
  drift the "single source" naming promises to catch) leaves this test green.
- `TestSubTabStripRendersBordered`'s "active label should still be marked" check
  is `strings.Contains(line, "Options")`, which is true whether or not
  `styleReverse` was applied — it cannot detect losing the active-tab marker.
- `TestDoctor_RealPTYFindingsInlineDetailAndIdentity` asserts `mustSee(t, s,
  "SSH", …)`, `mustSee(t, s, "Git", …)` and `mustSee(t, s, "[", …)`. All three
  strings are present in the nav header (`[2] SSH · [3] Git`) of **every** frame
  the app ever draws, so they prove nothing about the findings list or the
  detail pane.

**Fix:** compare the actual rendered strip height
(`indexOfFirstLineContaining(body, "╰") + 1 == gssSubTabStripRows()`); assert the
active label carries `styleReverse.Render(gssTabOptionsLabel)`; and replace the
PTY needles with list-scoped ones (e.g. `optionListLine(frame, "SSH · global")`
or the group-label text) rather than substrings the header guarantees.

### WR-08: New PTY tests diverge from the established sandbox-home helper and send empty keystrokes

**File:** `e2e/global_ssh_pty_e2e_test.go:416`, `e2e/global_ssh_pty_e2e_test.go:433`, `e2e/global_ssh_pty_e2e_test.go:450`, `e2e/global_ssh_storage_pty_e2e_test.go:601`, `e2e/global_ssh_storage_pty_e2e_test.go:613`
**Issue:** `TestGlobalSSH_RealPTYSubTabStripMouseClick` uses `home := t.TempDir()`
while every sibling test in the same file uses `ShortSandboxHome(t)`. On macOS
`t.TempDir()` yields a long `/var/folders/…` path — the exact class of long-HOME
wrapping this codebase already documents as breaking frame assertions
(`createflow_regions.go:1096-1102`), so this test is one rendering change away
from path-length-dependent flakiness. The same tests also call
`s.sendKey([]byte(""), keystrokeDelay)` four times: sending zero bytes is a
no-op and reads as an accidental leftover.

**Fix:** use `ShortSandboxHome(t)` for consistency with every other test in the
file, and delete the empty `sendKey` calls (if the intent was "let the frame
settle", the following `s.waitFor` already does that).

### WR-09: Global SSH's option list has no scroll window and just lost 2 rows of budget

**File:** `internal/tuikit/globalssh.go:709-724`, `internal/tuikit/globalssh.go:940-993`
**Issue:** unlike Global Git (which grew `gitComputeScrollWindow` /
`gitRowForScreenRow` precisely for this), Global SSH renders every option row
unconditionally and hit-tests clicks with plain arithmetic
(`row := (y - gssOptionsTopLines(s)) / optionRowLines`) with only a
`row >= len(options)` guard. With the bordered strip the usable budget is now
`25 - 3 - banner` rows, i.e. at most 11 two-line rows. The current policy table
has 6 rows so nothing clips today, but a 12-row table (Global Git already has 12)
would be silently truncated by `RenderFrame`, and clicks below the fold would
still resolve to rows that were never drawn — the exact drift class Global Git's
scroll-window plan was written to prevent.

**Fix:** either reuse the Global Git scroll-window helpers here (they are already
generic over row count and `optionRowLines`), or at minimum clamp the click row
against the number of rows the current budget actually renders, and add a
`+N more` cue when the list exceeds it.
