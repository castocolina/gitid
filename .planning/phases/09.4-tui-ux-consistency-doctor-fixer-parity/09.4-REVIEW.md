## Critical Issues

### CR-01: A stale commit-result message from an abandoned ceremony is misattributed to a newer, unrelated ceremony that is genuinely still in flight

**File:** `internal/tuikit/globalgit.go:222-284` (`handleMsg`, `GlobalGitCommitMsg` and
`GitFallbackAuthorCommitMsg` branches); `internal/tuikit/globalssh.go:209-306` (`handleMsg`,
`GlobalSSHCommitMsg` and `SSHStorageCommitMsg` branches) — the identical shape is present in all
four handlers.

**Issue:** BL-04's fix (previous round) correctly stopped dropping a completed write's reducer
action when the ceremony that started it had been abandoned via `Ctrl+P` + `activate()`. It did
this by computing a **local** `ceremonyOpen := m.ceremonyOpen && m.applyCommitPending` and gating
only the ceremony-UI mutation on it, while unconditionally dispatching the reducer action/note.
This closes the originally-reported case (commit lands, screen was abandoned, nothing else
happened in between).

It does **not** close the case where, between confirming the first ceremony and its message
arriving, the user abandons (`Ctrl+P` → back — `activate()` resets `ceremonyOpen`/
`applyCommitPending`/`fallbackCommitPending`/`m.ceremony` unconditionally, per CR-02/WR-01) and
then opens **and confirms a second, different** ceremony of the *same kind* before the first
message arrives. Because `applyCommitPending` (or `fallbackCommitPending`/`storageCommitPending`)
is a single boolean with no per-request token, and `m.ceremony`/`m.appliedKeys` are single fields
holding only the SECOND ceremony's data, the stale first message is indistinguishable from the
second one's own result:

```go
// globalgit.go
if commit, ok := msg.(GlobalGitCommitMsg); ok {
    ceremonyOpen := m.ceremonyOpen && m.applyCommitPending
    if ceremonyOpen {
        m.applyCommitPending = false
    }
    ...
    if ceremonyOpen {
        m.ceremony = m.ceremony.commitSucceeded(commit.Backups)   // wrong receipt: 2nd ceremony's UI,
                                                                    // 1st ceremony's backups/keys
    }
    return keyResult{model: m, note: ..., actions: []Action{ApplyGitBaseline{Backup: firstBackup(commit.Backups)}}}
}
```

Reproduced directly (throwaway probe against `globalGitModel`, removed after verification —
`git status` confirms no tracked file changed):

1. Select `init.defaultBranch`, press `a`, press `enter` — ceremony 1 confirmed,
   `applyCommitPending=true`, `CommitGlobalGit(["init.defaultBranch"])` dispatched (message not
   yet delivered — this mirrors a real async backend command).
2. Call `activate()` (the `Ctrl+P`-then-back round trip) — confirms `ceremonyOpen=false`,
   `applyCommitPending=false`.
3. Select `diff.colorMoved` instead, press `a`, press `enter` — ceremony 2 confirmed,
   `applyCommitPending=true`, `CommitGlobalGit(["diff.colorMoved"])` dispatched.
4. Deliver ceremony **1's** stale `GlobalGitCommitMsg` (backup path `backup-init.defaultBranch`)
   into `handleMsg` while ceremony 2 is the one on screen.

Result: `applyCommitPending` becomes `false` even though ceremony 2's own commit has not
returned yet, `m.ceremony` (still displaying ceremony 2's heading/targets) is driven to
`commitSucceeded` using **ceremony 1's** backup path, and `ApplyGitBaseline{Backup:
"backup-init.defaultBranch"}` is dispatched — a backup path that has nothing to do with the
`diff.colorMoved` write the user is actually looking at. When ceremony 2's genuine message
arrives afterward, `applyCommitPending` is already `false`, so it is now treated as "abandoned":
its reducer action fires (correctly, on its own — this doubles the `"N global git option(s)
applied."` note, once for each message) but the ceremony UI is **never** updated with the real
result — the receipt stays permanently stuck showing the wrong backup for a write that already
finished.

This is not hypothetical UI cosmetics: `firstBackup(commit.Backups)` is exactly what the app's
own restore/audit story keys off, and this project's CLAUDE.md is explicit that the write path
is "test → confirm + backup → re-test" with no tolerance for the confirmation UI showing a
different write than the one that happened. The same shape (single pending flag, single
`m.ceremony`/`m.storageTargetLayout` field, no request correlation) is present unmodified in
`globalssh.go`'s `GlobalSSHCommitMsg` and `SSHStorageCommitMsg` branches — confirmed by direct
code comparison; the reproduction above was run for the Global Git baseline path only, since the
mechanism is identical.

**Fix:** give each dispatched commit a monotonically-incrementing request token captured at
confirm time (mirroring the stale-guard idiom this same file set already uses elsewhere —
`internal/tuikit/identities.go`'s `run.Name == m.selected` / `commit.Name == m.selected` guards
on `UploadRunMsg`/`RotateDeleteCommitMsg`), and compare it in `handleMsg` before touching
`m.ceremony`:

```go
type globalGitModel struct {
    ...
    applyRequestToken int
}
// on confirm:
m.applyRequestToken++
token := m.applyRequestToken
return keyResult{model: m, handled: true, cmd: tea.Sequence(m.backend.CommitGlobalGit(keys),
    func() tea.Msg { return nil })} // or thread token through a wrapper Msg / closure
// in handleMsg:
ceremonyOpen := m.ceremonyOpen && m.applyCommitPending && commit.Token == m.applyRequestToken
```
Simplest concrete shape: change `GlobalGitCommitMsg`/`GitFallbackAuthorCommitMsg`/
`GlobalSSHCommitMsg`/`SSHStorageCommitMsg` to carry the token the backend command closure
captured, or wrap the `tea.Cmd` returned from `CommitGlobalGit`/etc. in a closure that stamps the
token onto the message before returning it from the screen's own confirm handler. Only clear
`applyCommitPending`/mutate `m.ceremony` when the token matches; otherwise still dispatch the
reducer action/note (BL-04's fix), but never touch the currently-displayed ceremony.

## Warnings

### WR-01: An abandoned ceremony's write that later fails produces zero user-visible feedback anywhere

**File:** `internal/tuikit/globalgit.go:227-236`, `:258-267`; `internal/tuikit/globalssh.go:264-277`,
`:295-306`

**Issue:** When `ceremonyOpen` (the local, BL-04-introduced variable) is `false` and
`commit.Err != ""`, all four commit-message handlers return `keyResult{model: m}` with no `note`
and no `actions`. This is not new behavior — the pre-BL-04 code dropped the whole branch on
abandonment too — but BL-04's fix specifically re-examined this exact code path and left this half
of it unaddressed: a background write that fails (including one whose restore-on-mismatch path
itself reports a problem, per `commit.Restored`) after the user has navigated away is now
completely silent. There is no toast, no persisted note, no badge — the user only discovers
anything went wrong by revisiting the screen and noticing the probe still shows the pre-write
state (or, worse, does not notice at all if the write partially applied). Given CLAUDE.md's
emphasis on the write path being auditable and confirmed, a failed write should surface
*somewhere* even when its ceremony is gone — at minimum via `App.note` (the field the successful
path already reaches through `keyResult.note`, just conditioned on `ceremonyOpen` above).

**Fix:** dispatch a `note` (e.g. `"Background write failed: " + commit.Err`) unconditionally on
`commit.Err != ""`, the same way the success path's `note`/`actions` are now dispatched
unconditionally by BL-04's fix — restoring the safety property that a write outcome is never
silently lost regardless of what the ceremony UI happened to be doing when the result arrived.

### WR-02: `gitVisibleRowCount`/`gssVisibleRowCount`'s new `height` parameter has no defensive floor against a persisted `lastHeight` from a stale, pre-shrink resize

**File:** `internal/tuikit/globalgit.go:198-207`, `:758-778`; `internal/tuikit/globalssh.go:212-221`

**Issue:** `rowBudgetHeight()` returns `m.lastHeight` whenever it is `> 0`, with no upper/lower
sanity check against the canonical frame bounds. `app.go`'s own too-small guard
(`a.width < minFrameWidth || a.height < minFrameHeight`) prevents `handleMouse` from running
below the minimum frame, but `tea.WindowSizeMsg` is still forwarded to every screen's `handleMsg`
unconditionally before that guard is ever consulted (`app.go:338-360`), so `m.lastHeight` can be
set to a value below `minFrameHeight` (e.g. during a terminal resize transient, or a host that
briefly reports `Height: 1` mid-resize) and then `rowBudgetHeight()` faithfully returns it.
`gitVisibleRowCount`/`gssVisibleRowCount` already clamp their own internal `budget` to a floor of
1, so this does not crash, but it does mean the scroll window's row budget can transiently collapse
to a single row (or a negative-turned-1 budget) independent of whatever `view()`'s own
`width, height` render arguments are doing — a divergence between the budget `handleKey`'s
`scrollWindowFor` advances by and the budget `view()` actually has room to draw, for exactly one
frame, whenever a too-small resize transient is delivered. This is the same "measured budget must
never disagree between handleKey and view" property WR-10's own doc comments call out as the
whole point of the fix; a floor at `minFrameHeight` closes the last gap.

**Fix:** clamp in `rowBudgetHeight()` itself:
```go
func (m globalGitModel) rowBudgetHeight() int {
    if m.lastHeight >= minFrameHeight {
        return m.lastHeight
    }
    return minFrameHeight
}
```
