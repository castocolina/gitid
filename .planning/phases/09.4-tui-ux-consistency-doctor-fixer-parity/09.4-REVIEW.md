## Warnings

### WR-01 (this round): `m.currentName`/`m.currentEmail` are now gated on `ceremonyOpen`, introducing an untested staleness window for the genuinely-abandoned (no-supersede) fallback-success case

**File:** `internal/tuikit/globalgit.go:367-371`

**Issue:** Prior to this commit, the fallback-author success branch
unconditionally set `m.currentName = m.pendingFallbackName` /
`m.currentEmail = m.pendingFallbackEmail` regardless of `ceremonyOpen`. This
commit's fix correctly changes the SOURCE (snapshot instead of the mutable
field, per CR-01/round-3's fix guidance) but ALSO newly gates the assignment
behind `if ceremonyOpen`:

```go
name, email := snapshot.name, snapshot.email
if ceremonyOpen {
    m.currentName = name
    m.currentEmail = email
}
```

Round 3's fix guidance (09.4-REVIEW.md, CR-01 "Fix" section) only asked for
the snapshot source change ("`m.currentName`/`m.currentEmail` in the
fallback branch should be set from the same snapshot, not from
`m.pendingFallbackName`/`Email`") — it did not ask for this additional
`ceremonyOpen` gate, and no test in this round's diff exercises it.

This is safe in the "superseded by a newer ceremony" case (not updating
`m.currentName` to a stale value while a different ceremony's UI is
genuinely open is the more correct choice, matching the same reasoning
already applied to `m.ceremony.commitSucceeded(...)`). But it introduces a
new, narrower staleness window in the "genuinely abandoned, nothing
superseded it" case: user confirms the fallback ceremony, Ctrl+P away and
back (CR-02's `activate()` resets `ceremonyOpen`/`fallbackCommitPending` and
re-seeds `m.currentName`/`Email` from the backend's PRE-write state, since
the write hasn't landed yet), then the write's success message finally
arrives with `ceremonyOpen == false` (no new fallback ceremony was opened).
Before this commit, `m.currentName`/`Email` would still get patched to the
just-landed values right away; after this commit, they will not — leaving
`fallbackApplyOffered()`'s "removal case" check (`globalgit.go:553`,
`return m.currentName != "" || m.currentEmail != ""`) reflecting stale
pre-write data until the user leaves and re-enters the Global Git screen
again (triggering a fresh `activate()`).

This is bounded and self-healing (one more screen re-entry corrects it), and
the actually-dispatched reducer Action (`ApplyGitGlobalEmail{Email: email,
Name: name, ...}`) is UNAFFECTED by this gate — `App.state.GitGlobalName`/
`GitGlobalEmail` and the master-list's fallback-row display (which reads
`s.GitGlobalName`/`s.GitGlobalEmail` from `DemoState`, not `m.currentName`)
are correctly updated regardless. So this is a screen-local UI nicety
regression, not a data-correctness regression — WARNING, not Critical.

**Fix:** Either revert to the unconditional assignment (matching round 3's
literal fix guidance — the snapshot source alone already fixes the
misattribution CR-01 was about, since `snapshot.name`/`email` are correct
regardless of `ceremonyOpen`):

```go
name, email := snapshot.name, snapshot.email
m.currentName = name
m.currentEmail = email
```

or, if the gate is intentional (to avoid visibly mutating state for a
ceremony the user can no longer see), add a regression test asserting
`m.currentName`/`m.currentEmail` DO update after a genuinely-abandoned
(no-supersede) fallback success, and document the intentional trade-off in
the doc comment so a future reader doesn't mistake it for an oversight.
