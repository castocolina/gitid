# Phase 09.4: Code Review Report (third independent re-review)

## Summary

This is a third independent re-review of commit `7c7dcd2` (`git log aaeb48c..HEAD`),
which claims to fix round 2's CR-01, WR-01, and WR-02. Each was independently
re-verified against the current code, not the commit message:

- **WR-01** (background-write-failure note for an abandoned/stale commit) —
  **CONFIRMED FIXED.** `handleMsg`'s failure branches in both files now return
  `note: "Background write failed: " + commit.Err"` when `ceremonyOpen` is
  false (`globalgit.go:290-295,325-327`; `globalssh.go:281-283,322`).
- **WR-02** (`rowBudgetHeight` floored at `minFrameHeight`) — **CONFIRMED
  FIXED.** Both `rowBudgetHeight()` implementations now use `>= minFrameHeight`
  instead of `> 0` (`globalgit.go:217-230`; `globalssh.go:223-231`), verified
  against `TestGitRowBudgetHeightFloorsAtMinFrameHeight` /
  `TestSSHRowBudgetHeightFloorsAtMinFrameHeight`.
- **CR-01** (stale-message-to-newer-ceremony misattribution) — **ONLY
  PARTIALLY FIXED.** The new `commitRequestToken` / `gitCommitTokenMsg`
  mechanism correctly prevents a stale message from touching the *ceremony
  UI* of a newer, genuinely in-flight ceremony of the same kind — that part
  of the original finding is resolved and is exercised correctly by all four
  dispatch sites (Global Git baseline, Global Git fallback, Global SSH apply,
  Global SSH storage) and all four `handleMsg` branches. However, the
  **reducer `Action` that the stale message unconditionally dispatches (kept
  unconditional on purpose, per BL-04) still reads mutable model fields
  (`m.appliedKeys`, `m.pendingFallbackName`/`m.pendingFallbackEmail`,
  `m.storageTargetLayout`) that get silently overwritten by the newer
  ceremony's own confirm before the stale message arrives.** The result:
  a stale-but-genuinely-succeeded write can commit the *wrong* values —
  including a different SSH option-key set, a different fallback
  name/email pair, or a different SSH storage layout — into `App.state`,
  attributed to a commit that never actually wrote them. This is the exact
  defect family (write/confirm-path misattribution) this whole review round
  targeted, and it survived the round-2 fix. See CR-01 below for the full
  reproduction and code citations.

Both of this round's own new regression tests
(`TestGitStaleCommitMsgNotMisattributedToNewerCeremony`,
`TestSSHStaleCommitMsgNotMisattributedToNewerCeremony`) only assert
`len(result.actions) == 1` — they never assert on the *contents* of that
action — so they pass despite exercising exactly the scenario that triggers
the gap. See WR-01 (this round) for that test-coverage weakness.

No new defects were found in the mechanical parts of the change itself: all
four `Commit*` dispatch sites wrap their `tea.Cmd` with `wrapGitCommitToken`,
all four `handleMsg` branches unwrap and compare the token before touching
ceremony UI, `wrapGitCommitToken` nil-guards its `cmd` argument, and the
token is a per-model monotonic counter that is never reset on `activate()`
re-entry (which is required for the whole scheme to work). The ~10 test
call sites that had to move to the wrapper were checked one by one; nine of
them correctly deliver the wrapped `gitCommitTokenMsg` (or construct one
with a matching token) end-to-end, and the one that still delivers a bare,
unwrapped `GlobalGitCommitMsg` (`globalgit_test.go:454`) happens to still
pass only because the reducer-dispatch is unconditional — it is a
pre-existing test that predates this round's wrapper and was not updated;
noted below as IN-01.

## Critical Issues

### CR-01: Stale commit message can attribute a NEWER ceremony's values to an OLDER, unrelated commit's success

**File:** `internal/tuikit/globalgit.go:296-310`, `internal/tuikit/globalgit.go:328-343`, `internal/tuikit/globalssh.go:296-304`, `internal/tuikit/globalssh.go:324-352`

**Issue:** The round-2 fix (CR-01, previous cycle) added `commitRequestToken`
and `gitCommitTokenMsg` specifically to stop a stale message from an
abandoned ceremony from being misattributed to a newer ceremony of the same
kind. The token comparison (`token == m.commitRequestToken`) correctly gates
the **ceremony-UI mutation** (`m.ceremony = m.ceremony.commitSucceeded(...)`),
but per BL-04 (kept intentionally, and documented as such in
`globalgit.go:75-89`) the **reducer `Action` and `note` still dispatch
unconditionally**, regardless of whether the token matched. That unconditional
dispatch reads the model's mutable "pending capture" fields —
`m.appliedKeys` (globalgit.go, globalssh.go), `m.pendingFallbackName` /
`m.pendingFallbackEmail` (globalgit.go), and `m.storageTargetLayout`
(globalssh.go) — which are **not snapshotted per request/token**. They are
plain model fields that get overwritten every time `ceremonyConfirmed` fires
for that same ceremony kind again, which — via the documented Ctrl+P
bypass (`CR-02`) — can legitimately happen while an earlier commit of the
same kind is still in flight.

Concrete reproduction (Global SSH apply, mirrors the fallback-author and
storage-migration cases identically):

1. User selects `HashKnownHosts`, opens the apply ceremony, confirms.
   `m.commitRequestToken` becomes `1`; `m.appliedKeys = ["HashKnownHosts"]`;
   `CommitGlobalSSH(["HashKnownHosts"])`'s `tea.Cmd` is dispatched, wrapped
   with token `1`. The backend call has not resolved yet (real I/O, or any
   delayed `tea.Cmd`).
2. User presses Ctrl+P and returns to the Global SSH screen. `activate()`
   resets `mode`, `applyCommitPending`, and `ceremony` — but **not**
   `commitRequestToken` (by design) and **not** `appliedKeys` (there is no
   code path that resets it — confirmed by `grep`).
3. User selects a *different* option, `StrictHostKeyChecking`, opens a new
   apply ceremony, confirms. `m.commitRequestToken` becomes `2`;
   `m.appliedKeys` is **overwritten** to `["StrictHostKeyChecking"]`;
   `CommitGlobalSSH(["StrictHostKeyChecking"])` dispatches, wrapped with
   token `2`. This second commit is genuinely still in flight.
4. The **first** commit (`HashKnownHosts`, token `1`) now succeeds and its
   message arrives. `handleMsg` correctly computes
   `ceremonyOpen := ... && token(1) == m.commitRequestToken(2)` → `false`,
   so the ceremony-2 UI is correctly left untouched. But the function still
   falls through, unconditionally, to:
   ```go
   return keyResult{
       model:   m,
       note:    fmt.Sprintf("%d global SSH option%s applied.", len(m.appliedKeys), plural),
       actions: []Action{ApplySSH{Keys: m.appliedKeys, Backup: firstBackup(commit.Backups)}},
   }
   ```
   `m.appliedKeys` is now `["StrictHostKeyChecking"]` — ceremony 2's keys,
   not ceremony 1's. `store.go`'s `ApplySSH` reducer
   (`store.go:441-452`) appends `a.Keys` directly to `next.SSHApplied`.
   The result: **`StrictHostKeyChecking` gets marked "Applied" in
   `App.state` on the strength of the `HashKnownHosts` commit's success** —
   even though `StrictHostKeyChecking`'s own commit (ceremony 2) has not
   resolved yet, and may later fail outright. Meanwhile `HashKnownHosts`,
   whose write actually did succeed, is never recorded as applied at all.

The identical pattern applies to:
- **Global Git fallback author** (`globalgit.go:328-343`): a stale
  `GitFallbackAuthorCommitMsg` success dispatches
  `ApplyGitGlobalEmail{Email: m.pendingFallbackEmail, Name: m.pendingFallbackName, ...}`
  and sets `m.currentName`/`m.currentEmail` — both read fresh from the
  model at delivery time, so a second, newer fallback ceremony confirmed in
  the interim overwrites `pendingFallbackName`/`pendingFallbackEmail` before
  the first one's message lands. `store.go`'s `ApplyGitGlobalEmail` reducer
  directly assigns `next.GitGlobalName = a.Name` / `next.GitGlobalEmail = a.Email`
  — the user's global git identity can silently end up set to a name/email
  pair that was never actually the subject of the commit that "succeeded".
- **Global SSH storage migration** (`globalssh.go:324-352`): `layout :=
  m.storageTargetLayout` is read at delivery time, so a stale storage-commit
  success can dispatch `SetSSHStorage{Layout: layout}` for whatever layout
  the *next* (still in-flight, or since-failed) migration targeted, not the
  layout the stale commit itself actually wrote. `next.SSHStorage = a.Layout`
  directly overwrites the app's notion of "which layout is on disk".

This round's own new regression tests exercise exactly this reproduction
(`TestGitStaleCommitMsgNotMisattributedToNewerCeremony`,
`TestSSHStaleCommitMsgNotMisattributedToNewerCeremony`) but only assert
`len(result.actions) != 1` / `== 1` — never the *value* carried by that
action — so neither test can catch the misattribution. In the SSH test,
substituting `Keys: []string{"HashKnownHosts"}` for the mock-asserted count
would fail today.

**Fix:** Stop reading the "what was submitted" values from mutable model
fields at delivery time. Snapshot them per request instead, correlated by
the same token that already exists — e.g. extend the wrapper (or add a
`map[int]<snapshot>` on the model, cleared as each token is consumed) so
`handleMsg` reads the value the STALE message's own ceremony actually
submitted, not whatever the model currently holds:

```go
type gitCommitTokenMsg struct {
    token int
    msg   tea.Msg
    // snapshot is the exact payload submitted at THIS request's confirm
    // time (keys / name+email / layout) — read back here instead of
    // m.appliedKeys / m.pendingFallback* / m.storageTargetLayout, which
    // get overwritten by any later same-kind ceremony confirmed before
    // this message is delivered.
    keys   []string
    name   string
    email  string
    layout SSHStorageLayout
}
```

and thread `wrapped.keys` / `wrapped.name` / `wrapped.email` /
`wrapped.layout` through to the `Action` construction in all four
`handleMsg` branches instead of `m.appliedKeys` / `m.pendingFallbackName`
/ `m.pendingFallbackEmail` / `m.storageTargetLayout`. `m.currentName` /
`m.currentEmail` in the fallback branch should be set from the same
snapshot, not from `m.pendingFallbackName`/`Email`.

## Warnings

### WR-01 (this round): New CR-01 regression tests don't assert action contents, so they cannot catch the misattribution they were written to guard against

**File:** `internal/tuikit/globalgit_test.go:1988-2053`, `internal/tuikit/globalssh_test.go:2110-2163`

**Issue:** `TestGitStaleCommitMsgNotMisattributedToNewerCeremony` and
`TestSSHStaleCommitMsgNotMisattributedToNewerCeremony` set up the exact
two-ceremonies-of-the-same-kind scenario described in CR-01 above (ceremony
1 confirmed with one key/value, abandoned, ceremony 2 confirmed with a
*different* key/value, then ceremony 1's stale message delivered) — but
both only assert `len(result.actions) != 1` (Git) and `== 1` (SSH). Neither
test inspects `result.actions[0]`'s field values, so neither can detect that
the dispatched action carries ceremony 2's key/value instead of ceremony 1's.
The tests were deliberately built to reproduce the misattribution scenario,
which makes the missing content assertion a real coverage gap, not an
unrelated omission.

**Fix:** Add, e.g. for the SSH test:
```go
applySSH, ok := result.actions[0].(ApplySSH)
if !ok || len(applySSH.Keys) != 1 || applySSH.Keys[0] != "HashKnownHosts" {
    t.Errorf("stale ceremony-1 message dispatched %+v, want ApplySSH{Keys: [HashKnownHosts]} — got ceremony 2's keys instead", result.actions[0])
}
```
and the analogous assertion in the Git test for whichever key ceremony 1
selected (`init.defaultBranch`). Both currently pass; adding the assertion
will fail against the current code, correctly reproducing CR-01's remaining
gap.

## Info

### IN-01: One pre-existing test still delivers a bare, unwrapped commit message

**File:** `internal/tuikit/globalgit_test.go:454`

**Issue:** `TestGlobalGitMouseTabClickBlockedWhileCeremonyOpen` calls
`deliverMsg(t, a, GlobalGitCommitMsg{Backups: []string{backupPath}})` —
delivering the raw message directly, not wrapped in `gitCommitTokenMsg` as
every real dispatch site now does. This test still passes only because the
reducer action/note fires unconditionally regardless of the token match
(the design BL-04/CR-01 preserved) — the raw delivery incidentally exercises
the "no token present → treated as stale" path rather than the real,
wrapped delivery path its neighboring tests (`globalgit_test.go:382,399`)
were updated to use. Not a functional bug (the test's own assertion still
holds for the right reason), but it means this call site doesn't exercise
what production code actually sends, and a future change that made the
token match a hard requirement for the reducer dispatch too would break
here for a reason unrelated to what the test claims to check.

**Fix:** Update to mirror the two sibling sub-tests immediately above it —
wrap with `gitCommitTokenMsg{token: ggitModel(t, a).commitRequestToken, msg: GlobalGitCommitMsg{...}}` before delivering.
