### BL-01: Global SSH "Resulting config" preview renders as an empty box after an Options↔Storage round-trip (CR-05 fix is incomplete)

**File:** `internal/tuikit/globalssh.go:589-594`, `:580-584`, `:791-793` (with `:1152-1158`)

**Issue:** `refetchStoragePlan()` was added to exactly two of the **four** sites that mutate
`m.storageChoice` — the keyboard `up`/`down` handler (`:614`) and the mouse radio click
(`:855`, `:858`). The other three sites set `m.storageChoice = s.SSHStorage` **without**
refetching:

```go
case "left", "right":                        // :589-594
    if m.subTab == gssOptions {
        m.subTab = gssStorage
        m.storageChoice = s.SSHStorage       // no refetch
    }
```
(the same two lines also appear in the empty-options branch at `:582-583` and in the sub-tab
strip click at `:792`).

The real backend populates the three preview fields **mutually exclusively** by requested
layout (`cmd/gitid/wiring.go:3027-3033`): `SentinelPreview` is set only when
`layout == StorageSentinel`, `MainPreview`/`OwnedPreview` only when `layout == StorageInclude`.
So after `↓` (radio → Include, refetch) → `←` (Options) → `→` (Storage, choice reset to
Sentinel, **no** refetch), `renderStorage` takes the Sentinel branch and reads
`m.storageView.SentinelPreview`, which is `""`.

Reproduced with a stub that mirrors the real backend's field discipline
(`m.storageChoice == s.SSHStorage == sentinel`):

```
 STORE-01 — where gitid-managed SSH config  │  Resulting config — sentinel blocks in place
lives                                       │ ╭╌╌╮
 ● Sentinel blocks in ~/.ssh/config         │ ┊  ┊
(default) — current                         │ ╰╌╌╯
```

This is invisible in every existing test because both `internal/dummytui/fixturebackend.go:867-878`
and `internal/tuikit/backend_stub_test.go:740-749` populate **all three** fields — so the dummy
binary, the visual-regression gate and the unit suite all mask a real-binary-only defect. The
pane whose entire purpose is "here is what your config will look like" shows an empty box.

**Fix:** route every `storageChoice` mutation through the same helper:
```go
case "left", "right":
    if m.subTab == gssOptions {
        m.subTab = gssStorage
        m.storageChoice = s.SSHStorage
        m = m.refetchStoragePlan()   // same for :582-583 and :792
    }
```
and add a stub/fixture variant that sets only the requested layout's preview field, so the unit
suite can actually observe this class of bug.

### BL-02: The Doctor tab's flagship destructive fix ceremony clips its Cancel/Confirm button row — no confirm affordance is rendered, and mouse confirm/cancel become impossible

**File:** `internal/tuikit/doctor_screen.go:428-450` (with `internal/tuikit/identities.go:3185-3197`)

**detail pane** (`detailWidth = 100 - 44 - 2 = 54`) and is clipped by
`fitPane(..., frameBodyRows(height))`. `fixCeremonyFor` sets no `PreviewMaxLines`, so it keeps the
default 10-line preview it had when it rendered full-width. For `ssh-identitiesonly-contradiction`
(the destructive flagship, `internal/tuikit/fixplans.go:38-47`) the ceremony overflows and
`fitPane` replaces the **last** lines — which are exactly the button row — with the overflow cue.

```
│ ╰╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╯

│ > T
│
│  … (+2 more lines)          ← the " Cancel (Esc)   Apply fix (Enter) " row
```

Consequences:
1. §6's "the affirmative action is never default-focused" is meaningless when neither button is
   drawn — the user is given a typed-confirm prompt with no visible confirm control.
2. `ceremonyClickKey` (`ceremony.go:497-517`) hit-tests `" Cancel (Esc) "` / `" Apply fix (Enter) "`

3. `Esc`/`Enter` still work by keyboard, so the e2e PTY test passes while the UI is wrong — the

asserts `headroom >= 4`). **No equivalent row-budget test exists for the Doctor tab** — `grep
'headroom\|availRows\|frameBodyRows(' internal/tuikit/doctor*_test.go` returns nothing.

**Fix:** give the in-pane fix ceremony an explicit budget and add the missing geometry test, e.g.

```go
// identities.go fixCeremonyFor

```
plus a `TestDoctorCeremonyFitsFixedGeometry` mirroring `globalssh_test.go`'s State 5/6 headroom
checks over the destructive fix, the non-destructive fix, and the batch-progress variant.

### BL-03: A body mouse click while editing the Global Git fallback fields desyncs focus — keystrokes keep landing in an input that is no longer rendered

**File:** `internal/tuikit/globalgit.go:822-862` (with `:526-545` and `:1087-1091`)

**Issue:** `handleKey` guards the text-edit state first (`if m.fieldEditing { ... }`), but
`handleClick` has **no** `fieldEditing` guard: it falls straight through to the master-list row
hit-test and sets `m.detailKey = o.Key`. `view()` then renders that other row's detail (the
name/email inputs disappear) while `m.fieldEditing` stays `true`, so every subsequent keystroke is
still routed into `m.nameInput`/`m.emailInput`.

Reproduced (Enter to edit the fallback row, then a click on the first option row, then type `z`):

```
after body click: detailKey="init.defaultBranch"  fieldEditing=true
after typing 'z':  name="z"  email=""
```
…with the rendered pane showing `init.defaultBranch`'s explanation and no form fields anywhere.
`view()` also still returns `capturesKeys: true`, so the header nav is blocked by the CR-02 mouse
guard and the reserved footer advertises `Esc/Enter done editing` for an invisible editor.

This is precisely the "mouse-driven field focus" desync class the code comments say this project
"has hit twice before" (`globalgit.go:836-841`, T-07-22) — the click handler was hardened against
*scroll* offsets but not against *mode*.

**Fix:**
```go
func (m globalGitModel) handleClick(x, y, width, height int, s DemoState) keyResult {
    if m.ceremonyOpen { ... }
    if m.fieldEditing {
        // The pane owns the keys; a stray body click must not silently move
        // the selection out from under the focused input.
        return keyResult{model: m}
    }
    ...
```
(or exit edit mode + blur both inputs before moving `detailKey`). Add a regression test that
clicks a non-fallback row while `fieldEditing` and asserts the model is coherent.

### BL-04: A completed async apply/migrate commit is silently discarded when the screen was re-activated in the meantime — the write happened, the receipt and the state refresh never do

**File:** `internal/tuikit/app.go:416-421`; `internal/tuikit/globalgit.go:116-156`, `:161-209`;
`internal/tuikit/globalssh.go:146-175`, `:205-275`

**Issue:** Both Global screens gate the async commit result on model flags:

```go
if commit, ok := msg.(GlobalGitCommitMsg); ok && m.ceremonyOpen && m.applyCommitPending { ... }
```

CR-02's fix added `m.ceremonyOpen = false; m.applyCommitPending = false; m.ceremony = ceremonyModel{}`
to `activate()` (`globalgit.go:127-130`, `globalssh.go:156-159`). But the ceremony's "keys are
inert while pending" guard lives in the **screen's** `handleKey`, and `App.handleKey` intercepts
`ctrl+p` **before** the screen ever sees the key (`app.go:416`). So the palette is still reachable
mid-flight, and re-entering the screen from it runs `activate()` and clears the flags while the
`tea.Cmd` — which performs the real, backed-up write — is still running. When its message finally
lands, `handleMsg`'s guard is false and the message is dropped on the floor.

Reproduced (confirm → `Ctrl+P` → `Enter` → `3` → deliver the commit message):
```
ceremonyOpen=false pending=false done=false GitBaselineApplied=false
```
i.e. the write completed, no receipt was shown, no `note` was set, and **no reducer action was
dispatched**, so `App.state` never re-reads. For the storage migration this is worse than cosmetic:
`renderStorage`'s "— current" marker reads `s.SSHStorage` (`globalssh.go:1123-1128`), so after a
successful migration the screen keeps telling the user the **old** layout is the current one.

The CR-02 fix covered the mouse (`app.go:528-540`) and the state machine, but left the keyboard's
own pre-screen escape hatch open — and made the consequence strictly worse than before the fix,
because `activate()` now actively erases the state `handleMsg` needs.

**Fix:** either (a) make the `ctrl+p` intercept respect the same guard the mouse now uses —
```go
if key == "ctrl+p" && a.overlay != overlayPalette &&
    !a.screens[a.tab].view(a.state, a.width, a.height).capturesKeys {
```
— or (b) make the commit-message handlers idempotent w.r.t. abandonment: keep dispatching the
reducer action (and a `note`) even when the ceremony is gone, gating only the *ceremony*
transition on `applyCommitPending`. Option (b) is the safer of the two, because it also covers
`q`-quit and any future pre-screen key.

**File:** `internal/tuikit/doctor_screen.go:129-136`

### WR-03: `extractGSSApplyHeading` / `extractGGitApplyHeading` scan forward unbounded, and their WR-12 regression test exercises a shape the renderer cannot produce

**File:** `internal/screenshot/createflow_regions.go:1116-1119`, `:1218-1221`;
`internal/screenshot/createflow_regions_test.go:21-42`

**Issue:** Two problems in one loop:

```go
for j := i + 1; j < len(lines) && !strings.Contains(stripANSI(lines[j]), "Touches"); j++ {
    out = append(out, lines[j])
}
```
1. The only terminator is the literal `"Touches"`. A frame that renders the heading without a
   `Touches` row would append **every remaining line of the frame** (status line, both footers)
   into a region documented as "the heading line ONLY". There is no upper bound and no test for
   that shape.
2. The premise is wrong for these two ceremonies: `ceremony.go:393` renders the heading with
   `styleBold.Render(c.cfg.Heading)` — **not** `wrap.Render` — and `RenderFrame` *truncates* body
   lines (`frame.go:456`) rather than wrapping them. The Global SSH/Git ceremonies render
   full-width, so their heading is a single physical row and the continuation loop can never fire
   on a real capture. `TestExtractGSSApplyHeadingAbsorbsWrappedContinuationRow` proves the loop
   against a hand-built fixture that the production renderer never emits.

**Fix:** bound the absorption explicitly and make the test derive its input from a real render:
```go
const maxHeadingContinuation = 2
for j := i + 1; j < len(lines) && j <= i+maxHeadingContinuation &&
    !strings.Contains(stripANSI(lines[j]), "Touches"); j++ {
```

### WR-10: The master-list scroll budget is pinned to `minFrameHeight`, so taller terminals hide rows behind a blank pane — and WR-09 propagated this to a second screen

forwards to every screen, and derive the budget from it in both `handleKey` and `view`.

key branch (`:574-586`) similarly offers only `←/→`, while Global Git's returns fully unhandled.

**Fix:** mirror Global Git's branch (banner + warning + hint) and align the two error-state key

### WR-13: `doctorModel.handleClick` was not given CR-04's parse-error guard

**File:** `internal/tuikit/doctor_screen.go:302-332` vs `:165-167`

**Issue:** CR-04 added
```go
if _, halted := parseErrorFinding(orderedFindings(rawState)); halted { return keyResult{model: m} }
```
to `handleKey` only. `handleClick` still walks `groupFindings(m.findings(rawState))` and sets
`m.selectedID` with `handled: true` for a list that `view()` is not rendering (the frame shows
"Checks paused until this configuration parses again"). It is currently harmless because the
ceremony button needles are absent from the parse-error body, but it silently mutates selection
state and swallows the click on a screen that is supposed to be inert.

**Fix:** hoist the guard to the top of `handleClick` as well — or, better, extract a single
`m.halted(rawState) bool` predicate that `view`, `handleKey` and `handleClick` all consult.

### WR-14: Duplicated region extractors and `git*`-named machinery shared by a non-git screen

**File:** `internal/screenshot/createflow_regions.go:1023-1042` vs `:1133-1152`;
`internal/tuikit/globalssh.go:728-755` vs `internal/tuikit/globalgit.go:747-776`

**Issue:** `gssCeremonyBodyAfter` and `ggitCeremonyBodyAfter` are byte-identical functions;
`extractDoctorCeremony` calls the `ggit`-named one, which is now simply misleading.
`extractGSSApplyHeading`/`extractGGitApplyHeading` differ only in their anchor string (and so
duplicate WR-03's unbounded loop twice). On the tuikit side, `gssComputeScrollWindow` is a
near-verbatim copy of `gitComputeScrollWindow`, and Global SSH reuses `gitScrollWindow`,

**Fix:** collapse each duplicated pair into one parameterised helper
(`ceremonyBodyAfter(lines, heading, endMarker)`, `applyHeadingRegion(lines, anchor)`) and rename the

### WR-15: `Tab` moves the Global Git fallback field focus with no visible feedback

**File:** `internal/tuikit/globalgit.go:580-585`, `:1008-1011`, `:1094-1096`

**Issue:** Outside edit mode, `Tab` sets `m.fieldFocus = 1 - m.fieldFocus` and the footer advertises
`{Key: "Tab", Label: "next field"}`. But the render computes focus as
```go
nameFocused  := m.fieldFocus == 0 && m.fieldEditing
emailFocused := m.fieldFocus == 1 && m.fieldEditing
```
so with `fieldEditing == false` **neither** field is drawn focused. The user presses Tab, sees no
change at all, and only discovers which field moved by pressing Enter. `focusFallbackField()` is
also not called on this path, so the underlying `textinput` focus and `m.fieldFocus` are out of sync
until the next Enter.

**Fix:** render the focus ring on `m.fieldFocus` regardless of `m.fieldEditing` (using a distinct
treatment for "selected" vs "editing"), and call `m.focusFallbackField()` from the non-editing Tab
branch too.
