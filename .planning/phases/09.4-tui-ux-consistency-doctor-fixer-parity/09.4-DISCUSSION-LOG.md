## Initial row focus (SSH vs Git)

Root cause confirmed via code read: `globalGitModel.activate()`
(`internal/tuikit/globalgit.go:127`) resets `detailKey` to the first row on
every activation (fixed in an earlier code review — see its own comment about
selection-cursor desync). `globalSSHModel.activate()`
(`internal/tuikit/globalssh.go:136`) never resets `detailKey`; it keeps
whatever `newGlobalSSHModel` set at construction:
`detailKey: "IdentitiesOnly"` (line 123).

The user then asked a follow-up: WHY was IdentitiesOnly ever chosen as the
default, and is it real live data or something hardcoded at startup? Answer
given: IdentitiesOnly's VALUE is real, live-probed data (not fabricated) —
but the DEFAULT FOCUS on that specific row traces back to the original
HTML/MUI mockup (`options-list.route.tsx`), which hardcodes the same
default because IdentitiesOnly is the project's flagship SSH contradiction
fix. That mockup default was carried into the real TUI verbatim without
reconsideration once wired to live data.

| Option | Description | Selected |
|--------|-------------|----------|
| Reset to first row, like Global Git | Remove the hardcoded default entirely | ✓ |
| Keep flagship default, explain it | Keep IdentitiesOnly highlighted, add a note why | |
| First actionable row instead | Slightly smarter: default to first needs-action row | (offered as a second-round option, not chosen — user confirmed plain reset-to-first-row) |

**User's choice:** Reset to first row, no special-casing.

**Follow-up (deferred, not part of this decision):** the user asked whether
gitid scans/shows ALL SSH/Git properties or only a curated subset, floating
the idea of a "properties list" feature. Answered: today's scope is a fixed
curated policy table only. User asked to defer this "a algo como 9.5" — see
CONTEXT.md's Deferred Ideas.

## Checkbox system: rationale, alignment, prominence

The user's underlying question — "who decides read-only and why, I never
said it should be read-only" — was answered in full BEFORE any option was
presented, per the user's explicit request ("no te digo hagas algo con eso
antes de explicarmelo"): the checkbox only appears when checking it would
produce a REAL write (state `NeedsAction`). `AlreadySet` rows have nothing
to write; `Differs` rows can't be meaningfully written because gitid's
managed block sits at the floor and a later hand-written value would still
win (a documented code comment: "a write into a key the user set later is
provably a no-op").

A scope-fence question was then asked: fix the visual/discoverability side
only, or scope in a real value-override/editing capability?

| Option | Description | Selected |
|--------|-------------|----------|
| Visual/discoverability fix only | Keep the apply-recommendation-only model; fix alignment, reason visibility, prominence | ✓ |
| Scope in value-override capability | Let the user actively set/pin a value even when AlreadySet/Differs | (explicitly deferred, see CONTEXT.md) |

**User's choice:** Visual/discoverability fix only.

**Alignment/placeholder:**

| Option | Description | Selected |
|--------|-------------|----------|
| Dot placeholder + inline reason | Every row reserves the same checkbox-column width; non-selectable rows get Global Git's existing `·` pattern; add a reason clause | ✓ |
| Dot placeholder only | Fix alignment, skip new reason text | |

**User's choice:** Dot placeholder + inline reason, with the clarification that
the existing "now: X → Y already set" second line already partially serves
as the reason — the fix folds a strengthened reason into that EXISTING line
(specifically for the `Differs` state) rather than adding a new third line.

**Toggle prominence:**

| Option | Description | Selected |
|--------|-------------|----------|
| Bold + color the checkbox glyph | Keep □/✓, make bold + colored | (superseded by the bracket-style follow-up) |
| Wider glyph with brackets | `[ ]`/`[x]` instead of □/✓ | (superseded) |

User asked whether Bubble Tea can even render bracket-style toggles like
Claude Code CLI's own UI does (with a colored check inside). Answered: yes,
fully supported — brackets are just styled text (Lipgloss), no different
from what the codebase already does elsewhere.

| Option | Description | Selected |
|--------|-------------|----------|
| Green when selected, gray when not | `[ ]` default/faint, `[✓]` bold green when selected | ✓ |
| Match row's risk color | Checkbox color ties to the row's own risk level instead | |

**User's choice:** Green when selected, default/gray when not.

## Submenu visual distinction (Storage & preview)

Confirmed via code read: `internal/tuikit/app.go`'s render() has an explicit
comment excluding `TabGlobalSSH` from the top-level arrow-switch footer hint,
because its own ←/→ already means "Options / Storage" locally — an
intentional D4/checkpoint-2 keybinding contract, not an oversight. The gap is
purely visual: nothing distinguishes this sub-tab bar from the main tab bar.

| Option | Description | Selected |
|--------|-------------|----------|
| Bordered/boxed sub-tab bar | Give the sub-tab row its own visible border/background, distinct from the main tab bar | ✓ |
| Footer hint text only | Keep current rendering, strengthen footer copy instead | |

**User's choice:** Bordered/boxed sub-tab bar.

## Doctor vs Fixer count parity

Initially framed as a simple banner-vs-something-stronger choice. The user
pushed back, floating their original idea more concretely: shouldn't fixing
just be a button/action inside Doctor, with Esc/back returning to Doctor and
refreshing on navigation to other views — rather than a whole separate tab?

Investigation before deciding: `internal/tuikit/doctor.go`'s header comment
and `.planning/phases/08-health-fixer/08-01-PLAN.md` confirmed the split was
NOT incidental — `FIX-02` (a shipped, Complete requirement) explicitly
mandated it, and Health's code was deliberately stripped of ALL fix
keybindings as a safety/isolation property (the read-only diagnostic tab
cannot even attempt a write). This was surfaced to the user in full before
asking for a final decision.

| Option | Description | Selected |
|--------|-------------|----------|
| Keep split + add cross-reference banner | Cheap, non-structural; reuses the existing banner pattern from Global SSH/Global Git Options; preserves FIX-02's isolation property | |
| Revert to single combined Doctor view | Un-completes FIX-02; merges Fixer into Health as one "Doctor" screen with inline fix, matching the original mockup's Doctor.tsx | ✓ |

**User's choice:** Revert to a single combined Doctor view.
**Notes:** Explicitly confirmed after the trade-off (loses the "diagnostic
tab literally cannot write" isolation property; write-confirmation ceremony
itself is unaffected) was named in full. This is the largest decision in
this phase (D-06 in CONTEXT.md), rated `costly` reversibility and flagged
for a `checkpoint:decision` gate at plan time.

**Tab naming follow-up:**

| Option | Description | Selected |
|--------|-------------|----------|
| Rename to "Doctor" | Matches original mockup naming; reflects combined diagnose+fix scope | ✓ |
| Keep "Health" | Less churn on existing copy/docs | |

**User's choice:** Rename to "Doctor". Main menu becomes 4 tabs:
`[1] Identities [2] Global SSH [3] Global Git [4] Doctor`.
