## Summary

This phase touches zero new external dependencies — it is a five-fix consistency
retrofit over `internal/tuikit`, a shipped, tested Go Bubble Tea v2 TUI. The
"research" that matters here is not library selection but **exact call-graph
tracing**: UXP-01..04 are small, well-scoped renderer fixes whose target shape
is already fully specified in `09.4-UI-SPEC.md` (verified against live source
this session — every UI-SPEC quote checked against `Read`/`codegraph_explore`
output matched byte-for-byte). UXP-05 is materially different: it reverses
Phase 8's FIX-02 split (`08-01-PLAN.md` Task 2), and this session's
`codegraph_explore` pass found the merge's true blast radius is **larger than
what CONTEXT.md's canonical-refs list names** — three additional registries
(the visual-regression `ScreenSpec` registry, its 100-line divergence
allowlist file, and the App's `[6]screenModel`/number-key/palette/click-chip
wiring) all hard-code the two-tab shape and will not compile or pass without
their own edits, on top of the five test files CONTEXT.md already flags.

**Primary recommendation:** Land Known Divergence #1's `TabID` enum change
FIRST (UI-SPEC already says this), then work outward through four *distinct*
call-graph layers in this order: (1) `internal/tuikit/app.go`'s tab-count
plumbing (`[6]screenModel`→`[5]screenModel`, `newScreens`, number-key switch,
`paletteEntries`, `checkFixBatchHalt`'s `fixerModel` type-assertion, the two
`TabHealth`-typed `res.healthIdentity` routing sites), (2) the merged screen
model itself (fold `fixer_screen.go`'s ceremony/batch machinery into
`health_screen.go`'s unfiltered data scope — reusing `doctor.go`'s helpers
unchanged), (3) the visual-regression spec registry
(`internal/screenshot/createflow.go`'s `healthFixerSpecs()`,
`createflow_regions.go`'s `RegionHealthBody`/`RegionFixerBody`/
`RegionFixerCeremony`, `.planning/design/health-fixer/visual-divergence-allowlist.txt`),
and (4) the test suite (12 files touch `TabHealth`/`TabFixer`/`TabGitIgnore`/
`healthModel`/`fixerModel`, plus a dedicated 379-line `e2e/health_fixer_pty_e2e_test.go`
with 8 real-PTY test functions named after the split). Every one of these four
layers must move together for `go build`/`go test`/`make gate-visual-regression`
to stay green — none is optional cleanup.

### Pattern 1: Screen model reuse — fold two thin models around one shared core

**What:** `doctor.go`'s five free functions (`orderedFindings`, `groupFindings`,
`selectFinding`, `fixableFindings`, `pluralS`) were ALREADY factored out from
a single pre-Phase-8 `doctorModel` specifically so two screens could share
them without duplicating logic (see `08-01-PLAN.md` Task 2's action text,
verified this session). The merge is the SAME factoring in reverse: fold the
two thin models (`healthModel`, `fixerModel`) back around the SAME shared
core, changing zero lines in `doctor.go` itself.

**When to use:** Any time a single-source-of-truth capability (`orderedFindings`)
has been duplicated across two consumer screens — recombine consumers, never
the source.

**Example (current, from health_screen.go:102-107 — the pattern to KEEP):**
```go
// Source: internal/tuikit/health_screen.go:102-107 (verbatim, read this session)
func (m healthModel) findings(s DemoState) []DemoFinding {
	if m.identityName == "" {
		return orderedFindings(s)
	}
	return orderedFindings(DemoState{Findings: FindingsFor(s, m.identityName)})
}
```
This UNFILTERED scope (all findings, optionally narrowed by identity — never
by fixability) is the scope the merged Doctor screen's list must use. Contrast
with `fixer_screen.go:114-117`'s `fixableState()`, which narrows
`s.Findings` to `fixableFindings(orderedFindings(s))` — this narrowing is
EXACTLY the count-parity bug UXP-05 exists to fix and must NOT survive into
the merged list (though the `f`/`F` handlers still gate on `sel.Fixable`
per-row).

### Pattern 2: `screenModel` interface as the merge boundary

**What:** Every tab's child model implements one interface
(`internal/tuikit/app.go:52-58`, verified this session):
```go
// Source: internal/tuikit/app.go:52-58
type screenModel interface {
	handleKey(msg tea.KeyMsg, s DemoState) keyResult
	handleMsg(msg tea.Msg, s DemoState) keyResult
	view(s DemoState, width, height int) screenView
	activate(s DemoState) (screenModel, tea.Cmd)
}
```
The merged Doctor model only needs to satisfy this SAME interface — `App`
never needs new plumbing for "a screen that both reads and writes," since
`globalSSHModel`/`globalGitModel` already do exactly that (read `Selectable()`
state, write via a ceremony). This confirms UXP-05 needs no new interface
method, only a model that combines both existing models' state.

### Anti-Patterns to Avoid
- **Hand-patching the visual-divergence allowlist file:** the 100-line
  `.planning/design/health-fixer/visual-divergence-allowlist.txt` is kept in
  sync with `internal/screenshot/createflow.go`'s `healthFixerSpecs()` by a
  dedicated test (`TestHealthFixerAllowlistMatchesRegistry`,
  `cmd/gitid/gate_visual_regression_test.go`, referenced from
  `createflow.go`'s own doc comment). Editing one without the other fails
  that test — regenerate/re-derive both together, do not diff-patch the
  `.txt` by hand.
- **Re-deriving `orderedFindings`/`groupFindings` inside the merged model:**
  these are the traceability guarantee CONTEXT.md's Inherited Non-Negotiables
  names explicitly ("a re-introduced second filtered copy would resurrect
  [the bug]") — call the existing functions, never inline a second sort/filter.
- **Treating the sub-tab strip's row-budget change as isolated to
  `subTabStrip()`:** `gssOptionsTopLines()` and `handleClick`'s `y == 0`
  hard-coded row assumption (both in `globalssh.go`) must change in the SAME
  commit as `subTabStrip()`'s render, or the click-to-switch-subtab
  affordance silently breaks (same defect class as the `refetchStoragePlan`
  bug already documented at `globalssh.go:149-160`, a real recurring pattern
  in this codebase — desynced click math after a render-layout change).

## Common Pitfalls

### Pitfall 1: `App.screens` is a FIXED-SIZE array — `[6]screenModel`, not a slice
**What goes wrong:** `internal/tuikit/app.go:147` declares
`screens [6]screenModel` on the `App` struct, and `newScreens`
(`app.go:726-735`) returns `[6]screenModel`. Reducing the tab count to 5
without updating this array's declared size fails to compile (`go build
./...` errors on the literal `[5]screenModel{...}` vs. the struct field's
declared `[6]screenModel` type) — this is not a runtime bug, it is a
compile-time array-size mismatch.
**Why it happens:** Go arrays encode their length in the type; unlike a
slice, `[6]T` and `[5]T` are different, non-assignable types.
**How to avoid:** Change BOTH `screens [6]screenModel` (app.go:147) and
`func newScreens(...) [6]screenModel` (app.go:726) together, in the same
commit as the `TabID` enum change.
**Warning signs:** `go build ./...` failing with "cannot use
[5]screenModel{...} (value of type [5]screenModel) as [6]screenModel value"
or similar array-literal-count mismatch.

### Pitfall 2: `checkFixBatchHalt` type-asserts to `fixerModel` — the D-16 rollback path breaks silently if not updated
**What goes wrong:** `app.go:314-332`'s `checkFixBatchHalt` (verified this
session) does `postFixer, ok := a.screens[a.tab].(fixerModel)` and
`preFixer, wasFixer := prevScreen.(fixerModel)`. If the merged screen's
concrete type is renamed (e.g. to `doctorModel`) but this function is not
updated, `ok`/`wasFixer` are always `false`, and `checkFixBatchHalt` becomes
a silent no-op — a failed fix-all batch walk would no longer halt or show
the rollback message (D-16), but nothing would fail LOUDLY; the ceremony
would just silently not roll back. This is the exact "injected-seam wiring
blindspot" class this project's own CLAUDE.md and MEMORY.md flag as
recurring (`doctor-injected-seam-wiring-blindspot.md`).
**Why it happens:** Go's type assertion `x.(T)` fails silently to `ok=false`
rather than a compile error when `T` is renamed and the assertion site is
missed — this is NOT caught by `go build`, only by a test that forces the
rollback path (which already exists:
`TestHealthFixer_RealPTYFixerBatchWalkHalt` in
`e2e/health_fixer_pty_e2e_test.go`, using a real `chflags uchg` failure
injection per `08-08-SUMMARY.md`).
**How to avoid:** Grep for every `.(fixerModel)` and `.(healthModel)` type
assertion in `app.go` (confirmed 4 sites: `app.go:454`, `app.go:457`,
`app.go:555`, `app.go:558` for `healthModel`; `app.go:315`, `app.go:319` for
`fixerModel`) and update them to the merged type in the SAME commit as the
model rename. Re-run `TestHealthFixer_RealPTYFixerBatchWalkHalt` (renamed
appropriately) as the acceptance gate for this specific pitfall — it is the
one test that actually exercises the silent-no-op failure mode.
**Warning signs:** batch-fix-all no longer shows the "Fix N of M failed and
was rolled back…" message after an injected write failure; the PTY e2e
suite's rollback test passes for the wrong reason (early-returns because
`ok=false`, not because the halt logic ran correctly) — inspect the test
for a positive assertion on the halt message text, not just "no panic."

### Pitfall 3: `res.healthIdentity` routes to `TabHealth` from TWO sites, plus a THIRD via the header health-chip click
**What goes wrong:** `identities.go:2556` dispatches
`keyResult{..., healthIdentity: sel.Name}` (the "h · Open Health for X" key
on an identity row, per `identities.go:4608`'s footer label). `app.go:453-459`
(keyboard path) and `app.go:554-560` (mouse path) both read `res.healthIdentity`
and route to `TabHealth` via `a.screens[TabHealth].(healthModel)` +
`a.setTab(TabHealth)`. Separately, `app.go:519-521`'s `handleMouse` routes a
click on the header's health-count chip (`headerChipAt`) directly to
`a.setTab(TabHealth)` with no identity filter. All THREE call sites hardcode
`TabHealth` and must become `TabDoctor`; the first two ALSO need their
`.(healthModel)` type assertion updated to the merged type, and the
`identityName` field they set must still exist as a field on the merged
model (it currently lives only on `healthModel`, not `fixerModel` — the
merge must carry it over, or per-identity Doctor filtering silently breaks).
**Why it happens:** three independent hand-written routing call sites for

### Pitfall 6: test helper functions hardcode number keys `"4"`/`"5"` to reach Health/Fixer
**What goes wrong:** `internal/tuikit/doctor_test.go:9-33` (verified this
session, full text read) defines `doctorApp(t)` (`press(t, NewApp(...), "4")`)
and `fixerApp(t)` (`press(t, NewApp(...), "5")`) as the two entry-point test
helpers used across the Health/Fixer test suite. Post-merge, key `"5"`

Fixer tab to reach), and any test still calling it after a naive rename will

merged, in which case Go's compiler catches every caller.
**Why it happens:** number-key test helpers are a common project pattern
(seen also in `mouse_test.go:74`, `globalgit_test.go:1598`,

fail with assertions about GitIgnore-screen content when the test's `t.Fatal`
