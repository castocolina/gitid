# Phase 9.4: TUI UX Consistency & Doctor/Fixer Parity - Context

**Gathered:** 2026-08-30
**Status:** Ready for planning

<domain>
## Phase Boundary

Fix five concrete UX inconsistencies a direct user audit found in the shipped
Global SSH, Global Git, and Fixer/Health screens: inconsistent initial row
focus, an inconsistent/misaligned checkbox affordance with unclear read-only
rationale, low toggle visibility, an undiscoverable sub-tab navigation
contract, and a Doctor-vs-Fixer finding-count mismatch severe enough that the
fix is a structural merge (reversing Phase 8's FIX-02 split), not a cosmetic
patch. Closes UXP-01 through UXP-05.

</domain>

<decisions>
## Implementation Decisions

### UXP-01: Initial row focus
- **D-01:** Global SSH's Options screen resets its highlighted row (`detailKey`)
  to the first row on every `activate()` call, exactly mirroring
  `globalGitModel.activate()`'s already-fixed behavior
  (`internal/tuikit/globalgit.go:127`). Remove `newGlobalSSHModel`'s hardcoded
  `detailKey: "IdentitiesOnly"` construction-time default
  (`internal/tuikit/globalssh.go:123`) — no row is special-cased in the focus
  logic. Root cause confirmed: this hardcoded default traces back to the
  original HTML/MUI mockup
  (`.planning/design/mockup-src/src/routes/global-ssh/options-list.route.tsx`),
  which hardcodes `highlighted = globalSshDetailTarget; // IdentitiesOnly`
  because IdentitiesOnly is the project's flagship SSH contradiction fix — a
  demo-authoring choice that was carried into the real TUI verbatim without
  being reconsidered once the screen was wired to live, real-machine data
  (where IdentitiesOnly is very often already correctly set, making it a
  poor default focus target compared to an actually-actionable row above
  it in the list).
  — **Reversibility:** reversible.

### UXP-02/UXP-03: Checkbox system (rationale, alignment, prominence)
- **D-02 (scope fence — explicitly confirmed with the user):** This phase
  fixes the VISUAL/discoverability side only. The underlying interaction
  model — the checkbox means "apply gitid's recommended value," shown ONLY
  when checking it would produce a real write (state `NeedsAction`) — is
  UNCHANGED. Rows in `AlreadySet` (already matches recommendation),
  `Differs` (set to something else — gitid's managed block sits at the
  floor, so applying its recommendation there is provably a no-op since a
  later hand-written value would still win), and `NotApplicable` states
  remain non-selectable BY DESIGN, not by oversight. A general "let the user
  actively set/override any value" capability was explicitly discussed and
  explicitly deferred — see Deferred Ideas.
- **D-03:** Every options row reserves the SAME checkbox-column width
  regardless of selectability. Selectable (`NeedsAction`) rows render a
  bracket-style toggle: `[ ]` unselected, `[✓]` selected — bold green when
  selected, default/faint color when not (mirrors gitid's existing
  `StatusTone`/healthy-tone color convention). Non-selectable rows render a
  `·` placeholder in the same column position, matching Global Git's
  existing pattern (`internal/tuikit`'s Global Git row renderer already does
  this; Global SSH's row renderer currently omits the placeholder entirely
  for non-selectable rows, which is the alignment bug — confirmed by
  comparing the two screenshots in this discussion).
- **D-04:** The existing per-row second line (`now: X → Y  already set` /
  `differs`, etc.) already carries most of the "why" explanation — no new
  third line is added. For the `Differs` state specifically, strengthen
  THAT existing line's wording so it explicitly states why nothing happens
  if the row were selectable (e.g. "set to a different value — gitid's
  block would be a no-op here"), rather than just showing the raw
  now/recommended values with no explanation of the no-op mechanics.
  — **Reversibility:** reversible (both D-03 and D-04).

### UXP-04: Submenu visual distinction
- **D-05:** Global SSH's local sub-tab bar (`Options` / `Storage &
  preview`) gets its own visible border/boxed treatment, distinct from the
  top-level main tab bar's style — an immediate visual signal that ←/→
  here means "switch sub-tab" (an existing, intentional D4/checkpoint-2
  keybinding contract — see `internal/tuikit/app.go`'s comment on why
  `TabGlobalSSH` is excluded from the top-level arrow-switch footer hint)
  rather than "switch main tab." No copy/footer-text change is required in
  addition to the visual treatment (a footer-hint-only fallback was
  considered and explicitly NOT chosen).
  — **Reversibility:** reversible.

### UXP-05: Doctor/Fixer merge (structural — reopens FIX-02)
- **D-06:** (major decision, explicitly confirmed with the user after the
  trade-off was named in full) Reverse Phase 8's FIX-02 split. Merge the
  standalone Fixer tab back into Health, producing a single combined
  screen renamed **Doctor** — matching the original mockup's shape
  (`.planning/design/mockup-src/src/demo/screens/Doctor.tsx`, which already
  implements exactly this: one findings list, inline `f · Fix this…` / `F ·
  Fix all (N)` actions, a fix ceremony rendered in place). The main menu
  goes from 5 tabs to 4: `[1] Identities [2] Global SSH [3] Global Git [4]
  Doctor`.
  - **What this removes:** FIX-02's specific isolation property — that the
    read-only diagnostic tab has literally zero fix-triggering keybindings
    wired (`internal/tuikit/health_screen.go` currently has no `f`/`F` key
    handling at all; `internal/tuikit/doctor.go`'s header comment records
    this as an intentional 08-01-PLAN.md Task 2 split).
  - **What this does NOT remove:** the write-confirmation discipline itself
    (preview + typed-confirm + backup ceremony, `FIX-01`, CLAUDE.md's
    global write-safety rule). Every fix in the merged Doctor screen still
    goes through the exact same ceremony as the old Fixer tab did — nothing
    about HOW a fix is confirmed/applied changes, only WHICH tab the action
    lives on.
  - **Rationale the user gave for choosing this over the cheaper banner
    fix:** the count mismatch (Doctor: "4 errors", Fixer: "no errors") is
    confusing enough on its own terms that patching the discoverability
    with a cross-reference banner treats a symptom; a single source of
    truth for "here are the findings, here's what I can fix" is more
    honest than two tabs that can report different numbers for the same
    scan.
  — **Reversibility:** costly — un-completes a previously shipped and
  tested requirement (FIX-02), touches `internal/tuikit/doctor.go`,
  `health_screen.go`, `fixer_screen.go`, `app.go`'s `TabID`/tab-count
  wiring, `cmd/gitid/wiring.go`, and every test file covering those symbols
  (`internal/tuikit/doctor_test.go`, `app_test.go`, and Fixer/Health PTY
  e2e coverage). Per CONTEXT.md's reversibility-gate convention, the
  planner should rate the merge task `one-way` and gate it behind a
  `checkpoint:decision` before implementation, given it reopens a
  previously-`Complete` requirement and changes the main menu's tab count.

### Claude's Discretion
- Exact wording of the strengthened `Differs`-state reason line (D-04) —
  keep it short (fits the existing row's second line without wrapping at
  standard terminal widths).
- Exact border/box styling treatment for the sub-tab bar (D-05) — follow
  existing Lipgloss border conventions already used elsewhere in
  `internal/tuikit` rather than inventing a new border style.
- Whether the merged Doctor screen's "Fix all" batch-walk UX needs any
  adjustment beyond what Fixer's existing `fixerModel` ceremony logic
  already does — the merge should reuse `fixer_screen.go`'s ceremony/batch
  logic as-is where possible, minimizing new logic surface.
- How `TabID`/main-menu numbering renumbers once Fixer's tab is removed
  (e.g. does anything currently keyed `[5]` need to shift, and are there
  hardcoded references to a 5-tab layout in tests/screenshots beyond what's
  explicitly listed in D-06's Reversibility note) — research this fully
  during planning; it is exactly the kind of blast-radius work the
  `checkpoint:decision` gate exists to surface before committing to it.

</decisions>

## Existing Code Insights

### Reusable Assets
- `internal/tuikit/doctor.go`'s shared helpers (`orderedFindings`,
  `groupFindings`, `selectFinding`, `fixableFindings`, `severityRank`) are
  ALREADY tool-agnostic between Health and Fixer — the merge's job is
  recombining two thin screen models around this already-shared core, not
  rewriting the finding logic.
- `fixer_screen.go`'s ceremony/batch-walk logic (`haltBatch`, the `f`/`F`
  key handling, `fixCeremonyFor`) is the direct reuse target for the merged
  screen's fix capability — do not re-derive it.

### Established Patterns
- Global Git's Options screen already demonstrates BOTH patterns this phase
  needs for UXP-01/02/03: reset-on-activate focus, and a placeholder-dot
  column for non-selectable rows. Treat it as the reference implementation,
  not something to redesign from scratch.
- The cross-reference banner pattern ("The doctor found N findings beyond
  these global options. Open Health (N)") already exists on the Global
  SSH/Global Git Options screens — considered for UXP-05 but explicitly
  NOT the chosen fix (D-06 chose the structural merge instead); this
  pattern remains relevant precedent for how gitid surfaces cross-screen
  finding counts elsewhere, unaffected by this phase.

### Integration Points
- Main menu tab count/order (`internal/tuikit/app.go`'s `TabID` enum and
  `tabLabels`) shrinks from 5 to 4 once Fixer is absorbed — every hardcoded
  reference to "5 tabs" or tab index 5 needs an audit pass during planning.

<specifics>
## Specific Ideas

- User's full original bug report (paraphrased, Spanish original in
  `09.4-DISCUSSION-LOG.md`), covering two screenshots:
  1. Why does the Global SSH Options screen focus a middle option
     (IdentitiesOnly) instead of the first, on load?
  2. Why are some options selectable and others not?
  3. The toggle on/off affordance is barely perceptible — can the "radio
     rune" be made bigger?
  4. Global Git's Options screen shows read-only rows with a dot instead of
     a rune, which is fine, but Global SSH should follow the same pattern
     for consistency. Who decides what's read-only, and why — the user
     never asked for "already matches the recommendation" rows to be
     locked, even if it's the recommended value.
  5. Reaching the Global SSH screen's second sub-tab ("Storage & preview")
     is jarring — it's a submenu with no visual cue distinguishing it from
     main-menu navigation, using the same background as everything else.
  6. It's inconsistent that Doctor reports 4 errors while Fixer reports
     none — maybe Fixer should be a derivative of Doctor rather than its
     own main-menu view.
- User explicitly asked for, and received, an explanation of WHY read-only
  rows exist and render the way they do BEFORE any decision was locked
  (see D-02's scope-fence note) — this consultative sequencing matters and
  should inform how any future gray-area discussion in this project is
  run: explain the existing design rationale first, then ask for the
  scope decision.

</specifics>

<deferred>
## Deferred Ideas

- **Full SSH/Git properties browser** — the user asked whether gitid scans
  and could show ALL SSH/git config properties (not just the curated
  `OptionPolicy` table), as a "properties list" feature. Confirmed today's
  scope is a fixed, curated policy table only (GSSH-01/GGIT-01), not a live
  enumeration of every directive/key that exists. The user explicitly asked
  to defer this "to something like 9.5" — flagged as a Phase 9.5 candidate,
  not scoped further here. Needs its own discuss-phase to decide which
  properties are safe/meaningful to surface, read-only vs actionable, and
  how to avoid overwhelming the user with unfamiliar keys.
- **General value-override/editing capability** (letting the user set an
  arbitrary or non-recommended value for an SSH/Git option, not just
  apply-or-not gitid's recommendation) — explicitly discussed and
  explicitly descoped from this phase (D-02). A future phase, if ever
  pursued.
- **CI/CD + installer, GitLab validation, global gitignore** — already
  scoped as Phases 9.1/9.2/9.3, not part of this discussion.
