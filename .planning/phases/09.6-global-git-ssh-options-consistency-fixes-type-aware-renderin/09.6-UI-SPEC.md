# Phase 9.6 — UI Design Contract

> Visual and interaction contract for Phase 9.6 (Global Git/SSH Options
> Consistency Fixes — type-aware rendering, `e`-to-edit, orange-`!`
> disambiguation, one-key-one-home). Written to satisfy `.planning/ONESHOT.md`
> Per-Phase Checklist item 2 for a phase `.planning/ROADMAP.md` marks
> **UI hint: yes**.

**This is a consistency correction on two shipped, working screens**, not a
new surface and not a redesign — the same discipline `09.4-UI-SPEC.md`
established for the previous consistency phase. Every rule below either
restates a pattern already live in `internal/tuikit` verbatim, or extends one
in the SAME idiom. Every claim about current behavior in this document was
read out of the live source while writing it:
`internal/tuikit/globalssh.go` (`optionRow` 1483-1523, `optionRowLine2`
1525-1544, the `handleKey` sub-tab switch ~1126, `applyCeremonyFor` 724-747),

## Ground truth: three defects, restated as UI rules

`09.6-CONTEXT.md` reports three user-observed defects. Restated as contracts:

1. **A row's glyph must tell the truth about its value's type.** Today every
   Options row on both screens renders the same checkbox column regardless of
   whether the underlying value is a boolean gitid can only apply-or-not, a
   closed value set, free text, or a multi-key preset. The checkbox is not
   wrong — it means "include this row in the `a` batch apply" — but on an
   enum or text row it is *insufficient*, because the row shows no value and
   offers no way to choose one.
2. **The orange `!` must mean one thing.** Both `optionRow`
   (`globalssh.go:1500-1503`) and the Git row loop (`globalgit.go:1973-1976`)
   currently render `styleWarning.Render("!")` for BOTH the needs-action state
   and the differs state. Two different situations, one glyph.
3. **A key must have exactly one home.** `user.email`/`user.name` render on
   the Options sub-tab (empty) and again on the general-keys sub-tab (with a
   value), because the Options row reads a DemoState pair nothing ever seeds
   from the machine while the general-keys list reads the real probe.

## Design System

Inherited wholesale from `02-STYLE-SPEC.md` and the shipped `internal/tuikit`
theme. This phase introduces **no new glyph, no new color role, and no new
layout primitive**. The complete vocabulary it uses:

| Role | Token / literal | Source | Used here for |
|---|---|---|---|
| Selection marker | `▸ ` (bold accent) / `  ` | `optionRow`, Git row loop | unchanged |
| Batch-apply checkbox | `glyphToggleOn` / `glyphToggleOff` | both row renderers | unchanged (PD1) |
| Non-selectable placeholder | faint `·` | both row renderers (9.4 D-03) | unchanged |
| Healthy tone | `styleHealthy` `✓` | both row renderers | unchanged |
| Warning tone | `styleWarning` `!` | both row renderers | **narrowed to needs-action only** |
| Inert tone | `styleFaint` `·` | the not-applicable branch in both files | **reused for the differs row** |
| Risk chip | `styleFaint` `[High]` | `optionRow` | unchanged |
| `init.defaultBranch` chip | `styleWarning` `[main vs master]` | Git row loop | unchanged, must not be displaced |
| Field row | `formFieldLine` | `identities.go:456` | the free-text editor |
| Helper/error row | `helperLine` | `identities.go:469` | the free-text editor's hint |
| Radio dot | `glyphRadioOn` / `glyphRadioOff` | Match-strategy group | the enum-cycle list |
| Change affordance copy | `(←/→ change)` faint suffix | Match-strategy header | the enum editor header |
| Width bound | `truncLine(line, width)` | both row renderers | every new composed line |

**Rule S-1 (no new vocabulary).** If a state this phase adds appears to need
a glyph or color not in the table above, that is a signal the state was
modelled wrong. Reuse or re-model; do not extend the palette.

## Layout

### The master row (both screens) — still exactly two lines

`optionRow` and the Git row loop each emit exactly two lines per row, and the
scroll window's arithmetic depends on it. The inline value cell is added to
the **first** line, to the right of the key and its chip; the second line's
`now: X → Y` sentence is untouched.

```
 ▸ [x] !  StrictHostKeyChecking  [Medium]                     ask
      now: ask → accept-new
```

```
 ▸ [x] !  init.defaultBranch  [main vs master]               master
      now: master → main
```

**Rule L-1 (two lines, always).** No row grows a third line in any state,
including while its editor is open. The open editor renders in the DETAIL
pane (Rule L-3).

**Rule L-2 (elision order).** When the composed first line exceeds the list
width, the VALUE cell is elided first — never the key, never the tone glyph,
never the chip. `init.defaultBranch`'s `[main vs master]` chip and
`StrictHostKeyChecking`'s `[Medium]` risk chip are pre-existing, pinned
content; a new cell may not displace them.

**Rule L-3 (the editor lives in the detail pane).** The Options master list is
a scrolling window. An arrow-cycle value list or a text field rendered inline
would break Rule L-1 for every row below it. The open editor renders in the
DETAIL pane — the slot Global Git's fallback-author fields already occupy —
while the master row keeps its two lines and shows the staged value in its
inline cell.

**Rule L-4 (detail-pane row budget).** The open editor's total height —
header + value list or field + reserved helper row + footer — must fit the
detail pane at `frameBodyRows(minFrameHeight)`. The binding worst case is the
longest declared value set in this phase: `diff.colorMoved`'s six values
(`no`, `default`, `plain`, `blocks`, `zebra`, `dimmed-zebra`). A plan that
adds a longer set must re-measure, not assume.

### Row kinds and what each one renders

| Kind | Example rows | Checkbox | Inline value cell | `e` opens |
|---|---|---|---|---|
| apply-or-not (toggle) | `ForwardAgent`, `HashKnownHosts`, `IdentitiesOnly`, `UseKeychain`, `core.ignorecase`, `user.useConfigOnly`, `push.autoSetupRemote`, `pull.rebase`, `fetch.prune` | yes (unchanged) | **no** | nothing |
| closed value set (enum) | `StrictHostKeyChecking`, `AddKeysToAgent`, `merge.conflictstyle`, `diff.colorMoved` | yes (unchanged) | **yes** | arrow-cycle list |
| free text | `init.defaultBranch`, `user.email (global fallback)` | yes (unchanged) | **yes** | `formFieldLine` field |
| multi-key preset (bundle) | `core.autocrlf / core.eol`, `alias (8 shortcuts)`, `color (ui/branch/diff/status)` | yes (unchanged) | **no** | nothing |

**Rule L-5 (the checkbox is additive, never subtractive).** Type-aware
rendering ADDS a value cell and an `e` affordance. It never removes the
checkbox from any row. The checkbox's meaning is unchanged on every row:
"include this row in the `a` batch apply of gitid's recommendation". It is not
and never becomes a value control.

## Interaction contract

### The gesture set (identical on both screens, every editable row)

| Key | While browsing | While an editor is open |
|---|---|---|
| `e` | opens the editor on an edit-eligible row | — |
| `←` / `→` | switches sub-tab | **cycles the enum value set** (never switches sub-tab) |
| printable | screen shortcuts | reaches the text input (free-text mode only) |
| `Tab` | moves field focus on the fallback-author row | moves between the fallback pair's two fields; **inert** on a single-field editor |
| `Enter` | row-specific (unchanged outside the editor) | **commits**: stages the value, marks the row chosen, closes the editor |
| `Esc` | leaves the screen | **dismisses**: restores the pre-edit value, drops the staged override, closes the editor |
| `a` | opens the apply ceremony | — (swallowed) |
| `ctrl+p` | opens the command palette | **still opens the command palette** |
| `ctrl+c` | app/terminal default | **app/terminal default — never swallowed** |

**Rule I-1 (one trigger, one commit key, one dismiss key).** `e` / `Enter` /
`Esc` mean the same thing on every editable row of both screens, regardless of
the row's kind. Only the mechanics between open and close differ.

**Rule I-2 (Enter and Esc must differ).** `Esc` restores the value the row
held at the moment the editor OPENED. A set/dismiss pair whose two keys
produce the same outcome is the inconsistency this phase exists to remove. The
snapshot is taken on open, not on screen activation, so a second edit session
reverts to what the first session committed.

**Rule I-3 (Enter stages, `a` writes).** `Enter` never touches disk. A staged
value reaches `~/.ssh/config` or `~/.gitconfig` only through the existing
preview + typed-confirm + timestamped-backup ceremony reached with `a`. The
ceremony's preview must name the STAGED value, never the policy
recommendation — a user must never confirm a diff that shows a value other
than the one they chose.

**Rule I-4 (the editor guard precedes the sub-tab binding).** `←`/`→` are
bound to sub-tab switching on both screens. The editor's key guard sits ahead
of that binding — on Global Git ahead of BOTH sites, the zero-options branch
and the generic case. The observable contract, and the one a test must assert,
is that cycling changes the value AND leaves the breadcrumb naming the same
sub-tab. A test that only checks the value passes with the guard missing.

**Rule I-5 (global keys are never trapped).** The guard's
"every other key is swallowed" rule has an explicit pass-through list.
`ctrl+p` is intercepted by `App.handleKey` (`app.go:433`) before any screen
sees it and must keep opening the palette with an editor open; `ctrl+c` is not
handled anywhere in `internal/tuikit` and must keep reaching whatever handles
it today. An editor a user cannot escape except through one key is a modal
trap, which no other gitid surface is.

**Rule I-6 (edit eligibility includes already-set rows).** A row whose value
already matches gitid's recommendation is still a value the user may
deliberately change. Refusing to open the editor there would recreate the
original complaint — "I need to go to Set keys to type into it". Edit
eligibility excludes only: toggle rows, bundle rows, not-applicable rows, rows
carrying a probe error, and rows with no writable target.

**Rule I-7 (a staged override is visible on a row that has no checkbox).** An
already-set row is not selectable, so it has no checkbox to mark. Its staged
change is communicated by the inline value cell showing the staged value
marked as pending — never by drawing a checkbox on a row that does not have
one.

### The enum editor (detail pane)

Reuses the Match-strategy group's idiom verbatim: a bold header naming the
directive with the faint `(←/→ change)` suffix, an **always-drawn** reserved
hint row beneath it (the 02-STYLE-SPEC.md STABLE HINT ZONE convention the
strategy group already implements at `identities.go:1042-1047`), then one row
per declared value with `glyphRadioOn`/`glyphRadioOff` and the cursor row in
`FieldFocused`. Cycling arithmetic is modulo the value-set length in both
directions, copied from `gitForm.handleEdit` (`identities.go:955-961`).

**Rule I-8 (the cycle indexes only the declared set).** A current value that is
not a member of the declared set — an exotic form such as
`AddKeysToAgent=30m`, or an unrecognised string — positions the cursor at
index 0. It is NEVER appended to the set, and opening plus dismissing the
editor never rewrites it. The row's second line keeps showing the real current
value so the user is not misled about what their machine currently says.

### The free-text editor (detail pane)

Reuses `formFieldLine` and `helperLine` directly — the identity wizard's own
primitives, per `09.6-CONTEXT.md` D-03 — never a bespoke Options-screen
widget. `formFieldLine` already gives the fixed 2-cell marker gutter, the
`padRight(label, 16)` bold label and the always-present `[…]` brackets in both
the focused and blurred states.

**Rule I-9 (the helper row is always reserved AT THIS CALL SITE).** The
Options free-text editor always emits its `helperLine` row, empty text
included, so the detail pane does not reflow as the user types or as a
validation error appears and clears. This is the caller-side discipline the
Match-strategy group already demonstrates. It is *not* a claim that
`formFieldLine`/`helperLine` are always-reserved primitives today — they are
not: the wizard's own SSH-form helpers at `identities.go:519-569` are emitted
conditionally per focus and validation state. Making the WIZARD's rows
always-reserved is Phase 9.7's D-07 and is out of scope here; this phase
delivers the property for its own editor without touching `identities.go`.

**Rule I-10 (validation is inline and pre-ceremony).** An invalid typed value
renders its error through `helperLine(..., true)` on the detail pane and does
NOT open the apply ceremony — the same shape the custom-key form already uses
when its own plan fails (`globalgit.go:1016-1040`). `init.defaultBranch` is
validated by git's real ref-name grammar, not by the custom-key render guard.

## Copywriting Contract

Per `09.6-CONTEXT.md`'s Claude's-Discretion clause, all new copy takes its
vocabulary from what these screens already say. Binding rules:

- **C-1.** The footer action that opens an editor uses the same short verb the
  Global Git fallback row's footer already uses (`globalgit.go:2090`,
  `{Key: ..., Label: "edit"}`).
- **C-2.** The in-editor footer names the commit and dismiss keys in the same
  `{Key, Label}` shape every other footer action on these screens uses; it
  REPLACES the browse-mode footer wholesale while the editor is open, the way
  the ceremony branch already does.
- **C-3.** The enum editor's header carries the faint `(←/→ change)` suffix
  verbatim from the Match-strategy header.
- **C-4.** Helper-row wording follows the wizard's own helper lines in
  register: one short sentence, no jargon, no trailing period on a fragment.
- **C-5.** Every new user-facing string is registered in BOTH gates — the
  `Makefile` `gate-copy-freeze` presence list and the
  `TestFrozenPropertiesCopy` byte-exact table. The Makefile gate is a presence
  grep and cannot prove a value; the Go table is the authoritative contract.
- **C-6.** The general-keys sub-tab label becomes the user's own wording from
  the bug report. The retired literal must not survive anywhere in the module
  source, enforced by a source-walk test, not by a one-off search.

## Color

No new color role. The only color CHANGE in this phase is a reassignment
within the existing palette:

| Row state | Before | After |
|---|---|---|
| needs-action | `styleWarning` `!` | unchanged |
| differs / set-but-differs | `styleWarning` `!` | **`styleFaint` `·`** |
| already-set | `styleHealthy` `✓` | unchanged |
| not-applicable | `styleFaint` `·` | unchanged |

**Rule K-1.** The differs row keeps its full explanatory second line
(`GlobalSSHWordDiffersUser` / `GlobalSSHWordDiffersOutside` on SSH, the Phase
9.4 differs wording on Git). Removing the alarm glyph must not remove the
explanation — the row still has something to say, it just is not a warning.

**Rule K-2.** This rule applies identically on both screens (`09.6-CONTEXT.md`
D-07). A fix landing on one screen only re-creates the asymmetry the phase is
closing.

## Registry Safety

- A visual-regression entry, the capture-driver keystrokes that produce its
  frame, and the dummy fixture data that makes the state reachable ship in the
  SAME commit. `CaptureGlobalSSHScreens` and `CaptureGlobalGitScreens` both
  hard-fail on an applicable spec with no captured frame.
- A state that genuinely cannot be driven in-process is recorded
  non-applicable on both surfaces with a **machine-checkable** reference to the
  real-PTY case carrying its evidence — a named test the tooling resolves to a
  real function and actually runs, not a prose mention.
- Every new entry has a persistent, automated negative control proving the
  gate can fail on it. A registration whose fail path exists only as a one-off
  manual note is a vacuous gate.
