# Phase 9.6: Global Git/SSH Options Consistency Fixes - Context

**Gathered:** 2026-09-08
**Status:** Ready for planning

<domain>
## Phase Boundary

Fix concrete UX inconsistencies a direct user audit found in the Global Git
Options and Global SSH Options screens: a checkbox glyph used regardless of
the underlying value's type (boolean, enum, or free text), an orange `!`
warning glyph that conflates two different classifier states, and a real bug
where `user.email`/`user.name` are read through two independent,
unreconciled paths (one for the Options row, one for the "Set keys" tab),
causing the value to appear differently — or require pressing a key
twice — between the two sub-tabs. This phase does NOT touch the
`GlobalGitOptionState`/`GlobalSSHOptionState` classifier enums themselves
(`internal/globalgit/classify.go`, `internal/globalssh/classify.go`) — those
are already correct; every fix here is rendering- and read-path-level.

</domain>

<decisions>
## Implementation Decisions

### Type-aware Options rendering
- A boolean option row renders the existing toggle glyph (`[✓]`/`[ ]`) only —
  unchanged from today.
- An enum option row (e.g. `StrictHostKeyChecking`) shows its current value
  inline; pressing `e` opens arrow-cycle selection (←/→ steps through the
  known valid values — the same convention the identity wizard's
  Match-strategy radio group already uses), Enter commits, Esc dismisses.
  Not a free-typed field — the value set is known/closed.
- A text option row (e.g. `user.email`) shows its current value inline;
  pressing `e` opens the SAME field pattern the identity wizard uses —
  `formFieldLine`/`helperLine`, fixed width, always-reserved hint row (Phase
  9.7's D-06/D-07) — not a bespoke inline-edit widget invented for this
  screen. Enter commits, Esc dismisses.
- One uniform entry gesture (`e`) across enum and text; the editing
  mechanics differ by type once open (arrow-cycle vs. type-in-field), but
  the trigger key, commit key (Enter), and dismiss key (Esc) are identical
  across both — explicit "consistency with the other views" requirement.

### Orange `!` disambiguation
- The `!` glyph is triggered ONLY by the `NeedsAction` state (unset, a real
  write would happen). This is the only state the user's original spec
  called "no recomended."
- `Differs` (set to a different, non-recommended value where gitid's block
  would be a no-op) renders with NO `!` — plain row plus the existing
  second-line explanation text (Phase 9.4's D-04 wording convention).
- Applies identically to both Global Git Options and Global SSH Options —
  Global SSH never received the fix Phase 9.4 gave Global Git, so both
  screens currently share this exact bug.
- No change to the classifier enum (`NeedsAction`/`AlreadySet`/`Differs`/
  `NotApplicable` in `internal/globalgit/classify.go` /
  `internal/globalssh/classify.go`) — this is purely a rendering fix in each
  screen's row-render function.

### user.email/user.name single source of truth + "Set keys" relabel
- `ReadGitFallbackAuthor` (`internal/gitconfig/fallbackauthor.go:79` — the
  dedicated managed-block reader) stays authoritative for the Options row's
  displayed value — it reads exactly what gitid itself manages.
- `AllGitSetKeys` (`internal/globalgit/properties.go:46`,
  `cmd/gitid/wiring.go:2123`) excludes any key gitid's curated `Policy`
  table already manages (`internal/globalgit/policy.go:124-238`) from its
  result — one key, one home; no key appears on both sub-tabs.
- Rename the "Set keys" sub-tab label to "Other keys" (the user's own
  wording from the original bug report: "Set key is fine for unknown keys
  only, we can relabel that as Others keys or simple add new keys") — same
  screen/logic underneath, the label now accurately reflects that it only
  ever shows non-policy-managed keys once the exclusion above lands.
- The custom-key add flow (`n` → `renderCustomKeyForm` →
  `CommitCustomGitKey`) is unaffected — it already targets exactly the
  "unknown key" case this relabel clarifies.

### Claude's Discretion
- Exact copy for the arrow-cycle selection hint line and the `e`/Enter/Esc
  footer action labels — follow existing footer-action wording conventions
  in `globalgit.go`/`globalssh.go` rather than inventing new phrasing.
- Whether the enum arrow-cycle widget is a new small helper or reuses
  existing radio-group rendering code from `gitForm.view`'s Match-strategy
  block — implementation detail, not a user-facing decision.

</decisions>

## Existing Code Insights

### Reusable Assets
- `gitForm.view`'s Match-strategy radio group (`internal/tuikit/
  identities.go:1050-1062`) is the direct precedent for the enum
  arrow-cycle widget — same ←/→-to-change, always-visible-options
  convention.
- `formFieldLine`/`helperLine` (`internal/tuikit/identities.go:456,469`) —
  the wizard's field-rendering helpers this phase's text-field `e`-to-edit
  reuses directly, per Phase 9.7 parity.

### Established Patterns
- Global Git's Options screen already has the placeholder-dot convention for
  non-selectable rows (Phase 9.4 D-03) — the type-aware rendering in this
  phase layers on top of that, not replacing it.
- The `NeedsAction`/`AlreadySet`/`Differs`/`NotApplicable` classifier
  vocabulary (`internal/globalgit/classify.go`, `internal/globalssh/
  classify.go`) is already correct and shared by both screens — this phase
  is a consumer of that vocabulary, not a modifier of it.

### Integration Points
- `AllGitSetKeys`'s policy-key exclusion is the integration point between
  `internal/globalgit/policy.go`'s curated table and `internal/globalgit/
  properties.go`'s general probe — the planner must trace exactly which
  keys the Policy table manages to build the exclusion set correctly.
