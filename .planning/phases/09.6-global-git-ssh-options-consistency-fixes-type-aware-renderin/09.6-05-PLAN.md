<objective>
Make "one key, one home" true and provable, keep everything the user set visible exactly once,
and relabel the general-keys sub-tab so its name matches what it now contains.

Purpose: this is the structural half of the defect in the original bug report ("now we have
user.email in Options and is displayed again where Set keys lives"). Plan 09.6-04 fixed what
the Options row DISPLAYS; this plan removes the competing second display and proves that
removing it hides nothing. The relabel only becomes truthful after the exclusion lands, so the
two ship in the same phase and in dependency order.

Output: a raw-key partition proof on a real machine, an Options fallback row that names the
effective author pair and its origin, and a sub-tab label that matches its contents — with a
machine-checkable test that the retired label is gone from the tree.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| raw `git config --list --show-origin` output -> the exclusion filter -> rendered key list | the filter decides what the user is allowed to see; a wrong decision hides real state |
| curated policy table -> the managed raw-key set | the exclusion's only legitimate source of authority |
| frozen copy gate -> `make test` | a label change that skips the gate turns the whole test target red |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-09.6-25 | Denial of Service | over-exclusion in `AllGitSetKeys` | critical | mitigate | An exclusion that is too broad silently hides a key the user set and needs to see — an availability failure on a tool whose whole purpose is making config visible. Mitigated by sourcing the exclusion ONLY from `ManagedRawGitKeys()`, by Task 1 Test 5's real-machine union/intersection proof, by PD21's effective-pair-with-origin rendering for the two keys that leave the general list, and by Task 3's end-to-end re-proof through the compiled binary. |
| T-09.6-26 | Spoofing | under-exclusion leaving a duplicated key | high | mitigate | A key visible in two places with two different values misrepresents the machine's state — the exact defect reported. Mitigated by the member-key lookup replacing the display-key lookup and by the empty-intersection half of Test 5. |
| T-09.6-27 | Information Disclosure | an externally-set `user.email` becoming invisible | high | mitigate | PD21: the Options fallback row names the effective value and its origin file when gitid's managed block is not what supplies it. Pinned by Task 1 behavior Tests 8 and 9 and by Task 3 behavior Test 4. Without this the exclusion would be a silent data-loss bug that every unit test still passes. |
