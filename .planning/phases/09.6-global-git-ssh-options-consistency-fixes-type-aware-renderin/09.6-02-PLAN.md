**PD25 (the editor renders in the DETAIL pane, never inline in the master list).** The
Options master list is a scrolling window with a per-row budget of exactly two lines, pinned
by `optionRowLines`. An open editor's value list cannot be rendered inside it without
breaking that invariant for every row below. The open editor renders in the DETAIL pane — the
same slot Global Git's fallback-author fields already occupy — while the master row keeps its
two lines and shows the staged value in its inline cell. This is the divergence
`09.6-PATTERNS.md` flagged from the wizard's always-visible radio group, which lives in a
fixed-height form pane rather than a scrolling list. `09.6-UI-SPEC.md` restates this as
Rule L-3 and adds Rule L-4: the open editor's total height must fit the detail pane at
`frameBodyRows(minFrameHeight)`, whose binding worst case in this phase is
`diff.colorMoved`'s six-value set.

**PD46 (the height bound is measured against the worst case, which this wave can only reach by
driving the shared editor directly).** Cycle-3 review caught a real gap in Rule L-4's proof:
`diff.colorMoved`'s six-value set belongs to the GIT policy table, and no Git screen grows an
editor until plan 09.6-03. The only value set reachable through THIS plan's screen is
`StrictHostKeyChecking`'s four values, so a Test 13 that drives only the SSH screen measures a
four-row list and silently reports the wrong bound as satisfied — the six-value case would
arrive one wave later with nothing checking it.

The fix keeps the bound in this wave, where the shared editor is built, by testing the editor
rather than the screen. The editor type `internal/tuikit/optioneditor.go` introduces (PD17) is
constructed from a value set and a mode; it does not know or care which policy table supplied
the set. So Test 13 drives it TWICE: once through the real SSH screen with
`StrictHostKeyChecking`'s four values, proving the integrated path renders inside the pane; and
once by constructing the editor directly on a literal six-element value set — the exact list
PD7 locks for `diff.colorMoved`, restated in the test with a comment naming PD7 as its source —
proving the phase's declared worst case fits. The second half needs no Git screen and no Git
backend, which is precisely why it can and must land here rather than being deferred.

Both halves measure from the renderer, never from a hard-coded row count. If the six-value
construction does NOT fit `frameBodyRows(minFrameHeight)`, that is a real finding this wave
must surface rather than absorb: record it in the SUMMARY and treat it as a blocking input to
plan 09.6-03, which is the wave that would ship the overflowing row. Plan 09.6-03 re-measures
the same bound through the real Git screen once `diff.colorMoved` is editable there, so the
worst case is proven twice — synthetically here, integrated there — and neither proof is the
other's substitute. (Resolves the cycle-3 09.6-02 LOW "Test 13 measures against the six-value
worst case but as written can only exercise a four-value SSH set through the real screen".)

**PD33 (an exotic CURRENT value is rendered honestly and never silently normalized).** PD6
deliberately classifies `ForwardAgent` as a toggle and `AddKeysToAgent` as an enum, leaving
their exotic real-world forms — a socket path, a `$ENVVAR` name, a `30m` time interval — to
PROP-04's custom-directive flow. That is a rationale-backed decision, not an oversight, but
it leaves one behavior unpinned: what a row does when the value ALREADY ON THE MACHINE is one
of those forms. This plan pins it:
- The row's second line keeps showing the real current value verbatim (via the untouched
  `optionRowLine2`), so the user is never told their machine says something it does not.
- For an ENUM row whose current value is outside the declared set, the editor opens with the
  cursor at index 0. The exotic value is NEVER appended to the value set and never becomes a
  cycleable option — the set is the curated policy table's, not the machine's.
- Opening the editor and pressing the dismiss key leaves NO staged override, so an exotic
  current value can never be silently rewritten by a look-and-leave. Only an explicit commit
  stages a replacement, and only the `a` ceremony writes it.
- For a TOGGLE row (`ForwardAgent`), an exotic current value changes nothing at all: the row
  has no editor and no value cell (UI-SPEC row-kind table), so the apply-or-not semantics are
  unaffected.
(Resolves the cycle-2 09.6-01 MEDIUM "no test pins exotic current-value forms".)

**PD34 (the editor guard never traps a global key).** The guard's "every other key is
swallowed" rule carries an explicit pass-through list, and the two members are established by
reading the live source rather than assumed:
- `ctrl+p` is intercepted by `App.handleKey` at `internal/tuikit/app.go:433` BEFORE any
  screen's handler runs, so it already cannot be swallowed. The contract is that this stays
  true with an editor open: the palette opens, and dismissing the palette with Esc returns to
  the screen with the editor still open and its snapshot intact.
- `ctrl+c` is handled NOWHERE in `internal/tuikit` (verified: no `"ctrl+c"` literal and no
  `tea.Quit` outside the quit overlay at `app.go:449`). The guard must therefore report it
  UNHANDLED so it keeps reaching whatever handles it today, exactly as it does when no editor
  is open. This plan does not add a ctrl+c handler; it forbids the editor from becoming the
  first thing in the app to eat one.
Esc remains the editor's own dismissal path. An editor a user can only leave through one key
would be a modal trap no other gitid surface is. (Resolves the cycle-2 09.6-02 MEDIUM
"ctrl+c/ctrl+p behavior while editing is untested".)
