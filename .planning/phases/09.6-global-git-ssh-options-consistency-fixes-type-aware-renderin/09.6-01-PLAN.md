## Plan-level decisions this plan LOCKS (recorded here because no SPEC.md exists)

These resolve the three items RESEARCH.md escalated plus the one architectural question
CONTEXT.md left implicit. They bind every later plan in this phase.

**PD1 (additive checkbox).** The Options-screen checkbox column keeps its EXISTING
meaning on every row: "include this row in the `a` batch apply of gitid's recommendation".
It is NOT a value toggle and is NOT removed from enum or text rows. What type-aware
rendering ADDS is (a) the resolved current value shown on the row for enum/text rows and
(b) the `e` affordance. CONTEXT.md's "a boolean option row renders the existing toggle
glyph only" is read as "bool rows gain nothing new", not "enum/text rows lose the
checkbox". Rationale: the subtractive reading would rewrite ~41 existing
`init.defaultBranch` assertions in `internal/tuikit/globalgit_test.go` alone and would
delete the batch-apply mechanic those assertions pin, for no user-requested benefit.

**PD2 (Enter stages, `a` writes).** "Enter commits" commits the edited value into the
model as a staged override and marks the row chosen. The value reaches disk only through
the row's existing `a` -> preview -> typed-confirm -> backup ceremony. Rationale:
CLAUDE.md forbids writing a user's `~/.ssh/config` or `~/.gitconfig` without a timestamped
backup, an idempotent managed block, and explicit confirmation. No new write mechanism is
created; the existing `runGlobalSSHApply` / `runGlobalGitApply` lifecycle writers stay the
only ones.

**PD3 (RESEARCH Open Question 2 — Esc really does revert).** "Esc dismisses" requires the
new revert-to-prior-value mechanism, not a relabel of today's exit-without-reverting
behavior. Rationale: the user's own wording is "enter for set, ecs to dismiss"; a set/
dismiss pair whose two keys produce identical outcomes is exactly the inconsistency this
phase exists to remove. Mechanism: snapshot the pre-edit value when `e` opens the editor;
Esc restores it and clears the staged override.

**PD4 (RESEARCH Open Question 3 — `Selectable()` asymmetry stays).** Global Git's
`Differs` rows remain non-selectable and Global SSH's remain selectable. No plan in this
phase edits either `Selectable()` body. It is out of scope, was not requested, and
reversing it would remove an SSH capability nobody asked to lose.

**PD5 (separate seam, zero churn).** The value-override write path is a NEW, SEPARATE
planner interface per screen, mirroring the project's own precedent (the D9
fallback-author seam is deliberately separate from `GlobalGitPlanner`; PROP-03's
`GitCustomKeyPlanner` and PROP-04's SSH custom-directive seam are likewise separate). The
existing `CommitGlobalSSH([]string)` / `CommitGlobalGit([]string)` signatures are NOT
changed — dozens of existing call sites in `cmd/gitid/wiring_test.go` depend on them.

**PD6 (SSH value-domain classification, verified this session).** Verified against
`OpenSSH_10.2p1` `ssh_config(5)` on the planning machine, not recalled:
`StrictHostKeyChecking` = enum `{yes, accept-new, ask, no}` (`off` is a documented alias
of `no` and is deliberately NOT offered — gitid would never write the alias when the
canonical spelling exists). `AddKeysToAgent` = enum `{yes, no, confirm, ask}` (its
`<time interval>` form is free text and is deliberately NOT offered through an
arrow-cycle; PROP-04's custom-directive flow already covers it). `ForwardAgent` = bool,
DESPITE its man page also accepting a socket path or a `$ENVVAR` name — offering a socket
path through an arrow-cycle is nonsense, so gitid classifies it apply-or-not and leaves
the exotic forms to PROP-04. `HashKnownHosts`, `IdentitiesOnly`, `UseKeychain` = bool.
