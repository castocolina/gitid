## Canonical numbering for CONTEXT.md's twelve locked decisions

plan set establishes the canonical numbering below and every plan in the phase cites it.

| D-01 | A boolean option row renders the existing toggle glyph only — unchanged from today. |

## Plan-level decisions this plan LOCKS (recorded here because no SPEC.md exists)

These bind every later plan in the phase. PD1-PD13 were locked by the previous plan set and
are restated here because this plan is now the phase's contract home; PD14-PD24 are new,
and each one resolves a specific finding in `09.6-REVIEWS.md` (see the Review Dispositions
Ledger at the end of this file).

**PD1 (additive checkbox).** The Options-screen checkbox column keeps its EXISTING meaning
on every row: "include this row in the `a` batch apply of gitid's recommendation". It is NOT
a value toggle and is NOT removed from enum or text rows. What type-aware rendering ADDS is
(a) the resolved current value shown on the row for enum/text rows and (b) the `e`
affordance. CONTEXT.md's "a boolean option row renders the existing toggle glyph only" is
read as "bool rows gain nothing new", not "enum/text rows lose the checkbox". Rationale: the
subtractive reading would rewrite roughly 41 existing `init.defaultBranch` assertions in
`internal/tuikit/globalgit_test.go` alone and would delete the batch-apply mechanic those
assertions pin, for no user-requested benefit.

**PD2 (Enter stages, `a` writes).** "Enter commits" commits the edited value into the model
as a staged override and marks the row chosen. The value reaches disk only through the row's
existing `a` -> preview -> typed-confirm -> backup ceremony. Rationale: CLAUDE.md forbids
writing a user's `~/.ssh/config` or `~/.gitconfig` without a timestamped backup, an
idempotent managed block, and explicit confirmation. No new write mechanism is created; the
existing `runGlobalSSHApply` / `runGlobalGitApply` lifecycle writers stay the only ones.

**PD3 (Esc really does revert).** "Esc dismisses" requires a real revert-to-prior-value
mechanism, not a relabel of today's exit-without-reverting behavior. Rationale: the user's
own wording is "enter for set, ecs to dismiss"; a set/dismiss pair whose two keys produce
identical outcomes is exactly the inconsistency this phase exists to remove. Mechanism:
snapshot the pre-edit value when the editor opens; Esc restores it and clears the staged
override.

**PD4 (`Selectable()` asymmetry stays).** Global Git's `Differs` rows remain non-selectable
and Global SSH's remain selectable. No plan in this phase edits either `Selectable()` body.
It is out of scope, was not requested, and reversing it would remove an SSH capability
nobody asked to lose.

**PD5 (separate seam, zero churn).** The value-override write path is a NEW, SEPARATE
planner interface per screen, mirroring the project's own precedent (the D9 fallback-author
seam is deliberately separate from `GlobalGitPlanner`; PROP-03's `GitCustomKeyPlanner` and
PROP-04's SSH custom-directive seam are likewise separate). The existing
`CommitGlobalSSH([]string)` / `CommitGlobalGit([]string)` signatures are NOT changed —
dozens of existing call sites in `cmd/gitid/wiring_test.go` depend on them.

**PD6 (SSH value-domain classification, verified against `OpenSSH_10.2p1`'s
`ssh_config(5)` on the planning machine, not recalled).** `StrictHostKeyChecking` = enum
`{yes, accept-new, ask, no}` (`off` is a documented alias of `no` and is deliberately NOT
offered — gitid would never write the alias when the canonical spelling exists).
`AddKeysToAgent` = enum `{yes, no, confirm, ask}` (its `<time interval>` form is free text
and is deliberately NOT offered through an arrow-cycle; PROP-04's custom-directive flow
already covers it). `ForwardAgent` = toggle, DESPITE its man page also accepting a socket
path or a `$ENVVAR` name — offering a socket path through an arrow-cycle is nonsense, so
gitid classifies it apply-or-not and leaves the exotic forms to PROP-04. `HashKnownHosts`,
`IdentitiesOnly`, `UseKeychain` = toggle.

`git help config` / `git help diff` on the planning machine, not recalled).**

**PD44 (a row's value KIND is platform-independent; only its APPLICABILITY is not).** One SSH
policy row — `UseKeychain` (`internal/globalssh/policy.go:37`) — carries `Platform: "darwin"`,
so on Linux it renders as not-applicable and its kind is never exercised by any screen test on
Linux CI. That makes a future silent reclassification of that one row invisible on the
platform this project's CI runs, which is the whole reason PD7's table is asserted per-row by
name. The rule: the value kind is a property of the DIRECTIVE's value domain, not of the
machine — `UseKeychain` accepts `yes`/`no` on macOS and would accept `yes`/`no` anywhere, so
it is apply-or-not on every platform, and a not-applicable row still carries its true kind
rather than a zero value. Task 1 behavior Test 3b pins this by reading the kind straight off
the policy table with no platform predicate consulted and no OS branch or build tag in the
test, so it runs and means the same thing on Linux and macOS alike. (Resolves the cycle-3
09.6-01 LOW "no test pins that a platform-excluded toggle row still classifies".)

**PD45 (`CurrentValue` is sanitized because it is the only field carrying bytes gitid did not
write).** Cycle-3 review asked why the sanitization pass is scoped to `CurrentValue` while
`GlobalSSHOptionStates` also composes `Recommended` and `Provenance`. The answer is a
provenance rule, not an oversight, and Task 1's action now states it beside the call:
`Recommended` is a Go string constant in gitid's own curated policy table, and `Provenance` is
composed by gitid from its own classifier vocabulary (`b.globalSSHProvenanceLabel(st)`) —
neither can carry a byte a user's config file supplied, so scrubbing them would be a no-op
that falsely implies they are untrusted. `CurrentValue` alone originates in a file gitid did
not write. The rule generalises: any DTO field whose bytes come from a probe gets the pass;
any field gitid composes from its own literals does not. A future plan that makes
`Recommended` or `Provenance` probe-derived extends the sanitization with it. (Resolves the
cycle-3 09.6-01 LOW "the plan scopes sanitization to `CurrentValue` only without saying why
the others are exempt".)

**PD8 (`init.defaultBranch` is text, and nothing breaks).** Its real value domain is any
valid git ref name, so the honest classification is text. RESEARCH.md's Pitfall 5 warned
this would break roughly ten existing assertions — that warning assumed the subtractive
reading of CONTEXT.md in which a text row loses its checkbox. Under PD1 the checkbox stays
on every row, so `init.defaultBranch` remains selectable, `space`-toggleable and
`chosen`-map-driven exactly as its existing assertions pin it, and simply gains an inline
value plus (in plan 09.6-04) a free-text editor. The executor MUST confirm this empirically:
run the existing Global Git suite unchanged before touching any test file, and if any
assertion does break, fix the RENDER, not the assertion, unless the assertion is provably
about a behavior CONTEXT.md changed.

**PD9 (the fallback-author row's WRITE path is unchanged).** The D9 fallback ceremony
reached with `a` stays the row's ONE writer, and the fallback pair is never routed through
the option-value seam — that row has `Members: nil`, is not an options-apply target, and has
its own dedicated ceremony. Plan 09.6-04 changes only WHICH KEY starts the edit, what Esc
does once open, and where the row's DISPLAYED value is read from (PD18).

existing entry point covers a case, widen `internal/gitconfig` (PD19 does exactly that)

**PD13 (the new label, and the freeze discipline it demands).** The general-keys sub-tab is
renamed to the user's own wording from the bug report. The exact final string is

**PD14 (preview is pure; only commit writes).** The option-value seam's PLAN method never
calls `runGlobalSSHApply` or `runGlobalGitApply` in any form, with any policy value. Those
functions write after their confirmation stage; a preview that entered them would violate
preview-before-confirm even with `DryRun` set, because a future edit to the stage table
would silently make the preview a writer. The plan method composes candidate bytes and a
diff and returns; only the seam's COMMIT method calls the lifecycle writer, and it is the
only layer permitted to assert `confirmationAlreadyObtained`. Pinned by a test that asserts
the target file's bytes are unchanged and no backup file exists after a plan call.
(Resolves 09.6-01 HIGH "confirmationAlreadyObtained during preview" and 09.6-02 HIGH
"preview and commit can diverge".)

**PD15 (one override request type, one explicit connection point).** The staged value
travels as `tuikit.OptionValueOverride{Key, Value}` from the model through the seam, and is
converted ONCE at the wiring boundary into `lifecyclePolicy.Overrides` (`map[string]string`)
— lifecycle types never learn a tuikit type and vice versa, the same one-way conversion
discipline `toGlobalSSHOptionState` already follows. The ceremony connection point is
explicit and conditional, NOT a parallel path: `globalSSHModel.applyCeremonyFor`
(`internal/tuikit/globalssh.go:724-747`) and `globalGitModel.baselineCeremonyFor`
(`internal/tuikit/globalgit.go:774-778`) call the pre-existing
`GlobalSSHApplyPlan`/`GlobalGitApplyPlan` when the chosen set carries NO staged override,
and the new seam's plan method when it does; the `ceremonyConfirmed` branches
(`globalssh.go:925-935`, `globalgit.go:945-951`) dispatch `CommitGlobalSSH`/`CommitGlobalGit`
or the seam's commit method under the SAME predicate. The two paths are never mixed within
one ceremony. (Resolves 09.6-01 HIGH "the new planner has no specified connection point".)

**PD16 (edit eligibility and apply eligibility, stated per state).**
- *Edit eligibility* (the row answers the edit key): the row's kind is enum or text, AND its
  `ProbeError` is empty, AND its state is not not-applicable, AND — on SSH — it is writable
  to `Host *`, or — on Git — it has a writable member (the fallback-author row is the one
  deliberate exception, wired by plan 09.6-04 through its own dedicated ceremony). Edit
  eligibility deliberately INCLUDES already-set and differs rows: a value that already
  matches gitid's recommendation is still a value the user may deliberately change, and
  refusing to open the editor there would recreate the "I have to go to the other sub-tab to
  type into it" complaint this phase exists to remove.
- *Apply eligibility* (the row joins the `a` batch): today's rule
  (`appliedOption.needsAction()` on SSH, `GlobalGitOptionView.Selectable()` on Git) OR the
  row carries a staged override. `applyChosen` (`internal/tuikit/globalssh.go:632-638`) and
  `gitApplyChosen` (`internal/tuikit/globalgit.go:659-667`) gain the staged-override arm; a
  staged override on an already-set row must NOT be silently dropped from the apply set.
- *Neither predicate changes `Selectable()`* (PD4). Because an already-set row is not
  selectable, its staged override is surfaced by the inline value cell showing the staged
  value marked as pending — never by drawing a checkbox on a row that has none.
- *Tally*: the ceremony's "N of M" denominator counts rows that need attention OR carry a
  staged override, so a staged override on an already-set row can never produce a receipt
  reading more applied than pending.
(Resolves 09.6-01 MEDIUM "applyChosen filters on needsAction()".)
