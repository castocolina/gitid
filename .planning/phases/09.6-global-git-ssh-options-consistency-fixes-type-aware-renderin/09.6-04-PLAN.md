<authority>
This plan inherits every decision `09.6-01-PLAN.md`, `09.6-02-PLAN.md` and
`09.6-03-PLAN.md` lock in their `<authority>` blocks.

**PD11 (the exclusion filters, it does not merely tag).** CONTEXT.md's D-10 says
`AllGitSetKeys` "excludes" policy-managed keys from its result. Today the function computes
a `PolicyBacked` flag and appends the row anyway. The fix must SKIP the append, not just
set a flag — otherwise the key still renders on both sub-tabs and the reported defect
survives.

**PD12 (`ReadGitFallbackAuthor` stays authoritative for the Options row).** CONTEXT.md's
D-09 is explicit: the dedicated managed-block reader remains the source of the Options
row's displayed value. This plan does NOT change what the Options row reads; it removes the
competing second display of the same keys from the other sub-tab.

**PD13 (the new label, and the freeze discipline it demands).** The sub-tab is renamed to
the user's own wording from the bug report: the tab that holds keys gitid's curated table
does not manage. The exact final string is `Other keys`. Because
`gate-copy-freeze` is a mechanical presence grep with no way to know a rename is
intentional, and because `make test` depends on that gate, the rename is not landable
incrementally — `Makefile`'s frozen-string entry, both Go string constants, and every
assertion pinning the old literal must move in ONE commit. That is also what CLAUDE.md's
buildable-boundary commit rule already requires.
</authority>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| raw `git config --list --show-origin` output -> the exclusion filter -> rendered key list | the filter decides what the user is allowed to see; a wrong decision hides real state |
| curated policy table -> exclusion set | the exclusion's only legitimate source of authority |
| frozen copy gate -> `make test` | a label change that skips the gate turns the whole test target red |

|-----------|----------|-----------|----------|-------------|-----------------|
| T-09.6-16 | Denial of Service | over-exclusion in `AllGitSetKeys` | high | mitigate | An exclusion that is too broad silently hides a key the user set and needs to see — an availability failure on a tool whose whole purpose is making config visible. Mitigated by sourcing the exclusion ONLY from exact member-key matches plus two named literals, and by Task 1's Test 5 asserting the two sub-tabs' key sets union to the full raw probe result on a real machine. Task 3 re-proves it end to end through the compiled binary. |
| T-09.6-17 | Spoofing | under-exclusion leaving a duplicated key | medium | mitigate | A key visible in two places with two different values misrepresents the machine's state — the exact defect reported.
