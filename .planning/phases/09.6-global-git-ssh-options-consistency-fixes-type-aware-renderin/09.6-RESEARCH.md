## Summary

This phase is a pure internal-refactor / rendering-fix phase — no new packages, no new
config shape (recipes/ is unaffected). The three CONTEXT.md decision areas map to three
independent, well-isolated code sites: (1) the row-render `switch` in
`internal/tuikit/globalgit.go`'s `view()` and `internal/tuikit/globalssh.go`'s
`optionRow()`, which currently render the SAME `!` glyph for `NeedsAction` and
`Differs`/`SetButDiffers` — confirmed byte-for-byte identical bug in both files; (2)
`AllGitSetKeys` in `cmd/gitid/wiring.go`, which tags (but does not exclude)
policy-backed keys, and — critically — uses the WRONG lookup (`globalgit.PolicyFor`,
which only matches SCALAR policy rows) for the exclusion CONTEXT.md asks for, so a
correct fix must switch to `globalgit.PolicyForMember` AND separately exclude the two
literal fallback-author keys `"user.name"`/`"user.email"`, which have zero `Policy.Members`
and are invisible to either lookup; (3) the "type-aware rendering" decision is the
**deferred "general value-override capability"** Phase 9.4's D-02 explicitly named and
punted — this is new capability, not a cosmetic relabel, and it lands on a Policy data
model (`globalgit.OptionPolicy` / `globalssh.OptionPolicy`) that today carries **zero**
type/domain metadata (no bool/enum/text distinction exists anywhere in the codebase).

**Primary recommendation:** (a) fix the `!` glyph by narrowing the `case` guard in both
`globalgit.go` and `globalssh.go` to `GlobalGitNeedsAction`/`GlobalSSHNeedsAction` only —
2-line diffs, already covered by an EXISTING SSH test that currently asserts the WRONG
(buggy) behavior and must be inverted (`TestOptionRowNeedsActionAndDiffersShareWarningGlyph`,
`internal/tuikit/globalssh_test.go:621`); (b) fix `AllGitSetKeys` by building an exclusion
set from `globalgit.PolicyForMember` (bundle-aware) plus the two literal fallback-author
keys, and rename `PropsGitSubTabLabel` (`internal/tuikit/design.go:892`) — this rename is
tracked by `make gate-copy-freeze`'s frozen-string list (`Makefile:604`, literal `'Set keys'`),
which WILL fail unless the Makefile entry is updated in the same commit; (c) add a new
`ValueKind`-style field to both `OptionPolicy` structs, classify all ~17 rows (11 git + 6
ssh), and build the enum/text edit widgets on top of the ALREADY-EXISTING `formFieldLine`/
`helperLine` (text) and the Match-strategy `←/→`-modulo-cycle pattern (enum) — but budget
real design time for classifying `init.defaultBranch`, which is the row used as the
canonical "selectable checkbox" fixture across ~10 existing tests and is not unambiguously
boolean under the new three-way taxonomy (see Common Pitfalls).

### Pattern 1: Enum arrow-cycle (reuse target)

**What:** a fixed-size, modulo-wrapping index into a known value list, changed by
←/→ while a specific field/row is focused.
**When to use:** UXG-01's enum rows (e.g. `StrictHostKeyChecking`).
**Existing precedent — read before designing a new widget:**
```go
// Source: internal/tuikit/identities.go:945-962 (gitForm.handleEdit) — VERIFIED, read this session
func (g gitForm) handleEdit(msg tea.KeyMsg, focus int) gitForm {
	key := msg.String()
	switch focus {
	...
	case gitFieldStrategy:
		if key == "left" {
			g.strategyIdx = (g.strategyIdx + len(matchStrategies) - 1) % len(matchStrategies)
		}
		if key == "right" {
			g.strategyIdx = (g.strategyIdx + 1) % len(matchStrategies)
		}
	...
```
`matchStrategies = []string{"gitdir", "hasconfig", "both"}` (`identities.go:740`).
**Important divergence from the literal precedent:** `gitForm.view` (`identities.go:1050-1062`)
renders ALL THREE strategy options as always-visible radio dots (`glyphRadioOn`/`Off` =
`"●"`/`"○"`, `internal/tuikit/theme.go:74-75`). The Options screen's master list is a
scrolling list of up to ~17 rows — rendering every enum's full value set inline for every
row would blow the row budget. CONTEXT.md's "shows its current value inline" wording
implies the CLOSED (not-editing) state stays single-line (current value only); only the
open (post-`e`) editing state needs the cycle-through-values interaction, and it should
render in the DETAIL PANE (the same slot the fallback-author text fields already occupy),
not the master list.

### Pattern 2: Text field entry (reuse target, NOT a new widget)

**What:** `formFieldLine`/`helperLine` already power the fallback-author row's text
editor — `gitFallbackFieldLine` (`internal/tuikit/globalgit.go:2129-2138`) is a thin
wrapper that ALREADY calls `formFieldLine` in both its editing and non-editing branches:
```go
// Source: internal/tuikit/globalgit.go:2129-2138 — VERIFIED, read this session
func gitFallbackFieldLine(label string, input textinput.Model, editing, selected bool) string {
	if editing {
		return formFieldLine(label, input, true, false)
	}
	if selected {
		name := styleBold.Render(padRight(label, 16))
		return " " + styleFaint.Render("▸ ") + name + DefaultTheme.FieldBlurred.Render("["+input.Value()+"]")
	}
	return formFieldLine(label, input, false, false)
}
```
This means UXG-01's "text option row reuses formFieldLine/helperLine, not a bespoke
widget" is **already mostly true today** for the ONE existing text row. The gap is
purely in the KEY GESTURE (see Pitfall 4) and the fact this pattern needs to generalize
to any future text-typed Policy row (there are none besides the fallback-author pair
today — see Type Classification table below), not the render primitive itself.

### Anti-Patterns to Avoid
- **Rendering the full enum value list inline in the master list row** — the identity
  wizard's Match-strategy pattern does this because it owns a fixed-height, single-form
  pane; the Options screen's master list is a scrolling, many-row list and cannot afford
  N extra lines per enum row without a fresh row-budget audit (mirror 09.7 D-08's
  explicit checkpoint convention for this class of risk).
- **Reusing `PolicyFor` for the `AllGitSetKeys` exclusion set** — `PolicyFor` matches
  against the Policy row's DISPLAY key (`"core.autocrlf / core.eol"`), not the raw git
  key (`"core.autocrlf"`) `AllSetKeys` returns. It silently under-excludes every bundle
  row's members. Use `PolicyForMember` instead (see Pitfall 2).

boolean option row renders the existing toggle glyph... unchanged from today" is

falling out of the classification exercise.

## Common Pitfalls

### Pitfall 1: An existing SSH test asserts the CURRENT (buggy) shared-glyph behavior
**What goes wrong:** `TestOptionRowNeedsActionAndDiffersShareWarningGlyph`
(`internal/tuikit/globalssh_test.go:621-639`) `[VERIFIED: internal/tuikit/globalssh_test.go:621-639]`
literally asserts:
```go
if !strings.Contains(needs, warn) || !strings.Contains(differs, warn) {
    t.Fatal("needs-action and set-but-differs must share the warning glyph and theme role")
}
```
This test's name and body encode the exact bug UXG-02 fixes. If the planner only changes
`globalssh.go`'s render code without updating this test, `go test -race ./...` goes RED
immediately after the fix — this is not a hidden regression risk, it is a guaranteed,
already-known test failure the plan must include as an explicit task (invert the
assertion: differs must NOT contain the warning glyph).
**Why it happens:** the test was written to LOCK today's (soon-to-be-wrong) behavior
during Phase 6/06-03's original implementation.
**How to avoid:** include "update `TestOptionRowNeedsActionAndDiffersShareWarningGlyph`"
as an explicit task alongside the `globalssh.go` render-code change, in the SAME commit
(CLAUDE.md's buildable-boundary commit-granularity rule already requires this).
**Warning signs:** `go test ./internal/tuikit/...` fails on this specific test name
immediately after the render fix, with no other test list changes.

The Global Git side has NO equivalent existing assertion (`TestGlobalGitDiffersRowRendersWordNotNewGlyph`,
`internal/tuikit/globalgit_test.go:1055-1085` `[VERIFIED: internal/tuikit/globalgit_test.go:1055-1085]`,
only asserts the row shows no CHECKBOX glyph for Differs — it says nothing about the
tone/warning `!` glyph). This is a genuine Wave 0 test gap: a NEW test asserting
"Differs rows on Global Git render no `!`" does not exist yet and must be added.

### Pitfall 2: The exclusion set for `AllGitSetKeys` needs THREE sources, not one
**What goes wrong:** `cmd/gitid/wiring.go:2123-2155` (`AllGitSetKeys`)
`[VERIFIED: cmd/gitid/wiring.go:2123-2155]` currently computes `PolicyBacked` via:
```go
_, policyBacked := globalgit.PolicyFor(k.Key)
```
`globalgit.PolicyFor` (`internal/globalgit/policy.go:250-257`)
`[VERIFIED: internal/globalgit/policy.go:250-257]` matches the Policy row's DISPLAY
key case-insensitively — for scalar rows this equals the raw git key
(`"core.ignorecase"` == `"core.ignorecase"`), so it happens to work there, but for
bundle rows the display key is a composite string (`"core.autocrlf / core.eol"`,
`"alias (8 shortcuts)"`, `"color (ui/branch/diff/status)"`) that will NEVER equal a raw
member key like `"core.autocrlf"` or `"alias.st"` returned by `AllSetKeys`. A naive
"exclude everything `PolicyFor` matches" implementation silently leaves every bundle
member key duplicated on both sub-tabs — the exact symptom class this phase exists to
fix, just for a different set of keys than the ones the user actually reported.

The codebase ALREADY has the correct lookup for this: `globalgit.PolicyForMember`
(`internal/globalgit/policy.go:280-287`) `[VERIFIED: internal/globalgit/policy.go:280-287]`,
explicitly documented as matching "the shape a free-form custom git key always takes,"
built for exactly this collision-detection need.

**Second gap:** even `PolicyForMember` will NOT match `"user.name"`/`"user.email"` — the
fallback-author Policy row (`Key: "user.email (global fallback)"`,
`internal/globalgit/policy.go:157-159`) has `Members: nil`
`[VERIFIED: internal/globalgit/policy.go:154-159]`, so it contributes zero entries to

## Open Questions

1. **Does `init.defaultBranch` become text or stay boolean?**
   - What we know: its value domain is technically free text (any git ref-name); its
     CURRENT and heavily-tested UI behavior is boolean (accept/reject the one
     recommendation "main").
   - What's unclear: CONTEXT.md's two examples don't cover this case; either answer is
     internally consistent.
   - Recommendation: resolve during planning as an explicit, named decision (not an
     implementation detail) — see Pitfall 5.

2. **Does "Esc dismisses" require a new revert-to-prior-value mechanism?**
   - What we know: today's fallback-author field does not distinguish commit from
     dismiss — both just stop editing, keeping whatever was typed.
   - What's unclear: whether CONTEXT.md's "dismisses" wording requires literally
     discarding in-progress edits (new mechanism) or is satisfied by the existing
     stop-editing behavior relabeled.
   - Recommendation: resolve during planning; see Pitfall 4.

3. **Should `Selectable()`'s Git/SSH asymmetry for `Differs` rows be left as-is?**
   - What we know: Global Git never lets you select a `Differs` row; Global SSH
     always has. CONTEXT.md's scope fence protects the 4-state classifier but says
     nothing about `Selectable()`.
   - What's unclear: whether this asymmetry is intentional (SSH's `Differs` can be a
     real, non-no-op write depending on `Host *` ordering, unlike git's provable
     floor-based no-op) or an oversight worth flagging to the user.
   - Recommendation: leave `Selectable()` untouched (out of this phase's stated scope);
     flag the asymmetry to the user/planner as a documented observation, not a defect
     to silently fix.
