## OpenCode Review (opencode)

## 09.6-01

**Summary**
Strong tracer intent and good safety constraints, but the proposed override seam is not executable as written. It does not connect the new planner to the existing ceremony, and its planned synchronous path risks writing during preview.

**Strengths**
- Correctly preserves classifier enums and `Selectable()` behavior.
- Reuses the existing backed-up lifecycle writer.
- Explicitly tests `IdentitiesOnly` scope refusal.
- Correctly targets the existing SSH warning-glyph regression test at `internal/tuikit/globalssh_test.go:621-639`.

**Concerns**
- **HIGH:** `applyCeremonyFor` currently calls `GlobalSSHApplyPlan(chosen)` and confirmation commits through `CommitGlobalSSH(keys)` (`internal/tuikit/globalssh.go:724-747`, `:926-935`). The plan introduces a separate planner but does not specify how either call receives the staged value.
- **HIGH:** The plan says the new planner calls `runGlobalSSHApply` with `confirmationAlreadyObtained` (`09.6-01-PLAN.md:227-235`). That function writes after its confirmation stage (`cmd/gitid/lifecycle.go:880-958`); using it for synchronous preview would violate preview-before-confirm.
- **HIGH:** The SSH `Backend` interface currently embeds only `GlobalSSHPlanner` (`internal/tuikit/backend.go:529-541`). The plan does not explicitly add the new interface there or update all backend implementations.
- **MEDIUM:** `applyChosen` filters on `needsAction()` (`internal/tuikit/globalssh.go:632-638`). If editing is allowed for `Differs` rows, staged overrides will be silently omitted.
- **MEDIUM:** The declared fixture file is `internal/dummytui/data.go`, but the actual SSH fixture implementation is in `internal/dummytui/fixturebackend.go:661-682`; it currently supplies no value-kind metadata.

**Suggestions**
- Define one explicit override request type and pass it through preview and commit.
- Make preview pure and reuse the same candidate builder as commit; never use `confirmationAlreadyObtained` for preview.
- Add the new planner to `Backend`, real backend, fixture backend, stubs, and screenshot wrappers.
- Specify edit eligibility for `AlreadySet`, `NeedsAction`, and `Differs`, then test each state.
- Add fixture `ValueKind` and `EnumValues` population.

**Risk Assessment**
**HIGH.** The core vertical slice can compile while still displaying a preview that differs from the committed value, or bypassing the intended confirmation boundary.

## 09.6-02

**Summary**
The policy classification and Git expansion are logically ordered, but the hard-gated override path is underspecified and currently conflicts with the existing write API.

**Strengths**
- Pins every policy row with completeness and per-row classification tests.
- Preserves bundle rows as apply-only presets.
- Correctly identifies `WriteValueFor` as the version-gate authority.
- Keeps the existing checkbox semantics explicit.

**Concerns**
- **HIGH:** `WriteValueFor` has no requested-value parameter and always returns the member recommendation or fallback (`internal/globalgit/version.go:60-81`). `runGlobalGitApply` currently calls it unconditionally (`cmd/gitid/lifecycle.go:1166-1185`). "Route the override through `WriteValueFor`" is not an implementable API contract.
- **HIGH:** `GlobalGitApplyPlan` independently builds recommendations (`cmd/gitid/wiring.go:2441-2475`). The plan does not specify how the preview receives the override, so preview and commit can diverge.
- **MEDIUM:** The planned local `ValueKind` types in `globalgit` and `globalssh` cannot be assigned directly; the wiring must explicitly map them to the tuikit type.
- **MEDIUM:** The plan again lists `internal/dummytui/data.go`, while the actual Git fixture implementation is in `internal/dummytui/fixturebackend.go:869-887`; the dummy would otherwise receive zero-value classifications.

**Suggestions**
- Add an explicit override-aware helper, for example `WriteValueFor(row, key, requested, gate)`, with tests for:
  - gate met + override,
  - hard gate below minimum + fallback,
  - no override + recommendation,
  - unknown member.
- Refactor both preview and commit to use the same override-aware candidate builder.
- Add DTO conversion tests and update all fixture/stub constructors.

**Risk Assessment**
**HIGH.** A naïve implementation either ignores user-selected values or bypasses the `merge.conflictstyle` fallback gate.

## 09.6-03

**Summary**
This plan addresses the gesture inconsistency, but it does not explicitly fix the authoritative fallback-author read path that caused the reported duplicate-value bug.

**Strengths**
- Clearly separates Enter commit from Esc revert.
- Preserves the dedicated fallback-author writer.
- Requires reuse of existing field rendering and validators.
- Includes real-PTY coverage for commit, dismiss, and rejected input.

**Concerns**
- **HIGH:** The real Options DTO currently gets its fallback row from `globalgit.Statuses` (`cmd/gitid/wiring.go:2268-2318`), while the dedicated authoritative reader is separate at `cmd/gitid/wiring.go:3128-3137`. The plan changes editing gestures but never explicitly hydrates the Options row from `ReadGitFallbackAuthor`, so the original "empty in Options, value in Set keys" defect may remain.
- **HIGH:** `ValidateCustomKeyValue` is designed for the custom-key block and rejects syntax characters (`internal/gitconfig/customkeys.go:81-108`); it does not validate Git ref names. Using it for `init.defaultBranch` does not establish that the typed value is a valid branch name.
- **MEDIUM:** The plan introduces enum editing, text editing, and fallback-field editing into the same `globalGitModel`, but does not define a mutually exclusive editor mode. The existing fallback guard already captures all keys while `fieldEditing` is true (`internal/tuikit/globalgit.go:959-980`).
- **MEDIUM:** The fallback policy row represents both `user.name` and `user.email`, but the plan only describes a single text-row value. It should specify how both fields are displayed and how their snapshots are maintained.

**Suggestions**
- Explicitly wire `GitFallbackAuthorState`/`ReadGitFallbackAuthor` into `GlobalGitOptionStates` or the model overlay before implementing the gesture change.
- Add a dedicated `ValidateDefaultBranch` helper using Git's ref validation semantics, rather than the custom-key validator.
- Replace multiple booleans with an explicit editor mode enum and per-mode snapshot.
- Add tests proving the displayed fallback value changes after a dedicated fallback-author commit and remains authoritative after dismissal.

**Risk Assessment**
**HIGH.** The plan may ship the requested keyboard behavior while leaving the primary read-path defect unresolved.

## 09.6-04

**Summary**
The exclusion mechanism correctly identifies `PolicyForMember` and the member-less fallback keys, but the claimed partition proof uses incompatible key namespaces unless the Options rows are expanded to raw managed keys.

**Strengths**
- Correctly targets `PolicyForMember` (`internal/globalgit/policy.go:271-287`).
- Correctly identifies the bundle display/member mismatch (`internal/globalgit/policy.go:146-152`, `:197-206`).
- Explicitly requires skipping excluded rows rather than merely tagging them.
- Includes label-gate and PTY coverage.

**Concerns**
- **HIGH:** The Options list uses display rows such as `"core.autocrlf / core.eol"` and `"alias (8 shortcuts)"`, while `AllGitSetKeys` returns raw keys such as `core.autocrlf` and `alias.st` (`cmd/gitid/wiring.go:2123-2155`). The fallback row is `"user.email (global fallback)"`, but it owns raw `user.name` and `user.email` (`internal/globalgit/policy.go:154-159`). A literal union/intersection test cannot prove partitioning without expanding policy ownership to raw keys.
- **HIGH:** Excluding `user.name` and `user.email` from the general list means they are absent from the raw-key result and absent by literal name from Options. The plan must define whether "owned by the fallback row" counts as visible coverage, especially for system-scope values.
- **MEDIUM:** The surviving `GitSetKeyView.PolicyBacked` field becomes false by construction, but the plan only says to "decide explicitly" whether it remains meaningful; it does not define the resulting renderer contract.
- **MEDIUM:** The label sweep touches screenshot and promotion metadata, but does not identify a machine-checkable inventory of every old literal beyond the final `rg` command.

**Suggestions**
- Define a canonical `ManagedRawGitKeys()` expansion: scalar members, bundle members, and fallback-author keys.
- Test `raw = managed + visible-other`, with exact empty intersection, case-normalized.
- Decide whether external/system `user.name` and `user.email` are intentionally hidden or need a separate provenance representation.
- Either remove `PolicyBacked` from surviving rows or document that it remains a compatibility field permanently false.

**Risk Assessment**
**HIGH.** The implementation can pass a naïve test while still hiding fallback-author state or failing to prove the required one-key-one-home invariant.

New editor states require explicit keystroke-driving capture code, not only `ScreenSpec` entries.

The plan now requires a differs state on both screens but does not specify seeded capture backends or fixture changes to make those states reachable.

- **MEDIUM:** The current Phase 9.6 roadmap section is still a TBD placeholder (`.planning/ROADMAP.md:458-467`), and the plans omit `cross_ai: true` from frontmatter. This violates the repository's mandatory execution rule (`.planning/ONESHOT.md:97-113`).

**HIGH.** The closeout can fail because required frames are missing, or worse, mark requirements complete without comparable evidence.

## Cross-Plan Risks

- **HIGH:** Plans 01–03 introduce a new editor architecture incrementally without first defining one shared state machine and one override request/preview contract. The existing architecture has separate plan and commit APIs (`internal/tuikit/backend.go:89-160`) and ceremony construction already calls those APIs directly (`internal/tuikit/globalssh.go:724-747`).
- **HIGH:** The fallback-author read-path defect is not assigned to a concrete task. `ReadGitFallbackAuthor` is authoritative only in `GitFallbackAuthorState` (`cmd/gitid/wiring.go:3128-3137`), while Options rows continue to originate from `globalgit.Statuses` (`cmd/gitid/wiring.go:2268-2318`).
- **HIGH:** The visual registry, capture driver, and dummy fixtures are not planned as one atomic change. Existing capture functions require a frame for every applicable `ScreenSpec`, so metadata-only registration is insufficient.
- **HIGH:** None of the five plan frontmatters contains `cross_ai: true`, despite `.planning/ONESHOT.md:97-113` making it mandatory.
- **MEDIUM:** The phase roadmap and state artifacts are inconsistent with the plan set: `ROADMAP.md` still says Phase 9.6 has zero plans and TBD requirements (`.planning/ROADMAP.md:458-467`), while the plans assume finalized UXG requirements.

**Overall Risk: HIGH**

The plans have strong source tracing, good test intent, and appropriate safety awareness. They should not execute yet. Resolve the override/ceremony contract, authoritative fallback read path, raw-key partition model, dummy/capture integration, and mandatory `cross_ai` metadata first.
