top-level nav entry all the way to a confirmed, backed-up write of a FUNCTIONAL global
ignore configuration, wired through BOTH binaries.

review (09.2-REVIEWS.md, both reviewers, HIGH) established that writing

`WriteGlobalGitignore` engine) on one path before any of it is built out.

## Cycle-3 finding REJECTED after source verification — recorded, not silently dropped

This section exists for the same reason cycle 2's rejected header-arithmetic claim was written
out rather than dropped: a reviewer's finding that is not acted on must carry its evidence, so
the next reader can check the rejection instead of re-raising it.

**codex-sol HIGH — "A wrong `core.excludesfile` target still permits a confirmed write to an
inactive file"** (`09.2-01-PLAN.md:564` citing `09.2-UI-SPEC.md:301`). **REJECTED. No behavior
change. Task 2's "leave a different target alone, keep the plan single-target" branch stands
exactly as written.**

The finding's load-bearing word is *silently*: it reads the plan as letting a confirmed write
"succeed for a `core.excludesfile` Git doesn't read" without the user being told. That is not
what this phase ships. `09.2-UI-SPEC.md:183` already pins a dedicated, frozen copy constant for
precisely this wiring state — one of the four the screen renders in words:

> `! core.excludesfile points at <other-path> instead of this file — that choice is left alone;
> writing here only affects the file below.`

That line is rendered in the pane BEFORE `a` is pressed, names the other path gitid actually
read, states that gitid is not overriding the user's choice, and states the exact scope of what
the confirmation will affect. The write is therefore fully disclosed at the moment of decision,
which is the property the review's own top consensus finding asked for. It is not silent, and
it is not a reproduction of the cycle-1 wiring gap — the cycle-1 gap was the screen reporting
success while saying NOTHING about wiring at all, and that gap is closed by the four-state
wiring enum and by the fail-closed no-baseline-block branch.

On the apparent conflict with `09.2-UI-SPEC.md:301`'s "Wiring honesty" focal point ("must never
let a confirmed write report success for a `core.excludesfile` configuration Git does not
actually read"): that focal point is about the UNSET and NO-BASELINE-BLOCK states, which this
plan handles by writing the key (Task 2) and by refusing to open the ceremony at all
(Task 1 §7) respectively. It is not a promise to seize a value the user deliberately set.

Overriding a user-chosen `core.excludesfile` — or refusing to let them manage the file gitid
owns because they aimed Git somewhere else — would violate this repository's own established
policy that a deliberate user value is surfaced and never overridden (`setDiffersFindings`,
`internal/doctor/checks/baseline.go:181-186`), and would contradict CLAUDE.md's
managed-blocks-only rule. The D-09 carve-out in CLAUDE.md that permits rewriting ONE existing
directive's value on hand-written config is scoped to the Phase-8 Fixer and explicitly does not
extend to any other write path in this codebase — including this one.

The cost of rejecting the finding is bounded and stated: a user who has aimed Git at their own
ignore file, and who then uses this screen, edits the gitid-managed file rather than the one
Git reads. They are told that, in those words, before they confirm — and, as of cycle 5, in the
success receipt afterwards as well (Task 1 §7's third receipt variant). The rejection is of the
*behavior* change; the *copy* inconsistency the narrowed cycle-5 reading identified is accepted
and fixed, so the receipt and the pre-write warning now say the same thing.

## Cycle-5 finding DOWNGRADED after source verification — one defensive test, no redesign

**codex-sol HIGH — "The proposed inspector ignores other managed-block names"**
(`09.2-01-PLAN.md:367`, citing `internal/filewriter/block.go:36`). **DOWNGRADED to MEDIUM for
this phase. The inspector stays requested-name-scoped and `internal/filewriter/block.go` stays
byte-unchanged. ONE defensive test is added to Task 1's `<behavior>` so the parser's real
behavior is written down instead of left unspecified.**

The finding is factually right about the parser and wrong about the consequence *for the safety
property this guard exists to provide*. `listBlocksWith` tracks exactly ONE open block regardless
of name — its own comment says so: "Ignore nested or duplicate begins — only the outermost
matters" (`internal/filewriter/block.go:41-46`) — and it only closes a block on an END whose name
matches the currently-open BEGIN, skipping a mismatched END silently (`:59`).

The hazard the inspector was invented to close is a **write divergence**: the block that informs
the preview must be the block the commit rewrites. Trace the cross-name nesting shape against
that property:

- A complete `url-rewrites` BEGIN/END pair NESTED inside a complete `baseline` block is absorbed
  into the outer block's BODY — `listBlocksWith` ignores the inner BEGIN and skips the
  non-matching inner END, then closes on the outer END. `ListBlocks` therefore returns exactly
  ONE `baseline` block, `indexBlocks` maps that one, and `replaceBlockWith` (which scans for the
  literal `baseline` BEGIN/END markers, `block.go:126-145`) rewrites exactly the same span. Read
  and write agree. There is no preview/commit divergence in this shape — which is precisely the
  difference from the cycle-3 duplicate-`baseline` case, where the read took the LAST block and
  the write took the FIRST.
- The other shape the finding names — an orphan OTHER-name BEGIN wrapping a complete `baseline`
  block — makes `ListBlocks` return NO block at all, so `ReadBaselineState` reports the machine as
  not-installed rather than mis-classifying one block as another. Every consumer in this phase
  then takes a fail-closed branch: the screen's no-managed-baseline-block branch keeps apply
  inert (Task 1 §7), and plan 09.2-02 Task 3's Fixer now reads the fragment body through the
  inspector instead of a `ListBlocks` first-match scan, so the same bytes the guard checked are
  the bytes the write means. Neither path silently patches a block it did not read.

So: a real parser edge case, but MEDIUM — it does not reach the write-divergence hazard this
phase's guard is for, and the second reviewer, re-reading the same parser, did not raise it and
called the five-shape fail-closed design intact.

Why not "just" widen the inspector to validate marker structure across ALL names: because that
converts a name-scoped read-shape guard into a global structural validator over a shared parser
whose ignore-nested/ignore-mismatched behavior 33-odd `ReplaceBlock` call sites already depend
on. Files that are legitimately healthy today for every other gitid surface (SSH config,
provisional blocks, url-rewrites) would start being refused by this screen, and the blast radius
of getting that wrong is every managed-block file in the product. That is a change to shared
parsing policy, not a fix inside GIGN-01, and it belongs to whoever owns `internal/filewriter`
— recorded here as a deliberate, considered-and-declined option so a later phase can take it up
with the right scope.

**What IS added:** one test, in Task 1's `<behavior>` (the inspector's own test file), asserting
the nested-other-name shape is accepted as one healthy `baseline` block whose body carries the
nested marker lines verbatim, AND that `filewriter.ReplaceBlock` rewrites that same span — i.e.
documenting the read/write agreement claim above rather than asserting it in prose. It is named
and commented as a parser-behavior record so a future reader does not mistake the acceptance for
an unnoticed gap. Plan 09.2-02 explicitly does NOT duplicate it.
</downgraded_findings>
