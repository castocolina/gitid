## The screen's key map, resolved once and binding on this plan AND `09.2-UI-SPEC.md`

Cycle-2 cross-AI review (09.2-REVIEWS.md, the cycle's only HIGH) found the edit key was
DUAL-SPECIFIED: this plan's Task 1 and its PTY recipe bound `Enter`, while
`09.2-UI-SPEC.md`'s copywriting table, footer row and focal points bound `e`. An executor
following the UI-SPEC would have shipped a footer whose advertised key the PTY suite never
sends; an executor following the plan would have shipped a footer that lies about itself.

**Resolved to `Enter`.** Verified against the live precedent the reviewer cited: the Global Git
screen enters its field-editing state on `"enter"` (`internal/tuikit/globalgit.go:573-579`) and
advertises it in the contextual footer as `{Key: "Enter", Label: "edit"}`
(`internal/tuikit/globalgit.go:1060`). `Enter` is also already the reserved-footer's global
`activate` verb (`internal/tuikit/frame.go:86`), so "Enter activates the thing the pane is
about" stays true on this screen instead of acquiring a screen-local exception. The full map:

| State | Key | Action |
|-------|-----|--------|
| browse | `Enter` | focus the editor (enter edit mode) |
| browse | `r` | reset the editor to `view.DefaultContent`, in memory only |
| browse | `a` | build the apply plan from the editor's current value and open the ceremony |
| editing | `Esc` | blur the editor, keep the typed content, return to browse |
| editing | every other key | forwarded to the textarea as text |

`e` is NOT bound on this screen, in either document. It is an ordinary character the editor
inserts as text like any other.

**Deliberate divergence from the Global Git analog, recorded so a reviewer does not read it as
drift:** Global Git advertises `Esc/Enter  done editing` for its single-line `textinput`
(`globalgit.go:1054`). This screen's editor is MULTI-LINE, where `Enter` must insert a newline,
so `Esc` alone leaves edit mode here. `09.2-UI-SPEC.md`'s `Esc  Done editing` copy is therefore
correct as written and must not be "fixed" to match the single-line analog.

Every task below, and `09.2-UI-SPEC.md`'s Copywriting Contract and Focal Points, use this map
and nothing else.

## What "persisted" means on this screen (review concern: "written verbatim" vs the normalizer)

codex-sol flagged that the previous revision promised verbatim persistence while plan 09.2-01
right-trims every line and drops the trailing blank run. The contract, stated once and binding
on every task below:

The editor's value is CANONICALIZED before it is previewed — each line right-trimmed, the
trailing run of blank lines dropped, interior blanks and comments kept. The ceremony's diff is
computed from that canonical candidate, so the bytes the user reviews ARE the bytes that get
written; there is no post-review transformation. The screen's copy says the content is written
as reviewed, never "verbatim". A user who types trailing spaces sees them gone in the diff
before they confirm, which is the honest ordering.
</persistence_contract>
