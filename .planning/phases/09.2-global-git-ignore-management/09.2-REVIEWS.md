# Cross-AI Plan Review

**Overall verdict: REVISION REQUIRED.** The architecture is generally sound—shared write machinery, an injected backend seam, real-PTY coverage, and staged delivery—but the plans are not execution-ready. The most important gaps are: the screen does not ensure `core.excludesFile` is wired, malformed managed blocks can be made worse, previewed content can become stale before commit, the doctor predicate would hide broken wiring, and the new screen is absent from the mandatory visual-regression inventory.

## Plan 09.2-01 — Read/review/write tracer

### Summary

This is a strong vertical tracer with appropriate unit, wiring, and real-PTY coverage. Reusing the existing managed-block writer is the right implementation direction. However, the proposed single-file write does not produce a functional global ignore configuration on an unconfigured machine, and several safety boundaries need explicit fail-closed behavior.

### Strengths

- The planned write chain reuses proven preservation and backup behavior. `ReplaceBlock` replaces only the matching block while retaining surrounding bytes, and `Write` performs an atomic rename with a timestamped backup for an existing target. `internal/filewriter/block.go:111-162`, `internal/filewriter/filewriter.go:24-61`
- The navigation changes cover the real integration surface: the current app has a fixed five-screen array, numeric routing, arrow clamping, mouse header hit-testing, and a matching screen constructor array. Expanding all of these together avoids an unreachable or partially wired screen. `internal/tuikit/app.go:134-179`, `internal/tuikit/app.go:452-473`, `internal/tuikit/app.go:488-542`, `internal/tuikit/app.go:701-713`
- Separating compact header labels from breadcrumb labels is justified by the fixed 100-column frame. Header rendering and hit-testing currently derive from the same tab text, so preserving that shared source maintains their invariant. `internal/tuikit/frame.go:26-75`, `internal/tuikit/frame.go:224-283`
- The proposed `commitPending` guard follows an existing sound pattern: unsolicited or duplicate commit messages are ignored unless an asynchronous ceremony commit is actually active. `internal/tuikit/globalgit.go:145-195`, `internal/tuikit/ceremony.go:184-311`
- Real-PTY tests are appropriate for this feature. The existing harness builds the real binary, provides a hermetic home, and supports byte-level before/after assertions rather than merely testing model state. `e2e/harness_test.go:47-149`, `e2e/harness_test.go:481-537`, `e2e/global_git_pty_e2e_test.go:158-189`

### Concerns

- **HIGH — The screen writes only half of the functional configuration.** The repository treats `core.excludesFile` and `.gitignore_global` as a coordinated pair, and the existing fixer explicitly writes both halves. The planned fresh-home path creates `.gitignore_global` but does not wire Git to use it, so confirmation can succeed while the global ignore remains ineffective. `internal/doctor/checks/baseline.go:103-135`, `cmd/gitid/wiring.go:4328-4383`
- **HIGH — Malformed or duplicate managed blocks are not handled safely.** `ListBlocks` silently omits an incomplete block, while `ReplaceBlock` appends a new block if it cannot find a complete match. With an orphan BEGIN sentinel, the proposed screen can report "no managed block" and append another block into malformed content. With duplicate complete blocks, `ReplaceBlock` replaces only the first. `internal/filewriter/block.go:26-62`, `internal/filewriter/block.go:128-153`
- **HIGH — The reviewed diff can become stale before confirmation.** The apply plan reads the current file and computes a diff, but commit later re-reads the file through `WriteGlobalGitignore`. `txMu` only protects gitid's own mutations; it does not prevent an external edit between preview and commit. The repository already has a stronger preview-token pattern that rejects changed configuration at commit time. `cmd/gitid/wiring.go:101-111`, `cmd/gitid/wiring.go:2548-2565`, `cmd/gitid/wiring.go:2601-2604`, `cmd/gitid/wiring.go:2647-2669`
- **MEDIUM — Planner-error behavior is incomplete.** Sentinel rejection occurs in `GlobalGitIgnoreApplyPlan`, before a ceremony exists, but the specified tests cover only state-loading errors. The existing Global Git screen explicitly retains apply-plan errors and refuses to open its ceremony. Without equivalent handling, hostile or invalid text may fail with no useful receipt. `internal/tuikit/globalgit.go:381-385`, `internal/tuikit/globalgit.go:582-609`
- **MEDIUM — Backup receipts can become misleading if the Global Git fallback is copied literally.** The existing analog synthesizes a preview backup path when `Backups` is empty, but the ceremony replaces placeholders only when the commit returns real backups. For a new file or byte-identical write, that can leave a receipt implying a backup exists when none was created. `internal/tuikit/globalgit.go:381-426`, `internal/tuikit/ceremony.go:284-293`, `internal/gitconfig/baseline.go:481-483`

### Suggestions

- Decide explicitly whether this screen owns the complete `core.excludesFile` pair. Prefer either: include the baseline-fragment update in the same reviewed transaction; or fail closed when wiring is absent/wrong and provide a clear route to Fixer.
- Validate the existing file before presenting defaults: reject orphan sentinels, mismatched sentinels, and duplicate `gitignore` blocks.
- Return a preview token containing the exact preimage hash or bytes. At commit, verify the file is unchanged before writing; otherwise require the user to review again.
- Add tests for apply-plan normalization errors, malformed existing blocks, duplicate blocks, and external mutation between preview and confirmation.
- Treat empty backup lists as valid. Assert that a no-op second confirmation creates no additional backup and never displays a fictitious backup path.

### Risk Assessment

**HIGH.** The implementation direction is good, but the current plan can report success for an ineffective configuration, worsen malformed files, or write content different from the reviewed candidate.

## Plan 09.2-02 — Catalog and doctor/fixer compatibility

### Summary

The catalog work is well structured, especially the split between rendered lines and comparison entries. Making doctor tolerant of intentional edits is also correct. The principal problem is that the proposed "populated" predicate conflates block content with `core.excludesFile` wiring and would suppress real configuration errors.

### Strengths

- `DefaultGitignoreEntries` is the right companion abstraction. The current read path already strips blank and comment lines, so using the same filtered representation prevents comment headers from making all comparisons fail. `internal/gitconfig/baseline.go:194-204`
- The planned negation-order test is important because gitignore negations depend on later lines overriding earlier wildcard matches. The current renderer preserves supplied ordering rather than sorting entries. `internal/gitconfig/baseline.go:407-420`
- Reclassifying deliberate catalog deviations as informational follows an established repository policy: user-set values that differ from recommendations are reported without an executable fix. `internal/doctor/checks/baseline.go:170-190`
- Inspecting the existing managed block before the doctor fix is a sound way to prevent destructive reseeding. `ListBlocks` exposes the exact body separately from foreign content, enabling a byte-preserving skip decision. `internal/filewriter/block.go:9-13`, `internal/filewriter/block.go:31-62`

### Concerns

- **HIGH — The plan relies on a nonexistent production command.** The current CLI explicitly archives the old `baseline` command surface, and the production wiring leaves `SetupBaseline` unset because no such v1 command exists. Therefore the truth that "`gitid baseline setup`, doctor fix, and the screen share one catalog" is not source-valid. `cmd/gitid/main.go:69-83`, `cmd/gitid/wiring.go:4064-4069`
- **HIGH — `managedGitignorePopulated` would hide broken wiring.** The current check only complains about an empty `core.excludesFile` when the gitignore predicate is false. Replacing the exact predicate with "block is populated" means an edited block plus a missing key can be declared configured. Likewise, a wrong but existing excludes-file path currently passes because the check tests existence, not equality with the expected target. `internal/doctor/checks/baseline.go:115-135`, `internal/doctor/checks/baseline.go:193-199`
- **MEDIUM — The doctor fix remains a non-atomic two-file operation.** It currently writes `.gitignore_global` first and then patches the baseline fragment. If the second write fails, the first mutation remains and its returned backup is not used for rollback. Preserving populated blocks reduces exposure but does not address missing or empty blocks. `cmd/gitid/wiring.go:4357-4381`
- **MEDIUM — Synthetic doctor-state tests may miss behavior in the real reader.** `ReadBaselineState` returns before parsing `.gitignore_global` when the baseline/include setup is absent or incomplete. A test that manually supplies `GitignorePatterns` can therefore disagree with the real doctor path. `internal/gitconfig/baseline.go:56-115`

### Suggestions

- Correct the plan and context to remove `gitid baseline setup` as a current caller. Restoring a retired CLI command would be unrelated scope expansion.
- Split doctor validation into independent conditions: (1) `core.excludesFile` is present and resolves to the expected path, (2) the expected file contains one valid, populated managed block, (3) missing curated entries are informational only.
- Add cases for: populated edited block plus missing `core.excludesFile`; populated block plus wrong-but-existing target; correct target plus edited block; real `ReadBaselineState` integration, not only constructed states.
- Make the two-file fixer transactional, or write the baseline fragment first and restore it if the gitignore write fails.

### Risk Assessment

**HIGH.** The catalog changes are low risk, but the proposed doctor predicate can incorrectly certify a nonfunctional configuration, which conflicts directly with the product's health guarantees.
