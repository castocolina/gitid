## Top 3 Priority Fixes

1. **Breadcrumb duplicates the screen heading — "Global Git Ignore" appears 3 times in the top 4 rows.** `internal/tuikit/gitignore.go:184` and `:229` pass `crumbs: []string{GitIgnoreHeading}`, and `GitIgnoreHeading` is the same string as `tabLabels[TabGitIgnore]` (`"Global Git Ignore"`), which `RenderFrame` (`internal/tuikit/frame.go:430`) already prepends. Every captured frame shows the literal line `Global Git Ignore › Global Git Ignore` directly above a body row that repeats `Global Git Ignore` a third time. Every other single-level screen in this codebase (`globalgit.go:871,896,1053,1068` → `"Options"`; `globalssh.go:900` → a distinct `crumb` var) passes a genuinely distinct sub-label, never the tab's own name. **Fix:** pass `crumbs: []string{}` (or omit the extra segment) for this screen so the breadcrumb reads `Global Git Ignore` once, matching the UI-SPEC's stated breadcrumb value.

2. **Frozen error copy from UI-SPEC is not implemented — raw internal error strings render to the user instead.** The malformed-file and sentinel-rejection UI-SPEC rows specify exact user-facing sentences (`~/.gitignore_global has a broken gitid marker at line <N> (<reason>) — repair the file by hand...` and `Line <N> looks like a gitid managed-block marker and can't be part of your content — edit or remove that line before applying.`). The captured frames instead show the raw `fmt.Errorf` text from `internal/gitconfig/baseline.go:538,590,600,606,612,618,629` verbatim — e.g. `! line 2: nested BEGIN sentinel — repair the file by hand before gitid will touch it` and `line 3 looks like a gitid managed-block sentinel and cannot be part of gitignore content`. These strings live in the core package, not as named constants in `design.go` behind the `02-STYLE-SPEC.md` §6 copy-freeze grep gate the plans explicitly required ("Declare the screen's user-facing copy ... as named constants"), so future engine-message wording changes will silently reword the UI with no test catching it. **Fix:** translate `InspectGitignoreFile`/`InspectManagedBlockFile` error values through the UI layer into the two frozen `design.go` constants (interpolating `<N>`/`<reason>`), instead of rendering `err.Error()` directly.

3. **Sentinel-rejection Error state has no glyph — the screen's ONE designated Error-red message is the only state on this screen with no glyph at all.** Every other advisory state (wiring warnings, malformed-file, no-baseline-block) renders with a leading `!`; the healthy state renders with `✓`. The sentinel-rejection line in `gign-error-sentinel-rejected.txt` renders as bare text: `line 3 looks like a gitid managed-block sentinel and cannot be part of gitignore content` — no `✗`/`!`/color-independent marker. This directly violates the spec's "Non-negotiable, carried forward unchanged: every colored state pairs with a glyph AND a word — never color alone" and the NO_COLOR-legibility contract in "Inherited Non-Negotiables." **Fix:** prefix the rendered error line with a glyph (the spec doesn't reuse `✓`/`!`/`Healthy` for this state — decide on `✗` to match the ceremony's own error convention, e.g. `gign-error-changed-since-preview.txt`'s `✗ this file changed since you last reviewed it`) when routing this message through the UI layer (also fixes finding 2's root cause in one pass).

## Detailed Findings

### Pillar 1: Copywriting (2/4)

- **Matches spec, verified byte-for-byte against frozen strings:**
  - `✓ Wired — core.excludesfile points at this file; Git reads it.` (`gign-existing-block.txt`, `gign-editing.txt`, `gign-error-sentinel-rejected.txt`)
  - `! core.excludesfile is not set — Git does not read any global ignore file yet. Confirming here will set it.` (`gign-seeded-defaults.txt`)
  - `No managed block found yet in ~/.gitignore_global — showing the curated defaults below. Nothing has been written.` (`gign-seeded-defaults.txt`, `gign-error-no-baseline-block.txt`)
  - `This write will also set core.excludesfile in your Git baseline, since it is not set yet.` (`gign-seeded-defaults.txt`)
  - `! No gitid-managed Git baseline configuration was found on this machine — open the Fixer to set that up before this screen can wire core.excludesfile.` (`gign-error-no-baseline-block.txt`)
  - `Global gitignore written to ~/.gitignore_global. core.excludesfile was also set to point at this file.` (`gign-receipt.txt`, both heading and footer instances — footer truncates cleanly with `…`)
  - `This file changed since you last reviewed it — press a to review the current content again before writing.` (footer of `gign-error-changed-since-preview.txt`)
  - Footer key maps: `Enter Edit · r Reset to defaults · a Review & write` (browse) and `Esc Done editing` (editing, alone — confirmed the cycle-2 HIGH resolution: no `e`/`Enter` dual-binding footer text anywhere in the ten frames)
  - `Leaving this screen discards unsaved edits.` present in every browse/editing frame — matches the discard-unsaved-edits sentence requirement
- **Does not match spec:**
  - Malformed-file refusal: spec text is `~/.gitignore_global has a broken gitid marker at line <N> (<reason>) — repair the file by hand before this screen can read or write it.` with `<reason>` constrained to one of three named phrases. Actual: `! line 2: nested BEGIN sentinel — repair the file by hand before gitid will touch it` — different sentence structure, different `<reason>` vocabulary ("nested BEGIN sentinel" is not one of the spec's three enumerated reasons), and doesn't name the file path.
  - Sentinel-injection rejection: spec text is `Line <N> looks like a gitid managed-block marker and can't be part of your content — edit or remove that line before applying.` Actual: `line 3 looks like a gitid managed-block sentinel and cannot be part of gitignore content` — lowercase start, "sentinel" vs "marker", missing the actionable "edit or remove that line before applying" clause, missing the leading glyph.
  - Breadcrumb: spec's Screen Identity table gives `Global Git Ignore` as the breadcrumb value; every frame instead renders `Global Git Ignore › Global Git Ignore` (see Priority Fix 1).

### Pillar 2: Visuals (2/4)

- Wiring-state hierarchy (bold heading → plain path → glyph+word wiring line) reads cleanly and matches the Typography role table.
- The `┃` left-rule on the content pane gives a clear focal point for the single full-width text panel, consistent with the "first screen to use this archetype" note.
- **Defect:** top of screen shows `Global Git Ignore › Global Git Ignore` (breadcrumb, row 2) immediately followed by `Global Git Ignore` again (heading, row 3) — three consecutive renders of the identical string in the first four screen rows, in every one of the six non-ceremony frames. This is the single highest-visibility surface on the screen and reads as broken, not as intentional hierarchy.
- **Defect:** `gign-receipt.txt`'s heading line truncates mid-word — `✓ Global gitignore written to ~/.gitignore_global. core.excludesfile was also set to point at this f` — cut off inside "file" with no `…` marker, while the footer line one screen-row below truncates the identical sentence cleanly with a trailing `…`. Two renderers of the same string handle overflow inconsistently on the same frame.
- Ceremony diff pane (`gign-review-ceremony.txt`) renders the two-target `+`/`-` diff legibly inside the fixed 10-line/58-col budget with room to spare — no truncation of sentinel lines, addressing the spec's "overflow: two-target diff" backstop item satisfactorily for this fixture size (long user-content case not present in the tracked frame set — see Pillar 6).

### Pillar 3: Color (2/4)

- All ten tracked frames were captured with no ANSI escape sequences (plain-text/`NO_COLOR`-equivalent capture) — actual color role assignment (`styleWarning` yellow, `styleHealthy` green, `styleError` red) cannot be directly verified from this evidence set. This is not a defect in itself — the spec's own NO_COLOR-legibility contract requires the glyph+word channel to carry full meaning independent of color, so this capture mode is a valid, arguably stronger test of that contract.
- Under that test, the wiring-state and malformed-file/no-baseline-block advisories all correctly carry a `!` glyph plus the word "Wired"/warning language, so meaning survives without color.
- **Defect, same root cause as Pillar 4 below:** the sentinel-injection rejection message — the spec's one designated `styleError` usage on this screen — has no glyph in the captured evidence. Whatever color role is applied at runtime, the NO_COLOR/glyph channel this contract requires is not present, so this specific state fails the color-independence promise the rest of the screen upholds.

### Pillar 4: Typography (2/4)

- Bold/plain/faint role usage cannot be independently confirmed from the plain-text captures, but role-appropriate placement (heading bold-weight text vs. plain body vs. faint footer note) is visually distinguishable in the frame layout and consistent with the spec's role table.
- **Defect:** "Non-negotiable, carried forward unchanged: every colored state pairs with a glyph AND a word — never color alone" is violated by the sentinel-rejection line, which has neither a glyph nor (evidenced) distinguishing weight — it renders identically to plain body text. This is the spec's single Error-red exception state and the one place this contract most needed to hold; it's the one place it visibly doesn't.

### Pillar 5: Spacing (3/4)

- Body-row budget matches the spec's Spacing/Layout table: header (1) + breadcrumb (1) + heading (1) + wiring line(s) (1–2) + content pane (remaining rows) + footer (1) is respected in every frame; no frame exceeds the 100×30 capture geometry.
- Overflow affordance for long content is present and legible: `gign-seeded-defaults.txt` and `gign-error-no-baseline-block.txt` both show `… (+4 more lines)` / `… (+3 more lines)` continuation markers below the 16-line visible window — a clear, non-ambiguous scroll cue, satisfying the "overflow: user-authored content" backstop for the tested fixture sizes.
- Ceremony's `ExactTextViewport{VisibleLines: 10, Width: 58}` renders exactly as specified in `gign-review-ceremony.txt`, box-drawn border intact, no dimension drift.
- Not deducted further because no tracked frame demonstrates the free-text-overflow-inside-the-ceremony-viewport backstop with content long enough to force scrolling inside the diff pane itself (all tracked fixtures are short) — this remains an open verification gap noted under Pillar 6, not a proven Spacing defect.

### Pillar 6: Experience Design (3/4)

- All six registered base states (existing block, seeded defaults, editor focused/mid-edit, after-reset, review ceremony, post-confirm receipt) and all four unregistered error states (no-baseline-block, malformed-file, sentinel-rejected, changed-since-preview) are present in the tracked evidence, matching the spec's "Approved Base States" table and "Additional states" list exactly by name.
- Wiring-honesty focal point is upheld functionally: the two-target apply note appears before `a` in the unset-key state; the receipt confirms both targets were written and backed up (`gign-receipt.txt`); the no-baseline-block state correctly keeps `a` un-advertised in the footer (apply is inert).
- Shortcut-capture correctness is evidenced: `gign-editing.txt`'s content pane shows `rae.DS_Store` — literal `r`, `a`, `e` characters typed into the textarea body rather than triggering their browse-mode bindings, directly proving the "shortcut letters typed, not triggered" focal point on the real keystroke path.
- **Deduction:** the same two error states flagged under Copywriting are also an experience-design defect, not just a wording nit — developer-facing engine vocabulary ("nested BEGIN sentinel", "orphan BEGIN sentinel with no END") reaching the end user breaks the "fail closed, always with a reason on screen" promise's spirit: the reason given is not one a non-technical user of this tool can act on, and it will silently reword itself if the parser's internal error strings ever change, since it is not behind the copy-freeze gate.
- **Open verification gap (not scored down further, flagged per spec's own "backstop" status):** no tracked frame exercises a genuinely long free-text body inside the ceremony's fixed viewport — the specific case the UI-SPEC calls "the highest-risk visual surface this phase carries." Recommend a follow-up capture with a multi-screen-length pasted body before this backstop item can be marked resolved rather than merely present-by-omission.
