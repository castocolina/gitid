### CR-01: A custom Git key colliding with a curated `global-git` key is neither surfaced nor deterministically resolved

**Files modified:** `internal/globalgit/policy.go`, `internal/globalgit/policy_test.go`, `internal/gitconfig/customkeys.go`, `cmd/gitid/wiring.go`, `cmd/gitid/lifecycle.go`, `cmd/gitid/lifecycle_customgitkey_test.go`, `cmd/gitid/lifecycle_globalgit_test.go`
**Commit:** `ff4b27c`
**Applied fix:** Implemented fix option 1 from the report, in both directions named by `09.5-03-PLAN.md` line 58's declared backstop:
- Added `globalgit.PolicyForMember(key)` — matches a MEMBER config key (e.g. `"core.autocrlf"`), unlike `PolicyFor`, which only matches a row's DISPLAY key (prose for a bundle row, e.g. `"core.autocrlf / core.eol"`) and would miss a bundle-row collision entirely.
- `CustomGitKeyPlan` (wiring.go, the plan-stage gate the TUI always consults) and `runCustomGitKeyWrite`'s own plan stage (lifecycle.go, the fail-closed backstop for any caller reaching the writer directly) both now REFUSE to create a custom key whose name collides with a curated Global Git baseline member, naming the curated row in the error.
- `runGlobalGitApply`'s verify stage now parses the `custom-git-keys` block via `gitconfig.ParseCustomKeysBlock` (and a new exported `gitconfig.GitKeysEqual` comparator) and emits an advisory naming any pre-existing custom key a curated apply may neutralise — so a collision that predates the new guard (or one created by a future bypass) is never silently invisible.
- Tests: `TestPolicyForMember_ScalarRow/BundleRow/CaseInsensitive/UnknownKey`, `TestCustomGitKeyPlanRejectsPolicyManagedKey`, `TestRunCustomGitKeyWriteRejectsPolicyManagedKeyAtPlanStage`, `TestRunGlobalGitApply_WarnsWhenNeutralizingExistingCustomKey`.
