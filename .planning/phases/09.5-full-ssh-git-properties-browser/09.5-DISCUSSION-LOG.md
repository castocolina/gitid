## SSH/Git enumerability asymmetry

Investigated before presenting any option: `ssh -G <host>` resolves the FULL
~90-directive OpenSSH set (set or default) in one call — genuinely
comprehensive, and already parsed elsewhere in the codebase
(`tester.ParseResolved`). Git's config key space has no equivalent "list all
possible keys" primitive — `git config --list --show-origin` only shows what
is actually SET, because git config keys are open-ended per subsystem
(any tool can invent `foo.bar`).

This was presented to the user as a factual asymmetry, not a choice, before
any scope question was asked.

**User's response:** "Si git tiene el mismo problema de que no se pueden
listar las posibles propiedades entonces abria que hacer igual en ambos
casos, no?" — i.e., since git can't be exhaustively cataloged either, treat
both sides symmetrically at whatever each one CAN honestly offer (full
directive dump for SSH, full set-keys dump for Git). This became D-01/D-02.

## Custom key-value write capability (scope expansion)

Mid-discussion, the user asked directly:

> "En ese caso entonces deberiamos tener opciones de poder agregar key-value
> globales"

This expanded the phase from read-only browsing into a write feature. Before
locking scope, the safety asymmetry between the two sides was surfaced:

- An unrecognized **git** config key is inert — nothing reads it, no parser
  can choke on it.
- An unrecognized **SSH** directive can be a hard parse error in
  `~/.ssh/config`, breaking connectivity for every host, not just gitid's
  managed ones.

The user confirmed this reasoning applied on both sides at once, framing it
as: "Si git tiene el mismo problema... abria que hacer igual en ambos
casos" (see above) — meaning symmetric TREATMENT of the enumerability gap
does not mean symmetric SAFETY handling; the write paths still need
different guards.

| Option | Description | Selected |
|--------|-------------|----------|
| Git: free-form. SSH: validate against known directives + confirm | Different write-time guard per side, matched to actual blast radius | ✓ |
| Both free-form, no validation | Simpler, ignores the SSH parse-failure risk | |
| Both name-validated | Over-constrains Git for no real safety benefit | |

**User's choice:** Git: free-form. SSH: validate against known directives + confirm.
**Notes:** SSH's validated write also routes through gitid's existing
prove-before-write `ssh -G` verification pattern (already used for identity
connectivity tests) — a bad directive is caught by re-resolving before it's
committed for real, not just trusted because its name matched a list. Rated
`costly`/one-way-adjacent reversibility given the blast radius, even though
the underlying write ceremony (backup, diff, confirm) is unchanged.

## Browse UX at scale

| Option | Description | Selected |
|--------|-------------|----------|
| Flat scrollable list + type-to-filter | No taxonomy to invent/maintain; matches existing terminal-list patterns in gitid | ✓ |
| Category-grouped (OpenSSH man-page sections / git config sections) | More structure, but a taxonomy to invent and keep in sync | |

**User's choice:** Flat scrollable list + type-to-filter.
**Notes:** Category grouping was explicitly named and set aside, not silently
dropped — noted in CONTEXT.md's Deferred Ideas in case flat+filter proves
insufficient once real directive/key counts are seen on screen.

## Claude's Discretion

- Authoritative source for OpenSSH's known-directive list (PROP-04
  validation) — research `ssh -G` supported-keyword output vs. a maintained
  static list vs. avoiding `man ssh_config` parsing (fragile). Not decided
  here; explicitly deferred to planning-time research.
- Whether a custom-added entry writes into gitid's existing managed-block
  scheme or needs a new managed-block identity of its own — flagged as a
  real architectural question for the planner, since custom entries fall
  outside the fixed `OptionPolicy` schema those blocks currently render
  from.
- Exact wording/placement of the type-to-filter input and match highlighting.
- Whether a custom-added entry that happens to match an existing curated
  policy key also appears in the curated Options list, or only in the
  properties browser (avoid double-rendering the same live value twice).
