> Visual and interaction contract for Phase 9.5 (Full SSH/Git Properties
> Browser & Custom Key Entry). Generated by gsd-ui-researcher, verified by
> gsd-ui-checker.

**This is a new-surface addition on top of two shipped, working screens**,
not a redesign — same discipline as `06-UI-SPEC.md`/`07-UI-SPEC.md`/
`08-UI-SPEC.md`/`09.4-UI-SPEC.md`. Every layout/style/glyph decision below
either reuses an existing pattern verbatim (as `09.4-CONTEXT.md` explicitly

## Ground truth: the SSH/Git asymmetry, restated as a UI rule

`09.5-CONTEXT.md` D-01/D-02 establish a real, non-cosmetic asymmetry between
the two browsers this phase adds. The UI must say this out loud, not just
implement it silently:

- **SSH's browser is exhaustive.** `ssh -G <host>` resolves the FULL,
  bounded ~90-directive set — set or default — so the sub-tab is honestly
  labeled **"All directives"**.
- **Git's browser is NOT exhaustive — it cannot be.** Git's key space is
  open-ended (any tool can invent `mytool.somekey`); `git config --list
  --show-origin` only shows what is actually SET somewhere. The sub-tab is
  honestly labeled **"Set keys"**, never "All keys"/"All properties" — that
  label would be a false comprehensiveness claim the underlying data cannot
  back up.

This naming asymmetry is a DELIBERATE, LOCKED copywriting decision (see
Copywriting Contract below), not an inconsistency to "fix" toward parity.

## Layout: the two new sub-tabs

### Global SSH gains a 3rd sub-tab (extends an existing strip)

Today's strip (`globalssh.go`'s `subTabStrip()`) renders exactly two
bordered labels: `[Options]` `[Storage & preview]`. This phase adds a
**third label to the SAME strip**, `[All directives]` — `gssSubTabStripRows()`
stays **3 rows** (top border + label row + bottom border); only the label
row's content grows by one label. No new row cost on Global SSH.

```
╭╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╮
┊  Options   Storage & preview   All directives  ┊
╰╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╯
```

`←`/`→` still cycles between sub-tabs, now wrapping across three instead of
two (`gssOptions` → `gssStorage` → **new `gssProperties`** → back to
`gssOptions`). Click-hit-testing is unchanged in mechanism: the new label's
span is read from the ACTUAL rendered strip via `hitNeedle`/`ansi.StringWidth`,
exactly like the two existing labels — never a hand-computed offset.

### Global Git gains its FIRST sub-tab strip (net-new, +3 rows)

`globalgit.go` today has **no sub-tab concept** — one single Options pane
that also inlines the D9 global-fallback-author section. This phase
introduces the screen's first split: sub-tab 1 = **`Options`** (today's
ENTIRE existing content, byte-for-byte unchanged — baseline rows + the D9
fallback-author section), sub-tab 2 = **`Set keys`** (new, PROP-02/PROP-03).

This is a **net +3 row cost** on Global Git (it had zero strip rows before),
the direct mirror of `09.4-UI-SPEC.md`'s own sub-tab-strip row-budget
callout for Global SSH. Port `gssSubTabStripRows()`/`subTabStrip()` verbatim
(rename to the screen-neutral shape or literally share the helper — Claude's
Discretion at plan time, not a design-contract fork) rather than inventing a
second bordered-strip implementation.

┊  Options   Set keys  ┊
╰╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╯

**Row-budget verification obligation (mirrors 09.4-UI-SPEC's own backstop):**

### The flat, filterable list (shared shape, both new sub-tabs)

Below the sub-tab strip, both new sub-tabs render the SAME shape (D-05:
flat, scrollable, type-to-filter — no category grouping):

```
Row 1 (strip)     ╭╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╮
Row 2 (strip)     ┊  Options   All directives  ┊
Row 3 (strip)     ╰╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╌╯
Row 4 (filter)    / stricthost                              23 of 91 shown
Row 5..N          <master list, 44% width>  │  <detail pane, remainder>
```

- **Filter row** (row 4, exactly one row — no separate result-count line):
  a bare `textinput.Model` (mirrors `newTextInput`/`updateInput`,
  `identities.go:93-106`) with prompt `"/ "` and placeholder
  `"Type to filter…"`. The live match count renders RIGHT-ALIGNED on the
  SAME line (`"%d of %d shown"`), reusing the density discipline that made
  `findingsBanner`/D-04 fold advisory text onto an existing line rather than
  spend a new one.
- **Activation key**: `/` focuses the filter input (unclaimed at this
  screen scope — verified: neither `globalssh.go` nor `globalgit.go` binds
  `/` today). `Esc` blurs the filter (does not clear it — clearing is a
  separate, explicit action, matching every other gitid text field's
  blur-vs-clear distinction). This is DELIBERATELY scoped to the new
  sub-tabs only — the app-level `Ctrl+P` palette (a DIFFERENT filterable
  list, `app.go`) is untouched.
- **Master list** (row 5+): ONE line per directive/key (not the 2-line
  shape `optionRow` uses for curated Options rows — this list has no
  toggle/apply affordance, so it needs no sub-line budget): `" " + key +
  padding + truncated-value"`, selected row via `styleSelected` (existing
  role), reusing `gitScrollWindow`/`scrollWindowFor`/`gitRowForScreenRow`/
  `gitCueLine` verbatim for the scroll-window + cue-line behavior (the SAME
  mechanism `gssComputeScrollWindow` already proves against ~90 rows'
  worth of Global SSH content).
- **Detail pane** (right side, `masterDetailGutter`-separated, same
  proportions as every existing master-detail screen): full key, full
  (unclipped) value, and a source line — SSH: `"Resolved via ssh -G — reflects
  Include/Match precedence already applied."` (TEST-02's existing "ssh -G
  proof" framing, reused); Git: the origin file path from `git config
  --list --show-origin`, plus scope (global/system/local) when derivable
  from that path. **Cross-reference note** (resolves `09.5-CONTEXT.md`'s
  open discretion item): when the selected row's key ALSO exists in the
  curated Options/GSSH-01 or Baseline/GGIT-01 policy table, the detail pane
  shows one extra faint line: `"Also tracked as a recommended option — see
  the Options tab for gitid's guidance."` — informational only, never a
  second interactive affordance, and the value is never rendered twice
  side-by-side (avoids the double-counting risk the context doc flags).

## Custom key/directive entry (PROP-03 / PROP-04)

Both new sub-tabs gain a footer action `n · Add custom key` (SSH:
`n · Add custom directive`) — reusing the `n` = "new" convention already
established (`identities.go:5400`, `{Key: "n", Label: "new"}`). This is a
**new affordance, not a repurposed existing one** — do not overload `n`
elsewhere on these two screens.

### Git (PROP-03) — 2-stage flow, free-form

1. **Form entry** (inline, reuses `globalgit.go`'s D9 two-field pattern
   verbatim: `key` + `value` textinputs, Tab moves focus, Enter on the
   second field advances). No directive-name validation (D-03's explicit
   choice — an unrecognized git key is harmless).
2. **Ceremony** (`ceremonyConfig`, unmodified contract): `Heading: "Write
   custom Git key to <resolved target>"`, `Preview`/`PreviewDiff: true`
   showing `+ <key> = <value>` against the resolved managed block,
   `ConfirmLabel: "Write"`, `Async: true` (matches every other gitid commit
   path). On confirm: backup + write, receipt = `"<key> = <value> written."`

### SSH (PROP-04) — 3-stage flow, validated + proven

The extra blast radius (`09.5-CONTEXT.md`: a bad directive can hard-break
`~/.ssh/config` parsing for EVERY host) earns one extra visible stage
between form entry and the write ceremony — this is a UI/copy requirement,
not just a backend one:

1. **Form entry** — same 2-field shape as Git's (`directive` + `value`).
2. **Validate + prove** (NEW stage, no Git equivalent): renders like the
   create-flow's existing two-stage test screen (TEST-01's "show the exact
   command, then its real output" contract) —
   - Directive-NAME check first: `"Checking '<name>' against OpenSSH's
     known-directive list…"` → pass/fail. A fail stops here with an inline
     error (`"'<name>' is not a recognized SSH directive — nothing was
     written."`) and does NOT proceed to the ceremony.
   - `ssh -G` proof second (only if the name check passed): shows the
     EXACT command run against a throwaway temp config (TEST-01/SSHUI-04's
     existing never-mutate-live-config-until-confirm discipline) and its
     real output. A fail stops here with an inline error naming what `ssh
     -G` rejected — again, no write.
3. **Ceremony** — identical shape to Git's (`Heading: "Write custom SSH
   directive to <resolved target>"`, diff preview, `ConfirmLabel: "Write"`,
   `Async: true`), reached ONLY after both validation gates pass.

**Non-negotiable:** stage 2 is never skippable and never optional — per
CLAUDE.md's "hypothesis → test → implementation" rule and the CONTEXT.md
D-03 rationale, an SSH directive is proven before it is ever written for
real, exactly like every other SSH value gitid writes (SSHUI-04/TEST-01/02).
