## Summary

This phase extends two already-shipped, well-tested screens rather than
building new subsystems. The critical finding of this research is that
**both PROP-01's and PROP-02's core parsing needs are already implemented
in the codebase**, one layer closer to this phase's actual scope than the
CONTEXT.md pointer (`internal/tester/tester.go`) suggested:

- `internal/globalssh/probe.go`'s `parseResolvedOptions` already parses
  `ssh -G` output into a **general `map[string]string`** (not the fixed
  `tester.ResolvedConfig` struct) and is already invoked against exactly
  the right host context for a *global* screen (`ProbeHost =
  "gitid-probe.invalid"`, which resolves ONLY the `Host *` wildcard
  stanza — never a per-alias block). PROP-01 needs a new **exported**
  sibling of the existing unexported `effective(deps)` that returns this
  same full map, not a re-derivation of `ssh -G` parsing.
- `internal/globalgit/probe.go`'s `effectiveProbe` already runs `git
  config --show-origin --show-scope --list -z` from a deliberately
  non-repo working directory and returns `map[string]EffectiveEntry{Value,
  Scope, Origin}` for **every key actually set** — exactly PROP-02's
  data shape. It already excludes repo-local values by design (its `Deps`
  contract requires `NonRepoCwd` NOT be inside a git repository), which is
  the *correct* scope for a Global Git screen, not a gap to fix.

For the write paths, this research also resolves both of CONTEXT.md's
open "Claude's Discretion" architecture questions with code evidence
(not speculation): SSH's custom directive can be written into the
**existing** `global-ssh` managed block (its `globalMap`/`renderGlobalBody`
machinery already preserves and renders any unrecognized key verbatim,
appended after the known policy keys — zero new plumbing needed at the
render layer). Git's custom key needs a **new** managed block, because
`gitconfig.RenderBaselineBlock` renders a fixed, hardcoded set of `[section]`
headers — an arbitrary free-form key can name any section, which the
baseline renderer has no way to accommodate without becoming a second,
divergent schema.

For PROP-04's "OpenSSH's known-directive list," this research closes the
open question directly: **no static list or third-party library is
needed.** `ssh -G` itself is the authoritative validator — verified live
this session on this machine (OpenSSH 9.9p2/LibreSSL 3.3.6): an unknown
directive in a staged config makes `ssh -G` exit 255 with stderr `Bad
configuration option: <lowercased-name>`, while a known directive (even an
unusual one) exits 0. The already-vendored `github.com/kevinburke/ssh_config
v1.6.0` package does NOT export a usable "is this a known keyword" API
(its `defaults` map is unexported; `Default()` returns `""` for both
"unknown" and "known but no default," making it useless for this
validation) — do not reach for it here.

**Primary recommendation:** Export new read functions on top of the
EXISTING `globalssh.effective`/`globalgit.effectiveProbe` probe machinery
(do not build new `ssh -G`/`git config` parsers); write SSH custom
directives through the EXISTING `sshconfig.EnsureGlobals` explicit-overlay
path; write Git custom keys into a NEW managed block distinct from
`baseline`; validate the SSH directive NAME by running `ssh -G` against a
staged temp config and classifying the `Bad configuration option:` stderr
substring, not a static list.

### Pattern 1: General key/value `ssh -G` parse (PROP-01 reuse target)

**What:** Parse every line of `ssh -G` output into a `map[string]string`,
matching only lowercase `<key> <value>` lines (OpenSSH always emits
resolved config in lowercase; a camelCase line never matches — a verified
property, not an accident).

**When to use:** Any time the full resolved directive set is needed rather
than a fixed subset of fields.

**Example (existing code, reuse verbatim — do not re-derive):**
```go
// Source: internal/globalssh/probe.go:163-177 (verbatim, current on-disk)
func parseResolvedOptions(out string) map[string]string {
	m := make(map[string]string)
	for _, line := range strings.Split(out, "\n") {
		idx := strings.IndexByte(line, ' ')
		if idx <= 0 {
			continue
		}
		key := line[:idx]
		if key != strings.ToLower(key) {
			continue // camelCase line: never match (tester.ParseResolved property)
		}
		m[key] = strings.TrimSpace(line[idx+1:])
	}
	return m
}
```
`effective(deps)` (`internal/globalssh/probe.go:122-124`) already calls
`runProbe(deps, "-G", ProbeHost)` → this exact parser, against
`ProbeHost = "gitid-probe.invalid"` (the `Host *`-only probe target). PROP-01
needs only a thin **exported** wrapper, e.g. `AllDirectives(deps) (map[string]string, error) { return effective(deps) }`,
or export `effective` itself under a clearer public name. No new `ssh -G`
invocation logic, no new parser.

### Pattern 2: NUL-delimited `git config --list --show-origin --show-scope` parse (PROP-02 reuse target)

**What:** Parse `<scope> NUL <origin> NUL <key> LF <value> NUL`-formatted
records (the only unambiguous layout for values that may contain tabs,
newlines, or `=`) into `map[string]EffectiveEntry{Value, Scope, Origin}`.

**When to use:** Enumerating every git config key actually set, with
provenance, from a location that is NOT inside any specific repository
(so the result reflects the machine's global/system state, not one repo's
local overrides).

**Example (existing code, reuse verbatim — do not re-derive):**
```go
// Source: internal/globalgit/probe.go:89-98 (verbatim, current on-disk)
func effectiveProbe(deps Deps) (map[string]EffectiveEntry, error) {
	ctx, cancel := context.WithTimeout(context.Background(), probeTimeout)
	defer cancel()
	out, err := deps.RunGitConfig(ctx,
		"config", "--show-origin", "--show-scope", "--list", "-z")
	if err != nil {
		return nil, fmt.Errorf("globalgit: effective probe: git config --show-origin --show-scope --list -z: %w", err)
	}

```
Live-verified this session (`git config --list --show-origin` on the
research machine) confirms the origin-prefix format `file:<path>\tkey=value`
this parser already handles. PROP-02 needs this exact function's output,
converted to a sorted `[]GitSetKeyView` for the flat list — no new probe.

### Pattern 3: PROP-04 directive-name validation via live `ssh -G` (not a static list)

**What:** Stage the candidate directive into a temp SSH config (mirroring
SSHUI-04's existing never-mutate-live-config-until-confirm discipline —
`internal/tester/tester.go`'s `ResolvedVia`/`resolvedViaArgs` pattern),
then run `ssh -F <tmp> -G <probe-host>` and classify:

- **exit 255 + stderr containing `"Bad configuration option: "`** → the
  directive NAME is unrecognized by the locally-installed OpenSSH. Stop —
  do not proceed to the ceremony.
- **exit 0** → the directive is both a recognized name and the given value
  parsed successfully; proceed.
- Any other outcome (non-255 non-zero exit, or a stderr not matching that
  prefix) → a different, non-name-related SSH config error; surface it as a
  value/syntax rejection, not a "not a recognized directive" message.

**Verified this session** (OpenSSH_9.9p2, LibreSSL 3.3.6, local machine):
```bash
$ printf 'Host *\n  ThisIsNotARealDirective yes\n' > /tmp/badcfg_test.txt
$ ssh -F /tmp/badcfg_test.txt -G gitid-probe.invalid
# stdout: (empty)
# stderr: /tmp/badcfg_test.txt: line 2: Bad configuration option: thisisnotarealdirective
#         /tmp/badcfg_test.txt: terminating, 1 bad configuration options
# exit code: 255

$ printf 'Host *\n  StreamLocalBindMask 0177\n' > /tmp/goodcfg_test.txt
$ ssh -F /tmp/goodcfg_test.txt -G gitid-probe.invalid
# stdout: ...streamlocalbindmask 0177...
# exit code: 0
```
[VERIFIED: local `ssh -G` execution, this session, OpenSSH_9.9p2/LibreSSL 3.3.6]

**When to use:** This is the ENTIRE mechanism for PROP-04's "known-directive
list" requirement. Do not add `github.com/kevinburke/ssh_config` or any
other library for this — see "Standard Stack: Alternatives Considered."

**UI-SPEC's two visible sub-stages** ("Checking '<name>' against OpenSSH's
known-directive list…" then the `ssh -G` proof) can be implemented as
either (a) ONE staged-config `ssh -G` call whose stderr is classified for
both concerns (simpler, fewer subprocess spawns), rendered as two
sequential UI beats from the one result, or (b) two separate `ssh -G`
calls (name-only isolated check, then full-context proof). Planner's
discretion — option (a) is recommended for simplicity since the SAME
"Bad configuration option:" substring signal answers the name question
regardless of how the value classifies, mirroring this codebase's existing
substring-classification discipline (`tester.ClassifyPreWrite`,
`internal/tester/tester.go:52-61`, which explicitly never trusts the exit
code alone for its OWN classification — though for `ssh -G` the exit code
0-vs-255 distinction IS reliable and should be used as a first-pass gate,
with the stderr substring as the second signal that distinguishes "unknown
directive" from "known directive, bad value").

**Git (PROP-03) — needs a NEW managed block, distinct from `baseline`:**

`gitconfig.RenderBaselineBlock(cfg BaselineConfig)`
(`internal/gitconfig/baseline.go:404-488`) renders a FIXED, hardcoded
sequence of section headers (`[core]`, `[push]`, `[pull]`, `[fetch]`,
`[color]`, `[diff]`, `[merge]`, `[init]`, `[alias]`) — there is no
mechanism for an arbitrary `[section]` a free-form key might name. Verified
by reading the full function this session (`internal/gitconfig/baseline.go:404-488`,
quoted section list above matches the `fmt.Fprintf(&b, "[core]\n")` /
`"[push]\n"` / etc. literals in that range). Extending this renderer to
accept dynamic section names would turn a byte-stable, SC-1-idempotent
function into a second, divergent config-writing code path.

**Recommended shape** (new file `internal/gitconfig/customkeys.go`, mirroring
`WriteBaselineFile`'s shape at `internal/gitconfig/baseline.go:540-575`):

```go
// Illustrative shape — not verbatim existing code; follows the established
// WriteBaselineFile pattern (EnsureDir -> ReadFile -> render -> ReplaceBlock
// -> idempotency check -> filewriter.Write).
func WriteCustomGitKey(path, key, value string) (backupPath string, err error) {
	if err := validateValue(key, value); err != nil { // internal/gitconfig/fragment.go:132
		return "", err
	}
	section, name, err := splitGitKey(key) // last-dot split, see Pitfall below
	if err != nil {
		return "", err
	}
	existing, _ := os.ReadFile(path)
	body := fmt.Sprintf("[%s]\n\t%s = %s", section, name, value)
	composed := filewriter.ReplaceBlock(existing, "custom-git-keys", body)
	if bytes.Equal(composed, existing) {
		return "", nil
	}
	return filewriter.Write(path, composed, gitconfigMode)
}
```

Each subsequent custom key can either append to the SAME `custom-git-keys`
block body (accumulating multiple `[section]\n\tkey = value` stanzas —
git tolerates repeated `[section]` headers and merges them at read time,
confirmed via `man git-config` this session) or the planner may choose
one block per key with a keyed sentinel name — either is functionally
correct; the accumulating single-block form matches the existing
`baseline`/`url-rewrites` precedent of one block per logical purpose.

## Common Pitfalls

### Pitfall 1: Running the Git "set keys" probe from inside a repository

**What goes wrong:** `git config --list --show-origin` run from inside
ANY git repository folds that repo's `local` scope (and any `includeIf
gitdir:`/`hasconfig:` fragments that repo happens to match) into the
output — making the "Global Git" browser show one arbitrary repo's
settings mixed in with the actual global/system state.

**Why it happens:** `git config --list` without `--global`/`--system`
resolves the FULL effective configuration for the CURRENT working
directory, exactly like any other `git config` invocation.

**How to avoid:** Reuse `effectiveProbe`'s existing contract exactly:
`Deps.NonRepoCwd` "MUST NOT be inside any git repository" (`internal/globalgit/probe.go:39-46`,
verified this session) — the SAME directory `cmd/gitid/wiring.go` already
supplies for the existing Global Git Options screen. Do not invoke the new
PROP-02 probe from any other working directory.

**Warning signs:** A "Set keys" list that shows keys the user never
configured globally, or an origin path pointing at a project's `.git/config`.

### Pitfall 2: `kevinburke/ssh_config`'s `Default()` is not a "known keyword" check

**What goes wrong:** Calling `ssh_config.Default(candidateName) != ""` and
treating a non-empty result as "known" and empty as "unknown" produces
false negatives: many genuinely valid OpenSSH directives (e.g. `HostName`,
`Match`, `Include`, `IdentityFile`'s exact wording variance) either have no
listed default in that package's `defaults` map or the map is simply
incomplete relative to current OpenSSH.

**Why it happens:** The package's `defaults` map (`validators.go:83-162`)
is unexported and was hand-curated against "OpenSSH_7.4p1 on a Mac" per its
own doc comment — it is not attempting to be an exhaustive keyword catalog.

**How to avoid:** Use Pattern 3 (live `ssh -G` classification) exclusively
for PROP-04's name validation. Do not import or reach for `ssh_config`'s
`Default`/`defaults` for this purpose.

**Warning signs:** A valid directive rejected as "not recognized," or an
actually-invalid string accepted because it happens to collide with an
unrelated key in the `defaults` map.

### Pitfall 3: Splitting a free-form Git key on every dot

**What goes wrong:** A free-form key like `remote.origin.url` or
`http.https://example.com.sslVerify` split naively on ALL dots produces
the wrong section/variable-name pairing.

**Why it happens:** Git's own rule (verified via `man git-config` this
session, `CONFIGURATION FILE` section): "the fully qualified variable name
of the variable itself is the last dot-separated segment and the section
name is everything before the last dot. The variable names are
case-insensitive, allow only alphanumeric characters and -, and must start
with an alphabetic character." A subsection name (the middle segment, when
present) can itself legitimately contain dots.

**How to avoid:** Split ONLY on the LAST dot: everything after is the
variable name (validated against `^[A-Za-z][A-Za-z0-9-]*$`), everything
before is the section-plus-optional-subsection, rendered as `[section
"subsection"]` when a subsection is present, or `[section]` when the key
is exactly two segments.

**Warning signs:** A custom key like `mytool.sub.key` silently written
under the wrong section, or a `git config --get` on the intended key
returning nothing after the write.

### Pitfall 4: Treating "no directive-name validation" (D-03, Git side) as "no validation at all"

**What goes wrong:** Writing a syntactically malformed free-form Git key
(containing whitespace, `]`, or a newline) directly into raw INI text
corrupts the managed block or lets a value smuggle in a bogus extra
`[section]` header.

**Why it happens:** D-03's "free-form, no directive-name validation" is
about NOT checking the key against a catalog of known/blessed keys (an
unrecognized key is harmless to git) — it is NOT license to skip basic
syntactic safety. gitid's Git config writer builds raw INI text directly
(not via `git config --add`, per CLAUDE.md's documented gitconfig
strategy), so an unescaped value or malformed key can corrupt the file
gitid itself renders.

**How to avoid:** Still call `gitconfig.validateValue(key, value)`
(`internal/gitconfig/fragment.go:132`, rejects `\n`/`\r` and `[remote`
injection) on the VALUE, and validate the KEY against git's own
`section[.subsection].variable` syntax rule (Pitfall 3) before ever
building the block body string.

**Warning signs:** A write that "succeeds" but produces a `~/.gitconfig.d/*`
file `git config --list` can no longer parse, or a key silently merged
into an unrelated existing section.

### Pitfall 5: Probing the SSH directive set against a per-alias host instead of the global wildcard

**What goes wrong:** Running the PROP-01 full-directive probe (or the
PROP-04 proof) against a real configured alias (e.g. `personal.github.com`)
instead of the `ProbeHost` wildcard-only sentinel would resolve per-alias
values (a specific `IdentityFile`, `IdentitiesOnly yes`) as if they were
global defaults, misleading the Global SSH screen's "what applies
everywhere" framing.

**Why it happens:** `ssh -G <host>` resolves the config for THAT host,
following first-match-wins `Host` block precedence — a specific alias
would match its own `Host` block first, shadowing the wildcard values the
Global screen is supposed to show.

**How to avoid:** Reuse the EXISTING `ProbeHost = "gitid-probe.invalid"`
constant (`internal/globalssh/probe.go:23`, verified this session — an
`.invalid` TLD host that matches only `Host *`) for both PROP-01's browse
and PROP-04's proof. Do not introduce a second probe-host constant.

**Warning signs:** The "All directives" list shows an `IdentityFile` value
pointing at a specific identity's key, or `IdentitiesOnly` reads `yes`
globally when it is actually only scoped per-alias by policy
(`internal/globalssh/policy.go:35`: `IdentitiesOnly`'s `Scope` is
`"per-alias"`, never written to `Host *`).

### Converting the Git effective-probe map to a sorted view slice (PROP-02)

```go
// Illustrative — internal/globalgit/probe.go's effectiveProbe already
// returns map[string]EffectiveEntry; the new read path sorts it for
// stable, deterministic list rendering (map iteration order is not
// stable in Go).
func AllSetKeys(deps Deps) ([]SetKeyView, error) {
	m, err := effectiveProbe(deps)
	if err != nil {
		return nil, err
	}
	keys := make([]string, 0, len(m))
	for k := range m {
		keys = append(keys, k)
	}
	sort.Strings(keys)
	out := make([]SetKeyView, 0, len(keys))
	for _, k := range keys {
		e := m[k]
		out = append(out, SetKeyView{Key: k, Value: e.Value, Scope: e.Scope, Origin: e.Origin})
	}
	return out, nil
}
```

### Directive-name + value staged proof (PROP-04) — reusing the temp-config discipline

```go
// Pattern mirrors internal/tester/tester.go's ResolvedVia (staged -F temp
// config, never the live file) — illustrative, not existing code.
func ProveCustomDirective(name, value, currentGlobalBody string) (ok bool, unknownName bool, sshOutput string, err error) {
	stagedBody := currentGlobalBody + fmt.Sprintf("\n  %s %s\n", name, value)
	tmp, cleanup, err := writeStagedConfig(stagedBody) // Host * wrapper + IgnoreUnknown guard
	defer cleanup()
	if err != nil {
		return false, false, "", err
	}
	cmd := exec.Command("ssh", "-F", tmp, "-G", ProbeHost) //nolint:gosec // arg-slice, fixed flags + gitid constants
	out, runErr := cmd.CombinedOutput()
	sshOutput = string(out)
	if runErr == nil {
		return true, false, sshOutput, nil
	}
	if strings.Contains(sshOutput, "Bad configuration option: ") {
		return false, true, sshOutput, nil
	}
	return false, false, sshOutput, nil // known name, rejected value/syntax
}
```
