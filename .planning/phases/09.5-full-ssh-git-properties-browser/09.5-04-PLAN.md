<objective>
Close PROP-04: custom global SSH directive entry from the `All directives`
sub-tab, gated by a name check against the locally installed OpenSSH and by a
real `ssh -G` proof against a throwaway staged config, before the standard
write ceremony.

Purpose: this is the phase's high-blast-radius half. An unrecognised SSH
directive is not a harmless no-op like an unknown git key — OpenSSH hard-fails
parsing `~/.ssh/config`, breaking connectivity for EVERY host, not just gitid's
managed ones. D-03 buys down that risk with one extra, un-skippable visible
stage, and CLAUDE.md's hypothesis→test→implementation rule requires the proof to
be a real command with real output, not a name-list match.

Output: the combined-output probe seam, `ProveCustomDirective`'s staged-config
classifier, the `SSHCustomDirectivePlanner` seam with both implementations,
`runCustomSSHDirectiveWrite` with its own post-write re-verification, the
three-stage TUI flow, the frozen copy in both gates, and real-PTY proof of both
the rejection path and the success path.
</objective>

<decision_record>
**D-H — `ssh -G` itself is the authoritative known-directive list; there is no
static list and no third-party lookup.** CONTEXT.md left the source open and
explicitly asked for it to be researched rather than guessed. RESEARCH verified
live on this machine (OpenSSH_9.9p2/LibreSSL 3.3.6) that an unknown directive in
a staged config makes `ssh -G` exit 255 with stderr
`Bad configuration option: <lowercased-name>`, while a known-but-unusual
directive exits 0. Rejected: (a) a hardcoded slice of ~90 keyword strings — it
drifts from whatever OpenSSH is actually installed, and CONTEXT.md explicitly
asked to avoid guessing at a hardcoded list; (b) `kevinburke/ssh_config`'s
`Default()` — its `defaults` map is unexported and hand-curated against
OpenSSH 7.4, and `Default()` returns `""` for BOTH "unknown keyword" and "known
keyword with no listed default", which makes it unsafe as a validation source in
exactly the direction that matters. Probing the locally installed toolchain is
already this project's standard approach for this class of question (PLAT-01).

**Reversibility: `costly`.** 09.5-CONTEXT.md asked for this to be rated
`one-way`-adjacent given the blast radius. In this unattended run the
`checkpoint:decision` is replaced by this record. The rating is `costly` rather
than `one-way` because the blast radius is bounded by three independent,
already-existing mechanisms that this plan does not weaken: the proof runs
against a THROWAWAY staged config so the real file is untouched until confirm;
`sshconfig.EnsureGlobals` re-parses the composed bytes and refuses to write an
unparseable result; and the write is a backed-up, journal-rolled-back
transaction. The validator itself is one function behind a seam — swapping its
source later is a localized change, not a data migration. What would be
genuinely one-way is shipping a static list users come to depend on; that is the
rejected option.

**D-I — one staged `ssh -G` invocation, classified into THREE outcomes,
rendered as two sequential UI beats.** RESEARCH flagged this as the planner's
call (its assumption A2). Chosen: a single call whose combined output is
classified as (1) accepted, (2) the candidate's OWN name rejected, or (3) a
failure naming a DIFFERENT directive — i.e. a pre-existing problem in the user's
current global block, which must NOT be blamed on what they just typed.
Rationale: the same `Bad configuration option:` signal answers the name question
regardless of how the value classifies, it halves the subprocess spawns, and it
keeps ONE classification site instead of two that can drift — mirroring
`tester.ClassifyPreWrite`'s existing substring-classification discipline.
Rejected: two separate invocations (an isolated name-only check, then a
full-context proof) — marginally easier to unit-test in isolation, but it
creates two places where "is this name known?" is decided. Reversibility:
reversible.

**D-J — the custom directive is written into the EXISTING `global-ssh` managed
block via `EnsureGlobals`'s `explicit` overlay; no new SSH block is created.**
CONTEXT.md left the write target open. `sshconfig.renderGlobalBody`
(globals.go:272-280) already renders any key NOT in `GlobalHostStarOrder`
verbatim, appended after the ordered ones — so an unrecognised key is preserved
by construction with zero new render plumbing, and `EnsureGlobals` already runs
`Parse(composed)` afterwards and refuses to persist an unparseable result.
Rejected: a second `Host *` managed block — two wildcard stanzas make
first-match-wins ordering ambiguous, `ensureGlobalsLast`'s position invariant
would need a companion, and the new sentinel would need its own reserved-name
registration; all of that for a capability the existing block already has.
Reversibility: reversible.
</decision_record>

| Boundary | Description |
|----------|-------------|
| user keystrokes (directive name + value) → a staged SSH config → the real `ssh` binary | User text becomes a file OpenSSH parses. The staging directory is gitid-created and short-lived. |
