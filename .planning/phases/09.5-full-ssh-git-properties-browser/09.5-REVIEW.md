## Critical Issues

### CR-01: A custom Git key with a non-printable/space subsection is silently mis-filed under a DIFFERENT key, and permanently bricks the custom-git-keys block

**File:** `internal/gitconfig/customkeys.go:43` (`forbiddenSubsectionCharRE`),
`internal/gitconfig/customkeys.go:114-116` (the guard),
`internal/gitconfig/customkeys.go:197` (the `%q` render),
`internal/gitconfig/customkeys.go:149-158` (the read-back parse)
**Severity:** BLOCKER — data integrity + a false success receipt + a
self-inflicted denial of service on the feature.

**Issue.** `SplitGitKey` rejects only `"`, `\`, `\n`, `\r` in a subsection:

```go
var forbiddenSubsectionCharRE = regexp.MustCompile(`["\\\n\r]`)
```

but `RenderCustomKeysBlock` renders the subsection with `%q`:

```go
fmt.Fprintf(&b, "[%s %q]\n", section, subsection)
```

`%q` is `strconv.Quote`, which emits a backslash escape for **every rune
`unicode.IsPrint` rejects** — TAB, DEL, NBSP (`U+00A0`, i.e. **Option+Space on
a macOS keyboard**), ZWSP, and every other non-ASCII space or control rune.
None of those four characters is in the guard, so all of them reach the
renderer.

Two independent consequences, both proven against the real `git` binary:

**(a) Silent mis-file.** git's subsection grammar recognises only `\"` and
`\\`; every other `\x` collapses to `x`. So the key the user asked for is not
the key that lands in the file:

```
$ EnsureCustomGitKey(nil, "http.a<NBSP>b.sslVerify", "true")   # accepted, no error
rendered:  [http "a b"]
           	sslVerify = true

$ git config --file nb.cfg --list
http.au00a0b.sslverify=true                     # <-- a DIFFERENT key

$ git config --file nb.cfg --get "http.a<NBSP>b.sslVerify"
exit=1                                           # <-- the requested key does not exist
```

The TUI then renders `PropsGitCustomReceiptFmt` — `"http.a b.sslVerify = true
written."` — which is false. This is precisely the failure this file's own
doc comment claims to prevent: *"Every rejection names the offending part so a
silent mis-file (RESEARCH Pitfall 3) is never mistaken for success."*

**(b) Permanent brick.** `ParseCustomKeysBlock` reads the header back with
`strings.Trim(..., "\"")` and performs **no unescaping**, so the subsection
comes back as the literal `a b` — which now contains a backslash. Every
subsequent `EnsureCustomGitKey` call, for **any** key, fails:

```
$ EnsureCustomGitKey(<the file just written>, "user.name", "Second")
gitconfig: EnsureCustomGitKey: gitconfig: RenderCustomKeysBlock:
  gitconfig: subsection "a\\u00a0b" must not contain a double quote, backslash, or newline
```

Same result reproduced for TAB (`http.atb.sslverify`) and ZWSP
(`http.au200bb.sslverify`). The "Set keys → n" feature is dead until the user
hand-edits `~/.gitconfig.d/00-baseline`, and nothing in the UI explains why.

Reachability: NBSP is a single keystroke on macOS (Option+Space) and survives
`bubbles` textinput unchanged; the key field has no character filter.

**Fix.**

```go
// 1) Make the guard cover exactly what the renderer escapes.
func validateSubsection(sub string) error {
	for _, r := range sub {
		if r == '"' || r == '\\' || !unicode.IsPrint(r) {
			return fmt.Errorf(
				"gitconfig: subsection %q contains %q, which git's subsection grammar "+
					"cannot represent — the key would be silently written under a different name", sub, r)
		}
	}
	return nil
}
// replace the forbiddenSubsectionCharRE check in SplitGitKey with validateSubsection(subsection).
```

```go
// 2) Render with an explicit escaper that matches git's grammar (only \" and \\),
//    never %q, so the render can never introduce an escape the parser cannot undo.
esc := strings.NewReplacer(`\`, `\\`, `"`, `\"`).Replace(subsection)
fmt.Fprintf(&b, "[%s \"%s\"]\n", section, esc)
```

```go
// 3) Close the loop in runCustomGitKeyWrite's verify stage (lifecycle.go:1510):
//    a syntax check is not a mis-file check. Read the key BACK.
got, gerr := gitconfig.RunGitConfigGet(target, key)
if gerr != nil || got != value {
	return fail(fmt.Errorf("post-write verification: %s reads back as %q, not %q", key, got, value))
}
```

### CR-02: A custom SSH directive value containing a TAB or repeated spaces is written correctly, then silently rewritten to a DIFFERENT value by the next unrelated managed-block write

**File:** `internal/globalssh/validate.go:115-123` (`ValidateDirectiveValue`),
`internal/sshconfig/globals.go:247-255` (`parseGlobalBody`), with a false
contract claim at `internal/sshconfig/globals.go:229-235`
**Severity:** BLOCKER — silent mutation of a security-relevant value in
`~/.ssh/config` (`IdentityFile`, `ProxyCommand`, `UserKnownHostsFile`, …), on a
write the user confirmed for something else entirely.

**Issue.** `ValidateDirectiveValue` rejects only `\n`, `\r`, `\x00`, and
all-whitespace. A TAB, or two consecutive spaces inside a quoted argument, is
accepted. `ssh -G` accepts them too, so `ProveCustomDirective` returns
`OK: true` and the write proceeds — correctly, the first time.

But `parseGlobalBody` reconstitutes every value with
`strings.Join(strings.Fields(trimmed)[1:], " ")`, which **collapses all
internal whitespace**. So the *second* time `EnsureGlobals` touches the block —
any curated Global-SSH apply, any later custom directive, any repair — the
value is rewritten.

Proven against the real code (`EnsureGlobals`, goos `linux`):

```
after write 1 (the user's confirmed custom directive):
  # BEGIN gitid managed: global-ssh
  IgnoreUnknown UseKeychain

  Host *
    IdentityFile "/pa  th/id"          <-- as typed and as proven by ssh -G
  # END gitid managed: global-ssh

after an UNRELATED write 2 (apply StrictHostKeyChecking yes):
  Host *
    StrictHostKeyChecking yes
    IdentityFile "/pa th/id"           <-- a DIFFERENT FILE PATH
```

Same for a tabbed argument list: `ProxyCommand /usr/bin/nc\t-X 5 %h %p` →
`ProxyCommand /usr/bin/nc -X 5 %h %p`.

And both forms are genuinely distinct to OpenSSH — this is not a cosmetic
normalisation:

```
$ ssh -F s2.cfg -G gitid-probe.invalid | grep -i identityfile
identityfile /pa  th/id
$ ssh -F s3.cfg -G gitid-probe.invalid | grep -i identityfile
identityfile /pa th/id
```

`parseGlobalBody`'s doc comment asserts the opposite of the observed
behaviour — *"a directive's value carries every token after the key, not just
the first, so a multi-token value (a quoted path with a space, a
space-separated argument list) survives round-trip intact (CR-02)"* — so the
contract is documented as held while the code breaks it.

The git side of this phase gets this right (it fails closed on any value it
cannot render faithfully). The SSH side, which touches the higher-blast-radius
file, does not.

**Fix.** Either (preferred, matches the git side's fail-closed posture):

```go
// internal/globalssh/validate.go — ValidateDirectiveValue
if strings.ContainsRune(value, '\t') || strings.Contains(value, "  ") {
	return fmt.Errorf("globalssh: directive value %q contains a tab or repeated space — "+
		"gitid's managed Host * block normalises internal whitespace on rewrite, "+
		"so the value would not survive the next write intact", value)
}
```

or fix the round trip so the guard is unnecessary:

```go
// internal/sshconfig/globals.go — parseGlobalBody
key := fields[0]
rest := strings.TrimLeft(trimmed[len(key):], " \t")   // preserve interior whitespace verbatim
m.set(key, rest)
```

and delete the now-true-or-false claim from the doc comment accordingly. Add a
round-trip regression test that writes a value with a tab and a double space
and asserts byte-equality after a second `EnsureGlobals`.

### WR-01: The post-write advisory fires falsely for every value `ssh -G` normalises

**File:** `cmd/gitid/lifecycle.go:1743-1765` (`customDirectiveVerifyAdvisories`)

**Issue.** The WR-08 "fix" replaced `strings.EqualFold` with an exact
comparison against `strings.TrimSpace(value)`. But `ssh -G` reports the
*resolved* value, which OpenSSH canonicalises. Real output from the installed
`OpenSSH_9.9p2`:

```
input line                       ssh -G reports
StrictHostKeyChecking yes    ->  stricthostkeychecking true
ServerAliveCountMax 03       ->  serveralivecountmax 3
Ciphers +aes128-cbc          ->  ciphers chacha20-poly1305@openssh.com,aes128-ctr,...,aes128-cbc
IdentityFile "/pa th/id"     ->  identityfile /pa th/id        (quotes stripped)
```

Every one of those produces:

> `advisory: X was written as "yes" but resolves to "true" — the write may be
> shadowed by another directive`

which is factually wrong and actively alarming: the write succeeded and nothing
shadowed it. `yes` → `true` was broken under `EqualFold` too; quote-stripping
and `+`/`-`/`^` list-modifier expansion are now broken as well.

**Fix.** Do not compare raw input text against a resolved value. Either drop
the value comparison entirely and keep only the presence check, or compare
against a *second* `ssh -G` reading taken from a staged config containing only
the candidate line (so both sides are canonicalised the same way):

```go
// compare resolved-vs-resolved, never typed-vs-resolved
expected, err := globalssh.ResolveDirectiveValue(deps, name, value) // staged, canonicalised
if err == nil && d.Value != expected { /* advisory */ }
```

### WR-02: Stage 2's "real result" shows the pre-write value for any directive the block already sets

**File:** `internal/globalssh/validate.go:238-250` (`stageDirectiveConfig`),
rendered at `internal/tuikit/globalssh.go:2061-2067`

**Issue.** `stageDirectiveConfig` appends the candidate line **after** the
existing block body. `ssh_config` is first-value-wins:

```
$ printf 'Host *\n  StrictHostKeyChecking yes\n  StrictHostKeyChecking no\n' > dup.cfg
$ ssh -F dup.cfg -G gitid-probe.invalid | grep -i stricthost
stricthostkeychecking true          # the FIRST value, not the candidate
```

Meanwhile the actual write goes through `merged.set(k, v)`, which **replaces**
the existing value in place. So for any directive already present in the
managed block, the stage-2 screen — whose entire stated contract is "show the
exact command, then its real output" (TEST-01) — shows the value the user is
*replacing*, presented as evidence for the value they are *adding*.

(Value validation itself is still safe: `ssh -G` reports `unsupported option`
for a shadowed bad value too — verified.)

**Fix.** Stage the candidate line **first**, before the existing body, so the
probe resolves the value the write will actually produce:

```go
if !hasHostStarLine(body) { b.WriteString("Host *\n") }
fmt.Fprintf(&b, "  %s %s\n", name, value)   // candidate FIRST
if body != "" { b.WriteString(body); b.WriteString("\n") }
```

### WR-06: One unrenderable entry anywhere in the block blocks every future custom key

**File:** `internal/gitconfig/customkeys.go:186-204` (`RenderCustomKeysBlock`),
called from `EnsureCustomGitKey:268`

**Issue.** `EnsureCustomGitKey` re-renders **all** parsed entries and aborts
the whole write if any single one fails. So one entry that round-trips badly —
whether from CR-01, a hand edit, a merge conflict, or a future format change —
takes the entire feature down rather than just itself.

Contrast the SSH sibling: `parseGlobalBody` tolerates anything it cannot
classify and `EnsureGlobalGit` (globalgit.go:122-129) explicitly *drops* a bad
adopted value rather than refusing to write ("we must not refuse to write just
because it had a quirky value"). The new code inverted that established policy
without saying so.

**Fix.** Render entry-by-entry; drop (and report, as an advisory on the
receipt) an entry that cannot be re-rendered, rather than failing the write:

```go
for _, e := range entries {
	if err := renderOne(&b, e); err != nil {
		skipped = append(skipped, fmt.Sprintf("%s (%v)", e.Key, err))
		continue
	}
}
```

The upserted key itself must still fail closed — it is validated before the
loop.

### WR-09: An empty custom Git value is accepted; the SSH sibling explicitly rejects one

**File:** `internal/gitconfig/customkeys.go:60-71` (`validateCustomValue`)

**Issue.** `validateCustomValue` rejects a whitespace-only value (because

### WR-12: `deterministicGlobalGitFixture` now truncates a `.gitconfig` another fixture wrote into the same sandbox HOME

### WR-13: `CustomSSHDirectivePlan` is documented as a fail-closed gate but validates nothing

**File:** `cmd/gitid/wiring.go:2610-2651`

**Issue.** The doc comment says *"a candidate that would not round-trip parse
fails HERE, at the plan stage, and the ceremony never opens"*, and
`backend.go`'s `SSHCustomDirectivePlanner` interface says *"a non-nil error
here must fail closed"*. The implementation calls only
`sshconfig.EnsureGlobals` — which is not a name/value validator. Proven:

```
EnsureGlobals(nil, {"": ""},                 "linux") -> err=<nil>, body: "Host *\n   \n"
EnsureGlobals(nil, {"Host": "evil.example"}, "linux") -> err=<nil>, body: "Host *\n  Host evil.example\n"
EnsureGlobals(nil, {"Include": "/tmp/x"},    "linux") -> err=<nil>, body: "Host *\n  Include /tmp/x\n"
```

i.e. the exact structural-keyword corruption prior-CR-02 was raised about
composes cleanly through the "plan gate". It is unexploitable today only
because `runCustomSSHDirectiveWrite` re-validates — so one of the two
advertised defence layers is a no-op while the doc claims two.

**Fix.** Call the real validators at the top of `CustomSSHDirectivePlan`:

```go
if err := globalssh.ValidateDirectiveName(name); err != nil { return tuikit.SSHCustomDirectivePlanView{}, err }
if err := globalssh.ValidateDirectiveValue(value); err != nil { return tuikit.SSHCustomDirectivePlanView{}, err }
```

### WR-14: The in-flight stage-2 render interpolates the raw, unvalidated directive name

**File:** `internal/tuikit/globalssh.go:2038-2040`

**Issue.** The WR-14 fix added `sanitizeProofOutput` for `proof.Output` — good

d.WriteString(" " + fmt.Sprintf(PropsSSHNameCheckFmt, sanitizeProofOutput(m.pendingDirectiveName)) + "\n")

Same treatment for `renderCustomDirectiveForm`'s raw
`customDirectiveNameInput`/`customDirectiveValueInput` values, and for
`globalgit.go`'s custom-key form.

### IN-01: Detail-pane wrapped lines lose their leading gutter space

**File:** `internal/tuikit/globalssh.go:1974-1981`

Visible in the tracked baseline `global-ssh-all-directives-browse.txt`: the
second line of a wrapped detail sentence renders flush against the `│` divider

### IN-02: `resolvePhase` and `resolveProvenanceText` duplicate the same map lookup and the same not-found error

**File:** `cmd/gitid-frame-promote/main.go:143-166`

Two functions, two `phaseFrames[phase]` lookups, two different error strings
for the same condition (one lists the known phases, the other does not).
`run()` calls both, so an unknown phase produces the *worse* message only if
`promoteForPhase` is bypassed. Collapse into one lookup returning the whole

### IN-03: `subTabStripRows()` is a function returning a literal

**File:** `internal/tuikit/frame.go:132-141`

`func subTabStripRows() int { return 3 }` with a doc comment insisting no

### IN-04: `EnsureGlobals` silently replaces a user's `IgnoreUnknown` argument

**File:** `internal/sshconfig/globals.go:251-252, 270`

(not introduced by this phase) but newly reachable now that arbitrary
directives can be added to the block. Worth an explicit advisory when the
