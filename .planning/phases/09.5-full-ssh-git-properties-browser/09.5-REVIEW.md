## Critical Issues

### CR-01: A custom Git key colliding with a curated `global-git` key is neither surfaced nor deterministically resolved — the declared backstop is unimplemented

**Files:**
`internal/gitconfig/customkeys.go:322` (`EnsureCustomGitKey`),
`cmd/gitid/lifecycle.go:1367-1545` (`runCustomGitKeyWrite`),
`cmd/gitid/wiring.go:2514` (`CustomGitKeyPlan`),
`cmd/gitid/lifecycle.go` `runGlobalGitApply` verify stage

**Issue:**
`09.5-03-PLAN.md`'s declared backstop (line 58) is:

> "A custom key that collides with a key the curated baseline block already manages
> does not produce two conflicting writers of the same key; the flow surfaces the
> collision rather than silently shadowing one block with the other."

Both halves fail. `custom-git-keys` and `global-git` are two separate managed blocks in
the SAME file (`~/.gitconfig.d/00-baseline`). `filewriter.ReplaceBlock` appends a block
when it is absent and updates it in place when present, so **which block appears last —
and therefore which value git's last-occurrence-wins resolution honours — is decided by
which of the two ceremonies ran first on that machine.** Nothing in `CustomGitKeyPlan`,
`customKeyCeremonyFor`, `runCustomGitKeyWrite`, or the receipt checks
`globalgit.PolicyFor(key)` or mentions a collision.

Proof (real `git config`, both orderings, same two user actions):

```
Case A — curated apply first, then the custom key:
  # BEGIN gitid managed: global-git
  [init]
  	defaultBranch = main
  # END gitid managed: global-git
  # BEGIN gitid managed: custom-git-keys
  [init]
  	defaultBranch = trunk
  # END gitid managed: custom-git-keys
  git resolves init.defaultBranch = "trunk"      <- the custom key wins

Case B — the custom key first, then the curated apply:
  # BEGIN gitid managed: custom-git-keys
  [init]
  	defaultBranch = trunk
  # END gitid managed: custom-git-keys
  # BEGIN gitid managed: global-git
  [init]
  	defaultBranch = main
  # END gitid managed: global-git
  git resolves init.defaultBranch = "main"       <- the custom key is INERT
```

In **both** cases every ceremony reported success and emitted **zero** advisories:

- Case A: `runGlobalGitApply`'s verify stage ran *before* the custom write existed, so
  it saw `main` and was happy; `runCustomGitKeyWrite`'s WR-08 read-back then saw
  `trunk` and passed. Neither ever re-checks.
- Case B: `runCustomGitKeyWrite`'s read-back passed at its own write time (nothing
  shadowed it yet); `runGlobalGitApply` then wrote the block that neutralises it, and
  its own verify only fires when *its* value loses — which it did not. The user's
  explicitly-typed, explicitly-receipted `init.defaultBranch = trunk` is now dead with
  no signal anywhere.

The T-09.5-19 mitigation text ("git's last-value-wins ordering resolves it
deterministically") is factually wrong: the outcome is order-of-first-write dependent,
so two machines that performed the same two actions in a different order end up with
opposite effective configurations. The second half of the mitigation ("the browser's
own `Set keys` list shows the effective value with its origin") shows only the
*effective* value with its file path — both blocks are in the same file, so the list
cannot distinguish which block produced it and never tells the user their custom key
is inert.

For contrast, the SSH sibling has no equivalent problem: `EnsureGlobals` merges the
custom directive into the SAME `globalMap` as the curated keys, so there is exactly one
writer of any key and `merged.set` replaces in place.

**Fix (either is sufficient; the first is closest to the declared backstop):**

1. Surface the collision at the plan stage, in both directions:

```go
// cmd/gitid/wiring.go, CustomGitKeyPlan (and mirrored in runCustomGitKeyWrite's
// plan stage as the fail-closed backstop)
if _, managed := globalgit.PolicyFor(key); managed {
    return tuikit.GitCustomKeyPlanView{}, fmt.Errorf(
        "gitid: %s is managed by the curated Global Git baseline block in the same file — "+
            "writing it as a custom key creates two writers of one key whose precedence "+
            "depends on block order; change it from the Options sub-tab instead", key)
}
```
   and symmetrically, have `runGlobalGitApply` refuse (or explicitly warn in its
   ceremony preview) when a selected policy key is already present in the
   `custom-git-keys` block — `gitconfig.ParseCustomKeysBlock(existing)` already gives
   it the list.

2. Or make precedence structural rather than incidental: have `EnsureCustomGitKey`
   guarantee the `custom-git-keys` block is always composed LAST in the file (the same
   `ensureGlobalsLast` post-condition `internal/sshconfig/globals.go:123` already
   applies to the `Host *` block), and document/render that "custom keys always
   override the curated baseline" as the defined rule.

Whichever is chosen, `runGlobalGitApply`'s verify stage should also compare against
`ParseCustomKeysBlock` so a curated apply that neutralises a user's custom key emits an
advisory naming it.

## Warnings

### WR-01: `SplitGitKey` accepts an empty subsection; the renderer silently re-files the key under a *different* name and clobbers the unrelated real key in the ceremony's own diff

**Files:** `internal/gitconfig/customkeys.go:149` (`SplitGitKey`), `:242`
(`RenderCustomKeysBlock`), `:281` (`gitKeysEqual`)

**Issue:** For `key = "http..sslVerify"`, `SplitGitKey` returns `section="http"`,
`subsection=""`, `variable="sslVerify"` — `validateSubsection("")` passes vacuously.
`RenderCustomKeysBlock` then takes the `subsection == ""` branch and emits `[http]`,
not `[http ""]`, so the key is written as `http.sslVerify`. Git treats those as two
genuinely different keys:

```
$ printf '[http]\n\tsslVerify = true\n' > a; git config --file a http..sslVerify; echo $?
1
$ printf '[http ""]\n\tsslVerify = true\n' > b; git config --file b http..sslVerify
true
```

This is the exact "silently written under a different name" failure class the round-2
CR-01 fix was written to eliminate; it just reaches it through the *drop-the-quotes*
branch instead of the escaping branch. `gitKeysEqual` compounds it: it compares
`subA == subB`, so `"http..sslVerify"` and `"http.sslVerify"` compare EQUAL and the
upsert overwrites the unrelated existing key.

End-to-end against the real writer, with a legitimate `http.sslVerify = true` already
present:

```
PLAN err=<nil>                            <- the plan ACCEPTS it and opens the ceremony
  diff="+ \tsslVerify = false\n... - \tsslVerify = true\n..."
                                          <- the preview shows the user's UNRELATED key
                                             being overwritten, never says the typed key
                                             was renamed
WRITE err=gitid: writing custom git key: post-write verification:
        http..sslVerify reads back as "", not "false"
  restored=[~/.gitconfig.d/00-baseline: restored ~/.gitconfig: restored]
```

The write *is* rolled back — the WR-08 read-back is the only thing that saves the
user's data — but the ceremony is a guaranteed dead end that takes a real backup and a
real (then reverted) mutation of an unrelated key on every attempt.

**Fix:** reject an empty subsection in `SplitGitKey` before anything is composed:

```go
if firstDot := strings.IndexByte(sectionPath, '.'); firstDot == -1 {
    section = sectionPath
} else {
    section = sectionPath[:firstDot]
    subsection = sectionPath[firstDot+1:]
    if subsection == "" {
        return "", "", "", fmt.Errorf(
            "gitconfig: %q has an empty subsection — the renderer would file it as %q, "+
                "a different git key", key, section+"."+variable)
    }
}
```

### WR-02: The two new properties browsers render machine-config values unsanitized — ANSI escapes reach the terminal and an embedded newline desynchronizes row accounting

**Files:** `internal/tuikit/globalgit.go` (`setKeyRow`), `internal/tuikit/globalssh.go`
(`propertyRow`, `sanitizeProofOutput:2019`), `cmd/gitid/wiring.go` (`AllGitSetKeys`,
`AllSSHDirectives`)

**Issue:** `AllGitSetKeys` routes `k.Value` through `b.displayMessage` (which only
shortens `$HOME`) and `setKeyRow` interpolates it directly; `truncLine` is
`ansi.Truncate`, which is deliberately ANSI-*preserving*. `SetKey.Value` comes from
`git config --show-origin --show-scope --list -z` over every scope on the machine
(including system scope) and git values legitimately carry both control characters and
real newlines:

```
$ printf '[alias]\n\tmulti = "line1\\nline2"\n' > nl.cfg
$ git config --file nl.cfg --list -z | xxd
00000000: 616c 6961 732e 6d75 6c74 690a 6c69 6e65  alias.multi.line
00000010: 310a 6c69 6e65 3200                      1.line2.
```

Rendered result (real `setKeyRow`/`propertyRow` output):

```
value="\x1b[31mRED\x1b[0m" -> row="   \x1b[1malias.x\x1b[m ... \x1b[31mRED\x1b[0m"  containsESC=true
value="line1\nline2"       -> row="   \x1b[1malias.x\x1b[m ... line1\nline2"        containsNL=true
ssh  value="\x1b[31mRED..." -> row="...\x1b[31mRED\x1b[0m"                          containsESC=true
body row count = 3 (expected 2)
```

The newline case is the more damaging one: `ggitSetKeysVisibleRowCount` /
`ggitSetKeysComputeScrollWindow` / `ggitSetKeysRowForScreenRow` all budget and hit-test
**one screen row per list item**, so a multi-line value shifts every subsequent row's
click target by one and pushes the tail of the list past `RenderFrame`'s `bodyHeight`
truncation. The same applies to `gssPropertiesRowForScreenRow`.

This phase already built the right tool for this in round 2 (`sanitizeProofOutput`,
WR-14) but applied it only to `proof.Output` and `pendingDirectiveName`.

**Fix:** route every externally-sourced value through the existing sanitizer at the
wiring boundary, where the round-2 fix already put `displayMessage`:

```go
// cmd/gitid/wiring.go — AllGitSetKeys / AllSSHDirectives
Value: b.displayMessage(tuikit.SanitizeDisplayValue(k.Value)),
```
exporting a `SanitizeDisplayValue` that strips C0 controls **and** `\n` (the browsers
are strictly one line per row, unlike the proof pane which needs `\n`), or collapses
`\n` to a visible `␊`/`⏎` marker. Apply the same to
`GitCustomKeyPlanView.Diff`/receipt and `SSHCustomDirectivePlanView.Diff` for
consistency.

### WR-03: `ValidateDirectiveValue` allows a whitespace-delimited `#`, which OpenSSH silently truncates — and the resolved-vs-resolved advisory is structurally blind to it

**File:** `internal/globalssh/validate.go:115` (`ValidateDirectiveValue`);
`cmd/gitid/lifecycle.go:1787` (`customDirectiveVerifyAdvisories`)

**Issue:** `ValidateDirectiveValue` rejects only `\n`, `\r`, `\x00`, and empty. A value
containing ` #` is accepted, the staged probe *passes*, the value is written verbatim,
and OpenSSH silently discards everything from the `#` onward:

```
$ printf 'Host *\n  ServerAliveInterval 60 #note\n' > p; chmod 600 p
$ ssh -F p -G gitid-probe.invalid | grep serveraliveinterval
serveraliveinterval 60           <- "#note" silently gone, exit 0
$ printf 'Host *\n  SetEnv FOO=bar #baz\n' > q; chmod 600 q
$ ssh -F q -G gitid-probe.invalid | grep setenv
setenv FOO=bar                   <- silently truncated, exit 0
```

Round-2's WR-01 fix made the post-write advisory compare
resolved-vs-resolved — which means **both sides get truncated identically**, so
`ResolveDirectiveValue(deps, name, "60 #note")` returns `"60"`, `d.Value` is `"60"`,
they match, and no advisory fires. The ceremony's confirm preview and receipt both
display the full `60 #note`. The write is honestly proven but the *report* is not.

Note the asymmetry with the Git sibling, which explicitly rejects `#` and `;` for
exactly this reason (`forbiddenCustomValueCharRE`, customkeys.go:79).

**Fix:** reject a comment-introducing `#` in `ValidateDirectiveValue`, mirroring the
Git side's own reasoning:

```go
for i, r := range value {
    if r == '#' && (i == 0 || value[i-1] == ' ' || value[i-1] == '\t') {
        return fmt.Errorf("globalssh: directive value %q must not contain a whitespace-"+
            "delimited '#' — OpenSSH treats it as a comment and silently discards the rest "+
            "of the value, so the receipt would report a value that is not in effect", value)
    }
}
```
(An inline `#` with no preceding whitespace, e.g. `FOO=bar#baz`, is safe — verified
above — so the guard should be narrower than a blanket `#` rejection.)

### WR-04: The Git post-write verify seam is not isolated from the ambient git environment, so a broken repo config in the process CWD rolls back a correct write and blames gitid's own file

**File:** `internal/gitconfig/reader.go:150` (`RunGitConfigGet`), `:166`
(`ValidateGitConfigSyntax`); consumed at `cmd/gitid/lifecycle.go:1534-1542`

**Issue:** Both helpers shell `git config --file <path> …` with the inherited working
directory and environment. `git config` parses the ambient repository/global/system
config at startup even for a `--file` read, so a malformed `.git/config` anywhere in
the CWD's repository makes both calls fail:

```
$ git init -q . && printf '[core]\n\tthis is not valid\n' >> .git/config
$ printf '[core]\n\tpager = less\n' > /tmp/good.cfg
$ git config --file /tmp/good.cfg --list; echo "rc=$?"
fatal: bad config line 9 in file .git/config
rc=128
```

`runCustomGitKeyWrite`'s verify stage then reports
`post-write verification: the written file does not parse as valid git-config syntax`
and rolls back a write that was perfectly correct — naming gitid's own managed file
for a fault that lives in an unrelated repository. Running `gitid` from inside any repo
with a config problem makes the whole custom-key feature unusable, with a misleading
diagnostic.

`internal/globalgit` already treats this exact hazard as load-bearing
(`Deps.NonRepoCwd` "MUST NOT be inside any git repository", properties.go:32); the
gitconfig read/verify seam does not inherit that discipline.

I verified the *good* direction as well: `--file` reads do **not** absorb
`GIT_CONFIG_COUNT`/`-c` overrides and do **not** follow `include.path` without
`--includes`, so there is no risk of the verify falsely *passing*. It only fails
falsely.

**Fix:** pin the invocation to a non-repository directory and neutralise ambient
config, mirroring `globalgit.BuildProbeDeps`:

```go
cmd := exec.Command("git", "-c", "core.hooksPath=", "config", "--file", file, key)
cmd.Dir = nonRepoDir          // e.g. the caller's fragmentDir, as globalgit already does
cmd.Env = append(os.Environ(), "GIT_CONFIG_NOSYSTEM=1", "GIT_CONFIG_GLOBAL=/dev/null")
```
and thread a `nonRepoDir` (or a `Deps`-style seam) through from `realBackend`, which
already has `b.fragmentDir` for exactly this purpose.

### WR-05: The Phase 9.5 promoted frame baselines have **no** provenance gate — `TestUploadFrameProvenanceMatches` is hardcoded to the Phase 9 directory

**Files:** `cmd/gitid-frame-promote/main.go:20-27` (doc claim),
`cmd/gitid/gate_visual_regression_test.go:2995` (`TestUploadFrameProvenanceMatches`)

**Issue:** `main.go`'s package doc states the provenance table
"verifies every row against the committed frame's real hash in both directions" and
names `TestUploadFrameProvenanceMatches` as the enforcer. That test hardcodes

```go
dir := filepath.Join("..", "..", ".planning", "phases", "09-upload-credentials-assist", "ui-frames")
```

and there is no sibling for `09.5-full-ssh-git-properties-browser/ui-frames`
(`grep -rn "09.5-full-ssh-git-properties-browser" cmd/ internal/ e2e/` returns nothing).
So the 17 frames this phase promoted, plus their README table, are entirely ungated: a
hand-edited frame, a stale hash row, or a frame promoted from a different run is
undetectable. The phase parameterised the promoter (`-phase`) but not the gate that
makes promotion trustworthy — which is the whole point of the mechanism.

Related: `promoteFrames` never deletes stale `.txt` files from the destination, so a
renamed or removed registry entry leaves an orphan tracked frame behind, contradicting
`writeProvenance`'s own claim that re-running "overwrites this table and every frame in
this directory".

**Fix:** parameterise the test the same way the promoter was, and add the 09.5
directory:

### WR-08: For a multi-valued OpenSSH directive, the staged proof shows a "real result" the write will not produce

**Files:** `internal/globalssh/validate.go:310` (`stageDirectiveConfig`),
`internal/sshconfig/globals.go:200` (`globalMap.set`)

**Issue:** `stageDirectiveConfig` prepends the candidate to the existing block body, so
for a directive OpenSSH *accumulates* (IdentityFile, CertificateFile, LocalForward,
RemoteForward, DynamicForward, PermitRemoteOpen, …) the staged probe resolves the union
of the candidate and the existing value. The actual write goes through
`EnsureGlobals`'s explicit overlay → `merged.set(name, value)`, which **replaces** the
existing value in place:

```
staged  : Host *\n  IdentityFile /tmp/b\nHost *\n  IdentityFile /tmp/a
  ssh -G: identityfile ['/tmp/b', '/tmp/a']
written : Host *\n  IdentityFile /tmp/b
  ssh -G: identityfile ['/tmp/b']
```

Stage 2 renders that staged output verbatim as "the exact command, then its real
result" (TEST-01's contract). For an accumulating directive it over-reports: the user is
shown a resolution that keeps their previous value, and the write silently drops it.
The ceremony's own diff *does* show the replacement, so this is a
"two screens disagree" honesty gap rather than silent data loss — but it is the same
class round-2's WR-02 fixed for the single-valued case, left unfixed for the
multi-valued one.

**Fix:** stage the candidate the way the write will compose it. The cleanest form is to
stage `sshconfig.EnsureGlobals(existing, map[string]string{name: value}, goos)`'s
rendered block body rather than hand-assembling `candidate + existing body` — that
makes the staged text byte-identical to what will be written and removes the
divergence for every directive class at once. Failing that, detect an accumulating name
and label the extra resolved entries in the stage-2 render.

### WR-09: `ProveCustomDirective` stages the candidate *before* gitid's own `IgnoreUnknown` guard line, producing a false rejection for the one directive that guard exists to protect

**File:** `internal/globalssh/validate.go:310` (`stageDirectiveConfig`)

**Issue:** gitid's rendered block always begins with `IgnoreUnknown UseKeychain`
(`renderGlobalBody`, globals.go:288). `stageDirectiveConfig` puts the candidate line at
file scope *ahead* of the whole body, so in the staged config the candidate precedes
that guard. `ssh_config(5)` is explicit: *"It is recommended that IgnoreUnknown be
listed early in the configuration file as it will not be applied to unknown options
that appear before it."*

On Linux, a candidate `UseKeychain yes` is therefore reported `UnknownName` and refused,
even though the file the write would produce places it *after* the guard and OpenSSH
would silently accept it. Same class, narrower: `-F <staged>` also makes OpenSSH ignore
`/etc/ssh/ssh_config`, so a system-config interaction is invisible at proof time (that
half is covered by the post-write advisory).

The direction is fail-closed (refusing a write that would have been fine), so this is a
usability defect rather than a safety one — but the affected directive is precisely the
one the guard line was added for.

**Fix:** emit the guard line ahead of the candidate when the existing body carries one,
or (better, and it also fixes WR-08) stage the composed `EnsureGlobals` output instead
of hand-assembling the staged text.

## Info

### IN-01: `subsectionEscaper` is unreachable
**File:** `internal/gitconfig/customkeys.go:59`
`validateSubsection` rejects both `"` and `\` before `RenderCustomKeysBlock` runs, so
the replacer can never make a substitution. It is correct as a defensive backstop, and
its doc comment says as much — but a reader can reasonably mistake it for the active
guard. Consider a one-line note that it is provably a no-op given the validator, or a
test that asserts the invariant.

### IN-02: `sanitizeProofOutput` lets C1 control characters through
**File:** `internal/tuikit/globalssh.go:2019`
The filter is `r == '\n' || (r >= 0x20 && r != 0x7f)`, which admits U+0080–U+009F (the
C1 controls, including CSI at U+009B). In UTF-8 these are two-byte sequences that most
modern terminals do not interpret as escapes, so the practical risk is low — but the
guard's stated purpose is "strips every C0 control byte (and DEL)", and adding
`&& !(r >= 0x80 && r <= 0x9f)` costs nothing.

### IN-03: The `←→ switch view` footer hint is now suppressed on Global Git even in the fail-open probe-error state
**File:** `internal/tuikit/app.go:681`
The new condition excludes `TabGlobalGit` unconditionally, but
`globalGitModel.handleKey` deliberately returns `handled: false` when
`optionsErr`/`setKeysErr` is set (the documented fail-open contract), so ←/→ *do* reach
the top-level tab switcher in exactly that state while the footer no longer says so.
Gate the suppression on the screen actually consuming the arrows.

### IN-04: `ParseCustomKeysBlock` silently drops unrecognized lines inside its own block
**File:** `internal/gitconfig/customkeys.go:183`
Only `[section]`/`[section "sub"]` headers and tab-indented `k = v` lines survive; any
other line inside the block (a hand-added comment, a merge-conflict marker, a blank-ish
artifact) vanishes on the next write with no trace. WR-06's `skipped` advisory covers
only entries that *parsed* and then failed re-render, not lines the parser never
produced. Consider carrying unrecognized lines as opaque raw entries, the way
`sshconfig.globalMap.addRaw` already does for the SSH block.

### IN-05: `gitid-frame-promote` resolves the repo root from the ambient CWD
**File:** `cmd/gitid-frame-promote/main.go:302`
`repoRoot()` runs `git rev-parse --show-toplevel` with no pinned `Dir`, so invoking the
tool from a nested or unrelated checkout writes into a different repository's
`.planning/phases/…`. `gitHead` correctly pins `cmd.Dir = root`; `repoRoot` should
anchor on a known marker (or refuse when the resolved root has no `.planning/phases`).
