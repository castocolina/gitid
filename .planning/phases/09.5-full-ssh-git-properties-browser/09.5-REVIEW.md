# Phase 9.5: Code Review Report

**Reviewed:** 2026-09-04
**Depth:** deep
**Files Reviewed:** 42
**Status:** issues_found

## Summary

The ceremony scaffolding of both new write paths is sound: `runCustomGitKeyWrite` and
`runCustomSSHDirectiveWrite` take `txMu`, drive `lifecycleStages` rows that carry
`confirm → backup → write` in order, gate on `confirmGate` (whose zero value fails
closed), open a `mutationJournal` and `watchFile` every path before touching any of
them, and roll back on any post-first-write error. I found **no confirmation bypass and
no missing-backup path** in either verb. `ProveCustomDirective` does what it claims
about isolation: `os.MkdirTemp` + 0700 + a `defer os.RemoveAll`, the staged path is the
only path handed to `ssh`, the argv is an arg slice through `exec.CommandContext` (no
shell), and a no-output transport failure returns a non-nil error with `OK:false`. The
`custom-git-keys` reserved-name registration is correct and is asserted at the doctor
layer, which is the assertion that actually matters.

What does not hold up is **input validation on both new free-form entry paths**. Neither
path validates the thing the user types before it reaches the user's real config files,
and the two engines are asymmetric in a way that produces two provable, reachable
config-corruption defects:

- The Git side reuses `validateValue`, which only blocks newlines and `[remote`. It does
  **not** block the characters that are structural in git's own config-file grammar. A
  value containing `"` or `\` — e.g. a Windows path — writes a file that git itself
  refuses to parse, and that file is `include`d from `~/.gitconfig`, so **every** git
  command in the user's shell starts failing. There is no verify stage on this verb to
  catch it (the `verify` stage is an explicit no-op) and therefore no rollback.
- The SSH side validates **nothing at all**. It relies entirely on `ssh -G` exiting 0
  against a staged config. I verified against the real OpenSSH on this machine that an
  empty directive name, a whitespace-only name, and the structural keywords `Host`,
  `Match` and `Include` all exit 0 — so all of them pass the "un-skippable proof gate"
  and get written into gitid's own `Host *` managed block. `Host <anything>` opens a
  nested stanza inside the managed block, and the very next `EnsureGlobals` write
  silently drops it (`parseGlobalBody` `EqualFold`-skips `Host`/`IgnoreUnknown`) — a
  confirmed user write, lost without notice, plus a poisoned staging base for the next
  proof (`hasHostStarLine` will then stage the next candidate under the injected
  stanza rather than under `Host *`).

Neither of these is the D-09 exception being abused — both stay inside gitid-managed
blocks — but both violate the recipe-coherence objective the managed blocks exist to
protect, and the Git one is a hard break of the user's whole git installation.

Secondary theme: the phase's own guard patterns were applied unevenly across its five
plans. Plans 09.5-01/02/03 each got an anti-embed reflection test; 09.5-04 — the highest
blast-radius seam — did not, even though `backend.go` documents that it did. Two
user-facing sentences on the new stage-2 render are hardcoded literals that bypass the
copy-freeze table the same plan built. And the new visual-regression region extractors
fail *open* (missing anchor → `""` on both surfaces → comparison passes), so a rename
can silently retire a standing guard.

## Critical Issues

### CR-01: A custom Git key value containing `"` or `\` writes an unparseable `~/.gitconfig.d/00-baseline`, breaking every git command — no guard, no verify, no rollback

**File:** `internal/gitconfig/customkeys.go:165,173,200` · `cmd/gitid/lifecycle.go:1487,1501-1505`

**Issue:** `EnsureCustomGitKey` and `RenderCustomKeysBlock` guard the value with only
`validateValue` (`internal/gitconfig/fragment.go:132`), which rejects newlines,
carriage returns and `[remote` — and nothing else. `RenderCustomKeysBlock` then emits
`fmt.Fprintf(&b, "\t%s = %s\n", variable, e.Value)`: the value is written **unquoted and
unescaped** into a git config file, where `"` opens a quoted region and `\` starts an
escape sequence. Proven against the real git binary:

```
$ printf '[demo]\n\tkey = foo"bar\n' > gc1 && git config --file gc1 --list
fatal: bad config line 2 in file .../gc1        (exit 128)

$ printf '[demo]\n\tkey = C:\\path\\to\n' > gc2 && git config --file gc2 --list
fatal: bad config line 2 in file .../gc2        (exit 128)
```

Both values are trivially reachable through the TUI form (bubbles' textinput only
collapses tabs/newlines; `"` and `\` are ordinary printable runes). The target file is
`~/.gitconfig.d/00-baseline`, which `runCustomGitKeyWrite` itself floors an `[include]`
pointer to in `~/.gitconfig` (Write 1, line 1466-1473). Once the baseline file is
unparseable, **every** `git` invocation in the user's environment fails with
`fatal: bad config line`, including gitid's own probes.

Nothing catches it: `CustomGitKeyPlan` (wiring.go) only calls `EnsureCustomGitKey`, and
`runCustomGitKeyWrite`'s `verify` stage is an explicit no-op with the comment "nothing
to re-probe beyond what the write itself already confirmed" (lifecycle.go:1501-1505) —
but the write confirmed nothing about git's ability to parse the result. The `journal`
is not consulted after Write 2 succeeds, so there is no rollback either. Contrast the
SSH sibling, which round-trip-parses via `sshconfig.EnsureGlobals` before returning.

`internal/gitconfig/customkeys_test.go:130` (`TestEnsureCustomGitKeyRejectsInjectionValues`)
covers only newline / CR / `[remote`. `TestGitReadsBackWhatRenderCustomKeysBlockWrote`
is exactly the right shape but only exercises `less -FRX` and `false`.

**Fix:** Add a git-config-file-syntax guard for this write path (a *value-render* guard,
distinct from `validateValue`'s injection guard) and give the verb a real verify stage
that rolls back:

```go
// internal/gitconfig/customkeys.go
// forbiddenCustomValueCharRE matches characters that are structural in git's
// config-file grammar and would make the rendered line unparseable (a double
// quote opens a quoted region; a backslash starts an escape sequence) or
// silently truncate the value (# and ; start a comment).
var forbiddenCustomValueCharRE = regexp.MustCompile("[\"\\\\#;]")

func validateCustomValue(key, value string) error {
    if err := validateValue(key, value); err != nil {
        return err
    }
    if forbiddenCustomValueCharRE.MatchString(value) {
        return fmt.Errorf("gitconfig: %s value %q must not contain a double quote, backslash, '#' or ';' — git would fail to parse the resulting file", key, value)
    }
    if value != strings.TrimSpace(value) {
        return fmt.Errorf("gitconfig: %s value %q must not have leading or trailing whitespace — git strips it on read", key, value)
    }
    return nil
}
```

Call `validateCustomValue` from both `EnsureCustomGitKey` (replacing the `validateValue`
call at line 200) and `RenderCustomKeysBlock` (line 165). Then make
`runCustomGitKeyWrite`'s `verify` stage load-bearing — run
`git config --file <target> --list` (the seam already exists as
`gitconfig.RunGitConfigGet`'s sibling) and, on a non-zero exit, `journal.restore()` and
return the error rather than reporting success. Extend
`TestGitReadsBackWhatRenderCustomKeysBlockWrote` with `"`, `\`, `#`, and a
leading/trailing-space value.

### CR-02: The custom SSH directive NAME is completely unvalidated — empty names and the structural keywords `Host`/`Match`/`Include` pass the `ssh -G` proof gate and are written into gitid's own `Host *` managed block

**File:** `internal/globalssh/validate.go:85,153-165` · `internal/tuikit/globalssh.go:1010-1027` · `cmd/gitid/lifecycle.go:1544-1576,1655`

**Issue:** The stage-1 submit handler (`globalssh.go:1016-1027`) reads
`m.customDirectiveNameInput.Value()` and `m.customDirectiveValueInput.Value()` and
dispatches them straight to `ValidateCustomSSHDirective` with **no** validation — no
empty check, no whitespace check, no token check. `ProveCustomDirective` then
interpolates them raw (`stageDirectiveConfig`, `validate.go:163`:
`fmt.Fprintf(&b, "  %s %s\n", name, value)`), and the ONLY acceptance criterion is
`ssh -G` exiting 0. `sshconfig.EnsureGlobals` likewise applies the pair unconditionally
(`merged.set(k, v)` for every entry of `explicit`) and `renderGlobalBody` emits
`hostIndent + key + " " + value` verbatim. Nothing in either engine or in
`runCustomSSHDirectiveWrite` looks at the name.

Verified against the real OpenSSH on this machine — all three exit 0, i.e. all three
produce `proof.OK == true` and open the write ceremony:

```
$ printf 'Host *\n  Host evil.example\n' > s2 && ssh -G -F s2 gitid-probe.invalid >/dev/null; echo $?
0
$ printf 'Host *\n  Include ~/nonexistent\n' > s3 && ssh -G -F s3 gitid-probe.invalid >/dev/null; echo $?
0
$ printf 'Host *\n   \n' > s4 && ssh -G -F s4 gitid-probe.invalid >/dev/null; echo $?   # empty name+value
0
```

Consequences, all inside the user's real `~/.ssh/config` (or the include'd
`gitid.config`):

1. **Empty submission writes garbage and takes a backup.** Pressing Enter on an empty
   form yields `explicit[""] = ""`, rendered as a whitespace-only line inside the
   managed block, followed by a receipt clairing `" written."` and the confusing
   post-write advisory "was written but could not be found in the re-read directive set".
2. **`Host <pattern>` opens a nested stanza inside gitid's own `Host *` block**,
   breaking the block's single-wildcard-stanza invariant that first-match-wins
   correctness depends on (`globals.go`'s own "PLACEMENT DIVERGENCE (D-09)" rationale).
3. **The user's confirmed write is then silently destroyed.** `parseGlobalBody`
   (`globals.go:247`) `EqualFold`-skips `Host` and `IgnoreUnknown`, so the very next
   `EnsureGlobals` write (any curated apply, any create, any rotate) drops the injected
   line with no notice — a confirmed, backed-up user write vanishing.
4. **The proof gate poisons itself.** `hasHostStarLine` (`validate.go:170`) only checks
   whether *some* `Host *` line exists; once a `Host evil` line lives in the block body,
   the next candidate is staged *under that stanza*, so the proof no longer says
   anything about the `Host *` context the write actually targets.
5. There is no newline/control-character guard at the engine level either. Today the
   bubbles textinput happens to collapse newlines to spaces on paste
   (`runeutil.ReplaceNewlines(" ")`) — that is an incidental third-party behavior, is
   asserted by no test in this repo, and does not protect
   `ProveCustomDirective`/`runCustomSSHDirectiveWrite`, which are exported/production
   entry points documented as the target of a future CLI verb.

This is a striking asymmetry: the Git sibling explicitly validates its key syntax
(`SplitGitKey`, `gitConfigNameRE`, `forbiddenSubsectionCharRE`), and this repo already
owns a token validator for exactly this file format —
`sshconfig.validateToken`/`ValidateHostBlock` (`internal/sshconfig/validation.go:26`,
the CR-11 hardening). Neither is reused here. No test in
`internal/globalssh/validate_test.go` or `internal/tuikit/globalssh_test.go` submits an
empty name, a whitespace name, or a structural keyword.

**Fix:** Add a directive-name validator in `internal/globalssh` and call it from
`ProveCustomDirective` (fail closed *before* staging) and from
`runCustomSSHDirectiveWrite`'s plan stage (defense in depth, mirroring
`runCustomGitKeyWrite`'s `SplitGitKey` backstop), plus an inline stage-1 guard in the
TUI so the user gets the error on the form:

```go
// internal/globalssh/validate.go

// structuralDirectives are keywords that change the SHAPE of the config rather
// than set a value. ssh -G accepts them, so the staged proof cannot reject them —
// but writing one into gitid's own `Host *` managed block breaks the block's
// single-wildcard-stanza invariant AND is silently dropped by parseGlobalBody on
// the next EnsureGlobals write.
var structuralDirectives = map[string]bool{
    "host": true, "match": true, "include": true, "ignoreunknown": true,
}

// ValidateDirectiveName rejects any candidate name that is not a single, safe,
// unquoted OpenSSH directive token. Mirrors sshconfig.validateToken's contract.
func ValidateDirectiveName(name string) error {
    if strings.TrimSpace(name) == "" {
        return errors.New("globalssh: directive name cannot be empty")
    }
    if len(strings.Fields(name)) != 1 {
        return fmt.Errorf("globalssh: directive name %q must be a single token with no whitespace", name)
    }
    for _, r := range name {
        if r <= ' ' || r == 0x7f || r == '#' || r == '=' || r == '"' || r == '\'' || r == '\\' {
            return fmt.Errorf("globalssh: directive name %q contains a character that is unsafe in an unquoted SSH config token", name)
        }
    }
    if structuralDirectives[strings.ToLower(name)] {
        return fmt.Errorf("globalssh: %q is a structural directive, not a settable option — gitid's managed Host * block cannot contain it", name)
    }
    return nil
}

// ValidateDirectiveValue rejects a value that would not survive rendering into a
// single unquoted directive line.
func ValidateDirectiveValue(value string) error {
    if strings.ContainsAny(value, "\n\r\x00") {
        return fmt.Errorf("globalssh: directive value %q must not contain a line break or NUL", value)
    }
    if strings.TrimSpace(value) == "" {
        return errors.New("globalssh: directive value cannot be empty")
    }
    return nil
}
```

Then at the top of `ProveCustomDirective`:

```go
if err := ValidateDirectiveName(name); err != nil {
    return DirectiveProof{}, err
}
if err := ValidateDirectiveValue(value); err != nil {
    return DirectiveProof{}, err
}
```

and the same two calls in `runCustomSSHDirectiveWrite`'s plan stage (before
`sshconfig.EnsureGlobals`). Add table tests for the empty name, whitespace-only name,
multi-token name, and each of `Host`/`Match`/`Include`/`IgnoreUnknown`, plus a PTY test
that submits an empty form and asserts the target file is byte-identical.

## Warnings

### WR-01: The "un-skippable proof gate" lives only in the TUI state machine, never in the writer it protects

**File:** `cmd/gitid/lifecycle.go:1544-1576` · `cmd/gitid/wiring.go:2613-2629`
**Issue:** `runCustomSSHDirectiveWrite` is declared "the ONE production writer for a
custom SSH directive", yet it never calls `globalssh.ProveCustomDirective`. Its doc
comment says the name "has already been proven … by `globalssh.ProveCustomDirective` at
the TUI's stage 2, before this function is ever called". `CommitCustomSSHDirective`
hands it `confirmationAlreadyObtained`, so the writer accepts any name/value pair with
no authorization prompt and no proof. Today only the TUI reaches it, but the file's own
precedent (`runGlobalSSHApply`: "plan 06-06 calls this function from the CLI") means the
gate will be bypassed the moment a CLI verb is added. Compare `runCustomGitKeyWrite`,
which *does* re-run `SplitGitKey` at its plan stage as a "defense-in-depth backstop for
any caller that reaches this function directly".
**Fix:** Re-run `ProveCustomDirective` inside `runCustomSSHDirectiveWrite`'s plan stage
(against the same `globalsBodyText(existing)` the TUI used) and return an error unless
`proof.OK`. The staged probe is bounded at 3s and the write is already an out-of-loop
`tea.Cmd`, so the cost is acceptable; correctness of the phase's central security claim
is not something to leave to a UI mode variable.

### WR-02: The proof is staged against a different config than the one that gets written when a legacy `_global` block is present

**File:** `cmd/gitid/wiring.go:3346-3353` (`globalsBodyText`) vs `internal/sshconfig/globals.go:160-178` (`existingGlobalBody`)
**Issue:** `ValidateCustomSSHDirective` builds the staged body with `globalsBodyText`,
which scans only for `sshconfig.GlobalBlockName` (`global-ssh`) and returns `""`
otherwise. The write path (`EnsureGlobals` → `existingGlobalBody`) falls back to
`LegacyGlobalBlockName` (`_global`) when the current name is absent. On a machine still
carrying the legacy block — a case `globals.go` explicitly documents as live — the proof
runs against an *empty* body while the write merges the legacy body's directives. The
proof therefore proves nothing about the configuration that is actually produced, and
D-I's `PreexistingError` classification can never fire for a problem living in the
legacy block.
**Fix:** Give `globalsBodyText` the same legacy fallback, or better, export
`sshconfig.ExistingGlobalBody` and call it from both places so there is one resolver:

```go
func globalsBodyText(content []byte) string {
    return sshconfig.ExistingGlobalBody(content) // one owner, legacy fallback included
}
```

### WR-03: A directive name containing whitespace is misclassified as the user's *pre-existing* config problem

**File:** `internal/globalssh/validate.go:128-137`
**Issue:** `offendingDirectiveName` returns the single token OpenSSH names in its
diagnostic; `strings.EqualFold(offending, name)` then compares it to the *whole*
submitted name. Submit `name = "Foo Bar"`: the staged line is `  Foo Bar <value>`, ssh
reports `Bad configuration option: foo`, `EqualFold("foo", "Foo Bar")` is false, and the
model sets `PreexistingError` — rendering
`'foo' already has a problem in your current configuration — unrelated to what you just
entered`, which is a false accusation about the user's own config. D-I's whole purpose
is to never mis-assign blame.
**Fix:** Compare against the first field of the candidate name
(`strings.Fields(name)[0]`), or — better — reject multi-token names outright per CR-02's
`ValidateDirectiveName`, which makes this branch unreachable.

### WR-04: The custom-Git-key ceremony promises a `~/.gitconfig` backup that the SC-1 skip then does not take

**File:** `cmd/gitid/wiring.go` (`CustomGitKeyPlan`) · `cmd/gitid/lifecycle.go:1467-1473`
**Issue:** `CustomGitKeyPlan` adds a backup entry for every target that already exists,
with the comment "promising a backup that will not be taken would be a lie in the
ceremony". But `runCustomGitKeyWrite` writes `~/.gitconfig` only when
`!bytes.Equal(composedGC, existingGC)` (SC-1). On the *second* and every later custom
key — the common case, once the `[include]` floor is in place — the composed bytes are
identical, the write is skipped, and no `~/.gitconfig` backup is taken. The preview
promised one. The receipt's `Backups` list will also be short by one entry relative to
what the confirm screen showed.
**Fix:** Compute the plan's promised backups from the same predicate the writer uses —
compose `ComposeBaselineInclude`/`EnsureCustomGitKey` in the plan and only list a backup
for a target whose composed bytes actually differ from disk:

```go
if fileExists(p) && !bytes.Equal(composedFor(p), existingFor(p)) {
    view.Backups = append(view.Backups, b.displayPath(p)+backupSuffixPreview)
}
```

### WR-05: `EnsureCustomGitKey` folds case over the whole key including the subsection, silently merging two distinct git keys

**File:** `internal/gitconfig/customkeys.go:186-188,207`
**Issue:** The upsert loop uses `strings.EqualFold(e.Key, key)` on the full dotted key,
justified by "git lower-cases keys in `--list` output". That premise is wrong for the
middle segment: git config **sections and variables are case-insensitive, subsections
are case-SENSITIVE** (`git-config(1)`, CONFIGURATION FILE). So
`http.https://Example.com.sslVerify` and `http.https://example.com.sslVerify` are two
genuinely different git keys, but `EnsureCustomGitKey` treats the second as an update to
the first and silently discards one of the user's values.
**Fix:** Compare section and variable case-insensitively and the subsection
case-sensitively:

```go
secA, subA, varA, _ := SplitGitKey(e.Key)
secB, subB, varB, _ := SplitGitKey(key)
if strings.EqualFold(secA, secB) && subA == subB && strings.EqualFold(varA, varB) {
    entries[i].Value = value
    upserted = true
    break
}
```

Correct the doc comment at lines 186-188 at the same time.

### WR-06: A custom Git value containing `#` or `;` is silently truncated by git while the receipt claims the whole value was written

**File:** `internal/gitconfig/customkeys.go:173`
**Issue:** Values are rendered unquoted, so git treats `#` and `;` as comment starts.
Proven:

```
$ printf '[demo]\n\tkey = foo #bar\n' > gc3 && git config --file gc3 --list
demo.key=foo
```

The ceremony receipt (`PropsGitCustomReceiptFmt`) reports `key = foo #bar written.` —
which is not what the machine will resolve. Leading/trailing whitespace is likewise
stripped by git but reported as written. This is the same class of dishonesty the whole
"shown == run" discipline exists to prevent.
**Fix:** Covered by CR-01's `validateCustomValue` (reject `#`/`;` and
leading/trailing whitespace). If a later requirement needs those characters, render the
value git-quoted and escaped, and add a `git config --get` read-back assertion.

### WR-07: A post-write verification failure on the SSH path never rolls back — a write that breaks `ssh -G` leaves the user's SSH config broken with only an advisory

**File:** `cmd/gitid/lifecycle.go:1673-1699`
**Issue:** After the write, `globalssh.AllDirectives` is run; if it errors the code
appends `"advisory: post-write verification could not run (…) — the directive was
written but not re-verified"` and returns success. But `AllDirectives` failing is
exactly the symptom of the write having made the live config unparseable — at which
point *every* subsequent `ssh`/`git-over-ssh` invocation on the machine fails too. The
journal is still in scope and the backups are still recorded; nothing uses them.
CLAUDE.md's stated ceremony is "test → confirm + backup → **re-test with the resolved
configuration**", and the D-09 reference ceremony restores automatically on any
mismatch. This verb re-tests and then ignores the answer.
**Fix:** Treat a `derr` from `AllDirectives` as a failed transaction on this verb (the
directive is unvetted against the *real* file, unlike the curated apply):

```go
directives, derr := globalssh.AllDirectives(globalssh.BuildProbeDeps(b.sshConfigPath))
if derr != nil {
    return fail(fmt.Errorf("post-write re-verification failed — the written directive may have made the configuration unparseable: %w", derr))
}
```

### WR-08: The post-write "could not be found" advisory fires falsely, and the value comparison is too lax

**File:** `cmd/gitid/lifecycle.go:1680-1698`
**Issue:** Two problems in the same block. (a) `ssh -G` does not echo every directive it
accepts — structural ones (`Host`, `Match`, `Include`) never appear in the resolved set,
so a write of any of them produces
`"advisory: <name> was written but could not be found in the re-read directive set"`
even though the write landed exactly as intended. (b) The value comparison uses
`strings.EqualFold(d.Value, value)`, which is wrong for case-sensitive values — a path
(`UserKnownHostsFile ~/A` vs a resolved `~/a`), a cipher list, or a `ProxyCommand` would
compare equal when they are not.
**Fix:** Use an exact comparison for the value (`d.Value != strings.TrimSpace(value)`),
and suppress the not-found advisory for names that `ssh -G` is known not to echo — which
CR-02's `structuralDirectives` set already enumerates and, once that fix lands, rejects
outright.

### WR-09: Two user-facing stage-2 sentences are hardcoded literals that bypass the copy-freeze gate this same phase built

**File:** `internal/tuikit/globalssh.go:2024,2035`
**Issue:** `renderCustomDirectiveValidate` renders
`styleFaint.Render("Nothing was written.")` and
`styleHealthy.Render("✓ '"+m.pendingDirectiveName+"' is a recognized SSH directive.")`
as inline literals. Every other sentence on this render comes from a frozen `design.go`

**Fix:** Promote both to `design.go` constants

two rows to `TestFrozenPropertiesCopy`, and bump `wantCount` to 26.

### WR-10: `ProveCustomDirective` panics instead of failing closed when `RunSSHGCombined` is nil

**File:** `internal/globalssh/validate.go:109`
**Issue:** `deps.RunSSHGCombined(ctx, args...)` is called with no nil check. `Deps` is a
plain struct of function fields; the doc on `Deps` says "Every field is non-nil in the
real `BuildProbeDeps` wiring", but that is a convention, not an enforcement, and this

if deps.RunSSHGCombined == nil {
    return DirectiveProof{}, errors.New("globalssh: RunSSHGCombined seam is not wired — refusing to report an unproven directive as accepted")

### WR-13: The new visual-regression region extractors fail *open* — a renamed anchor silently retires its own standing guard

**File:** `internal/screenshot/createflow_regions.go` (`extractSubTabStrip`,

**Fix:** Have `TestGateVisualRegression` assert that every `RequiredRegions` entry

### WR-14: Raw `ssh` stderr is rendered unbounded and unsanitized into the fixed-geometry frame

**File:** `internal/tuikit/globalssh.go:2040,2051`
**Issue:** `proof.Output` — the verbatim combined output of a subprocess — is written
straight into the body via `styleFaint.Render(proof.Output)` and again inside
`PropsSSHProofRejectedFmt`. Unlike `PreviewBlock` (used one line above for the command),

### WR-15: The visual-regression gate now depends on a real `ssh` subprocess and on the local OpenSSH build rejecting a specific name

### IN-04: `%q` uses Go quoting rules for a git subsection header

**File:** `internal/gitconfig/customkeys.go:169`
**Issue:** `fmt.Fprintf(&b, "[%s %q]\n", section, subsection)` applies `strconv.Quote`
semantics. Printable Unicode survives, but a non-printable rune is emitted as a Go
escape (`\x01`, `\u2028`) that git will read back literally, so
`RenderCustomKeysBlock` → `ParseCustomKeysBlock` is not round-trip stable for such a
subsection. `ParseCustomKeysBlock`'s `strings.Trim(..., "\"")` also strips *all* leading
and trailing quote characters rather than exactly one pair.
**Fix:** Reject non-printable runes in the subsection alongside the existing
`forbiddenSubsectionCharRE`, and use an explicit `"` + subsection + `"` render.
