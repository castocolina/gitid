collides with a key the curated baseline block already manages does not produce two
conflicting writers of the same key; the flow surfaces the collision rather than silently
shadowing one block with the other."* I verified both directions against the real `git`
binary through the production writers (temporary probe, since deleted).

`globalgit.PolicyForMember` is the correct lookup (member keys, not display keys) and the

## Warnings

### WR-01: A custom SSH directive silently overwrites a CURATED Global-SSH policy value — the unguarded twin of CR-01

**File:** `cmd/gitid/lifecycle.go:1656-1672` (runCustomSSHDirectiveWrite plan stage), `cmd/gitid/wiring.go:2674-2683` (CustomSSHDirectivePlan)

**Issue:** The Git side hard-refuses a custom key that collides with a curated
`globalgit.Policy` member (round 3's CR-01). The SSH side has **no equivalent guard**. A
custom directive whose name is one of `sshconfig.GlobalHostStarOrder` /
`globalssh.Policy` — `StrictHostKeyChecking`, `ForwardAgent`, `HashKnownHosts`,
`IdentitiesOnly`, `AddKeysToAgent`, `UseKeychain` — passes `ValidateDirectiveName`, passes
the staged `ssh -G` proof, and then `EnsureGlobals`'s `merged.set(k, v)` **replaces the
curated value in place**, in the same managed block, with no refusal and no advisory.

Proven against the compiled writer with real ssh (temporary probe, since deleted):

```
target …/.ssh/config.d/gitid.config after runGlobalSSHApply([StrictHostKeyChecking, HashKnownHosts]):
    Host *
      StrictHostKeyChecking accept-new
      HashKnownHosts yes
      …

CustomSSHDirectivePlan("StrictHostKeyChecking", "no")  -> ACCEPTED (no refusal)
runCustomSSHDirectiveWrite(...)                        -> err=<nil>

target after:
    Host *
      StrictHostKeyChecking no            <- curated hardening replaced
      HashKnownHosts yes
```

This is security-relevant (`StrictHostKeyChecking no` disables host-key verification, which
the curated row exists to prevent) and it desynchronises the Options sub-tab, which will
then render the row as "differs" with no explanation of who changed it. Not classified
CRITICAL because the ceremony diff does surface the replaced line (see WR-02 for why that
mitigation is weaker than it should be) and because `09.5-04-PLAN.md` declares no backstop
covering it — but the asymmetry with the Git side is not defensible on the merits.

**Fix:** mirror the Git guard at both gates.

```go
// cmd/gitid/wiring.go CustomSSHDirectivePlan, and cmd/gitid/lifecycle.go
// runCustomSSHDirectiveWrite's plan stage (fail-closed backstop):
if policy, managed := globalssh.PolicyFor(name); managed {
    return ..., fmt.Errorf(
        "gitid: %s is managed by the curated Global SSH Host * block (%s) — writing it as a "+
            "custom directive would replace the curated value in place; change it from the "+
            "Options sub-tab instead", name, policy.Key)
}
```

If an outright refusal is judged too strict for SSH (unlike Git, replacing in place at
least does not create two writers), then at minimum emit a named advisory on the ceremony —
but silence is not an option the Git side was allowed either.

### WR-02: `globalsTextDiff` reports unchanged lines as both added and removed, undermining the ceremony's frozen "everything else preserved verbatim" claim

**File:** `cmd/gitid/wiring.go:3466-3494`

**Issue:** The greedy line walk emits `+ <new>` and advances only `j` whenever the old line
is not found later in the remaining new lines. After the FIRST changed line the two cursors
are permanently offset, so every subsequent byte-identical line is emitted as an addition
and then again, in the tail loop, as a removal. Proven output from the WR-01 probe, where
exactly one line actually changed:

```
+   StrictHostKeyChecking no
+   HashKnownHosts yes          <- unchanged
+   AddKeysToAgent yes          <- unchanged
+   UseKeychain yes             <- unchanged
-   StrictHostKeyChecking accept-new
-   HashKnownHosts yes          <- unchanged
-   AddKeysToAgent yes          <- unchanged
-   UseKeychain yes             <- unchanged
```

This is rendered under the frozen title *"Exact change — everything else preserved
verbatim"*. It is factually wrong, and it is the reason WR-01's single security-relevant
line is easy to miss. The helper predates this phase (Phase 6/7 curated applies), but the
two NEW ceremonies added here are the ones where the user authored the change and must read
the diff carefully, which makes it newly load-bearing.

**Fix:** replace the greedy walk with a real LCS diff (or, minimally, resynchronise: after
emitting an addition, re-scan forward for the next matching pair before continuing).

```go
// Minimal correction: emit a paired -/+ when both sides differ at the same index and
// the old line reappears nowhere later, instead of advancing only j.
if !containsLine(newLines[j:], oldLines[i]) && !containsLine(oldLines[i:], newLines[j]) {
    out = append(out, "- "+oldLines[i], "+ "+newLines[j])
    i++
    j++
    continue
}
```

### WR-03: The custom-SSH-directive post-write verification never reads the file gitid wrote

**File:** `cmd/gitid/lifecycle.go:1784-1797`; `internal/globalssh/properties.go:25`; `internal/globalssh/probe.go:156-158`

**Issue:** `globalssh.AllDirectives(globalssh.BuildProbeDeps(b.sshConfigPath))` ignores the
`sshConfigPath` argument entirely — `AllDirectives` → `effective(deps)` → `runProbe(deps,
"-G", ProbeHost)`, with **no `-F`**. `BuildProbeDeps`'s `sshConfigPath` is consumed only by
`ReadConfig`, which this path never calls. OpenSSH then resolves `~/.ssh/config` from
`getpwuid()->pw_dir`, **not** `$HOME`. Proven with the real binary:

```
$ HOME=$PWD/fakehome ssh -G gitid-probe.invalid | grep serveralive
serveraliveinterval 0                      <- read the REAL user's config
$ ssh -F $PWD/fakehome/.ssh/config -G gitid-probe.invalid | grep serveralive
serveraliveinterval 777                    <- the sandbox file actually says 777
```

Consequences:
1. Any run where gitid's home is not the passwd home (containers, `sudo -E`, an explicit
   `HOME` override, and **the project's own e2e/gate harness**) verifies the wrong file.
   Observed live in a sandboxed write: `advisory: StrictHostKeyChecking was written as "no"
   but resolves to "ask"` — a false shadow advisory on a write that landed perfectly.
2. The verify stage the plan calls out as load-bearing ("`globalssh.Verify` skips any key
   the policy table does not know, so a custom directive needs its own re-read") is not
   actually exercised against the written file in any sandboxed test.

**Fix:** resolve through the file gitid wrote, or at least the config it owns.

```go
// Add an explicitly-scoped read, e.g.
func AllDirectivesForConfig(deps Deps, configPath string) ([]Directive, error) {
    m, err := runProbe(deps, "-F", configPath, "-G", ProbeHost)
    ...
}
// and call it from runCustomSSHDirectiveWrite with b.sshConfigPath, so the verify
// observes exactly what this write produced (mirroring the Git side's
// RunGitConfigGetIn(baselineDir, target, key), which reads `target` directly).
```

### WR-04: A pre-existing bad option ANYWHERE in `~/.ssh/config` rolls back a correct custom-directive write and blames the new directive

**File:** `cmd/gitid/lifecycle.go:1785-1796`

**Issue:** WR-07 (round 2) made an `AllDirectives` failure a FAILED transaction. But
`ssh -G` hard-fails on an unrecognised option in **any** stanza, including one that does
not match the probe host — proven with the real binary:

```
$ cat sshbad
Host someother
  NotARealOption yes

Host *
  ServerAliveInterval 60
$ ssh -F sshbad -G gitid-probe.invalid; echo "exit=$?"
sshbad: line 2: Bad configuration option: notarealoption
sshbad: terminating, 1 bad configuration options
exit=255
```

The plan-stage `ProveCustomDirective` cannot see this: it stages **only** the gitid global
block body (`stageDirectiveConfigForWrite` → `RenderGlobalBodyWithOverlay`), never the
user's foreign `Host` stanzas. So the plan passes, the ceremony opens, the write lands, and
then the verify fails with:

> post-write re-verification failed — **the written directive may have made the
> configuration unparseable**

…which is false, and permanently blocks every custom-directive write until the user finds
the unrelated stanza with no help from the message. This is precisely the misattribution
class round 3's WR-04 fixed on the Git side (`RunGitConfigGetIn` / `ValidateGitConfigSyntaxIn`
isolating from an ambient broken repo); the SSH side never got the equivalent treatment.

**Fix:** distinguish "the config was already unparseable" from "this write broke it". Run
the same probe against the pre-write bytes at the plan stage (or capture a baseline
`AllDirectives` result before the write) and, when both fail identically, report a
pre-existing configuration problem naming `proof.OffendingName` — the same D-I
`PreexistingError` classification `ProveCustomDirective` already implements — instead of
blaming the candidate.

### WR-05: `SetKey.Origin` bypasses `SanitizeDisplayValue`, leaving the round-3 WR-02 fix half-applied

**File:** `cmd/gitid/wiring.go:2149`; rendered at `internal/tuikit/globalgit.go:1678-1679`

**Issue:** Round 3's WR-02 sanitised `Value` on both browsers but left `Origin` routed only
through `b.displayPath`, which performs a home-prefix substring replace and no control-
character filtering. `Origin` is a filesystem path from `git config --show-origin`, and a
path may legally contain any byte but `/` and NUL. Proven with real git that an embedded
newline survives into the origin field:

```
$ git config --file main.cfg --includes --show-origin --list -z | od -c
…  /   s   c   r   a   t   c   h   p   a   d   /   o   r   i   g
 /   w   e  \n   i   r   d   .   c   f   g  \0 …
```

`renderSetKeys` writes `" " + styleFaint.Render(detail.Origin) + "\n"` on the assumption of
exactly one row; an embedded `\n` silently costs a row of the `fitPane`-clipped detail
pane, and a raw CSI/OSC sequence in a path reaches the terminal verbatim — the exact
exposure WR-02 closed for `Value`.

**Fix:**

```go
Origin: b.displayPath(tuikit.SanitizeDisplayValue(k.Origin)),
```

and extend `TestAllGitSetKeysScrubsOriginThroughDisplayPath`'s AST assertion to require
`SanitizeDisplayValue` on the `Origin` field too.

### WR-06: The custom-write ceremony fabricates a `+ key = value` preview for an idempotent write that changes nothing

**File:** `internal/tuikit/globalgit.go:894-897` (customKeyCeremonyFor); `internal/tuikit/globalssh.go:867-870` (customDirectiveCeremonyFor)

**Issue:** Both helpers do `preview := plan.Diff; if preview == "" { preview = "+ " + key + " = " + value }`. The comment on the sibling `targets` fallback says it exists "for a stub
that answers an empty plan", but in production an empty `Diff` has exactly one meaning: the
SC-1 idempotent case, where the writer will write **nothing** and take **no backup**.
Proven:

```
Diff="" Targets=[~/.gitconfig ~/.gitconfig.d/00-baseline] Backups=[]
second write err=<nil> backups=[]        (SC-1: nothing written)
```

…yet the ceremony renders `+ core.pager = less -FRX` under *"Exact change — everything else
preserved verbatim"*. A confirm ceremony that shows a change it will not make is the
opposite of this project's stated preview discipline.

**Fix:** render the honest no-op instead of inventing a diff.

```go
preview := plan.Diff
if preview == "" {
    preview = key + " = " + value + " is already set — this write will change nothing."
}
```

(and consider suppressing the ceremony entirely for a no-op, matching
`runGitFallbackAuthorApply`'s `Kind: "noop"` early return).

### WR-07: `user.email` / `user.name` are accepted as custom Git keys and silently shadowed by gitid's own fallback-author block

**File:** `cmd/gitid/wiring.go:2540`, `cmd/gitid/lifecycle.go:1433` (the `PolicyForMember` guard)

**Issue:** The CR-01 guard keys off `globalgit.PolicyForMember`, and the fallback-author row

`user.name` are not recognised as managed. Proven end-to-end:

```

runCustomGitKeyWrite("user.email", "custom@example.com")             -> ACCEPTED, advisories=[]
```

class of destination; (c) it bypasses `appendFallbackAuthorAdvisories`' includeIf-precedence

and the fallback pair is a different block by explicit design (D-04/D-05).

```go
if strings.EqualFold(key, "user.email") || strings.EqualFold(key, "user.name") {

        "fallback-author ceremony (a separate managed block in ~/.gitconfig that takes " +
```

### WR-10: The two new ceremonies have no preview-preimage guard, unlike their two established siblings

**File:** `cmd/gitid/wiring.go:2525-2583` / `2674-2709` (plans), `cmd/gitid/lifecycle.go:1390` / `1629` (writers)

**Issue:** `CustomGitKeyPlan` and `CustomSSHDirectivePlan` read the target files, render a
diff, and hand it to a ceremony; `runCustomGitKeyWrite` / `runCustomSSHDirectiveWrite` later
re-read those files and compose from whatever is there **then**. Nothing carries a preimage
digest across the confirm boundary. Two siblings in this same codebase already do:
`CommitGlobalGitIgnore` (`gitIgnorePreimageToken`, which even length-prefixes its two
payloads to defeat a boundary collision — 09.2 WR-08) and `CommitSSHStorage`
(`MigrationPlan` digests + `ErrConfigChangedSincePreview`). A concurrent gitid process,
another tool, or the user's editor can change the file between preview and write, and the
user confirms a diff that is not what lands. Damage is bounded (managed-block splice +
timestamped backup + journal), which is why this is a WARNING and not higher.

**Fix:** add a `sha256` preimage token over the read bytes to both `*PlanView`s and require
it on the commit seam, refusing with the existing `ErrConfigChangedSincePreview` shape.

### IN-02: `validateCustomValue` (Git) permits every C0 control byte except LF/CR, while its SSH sibling explicitly rejects NUL

**File:** `internal/gitconfig/customkeys.go:87-109` vs `internal/globalssh/validate.go:133-135`

**Issue:** `validateValue` rejects only `\n`/`\r`; `forbiddenCustomValueCharRE` covers
`"` `\` `#` `;`. ESC (0x1B), BEL, TAB and NUL all pass. `ValidateDirectiveValue` rejects
`\x00` explicitly. The NUL case is neutralised in practice by the read-back verify — proven
that git truncates a value at NUL (`a\0b` → `a`), so the readback mismatches and the write
rolls back — but the rollback message is confusing, and ESC survives into the ceremony diff
render (which does no ANSI stripping). The asymmetry looks unintentional.

**Fix:** add `if strings.ContainsAny(value, "\x00") { … }` and reject C0 controls other than
none, mirroring the SSH sibling's explicit list.

### IN-03: `SanitizeDisplayValue` strips C0/C1/DEL but not bidi-override or zero-width runes

**File:** `internal/tuikit/globalssh.go:2057-2066`

**Issue:** U+202E/U+202D and friends can visually reorder a rendered key/value row
("Trojan Source" display spoofing) without any control byte. Low practical concern (the
source is the user's own machine config), noted for completeness alongside the round-3
WR-02/IN-02 filter discussion.

### IN-04: `renderSubTabStrip` pads its label line asymmetrically

**File:** `internal/tuikit/frame.go:166-184`

**Issue:** `label := " " + join(...)` and `labelLine := "┊ " + label + " ┊"` gives two
leading spaces and one trailing space inside the box. Extracted verbatim from Global SSH's
original strip, so this is inherited, not introduced — but it is now the ONE shared
renderer for every screen, which is the right moment to make it symmetric.

### IN-05: `parseGlobalBody` silently drops any one-field line inside the managed block

**File:** `internal/sshconfig/globals.go:274-277`

**Issue:** `if len(fields) < 2 { continue }` discards a hand-added valueless keyword inside
gitid's own `Host *` block on the next `EnsureGlobals` write, with no advisory — the same
silent-drop shape CR-02 documented for the structural keywords, but undocumented here. A
comment (or a raw-line preservation, as already done for `#` comments) would close it.
