<decision_record>
**D-F — the custom Git key goes into a NEW managed block named
`custom-git-keys`, in the SAME baseline file the curated block already lives in,
accumulating every custom key in ONE block body.** CONTEXT.md flagged this as
"a real architectural question the planner must resolve, not a cosmetic detail."
`gitconfig.RenderBaselineBlock` renders a FIXED, hardcoded sequence of section
headers (`[core]`, `[push]`, `[pull]`, `[fetch]`, `[color]`, `[diff]`,
`[merge]`, `[init]`, `[alias]`); a free-form key can name ANY section, including
one with a subsection, which that renderer has no mechanism to emit. Rejected:
(a) extending `BaselineConfig` with a dynamic key map and teaching
`RenderBaselineBlock` to emit arbitrary section headers — it would turn a
byte-stable, SC-1-idempotent, well-tested renderer into a second parser with
different rules, for no benefit over a dedicated block; (b) one managed block
per custom key with a keyed sentinel name — functionally correct, but every new
name needs its own reserved registration and `IsReservedBlockName` would need a
prefix predicate, multiplying the surface of the destructive-loop failure this
project has already hit. The accumulating single-block form matches the existing
`baseline` / `url-rewrites` precedent of one block per logical purpose.
Reversibility: **costly** — the block name becomes a compatibility surface on
users' disks the moment the first write lands. Mitigated by registering the name
in `IsReservedBlockName` in the SAME commit that introduces it, so no gitid
version can ever see the block without recognising it.

**D-G — the git key is split on the LAST dot, then the section path is split on
its FIRST dot into section + optional subsection.** Verified against
`man git-config`'s CONFIGURATION FILE section: the variable name is the last
dot-separated segment, the section name is everything before it, and a
subsection may itself contain dots. So `mytool.sub.key` renders as
`[mytool "sub"]` / `key`, and `http.https://example.com.sslVerify` renders as
`[http "https://example.com"]` / `sslVerify`. The variable must match
`^[A-Za-z][A-Za-z0-9-]*$` (git's own rule); the section must match the same
shape; the subsection must contain no double quote, backslash, newline, or
carriage return. Rejected: splitting on every dot or on the FIRST dot only —
both mis-file a three-segment key, and the failure is silent (the write
"succeeds" and `git config --get` on the intended key returns nothing).
Reversibility: reversible.
</decision_record>
