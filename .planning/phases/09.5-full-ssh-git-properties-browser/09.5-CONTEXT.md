# Phase 9.5: Full SSH/Git Properties Browser & Custom Key Entry - Context

**Gathered:** 2026-08-30
**Status:** Ready for planning

<domain>
## Phase Boundary

New sub-tabs on the Global SSH and Global Git screens let the user browse
EVERY SSH directive / every set Git config key on their machine — not just
gitid's curated `OptionPolicy` tables — and add a custom global key on
either side. Closes PROP-01 through PROP-04. Scope grew during this phase's
own discussion from "read-only browse" to "browse + add a custom key," after
the user raised the point directly and a real asymmetry between SSH's and
Git's safety profiles was surfaced and resolved.

</domain>

<decisions>
## Implementation Decisions

### The SSH/Git asymmetry (grounds every other decision below)
- **D-01 (established fact, not a choice):** SSH has a bounded, ~90-directive
  set — `ssh -G <host>` reliably resolves EVERY directive, set or default,
  so a truly comprehensive browse is possible (`internal/tester/tester.go`'s
  `ResolvedConfig`/`Resolved`/`ResolvedVia` already parse this output
  elsewhere in the codebase — reuse the parsing approach, don't re-derive
  it). Git config keys are open-ended/extensible per subsystem; there is no
  "all possible keys" catalog. `git config --list --show-origin` (the
  pattern `internal/globalgit/authorresolve.go`'s `parseShowOriginGet`
  already parses for single-key lookups) only shows what is actually SET
  somewhere, across global/system/local scope.
- **D-02:** PROP-01 (SSH) is scoped as the full `ssh -G` dump — genuinely
  comprehensive. PROP-02 (Git) is honestly scoped as "every key currently
  set," not a fabricated catalog of possible keys — this is git's real
  limit, not an implementation shortcut.

### Custom key entry (scope grew here — read this section before planning)
- **D-03:** The phase includes WRITE capability, not just browsing — the
  user explicitly asked "shouldn't we be able to add global key-value
  pairs?" mid-discussion, and after a real technical asymmetry was
  presented and confirmed, both sides ended up in scope (PROP-03/PROP-04),
  each with a DIFFERENT safety treatment:
  - **Git (PROP-03):** free-form key=value entry, no directive-name
    validation. An unrecognized git config key is harmless — git and every
    tool that reads config simply ignores keys nothing looks for. Still
    goes through the same review-before-write ceremony (CLAUDE.md's
    confirmation rule) every other gitid write path uses.
  - **SSH (PROP-04):** the entered directive NAME is validated against
    OpenSSH's known-directive list BEFORE the write proceeds. Rationale:
    OpenSSH can hard-fail parsing `~/.ssh/config` on an unrecognized
    directive, breaking connectivity for EVERY host, not just gitid's
    managed ones — a materially higher blast radius than a stray git key.
    In addition to name validation, route the entry through gitid's
    existing prove-before-write `ssh -G` verification pattern (already used
    for identity connectivity tests — see `internal/tester/tester.go`) so a
    bad entry is caught before it is ever written for real, not just
    trusted because the name matched a known list.
  — **Reversibility:** costly — PROP-04's SSH validation path needs a
  reliable, maintained source for "OpenSSH's known-directive list" (see
  Claude's Discretion below); getting this wrong either blocks legitimate
  directives or lets through ones that break config parsing. Rate the SSH
  custom-entry task `one-way`-adjacent at plan time given the blast radius
  named above, even though the write itself goes through the standard
  backup/confirm ceremony.

### UI placement
- **D-04:** Both browsers are new SUB-TABS on their respective existing
  screens — Global SSH gains a third sub-tab (alongside today's `Options` /
  `Storage & preview`), Global Git gains a new sub-tab of its own — rather
  than standalone top-level main-menu items. Keeps them contextually
  grouped with the curated policy views they complement. This also means
  Phase 9.4's UXP-04 sub-tab visual-distinction fix (bordered/boxed sub-tab
  bar) directly benefits this phase's new sub-tabs — build on that pattern,
  don't invent a second one.
  — **Reversibility:** reversible.

### Browse UX (scale handling)
- **D-05:** Both browsers render as a flat, scrollable list with a
  type-to-filter/search input — no category grouping scheme. Simpler, no
  taxonomy to invent or maintain (an OpenSSH manual-page category grouping,
  or a git-section grouping, were both considered and explicitly not
  chosen), and matches the terminal-list pattern already used elsewhere in
  gitid.
  — **Reversibility:** reversible.

### Claude's Discretion
- The authoritative source for "OpenSSH's known-directive list" (PROP-04's
  validation) — research options during planning: parsing `ssh -G`'s own
  supported-keyword output, a maintained static list keyed to a minimum
  OpenSSH version (mirroring how `internal/globalssh` already version-gates
  some options), or shelling out to `man ssh_config` (fragile, avoid).
  Research this properly rather than guessing at a hardcoded list.
  - Whether the custom-added SSH directive/Git key is written into gitid's
  EXISTING managed block (`# BEGIN gitid managed: ...` sentinel scheme,
  `internal/filewriter.ReplaceBlock`), or needs its own new managed-block
  identity distinct from the curated-policy blocks — since custom entries
  are NOT part of the fixed `OptionPolicy` schema those blocks currently
  render from. This is a real architectural question the planner must
  resolve, not a cosmetic detail; read `internal/gitconfig/baseline.go`'s
  `WriteBaselineFile`/`RenderBaselineBlock` and
  `internal/sshconfig/globals.go`'s `ensureGlobalsLast`/`globalMap` before
  deciding.
- Exact wording/placement of the type-to-filter input and how a filtered
  match is highlighted.
- Whether a custom-added entry, once written, then also appears in the
  SAME curated Options list (if it happens to match a policy-table key
  gitid already tracks) or only in the properties browser — avoid double-
  counting/double-rendering the same live value in two places.

</decisions>

## Canonical References

**Downstream agents MUST read these before planning or implementing.**

### Requirements
- `.planning/REQUIREMENTS.md` §S (PROP) — PROP-01 through PROP-04, the
  requirements this phase closes.

### Existing SSH resolution/parsing (reuse for PROP-01/PROP-04)
- `internal/tester/tester.go` — `ResolvedConfig`, `Resolved`,
  `ResolvedVia`, `ParseResolved` — the existing `ssh -G` parsing this
  phase's full-directive browse should reuse/extend, not reimplement. Note
  today's `ResolvedConfig` struct only carries a handful of fields
  (`User`, `Hostname`, `Port`, `IdentitiesOnly`, `IdentityFiles`) — PROP-01
  needs the FULL directive set, so this likely needs a more general
  key/value parse of `ssh -G`'s output rather than a fixed struct.
- `internal/globalssh/classify.go` — the existing `OptionPolicy`/
  `OptionState` machinery this phase's browser sits ALONGSIDE (not instead
  of) — the curated Options screen and the new full-properties sub-tab
  both read from the same underlying `ssh -G` resolution, just at
  different scopes (curated subset vs everything).

### Existing Git key/origin parsing (reuse for PROP-02/PROP-03)
- `internal/globalgit/authorresolve.go` — `parseShowOriginGet`,
  `getAuthorKey` — the existing `git config --show-origin --get <key>`
  parsing pattern for ONE key; PROP-02 needs the LIST form
  (`git config --list --show-origin`), which returns multiple
  `file:<path>\t<key>=<value>` lines — extend the parsing approach, don't
  duplicate a second origin-parser.
- `internal/gitconfig/baseline.go` — `WriteBaselineFile`,
  `RenderBaselineBlock`, `BaselineConfig` — the existing managed-block
  write path for git config; read before deciding where a custom-added
  key's write target lives (see Claude's Discretion above).

### Write-safety precedent (governs PROP-03/PROP-04's ceremonies)
- `internal/filewriter` — `ReplaceBlock`/`Write`, the managed-block
  chokepoint every gitid write path uses; any custom-key write must go
  through it, not a bespoke file write.
- `internal/sshconfig/globals.go` — `ensureGlobalsLast`, `globalMap` — the
  existing global SSH block write machinery PROP-04's custom directive
  entry extends.
- CLAUDE.md "Working method: hypothesis → test → implementation" and
  "Engineering" — the confirmation/backup discipline every write in this
  phase must follow, and the "hypothesis → test → implementation" rule
  that directly motivates PROP-04's prove-before-write requirement (don't
  write an unverified SSH directive and hope).

## Existing Code Insights

### Reusable Assets
- `ssh -G`'s output format (directive-per-line, lowercase keys, resolved
  values) is ALREADY parsed elsewhere in this codebase
  (`tester.ParseResolved`) — PROP-01's full-list parse is an extension of
  an existing, proven pattern, not new ground.
- `git config --show-origin`'s `file:<path>\t<value>` line format is
  ALREADY parsed (`parseShowOriginGet`) — PROP-02's list-form parse
  extends this.

### Established Patterns
- Sub-tab bars already exist on Global SSH (`Options` / `Storage &
  preview`) — Phase 9.4's UXP-04 fix (bordered/boxed visual treatment) is
  the pattern this phase's new sub-tabs should use, landing AFTER 9.4 in
  execution order specifically so this reuse is available.
- Every gitid write path shows a diff/preview and requires explicit
  confirmation before calling its `Write*` engine function — PROP-03/
  PROP-04's custom-key writes follow the same discipline.

### Integration Points
- Global SSH's `globalSSHModel` (`internal/tuikit/globalssh.go`) gains a
  third sub-tab; Global Git's `globalGitModel`
  (`internal/tuikit/globalgit.go`) gains a new sub-tab. Both are existing,
  persistent screen models — extend their `subTab`/sub-navigation handling
  rather than creating parallel new screens.

</code_context>
