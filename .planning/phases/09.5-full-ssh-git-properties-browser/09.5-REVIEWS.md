## Findings from this run itself (about the reviewer setup, not the plans)

1. **HIGH — `review.reviewer_instances.opencode-plan-review.model` names a
   provider that doesn't exist in the active OpenCode config.**
   `.planning/config.json:105` pins `"model": "local-llm-env/my-plan-review"`,
   but `~/.config/opencode/opencode.jsonc` registers that model under the
   provider name `router-env`, not `local-llm-env` (see
   `~/.config/opencode/opencode.jsonc:5-9`, `:20-26`). The same stale
   `local-llm-env/*` prefix also appears in `.planning/config.json:51`
   (`cross_ai_command`). Confirmed the correct prefix is `router-env` by
   running `command opencode run "ping" --model router-env/my-plan-review`
   directly (it dispatched — "> build · my-plan-review" — rather than
   erroring on an unknown provider). This mismatch means the primary
   configured reviewer would silently mis-target a nonexistent provider
   alias even when the router-env backend is healthy again, independent of
   today's outage. This mirrors a previously logged issue in this project
   (the `gsd-codex-sol` model-string fix) — the fix pattern is the same:
   correct the pinned model string in `.planning/config.json` to the
   provider name OpenCode actually registers.
   **This is a reviewer-configuration finding, not a plan-quality finding —
   it belongs in project/tooling config, not in a PLAN.md.**

2. **MEDIUM — `opencode` is shell-aliased to `opencode --auto` in this
   environment**, which silently breaks `opencode run <subcommand-style
   invocation>` (the alias's leading `--auto` flag causes yargs to treat the
   `run` token as the positional `[project]` argument of the default `tui`
   command instead of dispatching the `run` subcommand, so it prints top-
   level `--help` instead of running). Diagnosed by comparing `opencode run
   …` (prints help, does nothing) against `command opencode run …` (works).
   If `gsd-tools`'s `review-lane invoke` shells out via the aliased name
   rather than an unaliased/absolute path, every OpenCode-backed lane could
   silently no-op on hosts with this alias. Worth confirming
   `review-lane-runner.cjs`'s OpenCode spawn path is immune to shell
   aliasing (it should be, if it spawns the binary directly rather than
   through an interactive shell) — flagging as MEDIUM because it did not
   visibly affect `review-lane invoke` in this run (its failures were
   attributable to the resource-pressure/usage-limit errors above, not to
   the alias), but it is exactly the kind of failure mode that would look
   identical to "empty output" if it ever did trigger.
