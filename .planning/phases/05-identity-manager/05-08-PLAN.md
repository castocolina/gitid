**Map the flags onto the confirmation ENUM, and refuse rather than default (review R2-03).** Plan 05-07 replaces the nilable confirm callback with a three-valued `confirmationMode` precisely because this handler and the TUI seam previously both used `nil` to mean opposite things — the TUI meaning "a human already confirmed on screen," this handler meaning "there was no way to ask" — so a scripted destructive run with no TTY and no `--yes` would have been read as pre-authorized. The mapping here is exhaustive and has no fallback branch:

  - `--yes` given → `Confirm: confirmationBypassedWithYes`, `Prompt: nil`.
  - `--yes` absent AND `stdinTTY && stdoutTTY` → `Confirm: confirmationRequired`, `Prompt:` the interactive prompt closure.
  - `--yes` absent AND not both terminals → **the handler returns a usage error BEFORE constructing a policy or calling any lifecycle function**, naming the confirmation flag as the way to proceed. This is the depthResolver's non-interactive branch extended to authorization: a missing confirmation is a missing input exactly like a missing required flag, and it is reported the same way.

`confirmationAlreadyObtained` is NEVER constructible from a CLI path — write that as a comment and add a test that greps the CLI handler sources for the identifier and asserts zero occurrences, so a future handler cannot borrow the TUI's value to silence a prompt. Belt and braces: because `confirmationRequired` is the enum's zero value and 05-07 fails closed on it, a handler that forgets the mapping entirely still refuses instead of writing.

A dry run is exempt because it cannot write: `--dry-run` is accepted without a terminal and without `--yes`, and 05-07's lifecycle stops after the plan stage, before the confirmation gate. Say so in the comment, since this is the one asymmetry a reader will otherwise mistake for a hole.
