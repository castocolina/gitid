**First, create the ONE lifecycle chokepoint per verb (review R-11-CLI).** D-02 requires that the CLI and the TUI run the same test → preview → confirmation → backup → write → re-test ceremony. Reusing only the final write transaction does not prove that: two callers could reach the same writer through different ceremonies. So introduce named lifecycle functions in a new section of `cmd/gitid/wiring.go` (or a sibling `cmd/gitid/lifecycle.go`), and make every other caller a thin adapter over them:

```
type confirmationMode int

const (
    confirmationRequired        confirmationMode = iota // ZERO VALUE — a prompt must be installed
    confirmationAlreadyObtained                         // the TUI's confirm screen already ran
    confirmationBypassedWithYes                         // --yes was given
)

type lifecyclePolicy struct {
    DryRun  bool
    Confirm confirmationMode
    Prompt  func(preview string) (bool, error) // required iff Confirm == confirmationRequired
    Stages  func(stage string)                 // test hook; nil in production
}
type lifecycleResult struct { Backups, Restored, Removed, ArchivedKeyPaths []string; ReTest tester.Result }

func (b *realBackend) runRotate(name string, p lifecyclePolicy) (lifecycleResult, error)
func (b *realBackend) runRepair(name string, p lifecyclePolicy) (lifecycleResult, error)
func (b *realBackend) runDelete(name string, scope identity.DeleteScope, p lifecyclePolicy) (lifecycleResult, error)
```

**Stages are declared PER VERB, in one table (review R2-02).** Cycle 1 asserted one literal six-stage sequence for every verb, which contradicts what delete can actually do and what plan 05-08's own dry-run contract states: a deleted identity has no Host block, no key, and no fragment left to connect with, so there is no connectivity test to run before or after it — and 05-08 requires delete's dry run to invoke zero test seams. Forcing a test stage into `runDelete` would mean either inventing a meaningless SSH attempt or recording a stage that does nothing, and a stage recorder that accepts a no-op stage stops proving anything. So define the sequences once, as data, next to the three functions:

```
var lifecycleStages = map[string][]string{
    "rotate": {"test", "plan", "confirm", "backup", "write", "retest"},
    "repair": {"test", "plan", "confirm", "backup", "write", "retest"},
    "delete": {"plan", "confirm", "backup", "write", "verify"},
}
```

Delete's closing `verify` stage is a re-read of the reconstructed inventory asserting the identity is gone and the surviving identities still parse — the coherence check that plays delete's structural equivalent of a re-test without pretending a connection is possible. Each function drives its own sequence from this table and calls `p.Stages(<name>)` at each boundary. The single-chokepoint property review R-11-CLI won is UNCHANGED and is what these edits protect: there is still exactly ONE function per verb, both skins still call it, and the table is the one definition both skins' tests assert against — so a stage list that drifts breaks the CLI test and the TUI test together. What is removed is only the false claim that all three verbs run the same list. Document on the table that `lifecycleStages` is the single source of truth for D-02's no-behavioral-fork claim, that plan 05-08's matrix and dry-run contract must agree with it, and that adding a verb means adding a row here first.

Preserve what is verb-INDEPENDENT and assert it as such: every row must contain `backup`, `confirm`, and `write`, in that relative order. Add a table-driven test over `lifecycleStages` itself asserting exactly that, so a future verb cannot be added with the backup stage quietly missing — that is the D-02 invariant, and it is stronger stated as a property over the table than as a literal sequence per verb.

`p.DryRun` stops the function after the plan stage, before the confirmation gate and therefore before any backup or write. State the ordering consequence in a comment: a dry run needs no authorization because it cannot write, which is what keeps `--dry-run` usable in non-interactive CI.

**Confirmation is a three-valued mode, never a nilable func (review R2-03).** Cycle 1 used `Confirm == nil` to mean "the caller already confirmed" here, while plan 05-08 used the same nil to mean "no prompt could be installed" for a non-interactive invocation. Those are opposite intents — "authorization already happened" versus "authorization cannot happen" — colliding on one sentinel, and the collision fails OPEN: a scripted `gitid identity delete --all` with no TTY and no `--yes` would take the already-confirmed path and destroy an identity nobody authorized. Separate them structurally, and choose the zero value so that the dangerous state is the one you must ask for explicitly:

  - `confirmationRequired` is the ZERO value. Reaching the confirm stage in this mode with `p.Prompt == nil` returns a new `errConfirmationUnavailable` sentinel immediately — before the backup stage, before any write, with the stage recorder showing nothing past `confirm`. A caller that forgets to set the field therefore fails closed rather than silently proceeding.
  - `confirmationAlreadyObtained` proceeds without a prompt. The TUI's commit seams set it, and only they may: write a comment stating that this value asserts a human already saw and accepted the preview on screen, so setting it from a code path with no such screen is a security defect, not a shortcut.
  - `confirmationBypassedWithYes` proceeds without a prompt because the user passed `--yes`. It is distinct from the previous value on purpose, so a receipt or a log can tell "a human clicked confirm" apart from "a script asserted consent up front" — and so the CLI can never reach the TUI's value.

The backup stage is NOT policy-controlled under any of the three modes: it always runs, and a comment at the call site states that no policy field can disable it (D-02).

Plan 05-08's CLI handlers call these same three functions and map their flags onto this enum; that is what makes the parity claim structural rather than incidental. Add a test now that asserts the recorded stage sequence for each verb equals its row in `lifecycleStages`, a test asserting the TUI commit seam contributes no stage of its own, and the fail-closed test for the zero-value policy.

**Then add the two real commit paths**, mirroring `CommitGit` step for step but delegating the ceremony.

Add `func (b *realBackend) CommitRotate(name string) tea.Cmd` and `func (b *realBackend) CommitNewKey(name string) tea.Cmd`. Each returns a closure that: checks the construction error and returns a `KeyCommitMsg` with the display message on failure; takes `txMu`; calls `b.runRotate` / `b.runRepair` with `lifecyclePolicy{Confirm: confirmationAlreadyObtained}` — the TUI's ceremony screen is the confirmation, and this is the only layer permitted to assert that value; and marshals `lifecycleResult` into `KeyCommitMsg`. All journal handling, file watching, and rollback live inside the lifecycle function, not in the seam.

Inside the lifecycle functions: build a `mutationJournal`; watch the SSH config target, the gitconfig, the fragment, the allowed_signers file, and both key paths; call the domain function **through `b.depsForTransaction(journal)`**; and on error call `journal.restore()` and return the restored list.

**Call the domain with the transaction-scoped Deps, never with `b.deps` (review R3-01).** Cycle 1 told this task to "reuse `b.deps`" while ALSO telling the archive closures to call `journal.recordCreatedFile` — and those two instructions cannot both hold. `b.deps` is built once by `buildIdentityDeps` inside `newBackendForHome`, with no transaction in scope, so a closure living there has no journal to call and the recording could never fire. Plan 05-03 Task 2 resolves that at the source: `archiveKeyPairSeam(onCreated)` holds the one archive implementation, `buildIdentityDeps` binds it to a refusal (`errArchiveOutsideTransaction`) so the backend-wide seam fails closed, and `depsForTransaction(j)` returns a copy of that same wiring with the archive seam rebound to `j.recordCreatedFile`. This task's job is to USE it: every lifecycle function obtains its Deps from `depsForTransaction(journal)` and passes that to `identity.Rotate`/`identity.RepairKey`. The cycle-1 rule survives in the form it was actually protecting — do not build a SECOND wiring in the commit path — and `identity.Deps` being a value type is what makes re-binding one seam not a second wiring. State that distinction in a comment so a future reader does not "restore" the `b.deps` call and silently unhook the journal.

Do the same for delete in Task 2: `runDelete` obtains its `identity.DeleteDeps` from `b.deleteDepsForTransaction(journal)`, whose `CopyKeyPairToArchive` seam is bound to the same journal (plan 05-04 Task 1 lands that constructor and its fail-closed backend-wide binding).

Extend the journal to cover key files AND created directories. `watchFile` snapshots content and mode; confirm it restores a file that did not previously exist by removing it, and that it restores modes as well as bytes — the key pair's 0600 must survive a rollback. If the current implementation does not restore modes, add that and pin it with a test.

**Add created-DIRECTORY recording to the journal; the created-FILE half already exists (review R-10, completed under R3-01).** Watched paths must be registered before the transaction starts, but archive filenames are timestamp-generated DURING the transaction and are unknowable at watch time — so a rollback that relies only on watched files leaves archive entries behind. Plan 05-03 Task 2 lands `recordCreatedFile(path string) error`, its disjointness rejection against `watchFile`, and its removal pass in `restore()`, because that is the wave where the first recorder is wired and a rotation must already be all-or-nothing there. This task adds `func (j *mutationJournal) recordCreatedDir(path string) error` with the same disjointness rule, so a newly created archive directory is removed too, and extends `restore()` to remove recorded directories after recorded files. Belt and braces at this layer: the domain also reports its archive paths (`RotateResult.ArchivedPrivatePath`/`ArchivedPublicPath`, `DeleteResult.ArchivedKeyPaths`), populated for failures from step 3 onward per plan 05-03, so the lifecycle function additionally records anything the result names before it decides to roll back — a second, independent path to the same fact. Because `recordCreatedFile` is idempotent on a path it already holds, recording the same archive path twice is a no-op rather than a disjointness violation; say so explicitly, since the observer and the result will normally both name it.

**State the journal's invariant as two disjoint sets, not as a precedence rule (review R2-08).** Cycle 1 wrote the ordering rule and then asked for a test where "a created file inside a restored directory" SURVIVES rollback — which contradicts the rule itself: a path recorded as created is by definition absent before the transaction, so nothing about it should outlive a rollback, and a directory that did not exist beforehand has no pre-existing contents to restore. Ordering is not the contract; disjointness is. Write the invariant this way and pin it:

  - **Every pre-existing WATCHED path is restored** to its pre-transaction bytes and mode (or removed, if it did not exist at watch time and the watcher recorded that absence).
  - **Every recorded CREATED path is removed.**
  - **No path may appear in both sets.** Make that structural rather than aspirational: `recordCreatedFile`/`recordCreatedDir` reject a path already watched, and `watchFile`/`watchDir` reject a path already recorded as created, each RETURNING an error naming the path. It is an error rather than a panic for a load-bearing reason cycle 3 settled: `recordCreatedFile` is handed directly to `keygen.CreatedFunc`, and a refusal there must ABORT the archive before any source is removed. Recording a path the same set already holds is an idempotent no-op, not a violation — the observer and the domain result will normally both name the same archive path. A path in BOTH sets has no correct rollback outcome, so the journal refuses it at registration time rather than picking a winner at restore time.

Restore order remains watched-first, creations-second, but it is now an implementation detail rather than the thing being asserted — with disjointness enforced, the two passes cannot interact. Document the resolution: a failed rotation leaves the filesystem exactly as it was found — no orphan archive entry hiding inside a doctor-reserved directory where `--fix` will never surface it. Add a failure-injection test asserting the archive directory contains no entry for this identity after a rolled-back rotation, INCLUDING the case where the failure is the archive step's own second-source removal (`failArchiveRemoveAt`, landed by plan 05-03 Task 2).

Add wiring tests over a hermetic fake home for every behavior, using the existing `failCommitAt`-style injection extended with the new steps. Include a concurrency test that launches both commits and asserts serialization, mirroring the existing WR-04 coverage.
