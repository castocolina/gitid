**Rebuild matches with kind-specific constructors, never by textual substitution (review R-12).** `gitconfig.Match` is a `Kind` plus an OPAQUE `Value`. Substituting the new name into that value is unsafe three ways: the source value may not contain the source name at all, may contain it coincidentally somewhere unrelated (a directory component, a repo name), or may have been hand-customized. So add two constructors to `internal/identity` and use only those:

  - `func GitdirMatch(cloneName string) gitconfig.Match` — reuse the existing `DefaultMatch` derivation so there is one gitdir shape in the project.
  - `func HasconfigMatch(alias string) gitconfig.Match` — rendering the recipe-canonical `hasconfig:remote.*.url:git@<alias>:*/**`.

`DeriveCloneInput` then maps each SOURCE match to a derived one by KIND only — a `gitdir` source yields `GitdirMatch(cloneName)`, a `hasconfig` source yields `HasconfigMatch(derivedAlias)` — preserving the source's kind and its position in the slice while discarding the source's opaque value entirely. Document the discard explicitly: the source's value is a fact about the SOURCE identity and carries no information about the clone.

**Record the recipe divergence in the doc comment (review R-23).** `identity.DefaultMatch` currently defaults to `gitdir:~/git/<identity>/`, while `recipes/README.md` names `hasconfig:remote.*.url:git@<alias>:*/**` as the PRIMARY match and gitdir as the alternative. That is an accepted, pre-existing project divergence, not something clone should quietly entrench or quietly fix. State in `DeriveCloneInput`'s doc comment that clone PRESERVES the source's kind (so a hasconfig source stays recipe-canonical) and that a source with no match at all falls back to the project default `gitdir` — and carry the divergence note into `05-05-SUMMARY.md` so it stays visible to Phases 6-9.

Populate `CloneNotices.CopiedFields` with the two author field identifiers only. D-14 restricts the review flag to `user.name` and `user.email`; every other field is re-derived and must not be flagged.

Validate before returning: the clone name must be non-empty and must differ from the source name, and the derived alias must pass the same host-block validator the create path uses. Return a typed error naming the offending field so the prompt can render it inline.

**Name availability and Host-pattern collision are two DIFFERENT checks (review R-29), and both must run.** A case-insensitive "is this name taken" scan over a list of literal names cannot detect that a derived alias `work-clone.github.com` is already MATCHED by an existing wildcard stanza `Host *.github.com` — and a matched wildcard silently changes which key SSH offers. So the composition root performs two checks:

  1. **Availability** — the derived NAME is not in the taken list built from `b.accounts()` unioned with every literal parsed Host pattern, compared case-insensitively (SSH host patterns are matched case-insensitively).

## Trust Boundaries

| Boundary | Description |
|---|---|
| source identity values → new managed blocks | copied text is interpolated into a new Host block, includeIf, and fragment |
| user-typed clone name → alias and file paths | a name becomes a Host pattern, a fragment filename, and a key filename |
| clone specification → the fail-closed store gate | a stale or foreign proof must not unlock a write |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |

| T-05-23 | Spoofing | clone silently shadowing an existing hand-written Host pattern | high | mitigate | The taken-name list unions managed identities with every parsed Host pattern, so the suggestion and the validation both see hand-written aliases. |
