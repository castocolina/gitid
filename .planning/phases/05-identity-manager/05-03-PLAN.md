<objective>
Build the two key-lifecycle ceremonies D-05 splits apart — rotate (retirement) and new-key (repair) — as UI-free domain orchestration over the primitives plan 05-02 shipped.

Purpose: `identity.Rotate` exists today as a correct SKELETON (staging, gate, four-writer pipeline) but its allowed_signers step REPLACES the block and it never archives the old key, directly contradicting D-06 and D-07. The repair path does not exist at all. 05-RESEARCH.md's Pitfall 2 warns that shipping the existing Rotate as-is silently breaks `git log --show-signature` for every pre-rotation commit — a data-integrity failure the user would not notice until much later.
Output: Two orchestration functions sharing one keygen-and-re-point core, a state-driven router between them, and the composition-root wiring for the two new injected seams.
</objective>

<task type="checkpoint:decision" gate="blocking">
  <name>Decision: does the repair (new-key) path append or replace the allowed_signers line?</name>
  <decision>What `RepairKey` (the KEY-07/MGR-05 new-key repair path) does with the identity's EXISTING allowed_signers line: replace it, append to it, or decide per key-presence.</decision>
  <context>
D-07 locks the APPEND behavior for rotate — the new pubkey line is added and the old line kept, so historic commit-signature verification keeps working. D-07's text is scoped explicitly to rotate. The repair path targets the key-missing and shared-key states, and CONTEXT.md never rules on what repair does to an existing signing line. 05-RESEARCH.md raises this as Open Question 1 and records it as assumption A1, explicitly asking for confirmation during planning rather than an assumption.

Why it is a blocking checkpoint: choosing replace and being wrong is effectively irreversible for an affected user. The replaced line is gone from the live file — a timestamped backup exists, but the user gets no signal that historic verification just stopped working, and Phase 8's pruning story assumes the accumulate-then-prune model. Choosing append or conditional is cheap to narrow later. This is the one genuine one-way door in Phase 5.
  </context>
  <options>
    <option id="replace">
      <name>REPLACE (recommended) — repair keeps the existing single-line write semantics, matching create and update</name>
      <pros>Matches every other non-rotate path; no accumulation of permanently unverifiable lines; a stale line pointing at an absent key verifies nothing today, so nothing of value is lost; this is 05-RESEARCH.md's own recommendation.</pros>
      <cons>If the user later restores the absent key from a backup, historic verification does not come back without manually re-adding the line.</cons>
    </option>
    <option id="append">
      <name>APPEND — repair uses the same append writer rotate uses</name>
      <pros>Historic verification survives if the old key is ever restored; one signer-writing rule across both key ceremonies, simpler to explain.</pros>
      <cons>Every repaired identity accumulates a line that verifies nothing; grows the Phase 8 pruning burden; the block gains lines for keys that were never valid.</cons>
    </option>
    <option id="conditional">
      <name>CONDITIONAL — append when the old key file still exists, replace when it does not</name>
      <pros>Preserves verification exactly when it is still possible and never accumulates a dead line.</pros>
      <cons>Two behaviors behind one menu row; harder to describe in the ceremony copy; more test surface; the user cannot predict which happens without inspecting disk.</cons>
    </option>
  </options>
  <resume-signal>Reply with one of: replace, append, or conditional (plus a one-line rationale if you deviate from the recommendation).</resume-signal>

  </verify>

## Trust Boundaries

| Boundary | Description |
|---|---|
| staged key material → canonical `~/.ssh` paths | new private key bytes cross onto disk at the live location |
