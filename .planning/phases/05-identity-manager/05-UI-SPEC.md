# Phase 5 — UI Design Contract

> Visual and interaction contract for Phase 5 (Identity Manager). Generated by
> gsd-ui-researcher, verified by gsd-ui-checker.

**This is a derivation, not a design exploration.** The design was approved
2026-07-06 by Pepe (DLV-08, `.planning/design/APPROVAL.md`) and is FROZEN. The
identity-manager's 8 named states (`list-populated` → `backup-notice`) are
BINDING, lifted verbatim from `.planning/design/identity-manager/FIELDS.md`.
This document consolidates that binding contract for Phase 5's scope (real
backend behind the manager, clone/rotate/new-key/delete lifecycle mutations,
SHELL-02 view set, SHELL-03 CLI parity) and specifies, in full, the **only**
new visual surfaces Phase 5 is allowed to introduce — the divergences implied
by `05-CONTEXT.md`'s D-05 through D-17, none of which FIELDS.md's frozen
8-state set anticipated (it only named ONE menu row, "Generate new key," for
what CONTEXT.md splits into two backend ceremonies). Every other value below
is cited from an approved upstream artifact, not re-decided. This project's
stack is a Go Bubble Tea v2 terminal app (not a web app); template sections
written for CSS/web design systems are translated to their TUI equivalent
(theme roles instead of hex/CSS tokens, 100×30 fixed capture geometry instead
of responsive breakpoints) — identical translation Phase 3's `03-UI-SPEC.md`
and Phase 4's `04-UI-SPEC.md` established. SHELL-03 (the Cobra CLI tree) has
**no visual surface** — D-03's TTY-aware table/`--json` output is data
formatting, not a design-contract concern, and is out of scope for this
document; the Executor implements it directly from `05-RESEARCH.md`.

## Design System

Same as Phases 3–4 — no shadcn / npm component registry. The "design system"
is the central Go `Theme` (`internal/tuikit/theme.go`), mirrored 1:1 by role
name with the archived web reference skin's `theme.ts` per `02-STYLE-SPEC.md`
§1 (the web mockup is a frozen historical artifact only, per the project's
active UI policy — the live `cmd/gitid-dummy` Bubble Tea mockup is the only
parity reference from Phase 3 onward). Phase 5 consumes the Theme unmodified
and introduces **zero new theme roles**.

| Property | Value |
|----------|-------|
| Tool | none (no shadcn — Go TUI, not React/Next/Vite) |
| Preset | not applicable |
| Component library | central Go `Theme` struct (`internal/tuikit/theme.go`) — 12 semantic roles + `Accent`/`FieldBorder`, ANSI-16 palette, used unmodified |
| Icon library | none — frozen glyph constants only: `glyphCheckOn/Off` (`☑`/`☐`), `glyphRadioOn/Off` (`●`/`○`), status glyphs `✓` healthy, `!` warning, `✗` error, `~` info (per `02-UX-DIRECTION.md` §2's color-semantics table, reused verbatim for the 8-state row glyphs). Phase 5 introduces **zero new glyphs** — every new ceremony note (grace-window hint, shared-key downgrade, unmanaged-reference scan) reuses the existing `!`/`✗`/`✓` + word convention, never a bespoke symbol |
| Font | terminal's own monospace |
| Capture geometry | fixed **100 cols × 30 rows** (`frameBodyRows(30) = 25` body rows), unchanged — kept identical for the visual-regression gate (Phase 3/4 mechanics, reused verbatim per `05-CONTEXT.md` code_context "UI wave") |

## Typography (TUI-adapted: semantic roles, not px sizes / weights)

Unchanged from Phases 3–4 / `02-STYLE-SPEC.md` §1 — Phase 5 introduces
**zero new roles**. The two notable reuses:

| Role | TUI treatment | Usage in Phase 5 |
|------|----------------|-------------------|
| Label | `Bold(true)` | list row's `row_state_word`, detail-view section headers, action-menu items |
| Field (value) | plain, no styling | clone-name-prompt's name field value |
| Field — focused | `Foreground(ANSI 4) + Bold`, no border (D1) | clone-name-prompt field, delete-choice's focused option |
| Field — blurred | `Faint(true)` | clone-name-prompt field, delete-choice's non-focused option |
| Hint | `Faint(true)` | grace-window hint, "copied from `<source>` — review" flag, `backup_explainer` |
| Warning | `Foreground(ANSI 3)` — yellow | D-13 unmanaged-reference scan warning (advisory tone — it warns, never blocks, per the project's advisory-≠-blocking convention) |
| Error | `Foreground(ANSI 1)` — red | `confirm_warning`'s "cannot be undone" heading, `row_glyph` for `key-missing`/`fragment-path-missing` rows |
| Healthy | `Foreground(ANSI 2)` — green | `row_glyph` for `complete` rows, rotate/new-key's post-write test-pass state |
| Info | `Foreground(ANSI 6)` — cyan | not used by any Phase 5 divergence beyond existing `list-populated` chrome |
| Preview | `Faint(true)` + dashed border | backup-notice's stacked path list, D-13's scan-hit list |

**Non-negotiable, carried forward unchanged:** every colored state pairs with
a glyph AND a word — never color alone. Phase 5's row taxonomy (8 MGR-02
labels) is the project's own canonical example of this rule (`row_glyph` +
`row_state_word`, verbatim vocabulary, already frozen by `FIELDS.md`).

## Color

ANSI-16 only, unchanged. Phase 5 reuses the existing role table exactly; no
new hue, no new role.

| Role | Value | Usage in Phase 5 |
|------|-------|-------------------|
| Dominant surface | terminal default fg/bg | body text, list row names, detail-pane field values |
| Secondary | `Faint`/`Hint` (dim) | hint copy, blurred fields, grace-window hint, "copied from" flag |
| Accent (ANSI 4, blue) | `FieldFocused`, `ActiveArea`, `ActiveNav`/`ActiveNavDimmed` | clone-name-prompt's focused field, the `1` Identities tab as ActiveNav |
| Warning (ANSI 3, yellow) | `Theme.Warning` | D-13 unmanaged-reference scan warning; rotate's `ReachableNotUploaded` outcome row (unchanged from Phase 3 D-02) |
| Error/Destructive (ANSI 1, red) | `Theme.Error` | `key-missing`/`fragment-path-missing` list rows; `confirm-destructive`'s heading; the "delete everything" option (never default-focused) |
| Healthy (ANSI 2, green) | `Theme.Healthy` | `complete` list rows; rotate/new-key's post-re-test pass state |
| Info (ANSI 6, cyan) | `Theme.Info` | not used by any Phase 5 divergence |

Accent reserved for (unchanged list, Phase 5 adds no new element): the
focused-field marker + value color (clone-name-prompt's one field), the
active header nav tab, the breadcrumb/divider line above an active pane —
never used to color the 8-state row taxonomy itself (that is glyph + word +
Healthy/Warning/Error, per the NO_COLOR-legible contract `FIELDS.md`
requires for `list-populated`).

**Explicit note on the shared-key downgrade note's color (D-12):** it is
`Hint` (faint), not `Warning`, because it states a FACT about what will
happen (the key stays, the sibling identity is named), not a risk the user
must weigh — the actual risk framing stays on `confirm_warning`'s existing
`Error` heading. The D-13 unmanaged-reference scan IS `Warning` (yellow)
because it names a real, un-scannable risk (`git@<alias>:` remotes) the user
must consciously accept — matching the project's advisory-never-blocking
convention for GSSH-01-class findings.

## Copywriting Contract

Frozen copy is governed by the `02-STYLE-SPEC.md` §6 grep-gate mechanism.
Phase 5 must NOT invent new copy for anything already frozen (`FIELDS.md`'s 8
identity-manager state labels, the four-beat ceremony language, `Write it
(Enter)`, Phase 3's D-02/D-03 `ReachableNotUploaded` string, etc.). It drafts
only the strings below, which join that same mechanism once approved — each
marked **DRAFT** is Claude's-discretion copy per `05-CONTEXT.md`, to be
frozen via the §6 grep once the UI wave's screenshots are approved.

| Element | Copy | Status |
|---------|------|--------|
| Primary CTA (delete-everything confirm) | `Write it` is NOT used here — delete's confirm reuses the frozen strongest-confirm pattern: default-focused `No`, explicit `Yes, delete everything` on the opposite side | CITED — `02-UX-DIRECTION.md` §5, `FIELDS.md` `confirm-destructive` |
| D-08 grace-window hint (rotate result, faint line under `ReachableNotUploaded`) | `The old key stays valid at <provider> during this window — upload the new key, verify it, then remove the old one there.` | DRAFT |
| D-12 shared-key downgrade note (delete-choice/confirm-destructive) | `This key is also used by "<sibling>" — it will be kept. Only this identity's SSH and Git artifacts are removed.` | DRAFT |
| D-13 unmanaged-reference scan warning (confirm-destructive) | `Found "<alias>" referenced in <file>: <line> — review before continuing.` per hit, plus the fixed honest disclaimer: `Repo remotes using git@<alias>: cannot be scanned and will break after this delete.` | DRAFT |
| D-14 clone pre-fill flag (create-wizard, entered pre-filled from clone) | `copied from <source> — review` (suffix on the `user.name`/`user.email` field rows only; SSH fields, gitdir, signingkey, and the allowed_signers line carry NO such flag since D-14 re-derives them, never copies them) | DRAFT |
| D-11 delete-everything confirm phrasing | `<name> will be removed from active use; a copy of the key pair exists at <backup path>.` — never "cannot be undone" for the KEY specifically (a backed-up key is recoverable); `confirm_warning`'s existing "cannot be undone" heading stays scoped to the Host block / gitconfig block removal | DRAFT, must not overclaim irreversibility per `05-CONTEXT.md` D-11 |
| D-06 archive path (backup-notice, rotate) | `Old key archived to <archive path>` (alongside the existing timestamped-backup path lines — same row template, new target) | DRAFT |
| D-17 clone suggested-name collision bump | `<source>-clone` (first suggestion) → `<source>-clone-2` (auto-bumped on collision, silently, before the prompt is ever shown to the user — never surfaced as an error) | CITED from D-17, not invented as a visible error string |
| Empty state | `No identities yet` / `Press n to create your first identity` | CITED — `FIELDS.md` `list-empty`, unchanged |
| Destructive confirmation | `delete-choice`: `Delete Git identity only` (default-focused, safer) vs. `Delete everything (SSH + Git + key)` (never default-focused) — `confirm-destructive` fires ONLY for the "everything" path, per `FIELDS.md` | CITED, `FIELDS.md` `delete-choice`/`confirm-destructive` |

### D-09 removal note (confirm-destructive / backup-notice, folded into the existing file list — no new copy element)

When the deleted identity is the LAST one for its provider, the existing
`confirm_warning` "what will be removed" file list gains one more named
target: the per-provider `insteadOf` block (e.g. `~/.gitconfig (insteadOf
block for github.com — removed, no other identity uses it)`). When a sibling
identity on the same provider survives, the block is NOT named in the list at
all (silently kept) — there is no "kept" copy variant to draft; omission IS
the signal, matching the project's existing convention of only naming what
changes.

## Scoped Additions (D-05 through D-17, mapped to visual surfaces)

These are the **only** new visual surfaces Phase 5 may introduce. Every one
reuses an EXISTING theme role, an EXISTING glyph, and either an EXISTING row
slot or an explicitly-budgeted new one (see the Spacing table above) — none
adds a new color, a new glyph, or an unbudgeted screen. Each is a documented,
allowlisted departure from the approved `FIELDS.md` states under the
project's visual-regression gate (Phase 3/4 mechanics, reused verbatim),
exactly like D9's precedent in Phase 2 and Phase 4's D-01..D-12 precedent.

### Rotate ceremony (D-05, D-06, D-07, D-08 — KEY-05)

No new screen. Entered from `action-menu`'s existing `action_new_key` row
when `ClassifyState` reports a healthy identity. Reuses Phase 3's
`test-running` → `test-pass`/`test-fail` → the four-beat mutation ceremony
verbatim. Additions:
- `backup-notice` gains the D-06 archive-path line (Copywriting table).
- `result-success` gains the D-08 grace-window hint (+1 row, Spacing table).
- The `allowed_signers` preview (wherever this ceremony shows one, mirroring
  the git-screen's `review-readonly` precedent) must render BOTH lines (old
  kept, new appended) — this is a content-fidelity requirement, not a new
  row: the preview block's line count simply grows by one, absorbed by its
  existing `maxLines`/clip-cue mechanism.

### New-key repair ceremony (D-05 — KEY-07/MGR-05)

No new screen. Entered from the SAME `action_new_key` row when
`ClassifyState` reports `key-missing` or a `key-used-*` shared-key state.
Reuses the SAME test-gate + four-beat ceremony as rotate, MINUS the archive
step (D-05: repair never touches pre-existing key material) and MINUS the
grace-window hint (there is no old key to keep valid). Visually this is the
plainest ceremony in the phase — it looks like a normal create-flow write,
just entered from the manager instead of the wizard.

### Delete-everything additions (D-09, D-11, D-12, D-13 — MGR-06)

All three additions land on `confirm-destructive` and/or `backup-notice`,
both already-approved screens (Spacing table above has the exact row
budget). No new screen. The `delete-choice` screen itself gains only the
CONDITIONAL D-12 downgrade note — its two-option, safer-default-focused shape
is otherwise unchanged.

### Clone additions (D-14, D-15, D-16, D-17 — MGR-04)

No standalone clone screen beyond the already-approved `clone-name-prompt`.
D-15 is explicit: after the name/key-choice prompt, clone opens the EXISTING
create-wizard pre-filled — so every screen the clone flow subsequently shows
is the create-wizard's OWN approved surface (Phase 3's `03-UI-SPEC.md`),
carrying only the D-14 "copied from" inline flag on two fields. D-16 (full
two-stage test re-run) and D-17 (silent auto-bump) add no visual surface of
their own — they are behavioral guarantees the existing screens already
render correctly.

## Inherited Non-Negotiables (quick reference for the executor)

Restated for convenience only — NOT decided by this document; each is cited
from its binding source and must not be re-litigated during Phase 5 planning
or execution.

- **Master–detail archetype, left list ⅓ / right detail ⅔** — the ONE body
  archetype `identity-manager` uses; do not introduce a guided-form layout
  here — `02-UX-DIRECTION.md` §2.
- **Key-allocation table is single-authority** — `1` (ActivationKey, home),
  `n`/`g` (LaunchKeys owned by create-flow/git-screen, NOT this phase), `a`/
  `c`/`d` (intra-surface `ScreenDef.Keys` → action-menu/clone-name-prompt/
  delete-choice) — `02-UX-DIRECTION.md` §2 table; Phase 5 claims no new key.
- **Glyph contract:** every colored state pairs with a glyph AND a word,
  never color alone — `02-UX-DIRECTION.md` §2. The 8-row taxonomy is this
  project's canonical example; every Phase 5 addition (grace hint, downgrade
  note, scan warning) follows the same rule.
- **Four-beat mutation ceremony** (preview → confirm → backup notice →
  result) for every write, no exceptions — `02-UX-DIRECTION.md` §5. Rotate,
  new-key, clone, and delete are all four-beat; none of Phase 5's additions
  add a FIFTH beat, they extend beats 1/2/3 with more content.
- **Destructive actions never default-focus "yes"** — `delete-choice`'s
  safer option and `confirm-destructive`'s default-`No` are both frozen;
  D-12's downgrade note and D-13's scan warning must not shift focus away
  from that default.
- **"The backup is the undo story"** must hold for every artifact this phase
  touches — `05-CONTEXT.md` "Specific Ideas." D-06's archive path and D-11's
  key backup path are both first-class lines in `backup-notice`, never
  buried or omitted.
- **Copy-freeze grep gate**, extended per this document's DRAFT strings once
  approved — `02-STYLE-SPEC.md` §6.
- **Recipe fidelity:** any rendered `Host`/`includeIf`/`insteadOf`/
  `allowed_signers` text this phase's ceremonies preview must match
  `recipes/ssh-config.recipe` / `recipes/gitconfig.recipe` structure exactly
  (ed25519 not RSA) — `recipes/README.md`.
- **Click-to-focus (D8, checkpoint-2):** the ENTIRE rendered field/row is the
  mouse hit target — applies unchanged to `clone-name-prompt`'s field and
  `delete-choice`'s two options.
- **100×30 capture geometry** is kept identical for the visual-regression
  gate — do not change frame dimensions to fit new copy; tighten
  `PreviewBlock` `maxLines` instead.
- **NO_COLOR legibility:** the 8-state row taxonomy and every new advisory
  line (grace hint, downgrade note, scan warning) must remain fully legible
  under `NO_COLOR` — glyph + word carries the meaning, color is additive
  only.
- **SHELL-03's CLI surface has no visual contract** — D-03's TTY-aware
  table/`--json` formatting is a data-shape concern, specified in
  `05-RESEARCH.md`, not this document.
